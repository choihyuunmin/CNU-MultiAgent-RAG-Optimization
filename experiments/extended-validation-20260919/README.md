# 확장 검증 (2026-09-19): 직접 실행 4라운드 재측정과 오케스트레이터 호출 겹치기

같은 200문항을 네 라운드 반복해 세 조건을 비교했다.

- **original**: 검색 도구 호출을 모델이 다시 쓰는 원래 경로.
- **direct**: 준비된 검색 인자를 검사한 뒤 같은 처리기로 직접 실행(`try_typed_single_tool_dispatch`).
- **overlap**: direct에 더해, 오케스트레이터의 검색 준비 호출을 분류 호출과 같은 시점에
  시작하고 원래 호출 지점에서 입력이 정확히 같을 때만 그 결과를 사용(`CallOverlapAdapter`).

모델, 프롬프트, 서빙 옵션, 응용 한도는 세 조건 모두 같다. 요청 2,400건 모두 정상 응답했다.

## 결과 요약

- **직접 실행**은 네 라운드 합산 800쌍에서 요청당 0.83초(3.4%) 빨랐다. 중앙값 차이 +0.37초,
  800쌍 중 453쌍이 빨라졌다(p<0.001). 평균 차이의 95% 구간은 [−0.34, +1.92]초로 0을 포함하고,
  평균 이득 하한은 −1.4%라 규약의 5% 기준에는 미치지 못한다. 검색 갈래당 제거된 시간은
  0.51–0.61초, 작업자 엔진 요청은 42% 줄었다(셀당 514 → 300).
- **호출 겹치기**는 종단 이득이 없었다. direct 대비 합산 800쌍 평균 −0.65초(overlap이 느림,
  95% 구간 [−1.96, +0.61]), 중앙값 −0.02초, 396/404로 차이가 없다. 겹치기가 실제로 적용된
  요청은 200건 중 86건(43%)이고 그 요청에서 준비 호출은 평균 1.1초 먼저 시작했지만, 200건당
  72건의 준비 호출이 버려져 오케스트레이터 호출이 10%, 생성 토큰이 13% 늘어 이득을 상쇄했다.
- 세 조건의 분류·준비 결과 해시 일치율은 같은 조건을 반복했을 때와 같아, 두 방법 모두 모델
  결정을 바꾸지 않았다.

## 규약 기준과 판단

- 규약(`performance_gate.PerformanceThresholds`)은 부하 1–100, 주 부하 100, 평균 이득 하한 5%,
  p95 비율 상한 1.05를 요구한다. 이번 측정은 동시성 4 한 점이며, direct의 평균 이득 하한은
  −1.4%, p95 비율 상한은 1.124로 기준을 통과하지 않는다. 앞선 부하 실험에서 direct의 이득은
  동시성이 높을수록 커졌으므로, 주 부하에서의 판정은 그 조건에서 별도로 재야 한다.
- 호출 겹치기는 현재 형태로는 채택하지 않는다. 적용 가능한 요청(43%)에서만 1초 남짓 앞당기고,
  폐기되는 호출이 엔진 부하를 늘려 전체로는 direct보다 느렸다. 분류 결과가 도착한 즉시 하위
  작업 분할이 확인되면 준비 호출을 바로 중단하거나, 응용이 질문을 다시 쓰지 않는 형태에만
  적용하도록 제한하면 낭비를 줄일 수 있으나 측정하지 않았다.

## 파일

- `analysis.json`, `analysis.requests.csv`: 분석 결과와 요청별 응답시간·호출 수·겹치기 사용 여부
  (문항 ID와 수치만 포함).
- `protocol.json`, `status.json`, `smoke-status.json`: 클라이언트가 기록한 규약과 진행 상태.
- `review-inventory.json`: 패키지·스크립트 해시.
- `harness/`: 서버 진입점(`serve_ext.py`), 직접 실행 부착(`review_dispatch_attachment.py`),
  매니페스트 생성, 원격 감독, 분석 스크립트. 호출 겹치기 부착은 `scripts/moleg_call_overlap.py`.
- 원자료(응답 본문, Pod 로그)는 저장소에 두지 않는다.
