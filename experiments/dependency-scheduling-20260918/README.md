# 의존성 기반 실행 검증 (2026-09-18/19): 장벽 결합 대 준비 즉시 시작

법령 검색 노드 `execute_search` 안의 온톨로지 읽기를, 원래처럼 네 갈래 `asyncio.gather`
장벽이 끝난 뒤 시작하는 **barrier** 스케줄과, 선행 작업(온톨로지 로더 준비)이 끝나는 즉시
시작하는 **ready** 스케줄로 나누어 같은 200문항을 두 라운드 반복 비교했다. 모델, 프롬프트,
서빙 옵션, 검색 인자, 응용 한도는 두 조건 모두 동일하며, 바뀌는 것은 이미 실행이 확정된
읽기의 **시작 시점**뿐이다.

## 결과 요약

- 노드 수준에서는 설계대로 동작했다. barrier 조건에서 읽기는 장벽에서 평균 1.07–1.10초를
  기다린 뒤 0.20초 동안 실행되고, ready 조건에서는 기다림 없이 실행되어 결합 시점에 이미
  끝나 있다(결합 대기 0). 검색 노드 소요 시간은 요청당 평균 163–188 ms 줄었다.
- 종단 응답시간에서는 그 차이를 분리해 낼 수 없었다. 두 라운드 합산 400쌍의 평균 차이는
  −0.15초(−0.6%), 95% 신뢰구간 [−1.95, +1.43]초로 0을 포함한다. 중앙값 차이 +0.31초,
  부호검정 226/174(p=0.011)로 작은 일관된 이동은 보이지만, 크기는 노드 수준 절감과 같은
  0.2–0.3초 규모이며 평균 응답시간 24.6초의 1% 미만이다.
- 읽기 자체의 입력·출력은 스케줄에 영향을 받지 않았다. 입력이 같은 요청에서 읽기 출력 해시는
  네 비교 모두 100% 일치했다.
- 검증 규약의 방출 기준(평균 이득 하한, p95 비율 상한)에는 미치지 못한다. 합산 평균 이득
  95% 구간은 [−7.9%, +5.8%]이다.

## 대상과 적용 방식

- 응용: 고정 이미지 `localhost/moleg-rag@sha256:3fb7072537de…` 안의 법령 검색 서비스.
  `src/core/query_loop/law_search/nodes.py`(sha256 `75c550ca5b07…`) 등 11개 소스 파일의
  해시를 서버 시작 시 검증한다(`scripts/serve_dependency_trial.py`의 `verify_sources`).
- 부착: `scripts/moleg_program_overlay.py`가 `execute_search`의 소스에서 온톨로지 읽기
  블록만 `ProgramHarness.after("ontology_search", ont_task, …)`로 옮기고, 원래 위치에서
  `ProgramHarness.join`으로 결과를 받는다. 조건부 시나리오 분해는 옮기지 않는다. 지문이
  다르거나 그래프가 이미 컴파일된 뒤에는 부착을 거부한다.
- 조건: `--schedule barrier`는 같은 계측을 붙인 채 읽기를 원래 결합 시점에서만 실행하는
  대조군이고, `--schedule ready`는 선행 작업 완료 즉시 실행한다.
- 실행 코드: 패키지는 커밋 `b4366dd`의 `src/cnu_rag_optimization`(adapter.zip sha256
  `16cbf00db05c…`), 스크립트는 커밋 `290fd7c`의 세 파일. 해시는 `review-inventory.json`에 있다.

## 노드 수준 계측 (`CNU_PROGRAM_HARNESS_V1`, 온톨로지 읽기 노드)

검색 노드가 실행된 요청은 각 셀 174문항(216 워크플로; 검색 노드를 두 번 실행한 요청 포함)이며,
나머지 26문항은 검색 없이 응답했다. 값은 평균/중앙값/p95(ms).

| 셀 | 선행 완료→시작 대기 | 읽기 실행 | 결합 대기 | 결합 전 겹침 | 검색 노드 소요 |
|---|---|---|---|---|---|
| r1 barrier | 1104 / 1038 / 1596 | 196 / 210 / 301 | 197 / 210 / 302 | 0 | 1315 / 1279 / 1842 |
| r1 ready | 0 | 201 / 214 / 306 | 0 | 201 / 214 / 306 | 1127 / 1050 / 1514 |
| r2 barrier | 1073 / 1041 / 1480 | 196 / 210 / 298 | 196 / 211 / 298 | 0 | 1284 / 1272 / 1769 |
| r2 ready | 0 | 201 / 214 / 302 | 0 | 201 / 214 / 302 | 1121 / 1064 / 1559 |

barrier 조건에서 읽기가 장벽에서 기다리는 시간(약 1.1초)은 읽기 실행 시간(약 0.2초)보다 길다.
따라서 ready 조건에서 읽기는 결합 시점 전에 항상 끝나고, 숨길 수 있는 최대치는 읽기 실행
시간 자체인 요청당 약 0.2초다. 실측된 검색 노드 소요 감소(188 ms, 163 ms)가 이와 일치한다.

## 입력·출력 동등성

| 비교 | 추적된 쌍 | 읽기 입력 동일 | 입력 동일 시 읽기 출력 동일 | 검색 노드 출력 객체 동일 |
|---|---|---|---|---|
| 1라운드 barrier vs ready | 174 | 159 | 159/159 | 81 |
| 2라운드 barrier vs ready | 174 | 154 | 154/154 | 80 |
| 영대조 barrier r1 vs r2 | 174 | 153 | 153/153 | 143 |
| 영대조 ready r1 vs r2 | 174 | 156 | 156/156 | 137 |

- 읽기 입력(국가 + 검색어)은 앞 단계 모델이 생성한 검색어를 포함하므로 같은 조건의 반복에서도
  약 12%는 달라진다. 조건 간 불일치율(9–11%)이 영대조와 같으므로 스케줄이 입력을 바꾸지 않았다.
- 입력이 같으면 읽기 출력은 항상 같았다(622/622). 추적 실패는 0건이다.
- 검색 노드 출력 객체(하이브리드 검색·시나리오 결과 포함)는 조건 간 46%, 같은 인스턴스
  반복 80%가 일치했다. 조건이 곧 인스턴스이므로 이 차이는 이전 실험에서 확인된 인스턴스 간
  차이와 구분되지 않는다. 법령 ID 집합 기준으로는 조건 간 재현율 97.3–97.6%, 완전 일치
  86–89%이고, 같은 인스턴스 반복은 98.7–99.2%, 92–94%다.
- 요청당 모델 호출 수는 4.61–4.64로 같고, 비교 모델의 문맥 초과 후 대체 경로 진입도
  셀마다 14건으로 같다.

## 한계와 주의

- 공유 엔진: 2라운드 barrier 셀 동안 오케스트레이터 엔진에 실험 외 요청 약 397건이 들어왔다
  (엔진 계수 1143 대 실험 호출 746). 이 셀의 평균이 0.4초 높은 데에는 이 부하가 영향을 줄 수
  있으며, 2라운드의 +0.45초는 그만큼 보수적으로 읽어야 한다. 대기열 시간은 셀당 10초 이하였다.
- 검출력: 종단 응답시간의 잡음이 효과 크기의 50배 이상이어서 평균 차이로는 결론을 낼 수 없다.
  효과의 상한은 계측된 읽기 실행 시간(요청당 0.2초, 0.8%)이다.
- 대상 범위: 옮긴 작업은 온톨로지 읽기 하나뿐이다. 다른 병렬 갈래(하이브리드 검색, 시나리오
  분해, 규제 후보)는 모델 호출이거나 조건부라 옮기지 않았다.
- 품질: 전문가 정답이 아닌 조건 간 일치도만 측정했다.

## 파일

- `analysis.json`, `analysis.requests.csv`: 본실험 분석 결과와 요청별 시간·노드 계측(문항 ID와
  수치만 포함).
- `smoke-analysis.json`, `smoke-status.json`: 예비 20문항 결과.
- `protocol.json`, `status.json`: 클라이언트가 기록한 실험 규약과 진행 상태.
- `review-inventory.json`: 패키지·스크립트·응용 소스 해시.
- `harness/`: 매니페스트 생성(`make_deptrial_manifest.py`), 원격 감독(`launch_deptrial_remote.py`),
  분석(`analyze_deptrial.py`). 서버 진입점은 `scripts/serve_dependency_trial.py`.
- 원자료(응답 본문, Pod 로그)는 저장소에 두지 않는다.
