# 2026-09-28 법령 검색 진단 실험: 분석 전용 근거

이 문서는 논문 수정본이 아니다. 기존 2026-09-21의 9,600요청 실험 중 동시 100요청의 기존/결합 방식 각 800건을 재검산하고, 별도로 200문항 × 100동시 × 2방식 × 2반복 = 800건을 진단 계측했다. 서로 다른 실험의 건수와 효과를 합산하지 않는다. 클라이언트의 `laws` 목록 비어 있음은 법률적 무관련성이나 검색 실패와 동의어가 아니다.

## 확인된 문제

기존 C100 집계는 기존 방식 323/800건, 결합 방식 120/800건에서 최종 법령 ID가 없었다. 두 방식 모두 800건이 형식 검사와 HTTP 응답 기준으로는 정상이었다. 재검산한 최초 문서 선택 입력 이벤트 길이는 법령 없는 응답에서 각각 양수 199/323건과 16/120건, 미기록 124건과 104건이다. [과거 재분석](historical-summary.json), [기존 CSV](../combined-comparison-20260921/analysis.requests.csv). 기존 분석기는 질문당 첫 `selection_input`만 CSV에 기록한다. 양수 길이는 유효 후보나 선택 성공의 증거가 아니며, 미기록은 검색 미실행의 증거가 아니다.

보존된 과거 앱 로그의 종료 시각은 모든 C100 셀 시작보다 이르다. 따라서 과거 323/120건을 요청·분기 수준 원인으로 소급 분류할 수 없다. 보존 범위와 각 셀 시각은 [로그 감사](historical-log-coverage.json)에 있다.

새 진단 실험은 네 셀 모두 200/200건 완료, 총 800건, 클라이언트 오류 0건, 형식 정상 800건이다. 원시 앱 로그에서 39,078개 구조화 이벤트를 추출했고 파싱 실패는 0건이다. 반올림된 클라이언트 시각과 나노초 로그 시각을 ±2초 허용해, 두 라운드에서 재사용된 `case_id`를 셀별로 분리했다. `request_finished` 추적 범위는 두 방식 모두 400/400이다. [실행 상태](status.json), [계측 품질](materialization.json), [분류 결과](analysis.json).

[요청별 자료](raw/requests.jsonl), [상호배타 분류](classified-requests.jsonl).

## 원인 근거

새 실험의 법령 없는 응답을 요청 단위 주원인 하나씩 분류했다. 부수적인 분기 오류는 별도 플래그다.

| 새 진단 실험의 법령 ID 없는 응답 | 기존 | 결합 |
|---|---:|---:|
| 검색 미실행 | 56 | 52 |
| 검색 결과 없음 | 0 | 0 |
| 후보는 있으나 선택 결과 없음(오류 없는 경우) | 0 | 0 |
| 내부 타임아웃/오류 뒤 빈 대체 응답 | 69 | 18 |
| 선택 ID 최종 전달 누락 | 0 | 0 |
| 기록 부족 | 0 | 0 |

빈 대체 응답 69/18건은 모두 검색 후보가 양수이고 선택 호출에 진입했으며, 120초 분기 타임아웃이 있었다. 즉 “클라이언트 응답 정상”과 “내부 경로 정상 완료”는 다르다. 기존 방식의 선택 노드 취소 130회와 결합 방식의 11회도 원시 분기 로그에 보인다. 모델 호출 `CancelledError`는 각각 244/26개 이벤트이며, 타임아웃의 하위 결과와 중복될 수 있으므로 별도 실패 건수로 합산하지 않는다. `BadRequestError` 이벤트는 기존 5회, 결합 14회로 결합에서 오히려 늘었다. 단일 요청 전체 실패와 병렬 분기 일부 실패도 분리했다. 후자는 위 표의 85/83건이며 법령이 남은 응답에서도 일어날 수 있다.

검색 미실행 56/52건 중 HITL 응답은 48/44건이고, 나머지 8/8건은 다른 조기 종료·경로로서 검색을 시작하지 않았다. 결합의 이 범주 4건은 다른 병렬 분기의 타임아웃도 있었으나 최종 법령 부재의 주원인은 검색 미실행으로 두고 부수 오류로 남겼다. HITL이나 관련 법령이 없다는 정상 판단을 자동으로 시스템 오류로 세지 않았다. 이번 법령 없는 응답 중 오류 없이 후보가 걸러지거나 모델이 관련 없음으로 판단한 사례는 관측되지 않았다. [요청·분기 이벤트](raw/events.jsonl), [분류 코드](harness/analyze_diagnostic.py).

코드 경로상 원래 방식은 `law_search_agent.run_search`에서 검색 도구 선택용 `run_tool_loop(max_rounds=1)`을 호출하고 도구 결과가 없으면 핸들러를 직접 호출한다. 결합 방식의 기존 부착 코드는 동일 인자를 검사한 뒤 핸들러를 직접 디스패치한다. 새 기능을 만들지 않았다. 양쪽 검색 핸들러 인자는 모두 준비값과 일치했고, 실제 핸들러는 검색 분기마다 한 번씩(기존 429/429, 결합 433/433) 호출됐다. 따라서 개선 구간은 검색 핸들러 자체가 아니라 핸들러 앞의 모델 왕복이다. [기존 실행 부착 코드](../combined-comparison-20260921/harness/review_dispatch_attachment.py), [동일한 진단 서버 구성](harness/serve_diag.py).

원래 애플리케이션은 단일 그래프 240초, 다중 분기 120초 제한을 두며 단일 경로 타임아웃 시 빈 법령 목록의 안내 응답을, 다중 경로에서는 실패 분기를 빈 결과로 처리한다. 선택 모델 호출 오류는 선택 모듈 내부에서 빈 선택으로 처리될 수 있고, 검색 도구 실패도 일부 경로에서 빈 검색 결과로 바뀐다. OpenAI SDK의 내부 재시도 상한은 2지만 개별 재시도 횟수는 이번 계측으로 확정할 수 없다. 별도의 `fallback_chain` 노드는 기존 0회, 결합 2회로, 위 타임아웃 대체 응답과 혼동하지 않는다. [환경·정책 명세](environment.json).

## 변경 기능의 효과

새 실험에서 검색 경계의 비핸들러 구간은 검색 분기당 평균 28.896초 → 0.001초, 실제 검색 핸들러 시간은 6.169초 → 5.423초였다. 문서 선택 입력은 기존 평균 10,687자, 결합 방식에서 축소 전 11,295자 → 축소 후 4,672자였다. 결합 방식의 후보 문서 수는 축소 전후 그대로(평균 10.07개)이고 `max_documents` 제한도 없다. 300자는 개별 문서 내용 필드 한도이며 총 입력 한도나 후보 300개가 아니다. 필터 전후 후보는 기존 평균 9.57→7.81개, 결합 10.12→8.15개이고 필터 후 0개는 둘 다 없었다. 이 계측은 모델 프롬프트·옵션이나 검색 후보 집합을 조정하지 않았다. [구간·선택 요약](analysis.json), [기존 선택 부착 코드](../combined-comparison-20260921/harness/selection_budget_attachment.py).

선택 노드 평균은 61.14초 → 34.79초, 취소는 130회 → 11회였다. 반면 답변 생성 노드 평균은 24.70초 → 70.31초로 늘었다. 성공 경로의 구성과 모델 호출량이 달라져 단계별 평균을 인과 효과로 단순 분해할 수 없다. 분기들은 병렬이며 전체 완료는 가장 늦은 필수 분기와 그 뒤의 합성에 의해 결정된다. 단계 시간을 합산하지 않는다. 이는 API 실행 추적이며 모델 내부 CoT 분석이 아니다.

vLLM 0.19.0의 누적 histogram 시간 증가량을 건수 증가량으로 나누면, orchestration 큐 평균은 26.12초 → 7.58초다. 완료 모델 요청은 1,514→1,424회, 요청당 프롬프트 토큰은 3,880→3,201, preemption은 18→12회였다. 반면 worker의 완료 호출은 974→521회로 감소하지만 남은 호출의 큐 평균은 23.05초 → 52.66초로 증가했다. 따라서 “두 서비스의 모든 대기가 줄었다”는 결론은 틀리다. orchestration KV 사용률은 양쪽 모두 표본 최대 1.0에 닿았고, worker 최대는 0.040→0.108이었다. 이들은 서비스 전체 지표이며 특정 요청의 KV 점유량이나 GPU 전체 메모리 사용률이 아니다. 네 셀 모두 큐 histogram 건수 증가량과 완료 건수 증가량이 같고, 수집 오류 및 계수기 초기화는 관측되지 않았다. 과거 48셀/192엔진 시계열도 같은 방식으로 감사했다. [진단 엔진 요약](analysis.json), [과거 지표 감사](historical-histogram-audit.json), [vLLM 0.19 지표 정의](https://docs.vllm.ai/en/v0.19.0/usage/metrics/).

동일 질문·동일 반복의 400쌍에서 기존−결합 전체 시간 평균은 16.17초(문항 단위 군집 bootstrap 95% 구간 8.80~23.40초)였다. 두 방식 모두 법령을 반환한 263쌍/144문항에서는 22.55초(13.20~31.56초)였다. 법령 포함 비율 차이는 +13.75%p(8.75~19.00%p)다. 과거 C100의 800쌍에서는 전체 28.40초(22.76~34.07초), 둘 다 법령을 반환한 471쌍/149문항에서는 41.91초(35.61~48.33초)였다. 두 실험의 차이를 환경·캐시·시간대 차이 없이 합산하거나 같은 효과 크기로 주장하지 않는다. [새 짝 비교](analysis.json), [과거 짝 비교](historical-summary.json).

## 남은 검증과 재현

- 당시 배포 이미지·Pod 자원과 토폴로지는 보존 명세로 확인했다. 두 핵심 vLLM 서비스는 2026-09-09 시작 로그와 2026-09-28 현재 동일 프로세스로 모델명·스냅샷·정밀도·양자화·설정이 확인된다. GPU 2×H200 NVL(각 143,771 MiB), GPU별 다른 서비스와 공유한다. 진단용 앱은 과거 C100과 동일한 이미지, 2 CPU/8 GiB 한도, 동시 허용 100을 사용했다. [환경 명세](environment.json), [프로토콜](protocol.json). 프로토콜의 `app admission raised to capacity`는 기존 러너의 범용 문구다. 이번 C100에서는 과거와 동일한 100이었고 정책을 새로 올리지 않았다.
- orchestration의 기동 시 KV 가용 예산은 24.23 GiB, 엔진 보고 수용량 26,464 토큰, worker는 31.0 GiB와 677,136 토큰이었다. 현 시점 엔진 블록 수는 각각 9,924/84,643, 블록 크기 16토큰이다. 예산·블록·토큰은 서로 다른 지표이며 정확한 할당 바이트 수나 요청별 KV 사용량으로 환산하지 않는다. 서비스 시작 로그는 과거 실험보다 앞서지만, 현 시점 `/metrics` 값은 당시 값으로 소급하지 않는다.
- 현재 검색 범위는 제목 인덱스 `moleg-title` 19,583문서=고유 `law_id` 19,583개, 국가 58개다. 번역 조문 인덱스 `world-law-translation` 468,104문서와 원문 조문 `world-law-origin` 3,183,227문서는 청크/문서 수이지 고유 법령·조항 수가 아니다. 제목 `law_id`는 정확한 composite 집계(21페이지), 국가는 누락 없는 terms 집계로 중복 제거했다. 세 조회는 같은 원자적 스냅샷이 아니며 2026-09-21 인덱스 스냅샷·고유 조항 수·국가별 대상 시점은 보존 자료로 확인되지 않는다. [환경 명세](environment.json).
- 네 셀 시작 전 핵심 엔진의 실행·대기 요청은 0 또는 1이었고, 순차 실행했다. 외부 공유 트래픽과 prefix cache 이력을 분리·초기화하지 않았으므로 두 조건의 큐 차이를 단독 기능의 순수 효과로 확정할 수 없다. 원시 전체 앱 응답·질문은 저장소에 포함하지 않고, 검증 가능한 식별자·해시·개수·시간·토큰·오류 유형만 둔다. 모델 SDK의 실제 재시도 횟수, 전문가가 판정한 관련성, 최종 법률 답변 정확도는 미확인이다.
