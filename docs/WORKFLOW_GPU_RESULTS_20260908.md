# 실제 GPU 어댑터 실험: KV 압력은 줄었지만 추가 가속·신뢰성은 미확인

2026-09-08. H200 NVL 2대의 현재 서빙과 K8s 검색 시스템을 사용했다.
운영 모델/배포를 수정하지 않고 현재 앱 소스 복사본의 loopback 프로세스로 비교했다.

**결론:** 고정 동시성 개선을 재관측했으나, 새 호출/토큰 예산 정책은 채택하지 않는다.
오케스트레이터 KV 압력 감소와 종단 성능 개선은 같지 않았다. 실패 요청에서는
워커의 reasoning 출력이 길어지고 답변이 나오지 않는 별도의 병목을 관측했다.

## 1. 완료 범위와 중단

[사전 계획](WORKFLOW_GPU_PROTOCOL_20260908.md)은 U16/32 × 3조건 × 64문항 × 2반복,
총 768회였다. U16 첫 반복의 192회를 실행한 뒤 C에서 240초 초과 1건이 발생해 중단했다.
SSE 완료는 191/192이며, **U32·둘째 반복의 576회는 실행하지 않았다.** 실패를 제거하거나
예산을 재조정한 뒤 이 holdout을 다시 검증 자료로 쓰지 않았다.

개발 64회와 별도 토큰 계측 재확인 32회는 본 결과와 분리한다. 이번 작업의 실제 앱
요청은 개발/재확인/본 비교를 합쳐 288회, 답변 자동 평가 레코드는 별도 63개다.
이 숫자는 모델 추론 호출 수나 새로운 고유 질문 수가 아니다.

기존 400문항에서 9월 7일의 64문항을 제외한 뒤 개발 32문항과 검증 64문항을 선택했다.
개발·검증은 질문과 출처 법령이 분리됐지만, 과거 모든 연구에서 미사용인 질문은 아니다.
예산은 개발 결과의 실제 usage로 03:42:29 UTC에 고정했다:
최대 동시 호출 8, prefill 46,232토큰, KV 예약 50,328토큰, 호출별 출력 예약 512토큰.
이는 논리 예약이며 생성 토큰 제한이나 물리 VRAM 보장이 아니다.

## 2. 사용자 16명 비교 — 중단된 실험의 기술 통계

| 조건 | 평균 관측시간¹ | p95¹ | SSE 완료 | 완료 처리량 | 30초 내 완료 |
|---|---:|---:|---:|---:|---:|
| A 기존 4/4·원래 전송·관측 | 70.49초 | 92.52초 | 64/64² | 0.200건/초 | 3/64 |
| B 고정 16/16·즉시 전송·관측 | 37.60초 | 62.58초 | 64/64 | 0.383건/초 | 11/64 |
| C B+오케스트레이터 호출/토큰 예산 | 42.13초 | 59.27초 | 63/64 | 0.232건/초 | 11/64 |

¹ 요청 시작부터 완료 또는 실패/기한까지의 관측시간. C의 240초 실패를 포함하며,
모두 성공했을 때의 평균 완료시간으로 해석하면 안 된다. 낮은 p95도 실패 1건을 감출 수 있다.
² A는 반환 완료와 별개로 q342에서 `BadRequestError` 1회, 후속 워커의 약 120초 비정상
scope 종료가 관측됐다. 따라서 A를 내부 오류 없는 기준군이라고 부르지 않는다.
q337의 스트림 scope도 일찍 종료됐으나 SSE는 완료됐다. scope 비정상 종료만으로
서빙 오류와 소비자 close를 구분할 수는 없다.

A→B 관측 평균 단축은 46.66%다. C는 B보다 관측 평균이 12.06% 길고 추가 가속을
보이지 못했다. 질문별 bootstrap 구간은 산출물에 남겼지만, 조기 중단·한 반복·A/B/C
고정 실행 순서이므로 완결된 사전 교차 검증의 확증 통계로 제시하지 않는다.
공유 warm cache와 서빙의 출력 변동도 통제 한계다. 과거 개선율과 합산하지 않는다.

## 3. 병목: 앞단 대기, KV 용량, 답변 전 reasoning을 분리

| 관측 | A | B | C |
|---|---:|---:|---:|
| 첫 계측 단계 이전 평균 | 51.257초 | 거의 0초 | 거의 0초 |
| 단계별 어댑터 대기 합계/요청³ | 거의 0초 | 거의 0초 | 16.408초 |
| 오케스트레이터 KV 최대 | 45.48% | 83.62% | 56.78% |
| 오케스트레이터 서버 queue 평균/호출 | 0.001초 | 0.241초 | 0.001초 |
| 오케스트레이터 prefill 평균/호출 | 0.531초 | 1.080초 | 0.635초 |
| 오케스트레이터 decode 평균/호출 | 3.552초 | 9.642초 | 5.978초 |

³ 단계 work의 합계이며 병렬 구간의 인과적 critical path가 아니다. 서버 통계는
공유 인스턴스 범위이고 개별 요청 전용 GPU 서비스 시간은 아니다.

C에서 모델 호출 상한 8, 대기 최대 11, KV 논리 예약 최대 49,997토큰을 관측했다.
서버 쪽 혼잡은 완화됐지만 앱 어댑터 대기가 생겼다. **동시 호출 상한과 토큰 예산을
함께 바꿨으므로, 토큰 예산만의 독립 효과를 분리한 실험은 아니다.**

Host RAM 가용량 최저는 **460.91GiB**였고 swap 입출력·major fault·OOM kill 증가는
각 조건에서 0이었다. 세 모델 계측의 선점도 0이었다. Host RAM 부족을 지지하는
증거는 없지만, 이것이 모든 메모리 병목을 배제하지는 않는다. 이번에는 NVML만
측정했으므로 HBM GB/s 또는 DRAM 대역폭 포화를 직접 판정할 수 없다. 이전 날짜의
Nsight 관측을 이번 구간의 직접 측정으로 재사용하지 않는다.

### 실패 질문 q191: 관측 가능한 CoT의 긴 꼬리

같은 source-paraphrase 질문에서 다음 차이가 있었다. reasoning 원문은 분석 산출물에
내보내지 않고 서빙 API에 노출된 문자 수만 센다.

| 조건 | 요청 결과 | 워커 스트림 수명 | reasoning 문자 | 보이는 답변 문자⁴ |
|---|---|---:|---:|---:|
| A | 100.79초 완료 | 22.46초 | 14,463 | 1,036 |
| B | 54.23초 완료 | 7.11초 | 2,958 | 1,006 |
| C | 240초 제한 초과 | 196.62초 | 126,142 | 0 |

⁴ 스트림 delta에서 센 문자 수. 최종 결과의 정규화된 comment 길이와 1문자 다를 수 있다.

C의 관측 순서는 약 14.23초 분류 이후 → 29.67초 준비 이후 → 43.38초 답변 생성 진입
→ 240초 기한 종료였다. 전체 어댑터 대기 구간 합집합은 14.25초였고, 가장 긴 수명은
오케스트레이터 gate를 적용하지 않은 워커의 답변 스트림이었다.

이는 **답변 전 reasoning 출력 장기화**라는 관측이지, reasoning 내용의 반복 루프를
분석했거나 GPU 서비스 시간 196.62초를 증명한 것은 아니다. reasoning 토큰 usage는
미제공이므로 문자 수를 토큰 수로 바꾸지 않는다. 같은 질문이라도 downstream 생성
입력/출력이 완전히 같다고 입증하지 못했다. 기존 비스트리밍 해시는 request_id까지
포함해 실행 간 불일치만으로 의미 입력 변화 여부를 판단할 수 없고, 스트림 입력 해시는
없다. 따라서 C가 이 현상을 일으켰다는 인과 결론도 내리지 않는다.

출처 QA 21문항 × 3조건을 별도 `microsoft/phi-4`로 조건명을 숨겨 평가했다.
63레코드 모두 평가 형식이 유효했고, 근거 context 축약은 0건이다. 실패한 빈 답변도

출처 지표의 실패는 반환 근거 없음으로 센다. 이는 timeout 전 내부 검색이 실패했다는
뜻이 아니다. B/C의 최종 근거 ID 목록 완전 일치는 58/64로, 내용 완전 동일성도 아니다.

전문가 정확도/비열등성·안전 회귀는 미검증이다. A/B의 자동 점수가 같거나 쌍 차이
bootstrap 구간이 [0,0]이어도 모집단 정확도 동등성 증명은 아니다.
새 C의 배포 게이트는 **release_allowed=false**이며 B 역시 자동 운영 배포하지 않았다.

리랭커는 각 조건 62회 모두 HTTP 200, 가드레일은 각 64회 모두 HTTP 200이었다.
이것은 접속/호출 상태이지 가드레일 판단 정확성 평가가 아니다. 본 비교의 tokenizer
579회는 실패·재시도 0, 실제 usage와 대조 가능한 비스트리밍 570회는 토큰 차이 0이다.
스트리밍 일부의 usage 미제공 9회를 일치 검증에 포함하지 않았다. 원 개발의 계측 실패
1회도 별도로 보존했다. 워크플로 trace는 192개, 누락 span 0이며 요청 조합 중복도 0이다.

## 5. 기존 실험과 어댑터에 반영할 판단

1. **실행 상한 개선은 유지할 연구 축이다.** 기존 U16/32의 고정 상한 실험과 이번 B는
   앞단 대기를 줄이는 방향을 지지한다. 과거 43.60%/49.49%와 이번 46.66%는 서로 다른
   질문·반복·완결성의 결과다. 기존 2.9%는 U16이 아니라 U4 종단 결과였다.
2. **정적 예산을 기본값으로 승격하지 않는다.** C는 KV 완화에는 작동했으나 대기 비용과
   실패를 상쇄하지 못했다. 이후 별도 개발 세트에서 call-cap-only와 token-budget 추가를
   분리하고, 실제 압력이 낮을 때 과도하게 제약하지 않는 정책을 검토한다. 이번 holdout으로
   새 임계값을 최적화하거나 기존 결과를 교체하지 않는다.
3. **워커의 답변 전 구간을 독립 제어 대상으로 둔다.** 첫 보이는 토큰까지의 시간,
   reasoning 문자 증가율, downstream 모델별 대기/수명, 소비자 취소 전파를 함께 기록한다.
   원문 분석이나 무조건적인 CoT 축약 대신 우선 관측을 보완한다. 재시도·reasoning 제한은
   모델 출력과 비용을 바꿀 수 있으므로 별도 정확도/근거성 검증 전 적용하지 않는다.
4. **성공 판정을 강화한다.** 알려진 실패 문구뿐 아니라 내부 fallback/모델 오류와
   미완료 스트림을 평가 입력에 넣는다. 현재 중단기는 SSE 실패/알려진 장애 응답만
   실시간 감지해 A의 fallback을 사후 발견했다. 후속 실험은 이 한계를 먼저 보완한다.
5. **아직 U32/100명 이상을 검증했다고 말할 수 없다.** 새 정책은 이번 중단 원인과
   품질 평가를 해결하고 새로운 사전 계획/질문으로 다시 비교해야 한다. D/E 선실행·서버
   추측 디코딩 결합은 이번에 실행하지 않았다.
