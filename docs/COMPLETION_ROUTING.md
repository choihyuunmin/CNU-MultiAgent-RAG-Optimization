# 예상 완료 시간 기반 요청 분산

## 변경 범위

모델이나 vLLM 엔진을 수정하지 않습니다. 기존 클라이언트의 호출 함수 앞에
`CompletionRouter`를 두어 **보낼 대상과 보내는 순서만** 결정합니다.
프롬프트, 모델 이름, 생성 옵션, 인증, 스트리밍 여부, 검색 결과는 수정하지 않습니다.
응답 캐시, 요청 복제, 자동 재시도, 실행 중 호출 중단도 없습니다.

이 코드는 개선 후보의 구현입니다. GPU 실험 결과나 정확도 향상을 입증한 자료가
아닙니다. 실행 예제의 가상 지연을 논문 성능 수치로 사용하면 안 됩니다.

## 동작

1. 각 호출에 질문 ID(`root_id`), 처리 단계(`stage`), 동등한 실행 조건을 나타내는
   `contract_id`를 붙입니다. 질문 본문은 스케줄러에 전달하지 않습니다.
2. 후보마다 **예상 대기 시간 + 새 호출의 예상 처리 시간**을 계산합니다.
   이미 실행 중인 호출과 앞서 기다린 호출의 예상 작업량을 함께 반영합니다.
3. 한가할 때는 빠른 곳을 선택합니다. 빠른 곳에서 기다리는 것보다 다른 곳에서
   먼저 끝날 것으로 예상될 때만 분산합니다. 보내기 전까지 대상을 확정하지 않아
   상황이 바뀌면 아직 보내지 않은 호출만 다시 배치합니다.
4. 같은 질문에 속하는 현재 미완료 호출들의 예상 작업량을 합산합니다. 남은 작업이
   적은 질문을 먼저 완료할 후보로 삼고, 오래 기다릴수록 우선순위를 높입니다.
   30초 이상 기다린 호출은 다음 사용 가능한 슬롯에서 FIFO 우선권을 얻습니다.
   30초는 중단 제한이 아닙니다. 이미 실행 중인 요청은 중단하지 않습니다.
5. 실제 호출이 끝나면 단계·작업 크기 구간별 추정치를 갱신합니다. 실패하거나
   중간에 닫힌 스트림은 학습하지 않습니다. 예상보다 길어진 실행은 잔여 비용을
   높여 아직 보내지 않은 요청을 재검토합니다.

`coflow`는 관측된 미완료 호출만 사용하는 휴리스틱입니다. 앞으로 발생할 모든
에이전트 호출을 미리 아는 DAG 최적화나 최적 완료 시간 보장은 아닙니다.
호출 간 데이터 의존성과 검색 결과 합치는 순서는 원래 애플리케이션이 유지합니다.

## 다른 환경에서 실행

```bash
git fetch origin
git switch agent/generalize-multi-agent-rag
git pull --ff-only
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[test]'
.venv/bin/python -m pytest -q
.venv/bin/python examples/completion_routing.py
```

`examples/completion_routing.py`에 기존 OpenAI 호환 클라이언트를 그대로 감싸는
`call_existing_clients`와 `stream_existing_clients`가 있습니다. 기본 실행은 가상
호출만 사용하며 네트워크에 접속하지 않습니다. 실제 적용 시 다음을 설정합니다.

- 클라이언트: 애플리케이션이 이미 사용하던 클라이언트를 복제본 ID에 연결합니다.
  URL이나 인증 키를 이 저장소에 넣지 않습니다.
- 실행 동등성: 같은 `contract_id`에는 동일 모델 가중치·토크나이저·API 동작·생성
  설정으로 검증한 복제본만 넣습니다. 문자열 일치는 동등성을 자동 증명하지 않습니다.
  다른 단계가 다른 모델을 쓰면 계약과 후보 집합을 분리합니다.
- 물리 자원: 같은 GPU/엔진을 공유하는 별칭은 같은 `resource_id`를 씁니다.
  `capacity`는 하네스의 동시 전송 한도이며 vLLM 옵션이 아닙니다. 별칭이 두 개라고
  처리 능력이 두 배가 되지 않습니다. 다른 모델이라도 물리 자원을 공유하면 묶습니다.
- 시간 추정: `initial_service_ms`는 별도 준비 질문으로 측정한 초기값입니다.
  `work_units` 기본값은 1이며, 필요할 때만 기존 메타데이터에서 얻은 상대 작업량을
  전달합니다. 예컨대 준비 실험의 기준 입력 길이 대비 비율을 쓸 수 있습니다.
  질문 재작성, 정답 조회, 예측용 추가 LLM 호출은 하지 않습니다.
- 수명: 프로세스·이벤트 루프마다 하나의 라우터를 공유합니다. 여러 프로세스가
  각각 라우터를 만들면 서로의 대기량을 알지 못합니다. 외부 운영 트래픽도 자동으로
  관측하지 않습니다. 이 구현의 예측은 라우터가 관측하는 트래픽에 한정됩니다.
- 스트리밍: `async with router.stream(...)`를 전체 소비 기간 동안 유지합니다.
  중간 종료·예외·취소에서도 원래 스트림을 닫은 뒤 슬롯을 반환합니다.
- 장애: 원래 호출 오류는 그대로 전달합니다. 기존 상태 점검에서 장애를 확인하면
  `set_enabled(replica_id, False)`로 신규 배치를 막을 수 있습니다. 활성 호출은
  끝까지 유지합니다. 모든 후보가 비활성 상태이면 호출자는 기존 타임아웃으로
  대기를 취소하거나 후보를 다시 활성화해야 합니다.

## 계측과 공정 비교

`on_event`에 JSON 로그 기록 함수를 연결합니다. `finished` 이벤트에는 다음이 있습니다.

| 필드 | 의미 |
|---|---|
| `wait_ms` | 하네스에 들어온 뒤 전송 시작까지 기다린 시간 |
| `service_ms` | 전송 시작부터 응답/스트림 종료까지 시간; 원격 대기 포함 |
| `total_ms` | 위 두 시간의 합. 하네스 밖으로 대기를 옮겨 숨기지 않음 |
| `first_chunk_ms` | 하네스 진입부터 첫 스트림 조각까지 시간 |
| `estimated_service_ms` | 배치할 때 사용한 처리 시간 추정치 |
| `prediction_error_ms` | 실제 호출 시간과 추정치의 차이 |

첫 스트림 조각은 메타데이터일 수도 있으므로 첫 LLM 토큰 시간과 같다고 가정하지
않습니다. `service_ms` 역시 순수 GPU 추론 시간과 같지 않습니다. 질문 ID·단계명은
내용이나 개인정보가 없는 식별자를 사용합니다. 프롬프트·답변·인증 정보는 기록하지
않습니다. 로그 기록 실패는 호출 결과에 영향을 주지 않습니다.

동일한 400개 질문을 각 방법에 모두 넣고, 동일한 도착 순서/간격과 동시 부하
1·4·8·16에서 측정합니다. 방법별 실행 순서를 교차하고 준비 질문은 평가에서
분리합니다. 방법마다 새 라우터로 시작해 학습 이력이 섞이지 않게 합니다.

| 비교군 | `routing` | `ordering` |
|---|---|---|
| 빠른 복제본 우선 | `fastest` | `fifo` |
| 최근 호출 시간으로 분산 | `recent` | `fifo` |
| 예상 완료 시간만 적용 | `completion` | `fifo` |
| 예상 완료 시간 + 질문별 순서 | `completion` | `coflow` |

빠른 복제본 **단독** 기준은 후보 집합도 그 복제본 하나로 제한합니다. 모든 비교군의
물리 자원 및 하네스 용량 한도를 동일하게 하고, 기존 하네스 없는 방식도 별도로
측정해 하네스 자체 비용을 분리합니다. 이 코드의 비교 모드는 앞선 실험 구현을
재현했다는 의미가 아니라, 같은 용량 제약 아래 정책 효과를 비교하는 대조군입니다.

평균·p95 전체 응답 시간, 처리량, 오류·취소 수를 함께 보고합니다. 대기 시간이
거의 없는 조건에서는 분산만으로 모델 계산 시간을 크게 줄일 수 없습니다.
기존 답변/검색 문서와의 일치도와 정답·근거 검증을 분리하고, 실패한 질문도 전체
400개 분모에 포함합니다. 동일 입력·설정이어도 서빙의 비결정성으로 출력이 달라질
수 있으므로 정확도 보존은 실제 평가로 확인해야 합니다.
