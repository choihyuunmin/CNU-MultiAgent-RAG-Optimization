# 접속 복구 후: 이중 수용 제한 독립 대조와 GPU 메모리 실측

2026-09-07. [프로토콜](MOLEG_SCALING_ISOLATED_PROTOCOL_20260907.md).
이 실험은 앞선 운영 NodePort 곡선과 별도로, GPU 호스트의 loopback 앱에서 실행했다.
현재 pod 소스·설정을 사용하되 공통 baseline 계측 어댑터가 있으므로 배포 환경과
완전히 동일한 시스템이라고 주장하지 않는다. 기존 592회 결과와 직접 합쳐 평균내지 않는다.
또한 이 대조의 개선율과 다른 조건에서 얻은 기존 추측 디코딩의 2.9%를 단순한
개선 전·후 수치로 연결하지 않는다.

## 1. 추정에서 직접 확인으로 바뀐 사항

현재 pod의 소스 해시 6개가 보관본과 일치했다. 생성 API에는 두 개의 제한이 있다.

| 제한 위치 | 현재 운영 상한 | 슬롯 반환 시점 |
|---|---:|---|
| `GlobalWaitQueueMiddleware` | 4, 앱 초기화에 고정 | ASGI 요청 전체 종료, 즉 SSE 전송 완료 |
| `GenerateQueue` | 4, 환경변수로 설정 | `execute_generate` 완료 |

라우터의 최종 fallback fake-stream은 내부 GenerateQueue 밖에서 실행되지만 HTTP
middleware 안이다. 따라서 이 경로도 긴 전송 동안 바깥 슬롯을 점유한다.
내부 큐의 대기 수가 0이라는 이유로 앱 전체에 대기가 없다고 판단하면 안 된다.
실제로 기준 조건에서는 내부 active 최대 4, 내부 queued 최대 0인데 첫 진행 이벤트
이전 평균이 약 42초였다. 처음 해석의 "생성 슬롯"을 두 수명으로 더 정확히 구분했다.

초기 launcher가 내부 상한만 변경하던 점을 첫 기준 trial 중 발견했다.
아직 실행하지 않은 C/D/E 앱만 다시 기동해 두 상한을 함께 8/8/16으로 맞췄다.
A/B의 4/4 조건은 변경하지 않았다. 변경 시점에 A는 59행, 나머지는 0행이었으며
`dual_limit_amendment.json`에 기록했다. 이후 관측된 내부 active 최대가 실제로 8 이상인지
확인하여 상한 변경만 기록하고 부하가 늘지 않는 오류를 방지했다.

## 2. 환경과 예비 검증

GPU는 H200 NVL 2개(각 143,771MiB), 드라이버는 580.126.09다.
RAM은 약 504GiB이며 swap은 구성되지 않았다. 원격 계정의 기존 앱 Python은 3.12.3,
Nsight Systems는 2025.3.2다. 서빙 프로세스와 운영 K8s deployment는 변경하지 않았다.

예전 호스트 설정을 사용한 첫 smoke 4회에서는 리랭커가 401 fallback을 사용했다.
현재 pod 설정과 달랐으므로 이 결과는 본 대조에서 제외했다. 현재 pod의 `.env`를
보호된 임시 경로에 전달해 공통 적용한 다음, 예비 4회에서 리랭커·가드레일 200과
정상 SSE 완료를 확인했다. 운영 인증 설정을 고치거나 느슨하게 바꾼 것이 아니다.

Nsight GPU Metrics는 API/CUDA trace 없이 두 장치의 SM/DRAM 지표를 100Hz로 표집했다.
이는 장치 전체 관측이며 특정 모델의 독점적 자원 사용량이 아니다. NVIDIA 문서의
DRAM read/write 지표는 해당 인터페이스 활동의 정수 백분율로, 실제 GB/s 실측이나
논리적 KV 사용 비율과 다르다. 지표를 무조건 이론 대역폭에 곱해 실제 전송량으로
환산하지 않는다. [NVIDIA 지표 정의](https://docs.nvidia.com/nsight-systems/UserGuide/index.html#gpu-metrics).

## 3. 요인 대조와 별도 반복 검증

고정 기준 30초 이내 완료 처리량(goodput)과 출처 라벨을 지연과 함께 판단했다.

완료된 A/B에서 평균 지연은 58.177초와 58.274초로 거의 같았다. q343의 첫 답변 이후
전송은 A 약 68.49초, B 약 0.004초로 크게 줄었지만, 다른 처리·대기 구간 변화 때문에

달랐다. 따라서 해당 요청의 종단 단축 전체를 전송 변경만의 순수 효과로 계산하지 않는다.

두 상한을 올리면서 첫 진행 이벤트 이전 평균은 A 42.044→C 20.301→E 0.032초로
감소했지만, 이후 평균은 16.133→23.131→36.018초로 증가했다. 요청을 더 일찍 실행하면
모델 자원 경합이 커지는 상충 관계다. E의 오케스트레이터 호출당 decode는 A의
3.026초에서 9.097초로 늘었다. 이때 호출당 입력은 약 3,970토큰, 출력은 약 83토큰으로
유사했다. 종단 감소와 모델 호출 지연 증가가 동시에 성립한다. 이 구간별 관측은
공유 서버 값이고 모델 단계의 독점적 인과 분해는 아니다.

13:30:04 UTC에 미리 정한 완료·출처 조건과 평균 기준으로 E를 선택하고
`selection.json`에 동결했다. 16·32명의 별도 반복 검증 결과는 선택용 표와 합산하지 않는다.

### 3.1 순서를 교차한 새 실행 512회

동일한 64문항을 U16·32, A/E, 각 2회 실행해 **512/512 정상 완료**했다.
질문별 두 반복을 평균한 뒤 짝지은 질문 bootstrap 4,000회로 신뢰구간을 구했다.
새 문항 holdout이 아니라 같은 워크로드의 새 실행이며, 시간대 전체 변동까지
포괄하는 신뢰구간이 아니다. 선택용 320회와 제외한 예비·중단 실행은 합산하지 않았다.

|---:|---|---:|---:|---:|---:|---:|---:|
| 16 | 기준 A | 60.360 | 78.283 | 59.135 | 0.238 | 6.25% | 14.34 |
| 16 | 개선 E | 34.045 | 56.585 | 33.127 | 0.434 | 37.50% | 14.77 |

| 32 | 개선 E | 52.611 | 78.585 | 51.645 | 0.465 | 8.59% | 24.48 |

U16 평균 단축은 **43.60% (95% CI 38.84~48.55%)**, U32는
**49.49% (46.55~52.34%)**다. 완료 처리량은 각각 약 1.83배·2.00배다.
다만 개선 E에서도 32명의 30초 이내 완료 비율은 8.59%에 불과하다. 상대 개선을
서비스 SLO 달성이나 100명 이상 확장 가능성으로 바꿔 말하지 않는다.

각 U·조건의 출처 법령 포함은 74/78(39문항×2회), 조문 포함은 32/42(21문항×2회)로

기록된 비스트리밍 모델 호출 오류는 0이었다. 정상 SSE 완료만으로 이 사실을 추정하지 않았다.

## 4. 메모리 병목 관측

기준 trial의 호스트 가용 RAM 최소는 460.20GiB였다. swap-in/out, major page fault,
OOM 카운터 증가는 모두 0이었다. 267초 구간의 누적 memory PSI stall은 약 0.004초였다.
이 구간은 호스트 RAM 용량 부족이나 swap thrashing으로 설명되지 않는다.

| 조건 | 실제 내부 active 최대 | 오케스트레이터 KV 최대 | GPU 0 DRAM read 평균/p95 | GPU 1 DRAM read 평균/p95 |
|---|---:|---:|---:|---:|
| A | 4 | 60.17% | 39.45 / 66% | 10.41 / 26% |
| B | 4 | 59.81% | 36.07 / 66% | 10.08 / 26% |
| C | 8 | 71.10% | 28.52 / 62% | 12.84 / 28% |
| D | 8 | 64.58% | 27.42 / 59% | 12.38 / 27% |
| E | 16 | 99.73% | 21.98 / 44% | 13.41 / 28% |

다섯 조건의 오케스트레이터 선점 증가는 모두 0이다. 다만 E의 논리적 KV 용량은
거의 다 사용한 순간이 있으므로 여유가 충분한 설정이라고 판단하지 않는다.
표집된 GPU 0의 DRAM read 최대는 조건별 64~69%, write 최대는 8~11%였으며
read ≥80% 표본은 없었다. GPU 0 GR Active 평균은 약 95~98%였지만 SM Issue 평균은
약 11~13%였다. 따라서 `nvidia-smi` GPU 100%를 연산 능력 100% 또는 HBM 대역폭
포화로 바꿔 말할 수 없다. 높은 batch에서 DRAM read 평균 감소와 Tensor Active 증가가
관측되었지만, 가중치 재사용·kernel 효율·동시 모델 간 간섭의 기여는 이 장치 전체
계측만으로 분리할 수 없다. 지속 HBM 포화의 증거는 없으며 개별 kernel의 메모리
지연 병목까지 배제하는 결과는 아니다.

Nsight의 첫 기준 trial은 시작 약 1.5~1.6초가 수집 밖이다(표본 구간 약 99.4%).
나머지 조건은 약 99.99% 이상이다. 구간 내 표본 간 최대 간격은 약 10ms였으며,
30ms 초과 간격이나 유실·overflow 진단은 없었다. NVLink/CTC 미지원 안내 20개는
SM·DRAM 지표의 유실과 구분했다. 이 확인을 포함한 최종 자원 집계는
`resources-audited.json`이며 초기 `resources.json`보다 상세하다.

모든 조건에서 가용 RAM 최소는 460GiB 이상, swap·OOM 증가는 0이었다.
B에서 호스트 전체 major page fault가 1회 증가했으나 메모리 부족·thrashing의 증거는 아니다.

기준에서 GPU 0의 온도 최대는 85°C였다. 후속 확인에서 GPU 0의 누적 HW/SW thermal
slowdown 카운터는 모두 0이었고, 현재 SM/메모리 클록은 설정값과 같았다. 높은 온도만으로
쓰로틀링이 발생했다고 판단하지 않으며, 종료 후에도 상태를 확인한다.

반복 검증의 8개 trial에서도 가용 RAM 최소는 460.53GiB 이상이었고 swap·major fault·
OOM 증가는 모두 0이었다. 개선 E의 KV 최대는 U16 97.55%, U32 98.93%, 선점은 0이었다.
GPU 0 DRAM read의 trial별 평균은 A 34.71~39.08%, E 22.89~24.62%, 전체 표본 최대는
70%였다. 8개 trial 모두 Nsight 시간 범위 안에 있고 30ms 초과 내부 간격·유실 진단은 없었다.

종료 점검에서 GPU 0의 HW/SW thermal slowdown 누적은 모두 0, GPU 1의 SW thermal
누적은 진행 중 확인값과 같은 2.1713초였다. **전력 제한은 별개**다. GPU 0의 SW power
capping 누적은 13:50:34~13:51:23 UTC 사이 확인값과 14:06:06 종료값 사이에
260.297초 증가했다. 따라서 클록 제한이 전혀 없었다고 주장하지 않는다.
이는 장치 전체 두 시점의 차이로, 조건별 전력 제한 비중이나 성능 기여를 분해한 값이 아니다.
전력·클록·열 설정은 변경하지 않았다. 전력 제한과 모델 공존 경합은 후속 원인 분리 대상이다.
[NVIDIA clock-event counter 정의](https://docs.nvidia.com/deploy/nvidia-smi/index.html#clock-event-reasons-counters).

## 5. 개선 방법의 구체화

첫 우선순위는 모델 실행과 전송을 구분하고 실제 유효 상한을 조절하는 것이다.
내부 큐만 조절하거나 모델 KV만 보는 외부 gate는 더 앞단의 HTTP 상한을 놓친다.
동시 실행을 늘릴 때는 지연·goodput뿐 아니라 실제 active, 모델 queue/prefill/decode,
KV 선점과 장치 압력까지 함께 확인해야 한다. 무조건 16·32로 올리는 정책은 제안하지 않는다.

단계별 추측 디코딩과 토큰·KV 예산 조절은 이 관측 위에서 발전시킬 후속 방법이다.
현재 서버 코드의 큰 기본 `max_num_seqs`와 CUDA graph/KV 예산도 별도 대조 후보지만,
이 앱 대조에서 vLLM 설정을 함께 바꾸지는 않는다. 여러 요인을 섞어 어느 변경이
개선을 만들었는지 알 수 없게 하지 않는다.

최종 답변의 전문가 정확도·동등성은 여전히 미평가다. 출처 포함의 동일성이나 유의차
없음을 답변 무손실성으로 확대하지 않는다. GPU 추가 없이 관측한 개선도 측정한 부하와
같은 자원·조건에 한정해 보고한다.

## 6. 제출용 기술 아이디어와 대조 조건

1. **실측한 개선:** HTTP 제한과 생성 제한의 유효 최소값을 함께 조정하고, 이미 준비된
   문자의 인위적 전송 대기를 제거한다. 검색·프롬프트·답변 길이 제한은 그대로 둔다.
   이 변경은 새 스케줄링 알고리즘이 아니라 현재 시스템의 검증된 실행 설정 대조다.
2. **단계별 자원 예산 제안:** 사용자 수 대신 모델별 활성 입력 토큰·예상 KV 블록 수에
   상한을 둔다. 짧은 분류/준비와 긴 문서 선별을 구분하고, 긴 요청에도 aging을 적용해
   기아를 방지한다. 슬롯은 해당 모델 RPC가 끝나면 반환하되 HTTP 스트림은 별도의
   유한 큐·백프레셔로 관리한다. 클라이언트 대기는 전체 지연에 포함해야 한다.
3. **압력 기반 추측 실행 제안:** 낮은 부하에서는 검증 가능한 준비 선실행을 허용하고,
   KV 포화·선점 증가·긴 queue에서는 새 투기 작업을 줄인다. authoritative 경로와
   전체 입력이 일치하지 않은 결과는 사용하지 않는다. 단순 상한 16, 내부 토큰 예산,
   토큰 예산+추측 실행을 같은 자원에서 비교해야 결합의 추가 효과를 주장할 수 있다.
4. **서빙 튜닝 후보:** `max_num_seqs`와 `max_num_batched_tokens`를 독립적으로
   비교한다. 현 설치 버전(v0.19.0)의 preemption·chunked prefill 지침을 참고하되,
   이미 여러 모델이 상주한 GPU의 메모리 비율을 무조건 높이지 않는다.
   [vLLM 0.19.0 공식 문서](https://docs.vllm.ai/en/v0.19.0/configuration/optimization/).

자원 예산은 단순 문항 수보다 **캐시에 없는 입력 토큰**과 **출력 길이의 보수적 추정**을
반영하는 편이 타당하다. 예를 들어 동일 GPU에서 `고정 16` → `모델별 토큰/KV 예산` →
`토큰/KV 예산+부하 적응 선실행`을 비교하고, 평균·p95와 함께 실제 모델 토큰 수,
취소된 투기 작업량, 대기 최대값, 출처 회귀를 기록한다. 예산·임계값은 별도 개발
워크로드에서 정한 뒤 고정해야 한다. 이번 64문항에 맞춰 사후 선택한 임계값을 같은
64문항의 독립 일반화 결과로 보고하지 않는다. KV 크기는 모델의 캐시 구조·그룹에
따라 달라지므로 토큰 수를 모든 모델에 공통인 바이트 상수로 변환하지 않는다.

앱 전체의 의존성을 드러내는 방향은 [Parrot](https://www.usenix.org/conference/osdi24/presentation/lin-chaofan),
prefill/decode 간섭과 goodput을 구분하는 방향은 [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)와
연결된다. 두 연구의 결과를 이 시스템에서 재현했다고 주장하지 않는다. 현재 두 GPU는
서로 다른 다수 모델을 공유하므로, prefill/decode의 물리적 분리는 자원 배치·통신 비용을
포함하는 별도 대조가 필요하다. 본 연구의 차별점은 도메인 다중 에이전트의 이중 대기,
전송 수명, 출처 지표, 실제 GPU 압력을 연결하는 실증으로 한정한다.

## 7. 제출 전 확인 범위

운영 적용이나 외부 제출은 하지 않는다. 핵심 그림은 초기 운영 API의 U1~32 곡선,
현재 pod 기반 U16 선택용 대조, 같은 설정에서의 U16·32 반복 검증을 서로 분리한다.
서로 다른 날짜·배포·클라이언트 경로의 평균을 한 곡선으로 연결하거나, 선택용 반복을
검증 표본에 합산하지 않는다. 시간대·GPU 공유 부하·warm cache와 유한 64문항의
시작/종료 구간은 장시간 정상상태 실험의 대체물이 아니다.

추가로 필요한 것은 전문가의 블라인드 답변 평가, 실제 사용자 질의·다중 턴을 포함한
외적 타당성, 장시간 반복·개방형 도착률에 대한 안정성, 제출처 양식·저자·윤리/공개 범위
확정이다. 100·1000명에 대한 가속이나 품질 동등성은 현재 근거로 주장하지 않는다.

순서 교정 전 중단한 검증은 완료된 기준 64행과 부분 후보 3행을 그대로 보존했다.
중단 시 이미 시작했지만 최종 행이 기록되지 않은 요청도 있으므로, 이 67행을 전체
시도 횟수나 완결된 검증으로 세지 않는다. 별도 `validation-excluded-note.json`과
`validation-excluded/`에 이유·부분 자료를 남겼으며 새 검증 통계에는 포함하지 않는다.

## 8. 완료 상태와 재현 자료

선택용 320회와 순서 교차 검증 512회, 합계 **주 대조 832회가 모두 정상 완료**했다.
예비 8회와 순서 교정 전 부분 캠페인은 별도로 보존한다. 91개 코드 테스트, 주 대조
무결성 감사, 공개 자료의 원문·인증 정보 제외 검사를 통과했다.

실험 앱 5개, 호스트 monitor와 Nsight collector를 종료했고 loopback 실험 포트가 닫혔음을
확인했다. 임시 인증 설정 사본 3개만 삭제했으며 원본은 보존했다. 기존 모델 API 프로세스
8개의 PID·시작 시간이 유지됐고 health는 모두 200이었다. 운영 K8s 앱은 Ready 1/1,
Running, pod 재시작 0회였다. 운영 배포·vLLM·전력 설정 변경과 외부 논문 제출은 하지 않았다.
