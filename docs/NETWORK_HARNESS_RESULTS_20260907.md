# 네트워크 하네스 실제 실험 결과 — 2026-09-07

## 결론

동일 100문항, 동시 사용자 16명에서 **속도 개선은 관측했으나 답변 보존은 입증하지
못했다. 현재 하네스의 운영 적용과 정확도 유지 주장은 보류한다.**

실제 원격 LLM을 호출한 비교다. 시뮬레이션·로그 재생 값을 아래 결과표에 섞지 않았다.
모델, 프롬프트 템플릿, vLLM 설정, LLM 호출 인자와 스트리밍 설정을 변경하지 않았다.
원본 검색기 소스와 `.env`도 수정하지 않았다.

## 무엇을 결합했나

| 방법 | 구체적인 처리 | 확인하려는 효과 |
|---|---|---|
| 기준 검색기 | 기존 질문 단위 실행 한도 4 유지 | 비교 기준 |
| 자원별 도착순 제어 | 질문 진입 한도는 32로 열고, LLM을 호출할 때 같은 추론 자원에 공유된 실행 자리를 획득. 분류 모델 8, 나머지 자원 4로 고정 | 질문 전체가 입구에서 기다리는 시간을 줄이고, 특정 모델에 요청이 몰리는 현상 완화 |
| 네트워크 하네스 | 위 실행 자리 제어에 질문별 대기줄·순환 처리를 결합. 원래 LLM 스트림을 별도 태스크가 읽고 최대 64조각의 버퍼로 전달 | 한 질문의 다수 하위 요청이 대기줄을 독점하는 현상 완화. 응답 후처리와 추론 자리 반환을 분리 |

하네스의 네트워크 개념은 **흐름별 큐·라운드로빈, 수신 측 크레딧, 제한된 버퍼와
역압 제어**다. 질문 문장이나 법령 지식을 해석하지 않는다. 모델 선택, 질문 재작성,
정답 캐시, 호출 생략, 토큰 절단, 추가 재시도는 도입하지 않았다.

실행 기회만 순환 배분한다. GPU 시간의 공정성, 진행 중인 추론의 선점, FQ-CoDel이나
DRR 전체 구현을 주장하지 않는다. 스트림 버퍼 상한은 **조각 수**이며 바이트 수가 아니다.
구조와 API는 [하네스 설명](NETWORK_HARNESS.md)을 참고한다.

## 평가 조건

- 기존 400문항 중 같은 100문항 사용. 20개 국가, 모든 질문에 국가명 포함.
- 기존 난이도 구분별 25개씩. 모든 방법에서 동일한 질문 파일·순서·시드 사용.
- 동시 사용자 16명, 각 방법 100요청, 방법마다 새 로컬 앱 프로세스.
- **모든 방법에서 화면 표시를 위한 인위적 대기만 동일하게 제거했다.** 이 제거 효과를
  하네스의 개선으로 계산하지 않았다. 따라서 기준은 화면 대기를 제거한 현재 검색기다.
- 질문·작업 내용은 기존 앱이 결정한다. 동일 템플릿이라도 이전 LLM 출력에 따라 후속
  호출 내용과 호출 수는 달라질 수 있다. 호출 수 차이를 하네스의 호출 생략 성과로 보지 않는다.
- 실패를 제외하지 않았다. 아래 평균·p95는 **실패를 포함한 100요청** 기준이다.
- 모델/엔진 유휴 상태를 확인한 뒤 시작. 완료된 세 조건은 모두 유휴 상태에서 시작했다.
- 기준 재측정 100건도 계획했으나, 시작 전 유휴 확인 60초와 추가 읽기 전용 확인 45초에서
  실행 중인 추론이 남아 있어 **실행하지 못했다**. 엔진을 중단하거나 설정을 바꾸지 않았다.
- 현재 완료 범위는 **100문항 × 3방법 = 300요청**. 서로 다른 300문항이나 사용자 수별
  전체 성능 곡선이 아니다. 최초 4문항 연결 점검은 본 평가와 별도다.

관측된 전체 평균 단축률은 도착순 제어 **33.4%**, 하네스 **39.2%**다. 하네스는
도착순 제어보다 평균 **8.7%**, p95 **24.7%** 짧았다. 질문별 비교에서는 도착순 제어보다
63건이 빨랐고 37건은 느렸다. 이는 한 번의 실행에서 관측한 차이며 통계적 유의성이나
하네스만의 인과 효과를 입증한 수치가 아니다.

원래 평가기의 성공 요청만 사용하면 기준 평균은 **145.69초**, p95는 **234.71초**다.
이 기준에서 하네스의 평균 단축률은 **38.8%**다. 실패 포함 평균과 혼용하지 않는다.

### 답변 품질 해석

법령 재현율은 첫 기준 답변의 법령을 얼마나 다시 찾았는지 나타낸다. **전문가가 평가한
법적 정확도가 아니다.** 기준에서 실패한 3건은 정답지가 없어 일치도 비교를 못 했으며,
97쌍으로 계산했다. 실패율의 분모는 여전히 100건이다.

기준과 하네스 모두 법령이 없는 답변은 14쌍이다. 원래 평가기의 빈 집합 처리 규칙을
그대로 사용했으므로, 높은 일치도가 반드시 실질적인 법령 검색 성공을 뜻하지 않는다.
유효 응답 중 법령이 없는 답변 수는 기준 15건, 도착순 제어 14건, 하네스 19건이다.
전체 법령 ID와 순서가 완전히 일치한 비율은 도착순 제어 54.6%, 하네스 50.5%다.

따라서 **“정확도를 유지하면서 39.2% 개선했다”는 결론은 사용할 수 없다.** 기준 재측정이
없어 원래 출력 변동과 실행 순서 변경의 영향을 분리하지 못했고, 전문가 정답 및 합의된
비열등성 기준도 없다. 현재 관측된 답변 차이 자체도 작지 않다.

문서 처리 자원은 `retrieval tool`과 `worker agent`가 공유하는 동일 모델 자원이다.
앱 입구 대기는 줄었으나, 후보 방식에서는 **LLM 호출 직전의 앱 대기**가 생긴다.
병렬 하위 작업의 대기 시간을 합한 값은 실제 경과 시간과 다르므로 전체 응답 시간에
단순 합산하지 않았다. 엔진 지표만 보고 대기가 사라졌다고 주장하지 않는다.

전체 자원 중 최대 KV 사용률은 약 32.2%였고 preemption 증가는 없었다. 이 결과만으로
물리 GPU 메모리나 메모리 대역폭 병목을 배제할 수 없다. KV 사용률은 예약된 캐시 영역의
사용 비율이며, 물리 VRAM·메모리 대역폭 지표는 이번에 확보하지 못했다.

공유 엔진 호출 수와 앱 로그 호출 수가 일부 일치하지 않았다. 하네스의 문서 처리 자원은
앱 성공 호출 511회, 엔진 완료 카운터 증가 517회였다. 측정 종료 시 실행 요청도 1개였다.
미완료·취소된 자체 호출, 측정 경계, 다른 트래픽을 분리하지 못했으므로 엔진 평균값을
실험 요청만의 순수 지표로 해석하지 않는다.

## 실제 실행에서 발견한 실패 예

최종 응답 성공은 내부 단계 전체의 성공을 뜻하지 않았다. 하네스에서는 긴 응답 생성
1건이 취소됐고, 문서 비교 호출 2건이 `BadRequestError`로 끝났다. 원래 앱의 최종 응답
처리 경로는 그대로 유지됐다.

아래는 원시 로그의 일부 필드를 발췌한 값이다. 가상 로그나 CoT 내용 재구성이 아니다.

```text
case_id: l4-033-ca-online-sales-r1-c16
request_id: 72590711
LLM: model="worker agent", status="cancelled", duration_ms=170664.357
harness: chunks_read=30970, buffer_peak_chunks=64, success=false
final request: status="ok", duration_ms=242037.523
```

30,970은 수신한 **스트림 조각 수**이지 토큰 수가 아니다. 내부 추론 내용을 근거로
어떤 사고 단계를 제거했다는 결론도 내리지 않는다. 54개 스트림 전달 작업 중 1개가
완전 소비되지 않았으며, 위 취소 기록과 대응한다. 버퍼 상한은 64개로 유지됐고 버퍼가
차서 기다린 시간은 전체 합계 약 77.70ms였다. 스트림 버퍼 자체의 큰 속도 이득은
이 값만으로 입증되지 않았다.

## 코드·재현성과 후속 검증

실행 코드: `src/cnu_rag_optimization/completion.py`,
`src/cnu_rag_optimization/network_harness.py`, `scripts/serve_scaling_adapter.py`.
원본 검색기 대신 실행 어댑터에 연결했다. 엔진·모델 변경이나 원격 배포는 하지 않았다.

측정 당시 하네스 파일 SHA-256:
`19f137771e580f2ed09e1a89e6e7e86e06157ddd26bc21f375b5135071f2c41b`.
실측이 끝난 후, 상위 스트림이 자기 태스크를 취소할 때 소비자를 깨우고 원래 취소 예외를
보존하도록 오류 처리를 보완했다. **이 사후 보완은 단위 테스트로 검증했으며 위 실측
속도에 보완 효과를 포함하지 않았다.** 현재 전체 단위 테스트는 109개 통과했다.

실측 두 실행 구간의 질문 SHA, 원본 앱 소스 및 실행 코드 SHA는 동일했다. 구간 사이에
수정한 것은 분석 스크립트뿐이다. 분석기는 다른 로그가 같은 줄 뒤에 붙은 온전한 JSON을
읽도록 보완했으며, 원시 로그를 수정하거나 잘린 JSON을 복원하지 않았다.

원시 자료는 로컬에 보존하고 Git에서 제외했다. 운영 키·원본 앱·원시 응답은 게시하지 않았다.
