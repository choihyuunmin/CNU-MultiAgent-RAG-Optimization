# 사용자 규모 증가와 성능 저하: 추가 실험 결과

2026-09-07. [프로토콜](MOLEG_SCALING_PROTOCOL_20260907.md).
이 문서의 기존 로그 재분석과 새 GPU API 실험을 구분한다.

후속: 같은 날 SSH 접근을 복구해 현재 pod의 **이중 상한**을 확인하고 별도 앱
대조와 GPU DRAM·host RAM 계측을 수행했다. 아래의 미측정·접속 제한 언급은
초기 592회 당시의 상태다. 새 증거는 [후속 실측 보고서](MOLEG_SCALING_ISOLATED_RESULTS_20260907.md)에
분리하며 초기 운영 API 결과와 합산하지 않는다.

## 1. 먼저 바로잡을 수치

추측 디코딩 후 **2.9% 단축은 동시성 4의 전체 응답시간**이다.
95% CI −4.4~+9.3%로 유의한 개선을 확인하지 못했다.
동시성 16에서 분류·준비 모델 호출은 51.3% 빨랐지만 이것은 종단 결과가 아니다.
따라서 "16명에서 2.9%"를 논문의 근거로 쓰지 않는다.

## 2. 기존 E1의 원시 로그 재분석

대상: 200문항 × 단일/이중 워커 × 동시성 상한 4·8·16 = 1,200개 종단 요청.
서버 로그는 2026-09-06 22시대부터 09-07 00시 이전의 동일 실험 구간에 맞췄다.
새 추론을 실행한 결과가 아니라 보관된 요청·LLM trace·10초 간격 로그의 재계산이다.

| 4 | 9.392초 | 2.90 | 4.433초 | 2.566초 | 38.9% | 1 |

실행을 기다리는 빈 구간은 제외했다. 지속 사용자 수나 정상상태 처리량이 아니다.

초기 세 번째 오케스트레이터 호출의 평균 입력 토큰은 4,794·4,781·4,769,
출력 토큰은 모두 약 103이었다. 부하 증가에서 호출 시간이 약 3.28배가 되지만
생성 길이가 늘어난 것은 아니다. 긴 입력의 처리와 요청 대기, 동시 decode 간섭을
추가로 분리해야 한다. 호출 순번을 모든 경로에서 동일한 의미 단계라고 단정하지 않는다.

상한 U=16에서 실제 평균이 6.18에 그친 이유는 매 묶음의 느린 마지막 요청이
완료될 때까지 다음 묶음을 넣지 않았기 때문이다. 이 설계를 지속 부하 설계로 바꾼
것이 새 실험의 중요한 수정이다. 낮은 부하에서의 개선율을 사용자 규모로 확장할 때
기존 묶음 처리율을 그대로 쓰면 안 된다.

KV 최대 81.3%와 대기 9건은 압력 증가의 관측 근거다. 그러나 10초 표집에서
100%가 없다는 이유로 순간적인 용량 제한을 배제할 수도, 이를 HBM 대역폭 부족의
증거로 확정할 수도 없다. 기존 보고서의 "prefill 병목 확인"은 이 범위로 제한한다.

## 3. 현재 서버에서의 새 실험

HTTP로 확인한 현재 오케스트레이터·워커의 vLLM 버전은 0.19.0이다.
이전 E1의 실행 환경과 다르므로 과거의 추측 설정과 오늘의 baseline을 직접 비교하지 않는다.
검색·답변 API와 서버 메트릭을 호출하며 운영 프로세스·모델 설정은 변경하지 않는다.

예비 8문항 × U=1·4, 총 16개 SSE 요청은 모두 정상 완료했다.
U=1 평균은 13.792초, U=4는 14.713초였다. 예비 U=4는 질문 수가 작아
정상상태 곡선으로 사용하지 않으며 본 측정에 합산하지 않는다.
예비 단일 사용자 구간의 오케스트레이터 호출 평균은 queue 0.00052초,
prefill 0.471초, decode 2.329초였다. 이 값은 모델 한 호출의 서버 평균이며
전체 API의 직접적인 시간 분할이 아니다.

### 3.1 첫 사용자 규모 스윕: 실제 API 384회

64개 고유 질문을 U=1,2,4,8,16,32에서 한 번씩 실행했다. 원래 계획은 두 번이었으나,
첫 U=32에서 180초 기한 초과가 발생해 중단 규칙에 따라 두 번째 반복을 실행하지
않았다. 실제 384개 행 중 정상 SSE 완료는 383개다. 모든 부하의 첫 반복은 보존되어
있지만, **계획한 두 반복 전체가 완료된 것은 아니다**. 따라서 단발·유한 워크로드의
진단 결과로 보고하고 시간대에 독립적인 성능 신뢰구간으로 일반화하지 않는다.

실패를 지연 통계에서 제거하지 않았다. U=32의 평균에는 180초에 중단된 요청이 포함되며,
그 요청이 정상적으로 모두 완료됐을 때의 지연은 알 수 없다. 30초는 탐색적 실험 기준으로,

U=1 대비 평균 관측 지연은 U=16에서 4.31배, U=32에서 7.80배였다.
처리량은 약 0.23~0.25건/초 부근에서 더 늘지 않았고, 30초 이내 완료 처리량은
U=4의 0.184건/초에서 U=16의 0.018건/초로 내려갔다. 이는 현재 제한된 경로의
유효 처리량이며 GPU의 최대 처리량으로 해석하지 않는다.

### 3.2 모델 서버 계측과 품질 감시

오케스트레이터의 요청당 서버 평균은 다음과 같다. 공유 인스턴스 histogram의
구간 delta로 계산했으며 API 한 요청의 전체 지연 분할이 아니다.

| U | 모델 queue | prefill | decode | KV 관측 최대 | 선점 증가 |
|---:|---:|---:|---:|---:|---:|
| 1 | <0.001초 | 0.391초 | 2.364초 | 36.27% | 0 |
| 2 | <0.001초 | 0.399초 | 2.569초 | 40.76% | 0 |
| 4 | 약 0.001초 | 0.493초 | 3.292초 | 58.34% | 0 |
| 8 | 약 0.001초 | 0.411초 | 2.635초 | 58.13% | 0 |
| 16 | <0.001초 | 0.458초 | 3.007초 | 41.74% | 0 |
| 32 | 약 0.001초 | 0.508초 | 3.153초 | 48.43% | 0 |

평균 생성 토큰은 대략 82~83개로 유지됐다. 워커 KV 최대는 모든 부하에서
약 1.3% 이하였고 선점은 0이었다. 메모리 **용량 부족**이 현재 대기 증가를
지배한다는 근거는 찾지 못했다. HBM 대역폭 포화 여부는 이 계측으로 판정하지 않는다.

공유 prefix cache를 초기화하지 않았다. 오케스트레이터의 구간 적중률은 약 64~66%였지만,
워커는 U=1의 58.7%에서 후속 U=2~32의 98.5~99.4%로 달랐다. 첫 반복은 U 오름차순이므로
부하와 실행 순서·cache 상태가 완전히 분리되지 않는다. 따라서 이 곡선을 cache 조건까지
동일하게 맞춘 GPU 처리능력 비교로 해석하지 않는다. 역순·독립 반복이 필요한 이유다.

출처 라벨이 있는 39문항의 법령 포함은 모든 U에서 36/39였고, 참조 조문 21문항의
포함은 모두 16/21이었다. 반환 문서 목록의 U=1 대비 완전 일치율은 성공 쌍에서
95.3~98.4%로, 같은 요청도 배치·생성 변동이 있었다. 출처 포함의 동일성은 전문가
답변 정확도 또는 무손실성의 증명이 아니다. U=32의 실패한 비교 질문에는 출처 정답
라벨이 없으므로 출처 지표가 같다는 사실이 그 실패를 상쇄하지 않는다.

실패 q343은 첫 진행 이벤트를 104.366초에, 첫 답변을 138.504초에 받았고,
10,165자를 받은 상태에서 180.003초에 클라이언트 전체 기한을 초과했다.
HTTP 상태는 200이었지만 최종 done 결과를 받지 못해 실패로 기록했다.
실험 종료 후 오케스트레이터·워커·비교 모델의 running/waiting=0을 확인했다.
이 기록을 GPU OOM이나 모델 자체의 180초 계산으로 해석하지 않는다.

### 3.3 외부 수용 제어 음성 대조

32명에서 기한 초과를 관측한 뒤, 모든 요청이 완료됐던 U=16에서 같은 64문항으로
baseline / 고정 상한 8 / 적응형 상한을 각 1회 비교했다. 192회 모두 정상 완료했다.
내부 상한 4가 있으므로,
추가 gate가 GPU 실행 용량을 늘리는 실험이 아니다. 집계 시 외부 대기와 HTTP
구간을 나누고 총 사용자 지연을 판단 기준으로 삼았다.

| U=16 조건 | 총 지연 평균 | 외부 gate 대기 | HTTP 구간 | p95 | 정상 완료/초 | 30초 이내 완료 |
|---|---:|---:|---:|---:|---:|---:|
| baseline | 59.819초 | <0.001초 | 59.819초 | 82.662초 | 0.2346 | 3/64 |
| 고정 상한 8 | 58.694초 | 27.866초 | 30.828초 | 79.256초 | 0.2445 | 6/64 |
| 적응형 8→16 | 59.416초 | 3.721초 | 55.695초 | 78.605초 | 0.2354 | 6/64 |

고정 상한은 HTTP 구간만 보면 약 48.5% 빨라 보이지만, 외부 대기까지 합산한 단축률은
1.88%였다(질문 단위 bootstrap 95% CI −6.37~+10.07%). 적응형은 0.67%였다
(CI −7.09~+8.18%). 둘 다 0을 포함하므로 유의한 종단 개선을 확인하지 못했다.
질문 단위 CI는 단일 실행의 요청 간 스케줄링 의존성이나 시간대 변동을 제거하지 않으므로
일반적인 성능 보장으로 사용하지 않는다. 30초 이내 건수도 3→6건에 불과해, 이를
"대규모 goodput 2배 개선"으로 주장하지 않는다.

적응형 상한은 여유 표집에 따라 8번 증가하여 16에 도달했고 감소하지 않았다.
내부 상한을 바꾸지 못한 채 외부 대기 위치만 조절한 결과와 일관된다.
오케스트레이터 KV 최대는 조건별 45.96·58.44·44.34%, 선점은 모두 0이었다.
적응형의 모델 평균 queue는 0.022초로 기준보다 늘었지만 API 첫 이벤트 전 평균
43.00초와는 규모가 달랐다. GPU 지표만으로 앞단 상한을 감지할 수 없는 한계를 보여준다.

출처 법령·조문 포함은 세 조건 모두 36/39·16/21이었다. 기준 대비 반환 목록 완전
일치는 고정 60/64, 적응형 61/64였으므로 답변 무손실성을 입증한 결과가 아니다.
한 번씩 순차 실행한 탐색적 음성 대조로 남기고, 두 정책을 새 기본 최적화로 채택하지 않는다.

## 4. 메모리 병목 판정의 범위

### 4.0 현재 운영 경로의 4개 생성 슬롯

보관된 실제 pod 소스와 검증된 실행 설정에는 생성 API 전역 상한 4가 있다.
현재 U=8의 최초 4개 요청은 약 30~40ms 안에 첫 진행 이벤트를 받았다.
이어진 4개 요청의 첫 이벤트 시각은 앞선 요청의 완료 시각과 최대 12ms 차이로
일치했다. 새 세션을 사용했으므로 동일 세션 직렬화로 생긴 대기는 아니다.
[설정·소스 해시와 실제 응답 정렬 근거](../experiments/results/moleg-scaling-20260907/app_queue_evidence.json)를
별도로 보관했다. 당시 pod와 CPU 재현의 세 emitter 함수 AST 해시는 모두 같았다.

첫 반복 U=8에서는 평균 29.595초 중 14.123초가 첫 이벤트 이전에 걸렸다.
U=16에서는 평균 약 59.78초 중 약 43.18초가 첫 이벤트 이전 대기였다.
U=1→16의 평균 지연 증가량 중 약 94%가 이 구간의 증가다.
반면 vLLM 내부 대기는 거의 0이고 KV 선점은 없었다. 현재 경로의 사용자 증가에
따른 지연을 GPU 메모리 부족만으로 설명할 수 없으며, 우선 앱 앞단의 수용 대기가
지배적인 구간을 분리해야 한다.

U=16·32에서 첫 이벤트 이후의 평균 관측 시간은 약 16.6초였다. 네 슬롯이 이 실행·전송
구간을 점유한다고 가정하면 `4 / 16.6 ≈ 0.24건/초`로, 관측 처리량 0.234·0.230건/초와
가깝다. 이는 앱 상한 가설과 처리량 평탄화가 수치적으로 일관됨을 보여주는 근사이며,
정상상태 용량 측정이나 GPU 연산시간 추정은 아니다.

이 곡선은 외부 사용자 U와 내부 상한 4를 함께 갖는 운영 API 곡선이다.
실제 GPU 파이프라인 동시성을 16·32로 올린 결과가 아니다. 앞선 E1의 별도 앱
복사본과도 동일 구성으로 취급하지 않는다. 외부 상한을 하나 더 두는 실험은
개선 주장이 아니라 이중 대기열의 음성 대조로 해석한다.

현재 접속 가능한 vLLM 메트릭에서 KV 사용·대기열·선점·queue/prefill/decode 시간을
읽는다. 추론 호스트 SSH는 로컬 배포 키로 인증되지 않았고 GPU/노드 exporter도
접근되지 않았다. 따라서 오늘 실험의 HBM bytes/s, SM/Tensor 활동,
추론 호스트 swap-in/out·PSI는 아직 미측정이다.

로컬 부하 발생기의 RTX 3050·RAM·swap 상태를 원격 추론 GPU의 문제로 해석하지
않는다. 추론 호스트 접근 후 `scripts/monitor_moleg_resources.py`로 호스트 메모리와
GPU 사용량을 수집할 수 있다. `nvidia-smi utilization.memory` 역시 메모리 활동
시간의 비율이지 최대 HBM 대역폭 대비 사용 비율은 아니다. 대역폭 결론에는 별도
GPU 프로파일링이 필요하다.

### 4.1 장문 비교 응답의 전송 대기: 다른 종류의 병목

첫 U=1 측정에서 비교 질문 q343은 16,749자를 반환하며 총 92.835초가 걸렸다.
첫 답변 delta 이후에는 68.039초가 걸렸다. 로컬에 보관된 앱 소스의 emitter는
5자 청크 사이에 20ms를 기다린다. 완성된 텍스트를 한 번에 전달하는 경우의 명시적
대기 합은 `(ceil(16749/5)-1) × 0.02 = 66.98초`이며, 관측과 가깝다.
다른 비교 질문에서도 1,432자의 예측 5.72초에 관측 5.80초,
1,031자의 예측 4.12초에 관측 4.21초로 비슷한 패턴이 나타났다.

현재 배포 소스를 직접 대조하지 못했으므로 이것을 현재 코드의 확정적 원인으로
표현하지 않는다. 다만 출력 길이와 전송 지연의 일치가 강한 단서다. 비교 모델은
주 계측의 오케스트레이터·워커와 별도이므로, 이 두 모델의 KV만으로 비교 모델의
메모리 상태까지 일반화하지 않는다. 비교·임베딩·리랭커·가드레일의 보조 메트릭은
U=2 실행 도중부터 별도 파일에 추가 수집했다. U=1의 해당 모델 관측으로 소급하지 않는다.

이를 검증하기 위해 보관된 실제 emitter 함수만 추출하고, 같은 길이의 **합성 완성
텍스트**를 사용한 CPU 재현을 수행했다. 실제 모델의 미세한 토큰 delta를 완성 답변
한 덩어리로 바꾸어 비교한 실험이 아니다. 대상은 이미 완성된 본문을 흘리는 경로다.
원 함수의 입력 텍스트는 모든 조건에서 동일하며 출력 문자·순서를 해시로 검사했다.

| 동시 전송 작업 | 기존 paced 전체 완료 | 즉시 emit | 출력 동일성 |
|---:|---:|---:|---|
| 1 | 67.670초 | 1ms 미만 | 1/1 동일 |
| 8 | 68.054초 | 1ms 미만 | 8/8 동일 |
| 32 | 69.394초 | 약 1ms | 32/32 동일 |

두 조건 합계 82개 전송 작업 모두 정확히 같은 텍스트를 반환했다.
이 결과는 GPU·네트워크·브라우저가 없는 CPU 전송 helper의 결과다.
실제 검색 API를 그 비율만큼 가속했다거나 운영 UI 회귀가 없다고 주장하지 않는다.
기존 실제 모델 delta 재생의 약 95ms 절감과도 모집단·청크 입력 형태가 다르다.

개선안은 서버에서 이미 준비된 데이터를 대기 없이 전송하고, 필요한 화면 표시 속도는
브라우저에서 제어하는 것이다. 서버에서 인위적 대기를 없애는 것은 모델 답변 축약이나
정확도 완화와 다르다. 특히 전체 HTTP 수명 동안 GPU 수용 슬롯을 점유하는 정책은
이러한 전송 대기까지 GPU 작업으로 오인할 수 있으므로, 후속 단계별 수용 제어에서는
모델 RPC 완료와 HTTP 스트림 완료의 수명을 분리해야 한다.

## 5. 제출 준비에 반영할 개선 방향

실측에 따라 다음 순서로 개선 요인을 분리한다.

1. **완성 텍스트의 인위적 전송 대기 제거**: 모델·프롬프트·답변 길이는 그대로 두고
   내부 슬롯 4에서 기존/즉시 emitter를 대조한다. CPU 재현의 이득이 실제 API에서도
   재현되는지, 특히 장문 비교 질문과 뒤따르는 다른 사용자의 p95를 확인한다.
2. **내부 생성 슬롯 4→8→16의 독립 조절**: 전송 조건을 고정한 별도 앱에서 실제
   파이프라인 동시성을 바꾸며, KV·선점·prefill/decode·호스트 메모리를 함께 측정한다.
   바깥에 gate를 추가하는 것과 구분한다. 안전 조건을 통과하기 전 16·32로 확대하지 않는다.
3. **단계별 자원 예산과 추측 디코딩 결합**: 분류·준비의 구조화 출력에는 이력 기반
   추측 디코딩을, 긴 입력을 읽는 선별에는 입력 토큰·KV 수요 기반 스케줄링을 적용한다.
   혼잡 시 투기적 병렬 작업을 줄이고 여유 시 중첩한다. 이는 아직 실측되지 않은 제안이며,
   모델 RPC 완료와 HTTP 전송 완료를 분리한 계측이 먼저 필요하다.

제어 입력에도 앱 단계별 대기·실행 슬롯 점유를 포함해야 한다. GPU KV 여유와 모델
대기 0만 보고 전체 시스템에 여유가 있다고 판단하면, 앞단 상한이나 전송에 막힌 요청을
더 받아 대기만 늘릴 수 있다. GPU·앱·전송의 압력을 구분하는 것이 이번 관측에서
도출한 단계별 제어의 구체적 설계 조건이다.

첫 두 요인의 A~E 독립 대조 launcher는 준비했지만, 추론 호스트 SSH 인증 실패와
앱/서빙 설정 파일 접근 부재로 **실제 A~E 비교는 실행하지 못했다**.
운영 프로세스나 모델 설정을 변경하지 않았으며, CPU 재현이나 외부 gate 대조를
이 개선안의 종단 성능 검증으로 대체하지 않는다.

추가 GPU를 확보하면 오케스트레이터 별도 GPU 복제와 TP를 동일 총 GPU 예산으로
비교한다. 같은 GPU에 워커 프로세스를 더 띄우는 것만으로 처리 용량이 늘었다고
보지 않는다. 배치 토큰 예산, KV 예산, 추측 길이의 효과는 독립 대조로 분리한다.

기존 400문항 결과의 품질 근거는 유지하되, 새 부하 실험의 품질·완료율도 별도로
평가해야 한다. 전문가 답변 평가, 목표 학회 형식, 장시간 정상상태와 독립 반복은
학술 제출 전 남은 항목이다. 작은 실험에서 유의차가 없다는 사실을 무손실로 표현하지 않는다.
