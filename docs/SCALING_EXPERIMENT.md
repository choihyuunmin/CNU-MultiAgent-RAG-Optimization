# 사용자 증가에 따른 병목 분리 실험

## 이번 변경의 범위

기존 검색기 소스와 환경 파일을 수정하지 않고 로컬 실행 어댑터를 연결한다.
모델, 프롬프트, 검색 내용, 스트리밍, 토큰 수, 추론 옵션은 변경하지 않는다.
기존 추론 API 호출 직전에 허용된 실행 자리(credit)를 얻고, 호출 또는 스트림이
끝나면 반환한다. 호출을 생략하거나 답변을 캐시·재작성하지 않는다.

기존 애플리케이션은 질문 전체가 끝날 때까지 전역 실행 자리를 점유한다.
그 질문이 검색 DB를 기다리는 동안에도 다른 질문의 LLM 실행이 막힐 수 있다.
개선안은 질문 진입 한도와 실제 추론 자원의 실행 한도를 분리한다.

| 방법 | 바꾸는 부분 | 비교 목적 |
|---|---|---|
| 기존 방식 (`control`) | 계측만 추가. 입구·생성 한도 유지 | 현재 검색기 기준 |
| 요청 창 확대 (`request_window`) | 로컬 입구·생성 한도 32 | 단순 설정 변경만으로 얻는 이득 분리 |
| 단계별 도착순 (`stage_fifo`) | 요청 창 32 + 추론 자원별 한도 + FIFO | 자원별 한도만의 효과 분리 |
| 단계별 질문 묶음 순서 (`stage_coflow`) | 자원별 한도 + 같은 질문의 대기 작업을 묶어 실행 순서 결정 | 묶음 순서의 추가 이득 확인 |
| 화면 전달 대기 제거 (`delivery`) | 원래 출력 조각은 유지, UI의 인위적 sleep만 제거 | 출력 지연을 추론 지연에서 분리 |
| 전달+단계별 제어 (`delivery_coflow`) | 화면 전달 대기 제거 + 단계별 실행 제어 | 정리된 출력 경로에서도 스케줄링이 추가 이득을 주는지 확인 |

질문 묶음 순서는 지금 확인 가능한 작업의 예상 잔여 시간을 사용한다. 미래의
전체 작업 그래프나 모델의 내부 추론을 아는 방식이 아니다. 최근 단계별 처리
시간을 추정값으로 쓰고, 오래 기다린 작업은 도착순 우선권을 준다.

이는 네트워크의 수신 측 흐름 제어와 coflow 스케줄링 개념을 응용한 실험이다.
기존 기법을 결합했다는 사실만으로 새로운 알고리즘이나 논문 기여가 입증되지는
않는다. 단순 요청 창 확대 및 FIFO보다 좋은지 실험으로 구분해야 한다.

## 자원 구분과 안전성

- API의 모델 별칭이 달라도 동일한 추론 주소를 사용하면 한도를 공유한다.
- 현재 구성에서 동일 모델의 독립 복제본은 확인되지 않았다. 복제본 라우팅
  성능을 측정하는 실험이 아니다. 다른 모델로 우회하지 않는다.
- 자원별 한도 기본값은 orchestrator 8, 나머지 4인 **실험 파라미터**다.
  GPU의 최적 처리량이나 물리 용량으로 검증된 수치라는 뜻은 아니다.
- 스트림 전체 수명 동안 자리를 유지하고 오류·취소에도 반환한다.
- 앱 실행은 로컬 `127.0.0.1`에 한정한다. 원격 엔진을 재시작하거나 설정을 바꾸지 않는다.
- 추론 대기가 64개 초과하거나 KV 캐시 비율이 95% 초과인 표본이 연속 5회면
  자신이 실행한 시험 프로세스만 종료한다. 원격의 다른 요청은 취소하지 않는다.

## 재현 실행

통합 애플리케이션은 `scripts/experiment/run_rag_experiment.py`,
`run_experiment_bundle.py`, `collect_vllm_metrics.py`를 제공해야 한다.
실행 환경은 그 애플리케이션의 Python 가상환경을 사용한다.
키는 기존 `.env`에서 읽으며 결과 문서나 명령행에 기록하지 않는다.

```sh
PYTHONPATH=src /path/to/application/.venv/bin/python scripts/run_scaling_experiment.py \
  --application-root /path/to/application \
  --questions /path/to/application/scripts/experiment/questions_400_country_law_balanced.jsonl \
  --count 400 --concurrency 1,2,4,8,16,32 \
  --modes control,request_window,stage_fifo,stage_coflow \
  --run-id scaling-400-unique-run-id
```

화면 출력 대기를 분리하는 후속 비교는 `--modes control,delivery,delivery_coflow`를
사용한다. LLM의 스트리밍·호출 인자는 그대로이며 로컬 화면 출력 대기만 다르다.
`STREAM_DELAY_S=0`은 원래 설정 파서가 기본값으로 되돌리므로, 어댑터는 원래
출력 함수의 지연 기본값을 명시적으로 0으로 바꾼다. 원본 파일은 수정하지 않는다.

빠른 연결 점검은 `--count 4 --concurrency 1`, 부하 예비 실험은
`--count 32 --concurrency 4,8,16,32`로 구분한다. **32문항 한 번의 버스트는
400문항 지속 부하의 대체물이 아니다.** 파일에 있는 실제 문항을 난이도별로
균등 추출하며 새 질문이나 정답을 만들어 넣지 않는다.

```sh
/path/to/application/.venv/bin/python scripts/analyze_scaling_experiment.py \
  experiment-results/scaling-400-unique-run-id \
  --application-root /path/to/application \
  --output-dir experiment-results/scaling-400-review-unique-id
```

모든 방법에 같은 문항·순서를 사용하고 사용자 수별로 방법 순서를 순환시킨다.
각 셀은 별도 로컬 프로세스에서 실행한다. 실패 응답도 분모에 포함하고 자동
재시도하지 않는다. 원래 앱·SDK 자체의 재시도 동작은 변경하지 않는다.
모든 원시 출력은 무시되는 `experiment-results/` 아래에만 저장한다.
같은 run ID로 결과를 덮어쓰지 않는다.

각 셀 시작 전 두 번 연속으로 엔진 실행·대기 요청이 0인지 확인한다. 기본 120초
(`--idle-timeout`) 동안 확보되지 않으면 새 추론 요청 없이 중단한다. 요청 전 유휴만으로
완전한 격리가 보장되지는 않으므로, 완료 후 앱 호출 수와 엔진 완료 수도 대조한다.

## 읽어야 할 지표

1. 사용자 관점: 전체 응답 평균·p50·p95, 첫 응답 시간, 완료 처리량, 실패율.
2. 애플리케이션: 기존 trace **이전**의 입구 대기, 생성 대기, 단계별 대기.
3. 추론 엔진: 실행·대기 요청 수, queue/prefill/decode 시간의 누적 카운터 차이,
   KV 캐시 사용률, 중단·재개(preemption) 증가.
4. 결과 보존: 같은 부하의 기존 응답 대비 법령 재현율, 순서 일치율, 첫 법령
   일치율, 답변 문자 유사도. 원래 평가기의 계산 함수를 재사용한다.

LLM API 시간에는 네트워크·프록시·엔진 대기가 포함된다. 병렬 LLM 호출 시간을
합산한 값은 사용자 대기 시간이 아니다. 분석기는 호출 구간의 합집합도 기록한다.
엔진 지표는 공유 인스턴스 전체 값이라 운영 요청이 섞일 수 있다. 카운터가
재시작하거나 빠지면 0으로 보정하지 않고 미측정으로 표시한다.

## 논문 결과로 채택하기 전

- 20개 국가의 실제 법령 질문 400개, 난이도별 100개다. 모든 질문에 해당
  국가명이 포함된다. 전문가가 지정한 `expected_law_ids`는 현재 비어 있다.
- 기존 답변을 기준 답변으로 쓰는 평가는 **법적 정확도**가 아니라 **일치도**다.
- 같은 모델·입력을 유지해도 병렬 배치와 비결정성 때문에 출력이 달라질 수
  있다. 기존 방식 자체도 반복하여 자연 변동을 측정해야 한다.
- 평균 시간만 좋아지거나 실패가 늘어난 후보를 채택하지 않는다. 답변 보존과
  p95·처리량도 함께 판단한다. 실행 후 유리한 임계값을 골라 통과시키지 않는다.
- 물리 VRAM·메모리 대역폭·GPU 연산 사용량은 별도 read-only GPU 계측이 필요하다.
  KV 캐시가 낮거나 preemption이 없다는 사실만으로 메모리 대역폭 병목을 배제하지 않는다.
- 이번 실행의 단순 한도 완화보다 제안 순서가 추가 이득을 주는지, 반복 실행
  및 다른 검색 도메인에서도 유지되는지 확인한 뒤 연구 기여를 주장한다.

## 지표 해석 근거

vLLM은 KV 캐시 사용률, 대기·실행 요청 수, queue/prefill/decode 시간을 서로
다른 지표로 제공한다. 캐시 부족으로 인한 preemption은 재계산과 지연을 일으킬
수 있다. 이번 실험에서는 지표만 읽으며 문서의 엔진 튜닝 옵션은 적용하지 않는다.
[vLLM 지표 정의](https://docs.vllm.ai/en/stable/usage/metrics/),
[preemption 설명](https://docs.vllm.ai/en/stable/configuration/optimization/).

`nvidia-smi`의 `utilization.memory`는 측정 구간 중 메모리 읽기·쓰기가 일어난
시간의 비율이다. VRAM 점유율도, 이론 최대 대역폭 대비 실제 전송량 비율도
아니다. 이 값 하나로 대역폭 병목을 확정하면 안 된다.
[NVIDIA 지표 정의](https://docs.nvidia.com/deploy/nvidia-smi/index.html).
