# 참조 ID 축약·복원: 동시 요청 1~200 비교 실험

## 실행 전 고정한 조건

2026-09-16 KST에 기존 검색기와 개선 구성을 실제 GPU 서버에서 새로 비교한다.
측정 지점은 **1·2·4·8·16·20·32·50·100·150·200**이다. 1~200의 모든 정수를
측정하는 설계가 아니라 범위를 포괄하는 대표 11개 지점이다.

- 기존 200개 고유 회귀 질문을 사용한다. 새로운 미관측 평가셋이라고 부르지 않는다.
- 조건당 질문 수 `n(C) = max(32, C)`. 같은 동시성에서는 두 방식·두 반복의 문항이 같다.
- 각 동시성의 문항을 질문 종류별 비율에 맞춰 선택하고 목록과 질문 해시를 동결한다.
- **2조건 × 2반복 × (32×7 + 50 + 100 + 150 + 200) = 2,896요청**.
- 한 동시성에서 두 반복을 모두 마친 후 다음 동시성으로 올린다. 비교 순서를 뒤집는다.
- `baseline`: 기존 방식과 기본 worker reasoning.
- `improved`: worker 낮은 reasoning + 공통 참조 ID 축약·복원 코드, 후보 16개 이상에 적용.
- 새 ID 기능만의 분리는 [이전 3조건 실험](STRUCTURED_HARNESS_RESULTS_20260915.md)을 참고한다.
  이번 두 조건의 차이는 낮은 reasoning과 ID 기능을 합친 효과이며 이를 ID 단독 효과라 하지 않는다.

## 실행 환경과 실패 처리

실행 중인 검색 pod의 Python 소스 124개가 보관된 소스와 일치하는지 다시 확인했다.
공유 모델 서버의 프로세스 ID와 명령행 해시도 확인한다. 운영 모델 설정을 바꾸지 않고
GPU 서버의 loopback 독립 앱 두 개로 측정한다.

한 요청의 최대 관측 시간은 240초다. 실패·시간 초과·내부 오류를 모두 보존한다.
SSE 종료와 내부 파이프라인 정상 완료를 구분한다. 실패를 성공 요청으로 바꾸어 재시도하지 않는다.
어댑터 자체의 ID 복원 실패에 따른 한 번의 원래 입력 재호출은 사용자 응답시간 안에 포함한다.

비교 조건 사이에는 모델 처리·대기 요청이 비었는지 두 번 확인한다. 이 준비 대기는
별도로 기록하고, 실제 요청 제출 이후 시간은 전부 지연에 포함한다. 요청이 남은 채 다음
조건을 실행하여 실패 요청의 잔여 연산을 다음 조건의 비용으로 섞지 않는다.
모델 상태가 나쁘거나 개선 조건의 완료율이 50% 미만이면 상승을 중단하고 미실행 지점을 표시한다.

## 보고할 지표

- 실패를 포함한 평균·p95 응답시간과 성공 요청만의 시간.
- 정상 파이프라인 완료율, 성공 요청 처리량, 30초 이내 정상 완료 처리량.
- 클라이언트에서 실제 관측한 최대·평균 진행 중 요청 수.
- 기존 응답 대비 법령 ID 재현율·일치율, 기존 방식 자체의 반복 변동.
- 원천 법령 포함률. 이는 전문가 정확도와 다르다.
- 모델 KV 점유·대기·선점 등 공유 인스턴스 지표.
- 성능 측정 종료 후 대표 부하 1/20/100/200의 자동 답변 근거 평가.

질문을 단위로 두 반복을 평균한 paired bootstrap 4,000회의 구간을 제공한다.
과거 실험의 관측값을 이번 결과에 합치지 않는다. 표본이 작은 저부하 p95와 구간은
불확실성이 크므로 정밀한 꼬리 지연 추정으로 과장하지 않는다.

## 부하의 의미

각 조건은 유한한 질문 묶음이다. 32명 이상에서는 질문 수가 동시 요청 수와 같아,
처음 한꺼번에 제출한 뒤 완료가 늘수록 진행 중 요청이 감소한다. 따라서 200 조건은
**200개 동시 제출 실험**이며 장시간 유지되는 200명 용량 보장이 아니다.
저부하와 고부하의 문항 수도 달라서 부하 곡선에는 질문 묶음 크기의 영향이 있다.
개선율은 각 부하 안에서 같은 문항·같은 요청 수로 비교한다.

## 보관

질문·응답 원문은 비공개 실험 디렉터리에 둔다. Git에는 수치·해시·설정·그림·설명만
기록한다. 인증 정보는 운영자 파일 또는 일시적인 인증 프로세스에서 읽으며 코드에 넣지 않는다.
실행 진입점: `scripts/run_reference_scaling_study.py`.

## 재실행에 필요한 입력

새 실험 디렉터리에 저장소의 `src/`, `scripts/`, 실제 앱 소스인 `pod_source/`,
검증한 `live-source-manifest.json`, 비공개 200문항 `cases.json`,
`baseline.adapter.json`, `combined.adapter.json`을 준비한다. 운영 환경·모델 인증 파일은
경로로 전달한다. 공개 결과에는 질문 원문과 운영 앱 전체 소스가 없으므로,
공개 저장소만으로 같은 질문의 GPU 실험을 재실행할 수 있는 것은 아니다.

```bash
python scripts/run_reference_scaling_study.py \
  --directory "$STUDY_ROOT" \
  --app-env "$APP_ENV_FILE" \
  --serving-env "$SERVING_ENV_FILE" \
  --proxy-config "$PROXY_CONFIG_FILE"

python scripts/finalize_reference_scaling.py \
  --directory "$STUDY_ROOT" \
  --app-env "$APP_ENV_FILE" \
  --serving-env "$SERVING_ENV_FILE" \
  --proxy-config "$PROXY_CONFIG_FILE"
```

첫 명령이 성능 측정을 수행한다. 두 번째 명령은 성능 측정 완료와 코드 동결을 확인한 뒤
자동 답변 평가를 실행하고, 감사한 공개 자료를 실험 디렉터리의 `public/`에 생성한다.
이미 실행한 디렉터리를 덮어쓰지 않는다. 공개 자료만으로도 표와 그림은 다시 만들 수 있다.

## 실행 후 추가한 분석

성능 측정과 사전 지정 자동 평가 236건을 완료한 뒤, 200개 구간의 큰 반복 변동과
첫 반복의 낮은 자동 근거 점수를 확인했다. 이에 저장된 두 번째 반복 답변 130건을
같은 모델로 추가 평가했다. 새 검색 요청은 없으며 성능 요청 총수는 2,896건 그대로다.
이는 **사후 민감도 확인**으로, 사전 지정 평가를 대체하거나 처음부터 계획된 것으로
표현하지 않는다. `scripts/evaluate_reference_scaling_repeat.py`에 위 운영 파일 경로 인자와
`--level 200 --repeat 1`을 전달해 별도 디렉터리에 생성한다.
