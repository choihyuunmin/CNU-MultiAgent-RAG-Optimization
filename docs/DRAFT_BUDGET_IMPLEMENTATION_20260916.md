# 검증 비용 기반 제안 길이 선택: 구현과 실행 상태

## 현재 결과

- 비용 선택 모듈, 엔진 측정 연결 함수, 보정 CLI, 환경 점검기, 고정-k GPU 단계 실행기를 구현했다.
- 신규 29개를 포함해 **전체 323개 테스트 통과**. 테스트 입력은 합성이며 GPU 성능 자료가 아니다.
- 지정 서버 SSH와 GPU API 포트 연결은 시간 초과다. **새 GPU 실험 요청은 0건**이다.
- 원격 vLLM 버전·모델 호환성, 동적 k 적용, 검색 종단 성능은 아직 검증하지 못했다.
  이번 코드를 설치된 엔진에 연결하거나 운영 서비스를 변경하지 않았다.
- GPU 예비 실험을 통과하지 않았으므로 본 실험으로 승격하지 않았다.

원시 연결 점검은 [preflight.json](../experiments/results/draft-budget-20260916/preflight.json)에 있다.
여기에 나온 RTX 3050과 vLLM 미설치는 **현재 작업 컴퓨터의 상태**다. 원격 H200 서버의
상태를 읽은 것이 아니다. 원격 점검은 지정한 TCP 포트 연결 여부만 확인했다.

## 구현한 선택 규칙

[speculation_budget.py](../src/cnu_rag_optimization/speculation_budget.py)는 모델 호출 수,
입력·출력 제한을 바꾸지 않고 추론 엔진 내부 제안기에서 사용할 k를 선택한다.

1. 엔진·모델·GPU 설정 해시, 호출 유형 해시, 실제 모델 배치 크기, KV 사용량 구간이 같은
   측정끼리만 비교한다. HTTP 동시 사용자 수를 엔진 배치 크기라고 간주하지 않는다.
2. 같은 trial의 무추측과 후보를 비교해 실제 확정 토큰당 시간을 계산한다.
   수락률이나 `k+1`을 확정 토큰 수로 대신 사용하지 않는다.
3. 기본 최소 8개 짝에서 평균 비용 5% 이상 감소하고 paired bootstrap 95% 구간 하한이
   양수인 k 중 평균 이득이 큰 값을 고른다. 이는 보정용 선택 기준이며 독립 검증 결과가 아니다.
4. 짝이 누락된 조건은 전체 조건을 비적용 처리한다. 중복 측정은 오류다.
5. 엔진·단계·배치·KV 조건이 달라지거나 선택한 k가 미지원이면 0을 선택한다.
   0은 제안기만 건너뛰고 원래 모델의 일반 디코딩을 수행한다는 뜻이다.
6. `propose()`는 스케줄러·제안기·검증기의 k가 함께 조정된다는 확인 없이는 실행을 거부한다.
   n-gram 제안기의 `self.k`만 바꾸는 패치는 제공하지 않는다.

반환한 제안 토큰은 반드시 원래 모델의 검증기에 전달한다. 모델 출력이나 다음 에이전트의
입력을 대체하지 않는다. 프레임워크를 가정하지 않는 엔진 연결 인터페이스지만, 모든
프레임워크·공급자에 대한 연결 플러그인을 완성한 것은 아니다.

## 측정 연결 함수

`measure_decode_window()`의 실행 순서는 다음과 같다.

```
이전 GPU 작업 동기화 → 시간 시작 → 제안·원래 모델 검증 → GPU 완료 동기화 → 시간 종료
```

전체 엔진 구간 시간에는 CPU 제안·호스트 작업이 포함된다. **순수 GPU 커널 시간과는 다르다.**
클라이언트 HTTP 시간이나 오라클 시뮬레이션의 검증 단계 수를 넣는 것은 거부한다.
prefill이 섞인 구간도 거부하며, 호출자는 측정 구간의 배치·KV 조건을 일치시켜야 한다.
분산 실행에서는 모든 참여 GPU의 완료를 기다리는 동기화 함수를 제공해야 한다.
동기화로 실행 겹침이 줄어들 수 있으므로 보정 측정과 계측을 뺀 독립 검증을 분리한다.

이 함수는 엔진 코드에 연결할 지점이다. 현재 원격 엔진에 삽입하거나 실제 비용 표를
생성하지 않았다. `measurement_source` 값은 측정의 출처를 스스로 증명하지 않으므로
소스 해시·실행 기록을 함께 보존해야 한다.

`calibrate_draft_budget.py`는 JSONL 측정값에서 동결된 정책 JSON을 만든다. 빈 입력,
클라이언트/오라클 비용, 기존 출력 파일 덮어쓰기를 거부한다. 학습에 쓴 질문을 독립 검증에
재사용하지 않으며, 보정 파일 생성만으로 본 실험 진입을 허용하지 않는다.

## 설치 엔진의 호환성 확인

[공식 Dynamic SD 문서](https://docs.vllm.ai/en/latest/features/speculative_decoding/dynamic_speculative_decoding/)는
배치별 k 설정을 제공하지만, 검증된 방식은 Eagle/Eagle3/DFlash이고 다른 방식은 추가 확인이
필요하다고 명시한다. 데이터 병렬 실행의 제약도 있다. 따라서 기존 n-gram 방식과 현재
서버 버전에서 지원한다고 가정하지 않는다.

`probe_draft_runtime.py`는 설치 버전·관련 소스 해시·설정 필드 존재를 읽는다.
필드가 있어도 실제 모델 호환성이 입증된 것으로 표시하지 않는다. 서버에 연결한 뒤 이
점검기를 해당 Python 환경에서 실행하고, 격리한 작은 모델 실행으로 실제 지원을 확인해야 한다.
미지원이면 고정-k 결과까지만 보고하며 동적 정책의 성능 결과라고 부르지 않는다.

## 고정-k GPU 단계 예비 실행기

[run_draft_stage_pilot.py](../scripts/run_draft_stage_pilot.py)는 별도 프로세스에서 하나의
엔진을 만들고 k=0/2/4/8/16 중 하나를 시험한다. 서비스 재시작·프로세스 중지 기능은 없다.

- 입력은 같은 모델의 챗 템플릿으로 이미 만든 token ID와 원래 SamplingParams를 사용한다.
  원본 도구 스키마·구조화 출력 제약을 포함한 설정을 정확히 동결해야 한다.
- 원래 `max_tokens` 명시를 요구하며 실행기가 출력 한도를 낮추지 않는다.
- 워밍업 문항은 평가 문항과 분리하고, 같은 워밍업·문항 순서를 대조군에 사용한다.
- `CUDA_VISIBLE_DEVICES`로 명시한 실험 GPU에서 실행한다. 기존 작업과 메모리 여유를
  확인한 뒤에만 실행한다. 이 환경 변수 자체가 GPU 독점 사용을 보장하지는 않는다.
- 입력·설정·코드 해시, 완료 토큰 수·출력 해시·종료 이유, 실제 배치 크기를 기록한다.
- 잘린 출력은 정상 완료로 집계하지 않는다. 실패한 배치도 실패 행과 시간을 남기고 중단한다.
- 이 단계 실행기의 지연 지표는 **질문별 엔진 요청 시간/배치 전체 시간**이다. 엔진 decode
  구간 비용으로 오인해 선택 모듈에 넣지 않는다.
- 이 비교는 KV 메모리 등 실제 사용량과 생성 결과를 추가 확인해야 한다. 같은 설정 값만으로
  추측/무추측 엔진의 실제 KV 용량이 같다고 주장하지 않는다.

GPU 서버에서 원본 문항과 설정을 확보한 후의 실행 형태:

```bash
CUDA_VISIBLE_DEVICES=<확인한_GPU> PYTHONPATH=src <GPU서버_Python> \
  scripts/run_draft_stage_pilot.py \
  --engine-config /private/frozen-engine.json \
  --cases /private/frozen-tokenized-cases.json \
  --warmup-cases /private/separate-warmup.json \
  --k 0 --levels 1 4 --repeats 1 --output /private/plain-repeat0
```

처음에는 같은 4문항으로 0과 4를 비교한다. 다음 반복은 순서를 바꾼다. 서로 다른 시간대에
무추측 전체와 후보 전체를 한 번씩 실행한 결과를 공정한 비교로 간주하지 않는다.
고정-k부터 이득이 없으면 광범위한 설정 탐색이나 본 실험을 수행하지 않는다.

실제 비용 표 작성 → 동적 엔진 연결 검증 → 별도 문항의 소규모 종단 비교 → 통과 시 1~200의
대표 지점으로 확대하는 순서는 [예비 실험 프로토콜](TECHNICAL_ACCELERATION_PILOT_20260916.md)을 따른다.
동적 엔진 연결과 실측 비용 표는 서버 접속 복구 후 완료해야 하는 작업이다.
