# 2026-09-07 재실험 결과 및 미완료 항목

## 결론

**최종 성능 개선은 아직 검증되지 않았다.** 실제 검색기를 실행해 예비 데이터를
수집했고, 사용자 응답 시간에 인위적인 화면 출력 대기가 포함된 사실을 확인했다.
이를 제거하는 로컬 어댑터를 구현했다. 같은 실제 답변의 출력 조각을 그대로
보존하는 전달 구간 검증은 통과했다. 순수 LLM 추론이 빨라졌다는 뜻은 아니다.

400문항 및 동시 사용자 1·2·4·8·16·32명의 최종 비교는 **미완료**다.
16·32명 재시도는 기존 추론이 60초 동안 끝나지 않아 새로운 추론 요청을 보내기
전에 중단했다. 다른 요청을 취소하거나 엔진을 재설정하지 않았다.

## 완료한 실제 검색기 예비 실험

원래 400문항(20개 국가, 난이도별 100개)에서 난이도별 8개씩 추출한 동일한
32문항을 각 방법에 사용했다. 모든 질문에 해당 국가명이 포함된다.
동시 사용자 4명, 방법별 1회, 준비 요청 없이 실행했다. 기준 답변은 이번에
측정한 기존 방식의 응답이다. 기존 평가기의 법령 비교 함수를 변경 없이 재사용했다.

| 방법 | 정상 HTTP/응답 | 평균 전체 응답 | p95 | 처리량(건/초) | 기존 법령 재현율 | 첫 법령 일치율 |
|---|---:|---:|---:|---:|---:|---:|
| 기존: 질문 전체를 동시에 4개 처리 | 32/32 | 30.76초 | 56.17초 | 0.127 | 기준 | 기준 |
| 질문 진입 한도만 32개로 확대 | 32/32 | 34.12초 | 59.24초 | 0.108 | 89.0% | 75.0% |
| 추론 자원별 실행 한도 + 질문별 작업 묶음 순서 | 32/32 | 64.92초 | 140.63초 | 0.060 | 89.0% | 71.9% |

**세 번째 행은 요청 수 불일치가 있어 알고리즘 효과를 단독 비교할 수 없다.**
문서 처리·답변 모델의 앱 성공 호출은 181건인데 엔진 완료 카운터는 183건이었다.
추가 요청 또는 내부 재시도 영향을 배제할 수 없다. 첫 두 행은 각 추론 자원에서
앱 성공 호출과 엔진 완료 수가 일치했다.

동시 사용자 4명에서는 요청 한도 4→32 변경이 원칙적으로 제약을 해제하지 않는데도
응답 시간과 결과가 달랐다. 출력 변동, 실행 순서, 내부 대체 경로 등을 통제하는
반복 측정 없이 이를 개선안 때문에 발생한 정확도 하락으로 단정할 수 없다.
반대로 **정확도를 유지했다고 주장할 수도 없다.**

`expected_law_ids`는 현재 400문항 모두 비어 있다. 표의 재현율·일치율은 기존
답변과의 비교이지 전문가 정답 기반 법적 정확도가 아니다. 양쪽 법령 결과가 모두
빈 질문도 있으며 상세 JSON에 별도 집계했다.

이후 동시 8명 셀은 8건 완료 시점에 원인 분리 목적으로 중단했다. 이 일부 결과를
32문항 완료 결과처럼 평균 내거나 표에 포함하지 않았다.

## 확인한 병목과 계측 문제

### 1. 질문 전체를 막는 두 개의 전역 제한

원래 앱의 입구 미들웨어와 생성 대기열에 동시 4개 제한이 있다. 입구 대기는
기존 요청 trace 생성 이전에 발생해 기존 로그에서 빠질 수 있다. 어댑터에서
입구 대기를 따로 기록하도록 했다. 사용자 수 증가에 따른 대기를 GPU 대기와
혼동하지 않기 위한 변경이다.

### 2. 인위적 화면 출력 대기가 LLM 측정에도 섞임

현재 통합 코드의 `core/query_loop/_helpers.py`는 기본적으로 5자씩 출력하며
조각 사이에 0.02초를 기다린다. 완성된 답변을 다시 타이핑하듯 출력하는 경우도
이 함수를 쓴다. 실제 LLM 스트림을 소비하는 경로에서도 이 함수를 기다리므로,
클라이언트가 기록한 LLM 스트림 시간에 화면 출력 대기가 포함될 수 있다.

새 `delivery` 어댑터는 원래 함수의 지연 기본값만 0으로 바꾼다. 5자 조각 크기,
문자열, 순서, 실제 LLM 스트리밍 호출은 유지한다. 응답 전의 임의적인 모의 생각
대기도 로컬 프로세스에서만 제거한다. 앱 원본 파일과 `.env`는 수정하지 않았다.

**동일한 실제 답변을 재생한 전달 구간 검증:**

| 항목 | 기존 출력 | 출력 대기 제거 |
|---|---:|---:|
| 답변 길이 | 4,952자 | 4,952자 |
| 출력 이벤트 수 | 991개 | 991개 |
| 로컬 출력 큐 적재 시간 | 20.6077초 | 0.000436초 |
| 이벤트 내용·순서 | 기준 | 전체 일치 |

입력은 `l3-016-de-transfer` 질문에 대해 실제 모델이 생성했던 답변이다.
두 이벤트 배열의 SHA-256이
`0c194cabb7daae4480d7e5579c8c7ac26fbfff44ccf4e7f101d73e824384bf02`로 일치했다.
**이 측정에는 새 LLM 추론이나 HTTP/화면 렌더링 시간이 없다.**
전체 검색 시간이 0.000436초로 줄었다거나 추론이 99% 개선됐다고 인용하면 안 된다.
UI 지연 제거 자체를 새로운 추론 가속 알고리즘의 기여로 주장해서도 안 된다.

실제 RAG에도 `delivery`를 적용해 4문항 정상 응답은 확인했다. 다만 첫 요청을
보내기 전에 이미 문서 처리 모델에서 2개 요청이 실행 중이어서, 이 실행의
전체 응답 시간은 속도 개선 판단에 사용하지 않았다.

### 3. 숨겨진 입력 길이 초과와 출력량 변동

비교 모델이 `ContextWindowExceededError`를 반환해도 앱이 대체 응답을 만들면
최종 요청은 성공으로 기록된다. 위 세 방법에서 내부 비교 모델 오류가 각각
1·2·1건 있었다. HTTP 성공률만으로 정확도나 정상 처리 여부를 판단하면 안 된다.

예를 들어 `l3-099-nz-platform`의 대체 답변 생성은 기존 실행 1,402토큰/
8.62초, 작업 묶음 순서 실행 5,359토큰/57.44초였다. 입력 길이 오류에 따른
대체 경로, 출력량 변동, 화면 대기, 추론 자원 간섭이 함께 영향을 줄 수 있어
이 차이를 순수 CoT 또는 네트워크 지연 차이로 해석하지 않았다.

### 4. 현재 메모리 증거의 범위

| 문서 처리·답변 추론 자원 | 기존 | 한도 확대 | 작업 묶음 순서 |
|---|---:|---:|---:|
| 엔진 대기 요청 최대 | 16 | 13 | 4 |
| KV 캐시 최대 사용률 | 4.07% | 4.20% | 7.72% |
| preemption 증가 | 0 | 0 | 0 |

다른 계측 대상도 이 세 셀에서 preemption 증가가 없었다. 이번 관측에서는
**KV 캐시 용량 부족으로 중단·재계산하는 현상은 확인하지 못했다.** 물리 VRAM,
GPU 연산 사용량, 메모리 대역폭 병목까지 배제한 것은 아니다. SSH 공개키 인증이
실패해 물리 GPU 계측은 아직 하지 못했다.

KV 캐시 비율과 엔진 대기는 서로 다른 지표다.
[vLLM 지표 정의](https://docs.vllm.ai/en/stable/usage/metrics/).
또한 `nvidia-smi`의 메모리 이용률은 읽기·쓰기가 일어난 시간 비율이지 최대
대역폭 대비 비율이 아니다.
[NVIDIA 지표 정의](https://docs.nvidia.com/deploy/nvidia-smi/index.html).

## 재실험 코드와 다음 실행 조건

- `scripts/serve_scaling_adapter.py`: 입구 대기 계측, 단계별 실행 제어, 화면 대기 제거.
- `scripts/run_scaling_experiment.py`: 같은 문항으로 사용자 규모별 실행, 원래 평가기
  재사용, 요청 전 유휴 확인, 카운터 수집, 과부하 중단, 부분 결과 보존.
- `scripts/analyze_scaling_experiment.py`: 오류·누락·대기·출력 일치도·엔진 호출 수 대조.
- `scripts/verify_display_delivery.py`: 실제 저장 답변의 전달 구간 보존 검증.
- 전체 단위 테스트: **98 passed**. 이는 실제 400문항 실험의 대체 결과가 아니다.

운영 추론을 변경하지 않고 이어가려면 다음이 필요하다.

1. 기존 요청이 정리된 측정 시간대. 유휴 확인 후에도 앱 호출 수와 엔진 완료 수를 대조한다.
2. GPU를 읽기 전용으로 계측할 SSH 프로필 또는 모니터링 URL.
3. 메일의 최선 결과를 재현할 정확한 코드 버전·실행 조건·원시 결과 경로.

다음 비교에서는 **기존 그대로 / 화면 대기만 제거 / 화면 대기 제거+단계별 제어**를
분리한다. 단순 출력 지연 제거보다 제안 스케줄링이 추가로 이득을 주는지 확인한다.
단일 사용자부터 동일 400문항의 사용자 규모별 곡선과 반복 실행 변동을 측정한 후
논문 표에 반영한다. 현재 상태에서 새 방법의 우수성 또는 정확도 유지는 미검증이다.

원시 자료는 공개 소스와 분리된 `experiment-results/` 아래에 보존했다.
실행 명령과 평가 주의점은 [재현 절차](SCALING_EXPERIMENT.md)에 있다.
