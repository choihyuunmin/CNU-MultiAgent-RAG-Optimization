# 통합 어댑터 실제 GPU 비교: 실행 전 조건

2026-09-08. 운영 K8s/vLLM을 유지하고 GPU 호스트의 새 loopback 앱에서 실행한다.
이번 본 대조는 A=HTTP/생성 상한 4+원래 전송+관측, B=16+즉시 전송+관측,
C=B+오케스트레이터 토큰 예산이다. 모델·프롬프트·retrieval·인증·답변 제한은 동일하다.
기존 자원 관측 없는 준비 선실행은 모든 조건에서 사용하지 않는다.

## 질문과 순서

기존 400문항에서 9월 7일 선택/검증의 64문항을 제외한다. 나머지에서 층화 개발 32문항을
먼저 선택하고, 질문 및 출처 법령이 개발 세트와 겹치지 않는 검증 64문항을 고정한다.
이는 이번 예산 개발에서의 holdout이며 과거 모든 연구에 미사용인 질문이라는 뜻이 아니다.
개발 세트는 U8의 A/B에서 예약량 결정과 실제 토큰화 오차를 확인하는 데만 사용한다.

본 검증은 U16/32 × A/B/C × 64문항 × 2회 = 768회 계획이다. 반복 간 부하 순서를
반전하고 조건 시작 순서를 회전한다. 3조건·2반복은 완전한 3순서 균형 설계가 아니다.
앞선 제안의 모든 U1~32 새 스윕과 D/E 결합까지 완료하는 캠페인이 아니라, 기존 규모
실험 위에서 고정 설정 대비 예산 제어의 추가 효과를 먼저 분리하는 단계다.

## 고정 예산 결정 규칙

개발 실행의 오케스트레이터 실측 usage로 출력 예약=max(512, ceil(최대 출력 토큰×1.5)),
prefill 예산=ceil(입력 p95×8), KV 예약 예산=ceil(입력 p95×8+출력 예약×8)으로 정한다.
최대 동시 모델 호출은 8이다. 개발 성능을 보고 여러 임계값 중 최상의 것을 선택하지 않는다.
이 값은 논리 예약량이며 물리 KV byte/block 또는 OOM 방지 보장이 아니다.
실제 입력은 매 호출의 서빙 `/tokenize`로 측정한다. 캐시 적중은 호출별로 알 수 없으므로
캐시 토큰 공제를 0으로 둔다. 출력 예약은 생성 max_tokens를 바꾸지 않는 예측값이다.
모든 대조군에 같은 tokenization/관측을 적용해 계측 오버헤드 차이를 줄인다.

## 관측·중단·품질

각 요청의 지연, TTFT, p95, 30초 goodput, 실패, 출처 포함, 답변 길이를 수집한다.
전체 기한은 240초, 유한 closed-loop 방식이며 실제 평균 미완료 요청 수도 보고한다.
모델별 queue/prefill/decode/KV/선점과 host RAM/swap/GPU 사용률·전력·온도를 관측한다.
이번 NVML 관측을 HBM 대역폭 GB/s 실측이나 커널별 원인 분해로 부르지 않는다.

SSE 미완료 또는 알려진 내부 장애 안내 응답이 있는 trial은 보존하고 후속 trial을 중단한다.
HTTP 200만으로 정상 파이프라인으로 판정하지 않는다. 리랭커·가드레일·모델 오류도 감사한다.
사용자 답변과 근거 원문은 0600 비공개 파일에만 저장한다. 출처 QA의 첫 반복 답변은
조건명을 숨긴 별도 모델로 관련성/근거 충실성을 평가하고 질문별 쌍으로 비교한다.
자동 평가 결과는 전문가의 답변 정확도·비열등성 증명이 아니다. 유의하지 않은 차이를
품질 동등성으로 해석하지 않으며, 전문가 미평가 상태에서는 운영 배포를 허용하지 않는다.

종료 시 실험 앱/계측을 정리하고 운영 모델 PID·health와 K8s 상태를 다시 확인한다.
결과가 부정적이어도 실패/느린 조건을 제외하거나 사후 임계값으로 검증을 대체하지 않는다.

## 본 검증 전 계측 보완

개발 64회는 모두 정상 완료했고 내부 모델 오류·리랭커/가드레일 오류도 없었다.
단, fixed16의 번역 질문 q377에서 토큰 계측 1회가 실패했다. 해당 모델 응답 usage의
입력 462토큰은 남아 있어 예산 계산 자료는 누락되지 않았다. 원 계측 실패의 예외 유형은
기록되지 않아 원인을 확정하지 않는다. 이후 tokenization HTTP/전송 실패에만 한 번의
재시도와 실패 유형/상태 계측을 추가했다. 답변 생성 RPC 재시도는 추가하지 않았다.
개발 자료는 제외하지 않고 그대로 보존하며, 같은 개발 32문항에서 계측을 별도 재확인한
후 본 검증으로 진행한다. 이 재확인은 예산의 성능 선택 자료나 검증 효과에 합산하지 않는다.

재확인 32회는 정상 완료했고, 99회 토큰화의 실패·재시도·실제 prompt usage 차이는
모두 0이었다. 03:42:29 UTC에 원 개발 자료의 194회 usage를 이용해 예산을 고정했다.
입력 p95=5,779, 최대 출력=280이며 최종 동시 호출=8, prefill=46,232토큰,
KV 예약=50,328토큰, 호출별 출력 예약=512토큰이다. 본 비교에서 값을 변경하지 않는다.
`calibration.json`에 원 계측 실패 1회, 별도 재확인 및 원 자료 해시를 모두 남긴다.
