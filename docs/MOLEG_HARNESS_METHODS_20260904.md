# 하네스 기반 지연 단축 방법 상세 설명과 400문항 결과

작성일: 2026-09-04 (Asia/Seoul)

이 문서는 방법을 코드 약어가 아니라 **서술형**으로 설명한다. 대상은 세계법제정보
지능형 검색시스템의 법령검색 응답이며, 정확도는 현재 운영 결과를 기준으로 한
검색 문서 ID 회귀 지표다(리랭커는 전 방법 공통 401, 운영과 동일 조건).

## 배경: 지연은 어디서 오는가

한 검색 요청은 대형 오케스트레이터(gemma-4-31B)를 **여러 번 순차 호출**한다. 의도
분류 → 검색어 추출(준비) → (검색) → 법령 선별 → 답변 생성이 차례로 일어난다. 실측
결과 이 대형 모델 호출이 비스트리밍 LLM 시간의 88%를 차지했고, 특히 디코드가
느렸다(gemma-31B 약 53 tok/s, 소형 모델의 1/4). 반면 의도분류·검색어추출 단계에는
숨은 추론(CoT) 토큰이 없었다(추론 0개). 즉 이 단계의 지연은 "생각이 길어서"가 아니라
"느린 대형 모델이 토큰을 하나씩 디코드"하기 때문이다. 따라서 정확도를 지키며 줄이는
길은 (1) 불필요한 호출을 없애거나 (2) 독립 호출을 겹치거나 (3) 디코드 자체를 빠르게
하는 것이다. CoT 축소가 효과 있는 곳은 실제로 추론을 길게 뱉는 모델(번역 에이전트)뿐이다.

## 방법 설명 (서술형)

### 1. 중복 도구-호출 제거 (typed direct dispatch) — 채택

검색 단계는 준비 단계에서 이미 확정된 인자(국가·키워드·검색어)를 가지고 있다. 그런데
현재 코드는 그 인자를 gpt-oss에게 다시 보내 "같은 인자로 search_laws를 호출하라"고
시키고, 그 도구 호출을 실행한다. 이 LLM 호출은 결과에 아무 정보도 더하지 않는 순수
왕복이다. 이를 없애고 검색 핸들러를 직접 호출한다. 인자가 그대로이므로 검색 결과도
같다. 400문항에서 검색 디스패치 단계가 47% 빨라졌고(0.95→0.50초) 문서 ID 일치
397/400, Recall 0.9988이었다.

### 2. 독립 호출 병렬 실행 (parallel analysis) — 채택

의도분류와 검색어추출은 둘 다 사용자 원문만 읽으므로 서로 의존하지 않는다. 현재는
순차로 부르지만, 동시에 부르면 출력은 그대로면서 벽시계 시간만 준다. 두 호출을
`asyncio`로 동시에 던지고 준비 단계 출력을 그대로 사용한다.

### 3. 검증 기반 빠른-경로 위임 (speculative cascade) — 신규 고안, 기각

최근 연구의 speculative cascade / deferral 아이디어를 적용했다. 빠른 소형 모델
(gpt-oss, 추론량 최소 = reasoning_effort low)이 먼저 검색어를 뽑는다. 그다음 **결정적
게이트**로 신뢰도를 검사한다. 게이트는 (가) 소형 모델이 뽑은 국가가 질문에 실제로
등장하는지, (나) 키워드가 질문에 실제로 있는지, (다) 검색어가 비어 있지 않은지를 본다.
통과하면 그 빠른 결과를 쓰고, 실패하면 정확한 대형 모델(준비 단계)로 위임한다. 이렇게
하면 gpt-oss의 추론(CoT)을 줄이면서도, 불확실할 때는 대형 모델로 돌아가 정확도를
지킨다는 설계였다. **결과적으로 기각됐다**(아래 표). 게이트가 90.8%를 통과시켰지만,
빠른 모델은 국가·키워드가 "질문에 있음"을 만족해도 표현이 대형 모델과 달라 검색 결과가
갈라졌다(Recall 0.422). 값싼 결정적 게이트로는 검색 충실도를 지킬 수 없고, 더 강한
게이트는 검색을 실제로 돌려 비교해야 해서 속도 이득이 사라진다.

### 4. 번역 에이전트 추론량 축소 (CoT 감축) — 채택(별도 경로)

유일하게 CoT가 실제로 낭비되는 곳은 번역 에이전트(ollama gpt-oss:20b)다. 앱이 추론
결과를 버리는데도 모델은 추론을 길게 뱉는다. `think=low`로 추론량을 낮추면 조문 번역이
약 2.3배 빨라지고(요청당 최대 19배) 번역문은 의미상 동일했다. 이는 출력이 사실상
보존되는 CoT 감축이다.

### (참고) 기각된 앱 레벨 치환

대형 모델을 빠른 모델로 통째 교체하거나 출력 스키마를 축소하면 7~8배 빨라지지만
400문항에서 검색 Recall이 0.33~0.45로 붕괴한다(추출 표현이 달라 검색이 갈라짐). 정확도
게이트를 통과하지 못한다.

### (참고) 서빙 레벨

fp8 양자화는 디코드를 +22% 빠르게 했으나 출력이 바뀌었다(유사도 0.569). 진짜 무손실
기법인 speculative decoding·tensor parallelism은 이 환경(venv numba 비호환, GPU 여유
부족)에서 측정하지 못했고, 유지보수 창에서 gemma-31B에 적용·검증해야 한다.

## 400문항 결과 (동시성 4, 검색까지 포함한 종단 지연)

| 방법 | 평균 | p50 | p95 | p99 | 속도 | 검색 Recall | Top-1 | 국가 | 판정 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 현재 운영(순차 2회 + 도구-echo 검색) | 4.67초 | 4.66초 | 6.37초 | 6.76초 | 1.00x | 1.000 | 1.000 | 1.000 | 기준 |
| **병렬 분석 + 직접 디스패치** | 3.75초 | 3.74초 | 5.27초 | 5.88초 | **1.24x** | **0.995** | 0.994 | 1.000 | **채택** |
| 검증 기반 빠른-경로 위임(신규) | 1.38초 | 1.01초 | 4.66초 | 5.99초 | 3.37x | 0.422 | 0.329 | 0.795 | 기각 |

빠른-경로 위임의 게이트 통과율은 90.8%였다.

## 결론

정확도를 지키며 종단 지연을 줄이는 조합은 **병렬 분석 + 중복 호출 제거**다. 400문항에서
4.67초를 3.75초로 24% 줄이면서 검색 Recall 0.995, 국가 일치 100%를 유지했다. 여기에
번역 경로의 추론량 축소(CoT 감축, 출력 보존)를 더할 수 있다. 반면 소형 모델 치환·스키마
축소·값싼 게이트의 빠른-경로 위임은 크게 빠르지만 검색 정확도를 지키지 못해 기각됐다.
더 큰 절감(디코드 자체 가속)은 출력 무손실 서빙 기법(speculative decoding·TP)을 유지보수
창에서 gemma-31B에 적용·검증하는 것이 다음 단계다.

## 방향 A 실험: 검색-등가 제약 추출 (400문항, 기각) — 비자명한 음성 결과

가설: 빠른 소형 모델의 추출이 표현 때문에 검색을 갈라놓는다면, 출력을 **추출적으로
제약**(국가는 폐쇄 enum, 키워드는 질문 토큰 부분문자열, 검색어는 결정적으로 국가만
제거)하면 검색 등가성이 회복될 것이다. 이를 400문항으로 검증했다.

| 방법 | 평균 | p95 | 속도 | 검색 Recall | Top-1 | 국가일치 |
|---|---:|---:|---:|---:|---:|---:|
| 기준(gemma) | 4.06초 | 5.70초 | 1.00x | 1.000 | 1.000 | 1.000 |
| 빠른모델(자유 생성) | 0.95초 | 1.45초 | 4.27x | 0.347 | 0.247 | 0.690 |
| + 국가 enum 제약 | 0.95초 | 1.51초 | 4.26x | 0.359 | 0.256 | 0.705 |
| + 완전 제약(추출 키워드·결정적 검색어) | 0.99초 | 1.45초 | 4.09x | 0.336 | 0.256 | 0.703 |

**기각.** 출력 제약은 검색 충실도를 회복하지 못했다.

- 국가 enum 제약은 국가 일치를 0.690→0.705로 거의 못 올렸다. 즉 국가 불일치는
  **표기/정규화 문제가 아니라 두 모델이 국가를 다르게 고르는 의미적 차이**다. enum으로
  형태를 맞춰도 소용없다.
- 키워드·검색어까지 추출적으로 제약해도 Recall은 0.34로 자유 생성과 같았다.

### 비자명한 결론

두 모델 사이의 **추출→검색 발산은 출력 형태의 문제가 아니라 모델 고유의 문제**다.
값싼 제약·게이트·캐스케이드로 소형 모델을 대형 모델의 검색과 정렬시킬 수 없다. 따라서
정확도를 지키는 가속은 **검색을 결정하는 경로에서 같은 모델을 유지**해야만 가능하다.
남는 지렛대는 (1) 같은 모델의 호출을 줄이거나 겹치는 하네스 변경(정확도 보존, 이득은
중간), (2) 출력이 동일한 **서빙 레벨 디코드 가속**(speculative decoding·tensor
parallelism)뿐이다. 모델 치환·제약 추출·빠른-경로 캐스케이드는 이 파이프라인에서
정확도 게이트를 통과할 수 없음을 400문항으로 확인했다.

이로써 논문의 축은 분명해진다: "멀티에이전트 RAG에서 검색을 결정하는 추출 단계는
모델 치환에 극도로 취약하며(작은 표현 차이가 Recall을 0.35로 붕괴), 이 발산은 출력
제약으로 복구되지 않는다. 정확도 보존형 가속의 유일한 길은 동일 모델의 디코드를
무손실로 가속하는 것이다." — 이는 값싼 대체를 배제하는 비자명한 근거다.

## 방향 B: speculative decoding 실측 (프록시) — 무손실 확인, 이 프록시에선 느려짐

요청대로 무손실 서빙 가속(speculative decoding)을 실측했다. 다만 gemma-4-31B를 띄울
GPU 여유(~90GB)가 확보되지 않아(GPU0 ~2GB, GPU1 ~25GB), 25GB에 들어가는 **프록시**로
측정했다: target Qwen3-14B(fp8), draft Qwen3-0.6B(동일 vocab 151936), num_spec=5,
같은 target에 대해 spec on/off 비교.

| 설정 | 추출 tok/s | 생성 tok/s |
|---|---:|---:|
| spec 없음(baseline) | 155.9 | 160.1 |
| draft-model spec | 66.4 | 71.4 |

- **출력 무손실 확인**: spec on/off 출력이 10/10 완전 동일(유사도 1.000). speculative
  decoding은 설계대로 target 분포를 보존한다 = 정확도 100% 보존.
- **그러나 이 프록시에선 느려졌다**(156→66 tok/s). vLLM이 "draft-model spec에서 async
  scheduling 비활성" 경고를 냈고, 이 한국어 법령 구조화 작업에서 draft 수용률이 낮아
  draft+검증 오버헤드가 이득을 넘었다.

### 해석과 한계

- 이 프록시는 gemma-31B에 대한 spec 이득을 **과소평가**할 가능성이 크다. spec은 target이
  느릴수록(디코드 병목) 유리한데, gemma-31B는 53 tok/s로 훨씬 느린 반면 프록시 target
  (fp8 14B)은 이미 156 tok/s로 빨라 draft 오버헤드가 상대적으로 컸다.
- 구조화 JSON 출력에 잘 맞는 **n-gram(prompt-lookup) spec**은 draft 없이 동작하고 수용률이
  높을 수 있으나, venv의 numba가 NumPy 2.4와 비호환이라 실행하지 못했다(운영 venv 미수정).
- **결론**: 무손실은 확인됐지만 speedup은 target·draft·작업 의존적이며 자동 보장이 아니다.
  실제 이득은 gemma-31B(느린 target)에서 직접 재고 num_spec·draft·n-gram을 스윕해야 한다.
  이를 위해 한 H200에 ~90GB를 비워야 한다(gemma-31B 59GB + E4B draft 15GB + KV). 준비된
  스크립트(spec_bench.sh)는 그 환경이 생기면 즉시 실행 가능하다.
