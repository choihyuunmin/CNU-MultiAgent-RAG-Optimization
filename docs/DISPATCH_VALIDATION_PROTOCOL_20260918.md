# 직접 실행 어댑터: 동작 보존과 전체 응답 시간 검증

상태: **실행 전 초안. 이번 변경으로 GPU 실험을 시작하지 않았다.**
아래 수용 기준은 제안값이며 사용자/지도교수와 확정한 뒤 실행 전에 동결한다.
기존 200문항 결과를 새 구현의 결과로 재사용하지 않는다.

## 문제와 이번 수정의 범위

기존 구현은 완성된 검색 인자를 LLM으로 다시 생성한다. 이 호출을 제거했을 때
경계 지연·서비스 호출량·전체 응답 시간이 함께 개선되는지 새로 검증한다.
부하별 오케스트레이터 큐와 KV 사용량도 기록한다. 큐 시간의 합을 사용자 시간에
더하거나 빼서 개별 요청의 인과를 설명하지 않는다.

먼저 해결해야 할 검증 오류도 있었다. `analyze_followup.py`는 준비 이벤트의
발생 순서와 검색 분기의 완료 순서를 연결했다. 두 검색이 역순으로 끝나면
다른 분기의 입력과 출력이 결합됐다. 동일 결과를 서로 다르다고 집계하는
회귀 사례를 재현했고, `(round, arm, request_id, branch_id)`로 연결하도록 수정했다.
과거 조건부 출력 해시 통계는 이 수정본으로 원로그를 다시 분석하기 전에는
품질 보존/품질 저하의 근거로 쓰지 않는다. 최종 응답의 법령 집합 통계는 별개다.

이번 커밋은 새 속도 향상을 주장하는 커밋이 아니다. 다음을 구현한다.

1. 직접 실행 시 validator 필수, 손실 없는 JSON 복사, 중첩 입력 공유 제거.
2. validator가 입력을 바꾸면 직접 실행 거부. 검색 함수 결과는 그대로 반환.
3. 검색 함수 실행 실패는 전파하며 재실행하지 않음.
4. 분기 ID 기반 준비/실행/출력/후속 객체 비교. 누락·중복·실패 이벤트는 검증 불가.
5. 다른 실행 간 동일 인자 분기가 여러 개이면 출력으로 짝을 맞추지 않고 모호함으로 분리.
6. 전체 응답 시간과 독립 품질 평가를 모두 요구하는 수용 판정 함수.

모델, 프롬프트, vLLM 설정·API 형식·추론 옵션은 변경하지 않는다.
동시호출 제한, 질문 예측, ID 축약, 응답 캐시, 추가 LLM 판단은 넣지 않는다.
주 비교는 원본 대 **서명 없는 직접 실행**이다. 서명은 핵심 기능이나 가속 기여가 아니다.

호환성: `try_typed_single_tool_dispatch`를 validator 없이 호출하던 통합은 이제
`validator_missing`으로 기존 경로를 택한다. 손실 있는 JSON 변환도 직접 실행하지 않는다.
통합자는 반려 결과를 기존 경로로 넘기고, 이미 실행한 함수의 예외는 재시도하지 않아야 한다.

## 단계 0: 실행 의미 검증 — GPU 부하 실험 전

- 로컬 회귀 시험은 실제 GPU 성능 결과가 아니라 구현 정확성 검사다.
- 격리된 검색기에서 원본/직접 실행에 같은 준비 인자를 넣고, 동일한 고정 검색
  응답을 핸들러에 주입한다. 모델과 검색 인덱스의 변동을 제거한 계약 시험이다.
- 검색 함수 호출 수, 준비/실행 인자, 원시 핸들러 반환값, 파싱 후 다음 단계 객체,
  순서가 있는 법령 목록을 모두 비교한다. 입력→출력 중 최초 차이 지점을 보고한다.
- 검색 생략, 국가 비교의 병렬 분기, 빈 결과, 실패, 취소, 잘못된 인자도 포함한다.
- 고정 핸들러 응답에서 후속 객체가 다르거나 중복 실행이 생기면 실험 중지 후 수정.
- 해시 일치만으로 정답성을 주장하지 않는다. 원문은 접근 제한된 로컬 산출물로
  보관하고, 공개 로그에는 원문/질문/비밀키 대신 해시와 시간만 둔다.

## 단계 1: 소규모 실제 검색기 점검 — 별도 실행 승인 후

기존 200문항은 개발/원인 분석용으로 사용한다. 우선 20문항으로 원본·직접 실행
각 1회, 동시성 4에서 연결·추적만 확인한다(총 40요청). 성능 결론은 내리지 않는다.
스모크 후 전체 200문항을 동시성 4에서 두 방식으로 1회 비교한다(400요청).
기존 방식 반복은 별도 200요청으로 잡는다. 이 640요청은 확증 표본에 합치지 않는다.

문항별로 다음을 기록한다.

| 범위 | 기록 |
|---|---|
| 전체 요청 | 시작/종료, 상태, 전체 시간, 최종 답변, 인용 법령 집합 |
| 검색 분기 | request/branch ID, 준비/실행 인자 해시, 핸들러 출력 해시, 후속 객체 해시 |
| 중간 종점 | 첫 검색 준비, 마지막 검색 완료, 이후 응답 생성 완료 |
| LLM 호출 | 단계/모델 ID, 부모 요청, 입력/출력 토큰, API 시간, 성공/실패 |
| 엔진 | 읽기 전용 큐·KV·선점·요청·토큰 카운터, 표본 수와 누락 수 |
| 실행 환경 | 이미지/코드/질문/설정 해시, 앱 슬롯, CPU/메모리, 시간 동기화 |

0분기 요청은 원시 로그만으로 '검색 생략'과 '추적 누락'을 구분하지 못하므로
클라이언트 상태 및 앱 경로와 함께 확인한다. 누락을 빈 검색과 같다고 처리하지 않는다.
모든 시간은 동일 호스트 시간 기준으로 정렬하고, API 시간에서 엔진 큐를 단순 차감해
순수 GPU 추론 시간으로 부르지 않는다.

## 단계 2: 확증 실험 — 계획/예산/정답 확정 후

성능·품질에 맞춰 튜닝한 기존 200문항과 분리된 **새 200문항 holdout**을 마련한다.
모든 방식에는 같은 200문항을 사용한다. 20개 국가·4유형×50개 구성을 유지하고,
국가명이 질문 본문에 포함됐는지 검수한다. 질문 생성에 사용한 원본 답변은 정답으로
인정하지 않는다. 정답 법령과 답변 평가표는 방식명을 가린 전문가 검수로 확정한다.

설계:

- 동시 요청: **1, 2, 5, 10, 20, 50, 100**. 이는 로그인 사용자 수가 아니라 outstanding 요청 수다.
- 조건: original-a, original-b, direct-a, direct-b. 같은 방식 두 인스턴스로 자기 변동도 확인한다.
- 4블록, 4위치 Williams 순서. 각 조건은 모든 위치에 한 번씩 배치된다.
- 블록별 격리 앱의 물리 슬롯을 교차한다. 운영 앱이나 실행 중인 인스턴스 설정을 바꾸지 않는다.
- 각 블록의 질문 순서는 고정 seed로 섞고 모든 조건에 동일하게 사용한다.
- 부하 수준의 실행 순서도 블록별로 섞는다. 원본/후보는 동시에 실행하지 않는다.
- 총 `200 × 7 × 4조건 × 4블록 = 22,400요청`. 단계 1과 별도이며 자동 실행하지 않는다.
- 4블록은 검정력을 보장하지 않는다. 파일럿 분산·목표 효과로 사전에 표본 수를 검토한다.
  예산이 부족하면 결과를 탐색적 실험으로 보고하고, 유의해질 때까지 반복하지 않는다.

전용 부하 생성기를 사용하고, 실험 시작 전 모든 엔진 running/waiting=0을 확인한다.
고착 요청이 있으면 실행을 멈추며 idle 기준을 완화해 확증 배치에 섞지 않는다.
가능하면 전용 시간대를 확보한다. 공유 부하·계측 누락이 있으면 해당 블록을
사전 규칙에 따라 invalid 처리하고 결과/이유를 보존한다. 실패를 숨기고 재시도하지 않는다.
앱 기본 admission이 동시성을 낮추면 배치를 유효한 고부하 측정으로 인정하지 않는다.
엔진 옵션은 그대로 두고 격리 실험 앱의 실제 활성 요청 수를 검증한다.

## 지표와 수용 기준 초안

주 성능 종점은 **동시성 100에서 전체 응답 시간 평균**이다. 기본 목표는 원본 대비
5% 이상 단축의 신뢰구간 하한 확보다. 다른 부하는 5%를 넘는 평균 악화가 없다는
회귀 검사를 한다. 모든 부하에서 p95 비율의 상한이 1.05 이하여야 한다.
주요 부하를 결과를 보고 바꾸지 않는다. 다른 부하의 유의성은 탐색적으로 보고한다.

- 원본/후보 두 인스턴스를 동일 가중으로 묶고 질문×블록 단위로 짝을 만든다.
- 반복 질문을 독립 표본으로 세지 않는다. 질문과 블록을 모두 재표집하는 구간을 사용한다.
- p95는 매 재표집의 요청 분포에서 다시 계산한다. '문항 평균의 p95'로 대체하지 않는다.
- 평균, p50/p95, 처리량(정상 완료 수/배치 wall time), 실패율을 함께 보고한다.
- 시간 초과는 설정값 600초 및 실제 관측 시간과 함께 별도 보고한다.
  완료 쌍 평균과 전체 시도 요약을 둘 다 제시하되, 실패를 제거한 수치로 통과시키지 않는다.
- 기존 시스템 대비 법령 집합 일치는 호환성 지표일 뿐 정확도 지표가 아니다.
- 독립 정답에 대한 법령 재현율·답변 정확성·근거 충실성을 모든 부하에서 평가한다.
- 품질 비열등성 허용폭은 기본 0이다. 1%p 등 허용폭을 사용할 경우 사전 승인이 필요하다.
- 법령 정답이 없는 문항은 '정당한 무결과 응답' 평가로 분리하고 분모를 공개한다.
- 경계 호출 제거율이나 서비스 호출 감소율만으로 수용 판정을 통과할 수 없다.

`performance_gate.evaluate_release_gate`는 실제 분석에서 산출한 신뢰구간과
`QualityEvidence`를 소비한다. 구간 자체를 생성하거나 전문가 평가를 대행하지 않는다.
원시 로그→짝 구성→통계/전문가 평가 산출은 별도 단계이며, 빈 값을 임의로 채우지 않는다.
missing/inconclusive는 pass가 아니다. 이 검사는 주어진 표본 범위의 수용 판단이지
모든 질문에서 품질과 속도를 보장하는 증명은 아니다.

## 실행 파일과 확인 명령

```sh
python -m pip install -e '.[test]'
python -m pytest tests/test_dispatch_contract.py tests/test_dispatch_trace_audit.py tests/test_dispatch_validation_gate.py -q
python scripts/build_dispatch_validation_plan.py --questions /absolute/path/holdout200.jsonl --output /absolute/path/dispatch-plan.json
PYTHONPATH=src python docs/paper-draft-20260917/followup/analyze_followup.py --root /absolute/path/trial --logs /absolute/path/logs --output /absolute/path/reanalysis.json
```

계획 생성기는 파일만 쓰며 HTTP·SSH·GPU 작업을 시작하지 않는다. 출력 파일 덮어쓰기도 거부한다.
계획의 200개 ID 검사는 정답 검수·holdout 독립성·국가 분포 검사를 대신하지 않는다.
기존 원격 `run_followup_trial.py`에는 `--concurrency`/`--timeout`/`--seed`를 추가했다.
동결 실험 번들의 기존 수집기/클라이언트 의존성이 필요하다. 계획 JSON은 자동 배포
매니페스트가 아니며, 슬롯 교차와 외부 정답 평가는 실행 담당자가 연결해야 한다.
실행기는 계획의 블록별 seed를 사용하고, 실제 전송 순서가 계획의 question_ids와
일치하는지 시작 전 확인한다. 기존 클라이언트의 질문 재배열 방식이 다르면 먼저 연결부를
수정하고 검증한다. 기존 매니페스트 생성기는 adapter.zip을 복사하므로 새 공개 패키지로
번들을 다시 만들고 코드 해시를 대조해야 한다. 오래된 ZIP을 새 구현으로 간주하지 않는다.
일반/직접 실행 모드는 공개 패키지만 필요하다. 기존 capability 모드는 별도
`capability_rpc` 모듈이 필요한 과거 대조군이므로 이 확증 실험에서 사용하지 않는다.

## 결과별 다음 행동

- 전달 객체 차이: 어댑터 통합 수정. 속도 결과보다 먼저 해결한다.
- 입력 동일·검색 결과 차이: 인덱스 스냅샷/검색 설정/동시 갱신을 먼저 통제한다.
- 경계는 빠름·전체는 동일: 원인 제거의 범위를 제한해서 보고한다. 오케스트레이터가
  지배하면 해당 단계에 대한 별도 코드 개입을 설계하고, 같은 확증 표본으로 재튜닝하지 않는다.
- 품질 기준 미달: 배포/가속 성공 주장 중지. 원인을 찾은 뒤 새 holdout으로 검증한다.
- 전체 시간·품질 동시 충족: 정해 둔 부하/데이터/환경 범위 안에서만 효과를 주장한다.
