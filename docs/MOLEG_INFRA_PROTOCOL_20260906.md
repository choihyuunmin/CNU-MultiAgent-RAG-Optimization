# 검색기 코드를 바꾸지 않는 외부 중계·GPU 요청 실험

실험일: 2026-09-06. 주 실험 전에 작성한 내부 프로토콜이며 외부 사전등록은 아니다.

## 목적과 범위

운영 `moleg-search-prod`와 `moleg-rag`의 소스, 이미지, 설정, Pod를 바꾸지 않는다.
GPU 모델 서버도 재시작·업그레이드·재배치하지 않는다. 이 저장소와 별도 실험
프로세스만 추가한다. 목표는 검색기 밖의 CPU 중계 장치와 모델 호출 경로만으로
지연을 줄일 수 있는지 확인하고, 도움이 되지 않는 방법도 제외하는 것이다.

확인한 구조는 .52의 검색 화면 → .53의 Kubernetes RAG 백엔드 → .53의 모델
서비스다. .53의 H200 NVL 2개에는 기존 모델이 상주한다. 추가로 발견한 .54는
사용 권한 확인 전에는 접속하거나 사용하지 않는다.

## 기술적 질문

1. 기존 모델 프록시를 통과하는 것과 별도 CPU 중계기가 같은 GPU 모델로 직접
   보내는 것 사이에 지연 차이가 있는가?
2. GPU에 들어가는 요청 수를 제한하면 빨라지는가, 아니면 GPU가 여러 요청을
   함께 처리하는 이점을 잃어 느려지는가?
3. 처리할 내용이 짧은 분류 요청을 먼저 보내면 전체 요청과 긴 준비 요청의
   시간은 어떻게 변하는가? 짧은 요청만의 이득을 전체 이득으로 보고하지 않는다.

## 입력과 예비 검사

### 배포 소스 확인에 따른 정정

호스트의 작업용 소스와 운영 Pod의 소스 해시가 다름을 발견하여 호스트 소스의
부분 실행을 중단했다. 이 자료는 완료 본 실험에 합산하지 않고 그대로 보존한다.
운영 Pod에서는 Python 소스만 읽어 별도 디렉터리로 복사했으며, 운영 설정·소스는
수정하지 않았다. 실제 Pod의 세 핵심 파일과 새 실험 복사본의 해시 일치를 확인했다.
이후 본 실험 입력과 예비 검사는 `pod_requests` 계열로 구분하여 다시 생성한다.
클라이언트 원시 응답 해시 계측도 새 본 실험 시작 전에 추가했다.

운영 소스에는 생성 요청 전체의 FIFO 제한도 존재한다(기본값 4). 외부 모델 요청
16개를 동시에 보낸 실험은 이 앱 제한을 그대로 재현한 운영 유입 분포가 아니다.
GPU 처리 구간의 혼합 부하 시험으로 한정하고 종단 효과로 대입하지 않는다.

추가 비교 결과, 소스 파일 자체는 다르지만 선택한 두 단계의 요청 본문은 호스트
소스와 Pod 소스 사이에 800/800개 동일했다. 최초 입력이 틀렸다고 주장하지 않는다.
그래도 출처와 실행 집계를 명확히 하기 위해 중단 자료와 새 본 측정은 분리한다.

### 보조 상태 조회 실패에 따른 재개

본 측정 880개 요청이 완료된 시점에, 요청 완료 뒤의 `/metrics` 조회에서 연결 종료
오류가 발생했다. 모델 요청 오류가 아니며 GPU 서버 상태는 정상이었다. 계측기는
보조 조회를 별도 새 연결로 수행하고 조회 오류가 본 측정을 중단하지 않도록 보완했다.
기존 요청은 재실행하지 않고 완료 키를 건너뛰어 이어서 측정한다. 조건·입력·생성
설정·중계 정책은 변경하지 않으며 계측 코드 버전과 재개 시각을 manifest에 남긴다.

해당 묶음의 개별 요청 시간 16개는 모두 보존됐지만 묶음 전체 완료 시간은 저장되지
않았다. 이 한 값은 null로 표시하며 추정값을 만들어 넣지 않는다. 개별 지연 비교에는
실측값을 유지하고, 묶음 완료 시간의 짝 비교에서는 해당 쌍만 제외한다.

전날 구성한 고유 질문 400개를 고정하여 재사용한다. 실제 앱 소스에서 현재
분류+분해 지시문과 검색 준비 지시문을 읽어 두 종류의 요청을 만들었다. 신규 세션의
질문, 응답 형식, temperature=0, enable_thinking=False를 사용하며 답변 길이 제한을
새로 추가하지 않는다. 검색 준비의 지원 국가 목록은 기존 읽기 전용 함수로 얻는다.

소스·질문·요청 해시를 저장한다. 출력이나 정답을 이용해 요청 순서를 예측하지
않는다. CPU 중계기는 시스템 지시문 해시 두 개로 요청 종류만 구분한다.

독립 예비 24문항 × 두 종류의 요청으로 4개/8개 제한과 우선 처리를 점검하였다.
작은 제한이 오히려 느려지는 경향이므로 본 비교에는 제한 없는 기준을 반드시 둔다.
예비 중 HTTP 연결 읽기 오류 1회가 중계기에 도착하기 전에 발생했다. 원인을 확정하지
않으며 원 자료를 보존한다. 본 측정용 중계기는 idle 연결 유지 시간을 30초로 하고
클라이언트의 5초 재사용 만료보다 길게 설정한다. 변경 후 별도 smoke test를 수행한다.

## 본 비교 조건

| 조건 | 설명 |
|---|---|
| proxy | 기존 LiteLLM 프록시와 기존 모델 별칭으로 요청 |
| pass | .52의 실험용 CPU 중계기가 본문을 그대로 .53의 동일 모델에 전달 |
| fifo8 | 같은 중계기에서 한 번에 8개까지, 도착 순서대로 전달 |
| fair8 | 같은 8개 제한에서 분류 우선, 준비 요청도 보호하여 전달 |

fair8은 짧은 요청을 연속 3개 선택하면 기다리는 긴 요청에 기회를 준다. 가장 오래
기다린 요청이 6초를 넘으면 그 요청을 우선한다. 이미 실행 중인 요청을 중단하지 않는다.
pass·fifo8·fair8은 프롬프트, 모델, 생성 설정과 요청 본문 바이트를 바꾸지 않는다.
proxy는 기존 역할 별칭을 사용하고 나머지는 그 별칭이 가리키는 실제 모델명을
사용한다. 이 모델명 표기 차이와 실제 모델 교체는 구분한다.

중계기는 고정된 upstream만 사용하며 실험 클라이언트인 .53의 주소만 허용한다.
인증은 그대로 전달하고 기록하지 않는다. 숨은 추론 본문도 기록하지 않는다.
재시도, 답변 캐시, 질의 재작성, 안전 검사 우회는 없다. 이 중계기는 분석 호출용
시제품이며 스트리밍 전체 경로를 구현한 운영 대체품은 아니다.

## 요청 수와 순서

400문항에 대해 고정 시드로 분류 200개·준비 200개를 배정한다. 각 질문은 한 가지
단계로 고정하며 모든 비교 조건과 반복에서 같은 요청을 사용한다. 400문항 ×
4조건 × 2회 = 3,200회의 모델 요청을 측정한다.

이는 실제 운영의 호출 비율을 재현한 자료가 아니라 1:1로 섞은 통제 부하다.
분류 출력에 따라 실제 검색·생성 경로를 실행하지 않는다. 전체 RAG API 응답 시간이나
400명의 사용자 세션 시간으로 부르지 않는다.

16개 요청을 한 묶음으로 동시에 시작하고 모두 완료된 후 다음 조건을 실행한다.
묶음 구성은 조건 간 같고 반복별로 섞는다. 조건 순서는 묶음마다 회전하고 두 번째
반복에서는 반전한다. 조건끼리 GPU 작업이 겹치지 않는다. 조건별 2회 warmup은 제외한다.
실패와 긴 지연을 제외하지 않으며 한 묶음에 오류가 2개 이상이면 안전 점검을 위해 중단한다.

## 지표와 해석

- 요청 시작부터 전체 응답 수신까지: 외부 중계기의 대기 시간까지 포함.
- 평균·p50·p95·p99·최대 지연, 분류/준비별 지연, 묶음 전체 완료 시간.
- 동일한 요청 묶음을 처리한 시간 기준 처리율. 지속 유입 포화 처리량은 아니다.
- HTTP 성공, 유효 JSON, 종료 사유, 출력 토큰 수, 출력 일치도.
- 같은 pass 조건 두 반복의 자연 출력 차이와 조건 간 출력 차이.
- 중계기 수신·전달 본문 해시, 클라이언트와 중계기의 응답 해시 대조.
- 모델 서버의 처리 중/대기 요청, 캐시 재사용, 처리 토큰 누적 카운터의 전후 값.

비교의 95% 신뢰구간은 짝지은 묶음 단위 bootstrap을 주로 사용한다. 같은 묶음의
요청은 GPU를 공유하므로 완전히 독립인 16개 표본으로 취급하지 않는다. 질문별
반복 평균의 bootstrap은 보조 결과로 함께 보고한다. 출력 완전 일치는 전문가
정답률이 아니며 프롬프트 동일성도 모델 출력의 동일성을 보장하지 않는다.

캐시는 비우지 않으며 GPU 외부 부하를 독점 통제하지 않는다. 기존 프록시와 외부
중계기는 네트워크 경로도 다르므로 관측 시간 차이를 순수 TCP 비용으로 부르지 않는다.
실험 전후 배포 템플릿 해시, Pod UID·재시작 수, 모델 PID·GPU 배치를 확인한다.

## 관련 기술과 신규성의 경계

GPU에서 여러 요청을 묶어 처리할 때 처리량과 응답 시간 사이에 절충이 있다는
문제는 [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal)가
다룬다. 여러 모델 인스턴스 사이의 요청 이동은
[Llumnix](https://www.usenix.org/conference/osdi24/presentation/sun-biao)의 접근이다.
이 기법들을 이번 시제품에서 구현했다고 주장하지 않는다.

현재 서버에서 prefix cache가 켜져 있음을 확인했다. 이 캐시는 입력의 공통 부분을
다시 읽는 작업을 줄이지만 답변을 한 토큰씩 만드는 비용을 직접 줄이지 않는다는
[설치 버전의 공식 설명](https://docs.vllm.ai/en/v0.19.0/features/automatic_prefix_caching/)을
참고한다. 단순히 캐시를 켠 것을 새로운 기여로 제시하지 않는다.

후보 기여는 기존 검색기를 건드리지 않고 요청 종류와 실제 GPU 상태에 맞는
외부 처리 방식을 검증하는 것이다. 본 데이터에서 제한·우선 처리가 실패하면
실패한 대안으로 명시하고, 향후 적응형 정책의 성공을 미리 가정하지 않는다.

## 추가: 실제 요청 본문의 압축 전송

GPU 본 측정 후 같은 400개 요청 본문을 .52에서 .53으로 보낸다. 원문 전송과
gzip level 1 전송을 질문마다 순서를 바꾸어 3회 비교한다(2,400회 전송).
수신기는 압축을 해제한 본문의 해시와 길이만 돌려주며 모델은 호출하지 않는다.
클라이언트 압축, 전송, 수신기 압축 해제와 해시 확인까지 시간에 포함한다.
양쪽 모두 연결을 재사용하고 수신기의 TCP_NODELAY를 켜 인위적인 작은 패킷
지연을 만들지 않는다. 초기 연결용 두 요청은 본 측정에서 제외한다.

목표는 실제 지시문 크기의 전송 비용과 압축 이득을 분리하는 것이다. 전송 본문
바이트 감소율은 IP/TCP 헤더·ACK까지 포함한 전체 네트워크 사용량 감소율이 아니다.
이 실험에서 줄어든 시간을 LLM 추론이나 전체 검색의 단축률로 바꾸어 쓰지 않는다.

## 추가: 두 GPU 사이의 데이터 이동

읽기 전용 연결 구조 확인에서 두 GPU 사이가 NVLink가 아니라 CPU 소켓 사이를
거치는 SYS 경로로 표시되었다. 모델 측정이 모두 끝난 뒤 1KiB–64MiB의 작은
배열을 GPU 내부 및 GPU 사이에서 복사해 실제 이동 시간을 비교한다. 장치당
데이터 버퍼는 128MiB 이내이며 여유 메모리가 1.5GB 미만이면 실행하지 않는다.
세 번의 준비 복사 후 크기·방향당 30회 측정하고 전체 버퍼 내용이 같은지 검사한다.
모델 재시작, 메모리 설정 변경, GPU 재배치는 없다.

이 검사는 여러 GPU로 모델을 나누는 아이디어의 통신 여건을 확인하는 것이다.
배열 복사 속도만으로 모델 분산 실행의 배속이나 느려짐을 계산하지 않는다.

## 추가: 낮은 동시 요청 수의 탐색적 대조군

본 실험 도중 운영 앱의 동시 요청 제한과 실험 부하의 차이를 확인하여 추가한다.
이는 최초 본 실험과 구분하는 사후 설계 보조 실험이다. 본 실험의 단계 배정을
유지하면서 고정 시드 6202610으로 분류 24개·준비 24개를 선택한다. 48개 요청을
proxy/pass 두 조건, 동시 요청 4개, 두 번 반복한다(192회). 본 실험의 400문항
수치에 합산하지 않는다. 이 조건도 전체 사용자 세션의 유입 과정을 재현한 것은 아니다.
