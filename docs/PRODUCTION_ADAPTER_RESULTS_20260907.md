# 실제 검색 이미지에 어댑터를 연결한 측정 결과

측정일: 2026-09-07. 결론: **화면 전달 대기 제거의 시간 단축은 관측했지만, 네트워크 하네스의 추가 효과와 정확도 유지는 입증하지 못했다.** 운영 트래픽은 전환하지 않았다.

## 무엇에 연결했나

로컬 개발용 RAG를 대신 측정한 것이 아니다. 운영 중인 검색 컨테이너와 동일한 불변 이미지에 어댑터를 먼저 로드하고 원래 검색 서버를 실행했다. 실제 검색 DB와 기존 모델 연결을 사용했다. 원본 앱 파일이나 `.env`는 수정하지 않았다.

확인 결과, 검색 서비스의 제어 노드와 실제 RAG 컨테이너 실행 노드는 달랐다. 운영 RAG는 GPU 노드에 배치되어 있었고, 시험 컨테이너도 같은 노드에서 실행했다. 세 조건은 동일한 CPU 2개·메모리 8GiB 제한을 사용했다.

- GPU: NVIDIA H200 NVL 2개. 장치당 보고된 메모리 143,771MiB.
- 질문 판단·오케스트레이션: `google/gemma-4-31B-it`.
- 검색어 준비·답변 종합: `openai/gpt-oss-20b`.
- 비교: 기존 Gemma 비교 모델. 제공 별칭은 `moleg/gemma4-e4b-comparison-v3`이나 실행 경로는 `comparison-v4/final`로 끝나므로, 별칭만으로 학습 산출물 버전을 확정하지 않았다.
- 입력 안전성 검사: `OpenLLM-Korea/kanana-safeguard-8b`.
- 임베딩·재순위화: 기존 `BAAI/bge-m3`, `dragonkue/bge-reranker-v2-m3-ko` 연결 유지.

모델, 프롬프트, LLM 요청 인자, SDK 재시도·시간 제한, 스트리밍 호출 여부, vLLM 설정은 변경하지 않았다. 질문 동시 실행 한도도 기존 4개를 유지했다. 여러 모델을 다른 GPU로 옮기거나 새 추론 엔진을 띄우지 않았다.

시험 API는 로컬 전용 SSH 터널로 접근했다. 운영 Service·Ingress·사용자 요청 경로는 변경하지 않았다. 따라서 아래 시간은 동일 시험 경로에서 측정한 **검색 API 완료시간**이며, 브라우저 렌더링 시간은 포함하지 않는다.

## 질문과 평가 방법

기존 400문항 파일에서 고정 시드 `20260907`로 100문항을 선택했다. 국가명은 모든 질문 본문에 포함됐으며, 총 20개 국가를 포함한다. 네 유형에서 각각 25문항을 뽑았다.

| 질문 유형 | 개수 |
|---|---:|
| 특정 국가의 법령 찾기 | 25 |
| 한 국가의 법령 내용 설명 | 25 |
| 두 국가의 법령 비교 | 25 |
| 한 국가의 여러 법령을 종합한 상황 분석 | 25 |

동시 사용자 16명이 응답을 받으면 다음 질문을 보내는 방식으로, **각 방법에 동일한 100개 질문을 한 번씩** 넣었다. 방법별 질문 순서와 시드를 같게 유지했다. 총 본 실험 300건이며, 사전 연결 점검 4건 × 3조건은 결과에서 제외했다.

기존 앱의 평가 프로그램과 법령 비교 함수를 수정 없이 사용했다. 실패를 제외해 평균을 낮추지 않았으며, 세 조건 모두 응답 100건이 유효 형식으로 반환됐다. 기존 방식의 이번 100개 응답을 비교 기준으로 사용했다. 외부 전문가 정답지는 없다.

## 어떤 방법을 적용했나

| 방법 | 실제 작업 | 간단한 예 |
|---|---|---|
| 기존 검색 방식 | 원래 처리 방식에 시간·호출 계측만 추가 | 먼저 들어온 질문이 기존 대기열을 거쳐 실행됨 |
| 화면 전달 대기 제거 | 글자를 천천히 표시하기 위한 기본 대기를 제거. 원래 청크와 LLM 호출은 유지 | 이미 준비된 답변을 일부러 쉬었다가 내보내지 않음 |
| 네트워크 하네스 결합 | 위 방법에 질문별 순환 대기열, 수신 자원별 동시 호출 슬롯, 64청크 중계 버퍼를 추가 | 한 질문의 여러 호출이 다른 질문을 계속 밀지 않게 하고, 응답 읽기와 전달을 분리 |

하네스의 슬롯은 오케스트레이터 자원 8개, 나머지 자원 4개로 구성했다. 같은 수신 자원으로 연결되는 별칭들은 용량을 공유한다. 알려지지 않은 별칭은 원래 호출을 그대로 통과시키고 미관리 호출로 기록한다. 원래 모델 선택을 고정했으므로 복제본 간 지연 인지 라우팅 실험은 아니다.

## 결과

| 방법 | 응답 | 평균 완료시간 | 느린 상위 5% 경계(p95) | 기존 대비 평균 단축 | 기준 법령 재현율 | 첫 법령 일치율 |
|---|---:|---:|---:|---:|---:|---:|
| 기존 검색 방식 | 100/100 | 100.13초 | 147.90초 | — | 기준 | 기준 |
| 화면 전달 대기 제거 | 100/100 | 84.34초 | 114.44초 | 15.8% | 98.2% | 96.0% |
| 네트워크 하네스 결합 | 100/100 | 86.51초 | 122.95초 | 13.6% | 96.0% | 94.0% |

하네스는 화면 전달 대기만 제거한 조건보다 **평균 2.18초, 2.6% 느렸다.** 동일 질문 기준으로 48개는 빨랐고 52개는 느렸다. 따라서 기존 대비 13.6% 단축을 하네스만의 성과라고 주장할 수 없다.

법령 재현율은 기준 답변이 제시한 법령 중 후보 답변에도 포함된 비율의 질문별 평균이다. 조항의 완전성이나 법적 정답률은 아니다. 기준·후보 모두 법령이 없는 질문 14개는 원래 평가기 정의에 따라 일치로 계산된다. 이를 제외한 86개 기준 비어 있지 않은 질문의 재현율은 각각 97.9%, 95.3%다.

기준 법령이 하나 이상 빠진 질문은 전달 대기 제거 7개, 하네스 12개였다. 누락 ID와 첫 법령 변경 질문은 분석 JSON에 전부 보존했다. 모델·호출 인자를 유지했더라도 출력이 같다고 보장할 수 없으며, 이번 한 번의 순차 실행만으로 출력 변동과 방법의 영향을 분리할 수 없다. **정확도 유지 판정은 보류한다.**

## 어디에서 오래 걸렸나

| 관측 항목 | 기존 | 전달 대기 제거 | 하네스 |
|---|---:|---:|---:|
| 검색기 입구 평균 대기 | 73.10초 | 61.67초 | 63.21초 |
| 관측 LLM 호출 한 번의 평균 API 시간 | 5.04초 | 5.27초 | 5.30초 |
| 주 모델 엔진의 평균 대기 | 0.725ms | 0.673ms | 1.060ms |
| 주 모델 엔진의 평균 토큰 생성 구간 | 3.89초 | 4.16초 | 4.17초 |
| GPU 0 평균 사용률 | 95.8% | 98.8% | 97.4% |
| GPU 1 평균 사용률 | 56.8% | 61.6% | 61.0% |
| 주 모델 KV 캐시 최대 사용률 | 47.2% | 48.8% | 51.8% |

가장 큰 관측 대기는 **LLM 엔진에 들어가기 전, 질문 전체를 4개씩 처리하는 검색기 입구**에 있었다. 이번 조건에서 하네스는 그 한도를 그대로 두었으므로 이 대기를 구조적으로 없애지 않았다. 하네스 내부 슬롯 대기는 호출당 평균 0.275ms에 불과했다. 스트림 55개의 버퍼가 가득 차서 기다린 시간도 모두 합쳐 10.2ms여서, 중계 버퍼가 줄일 수 있는 지연은 작았다. 이는 추가 효과가 작았던 원인을 설명하는 관측이며, 단일 원인의 인과 증명은 아니다.

주 모델의 토큰 생성시간은 줄지 않았다. 따라서 이 결과를 “LLM 추론을 단축했다”거나 “CoT를 제거해 빨라졌다”고 설명하지 않는다. API 시간에는 SDK·네트워크·엔진·스트림 소비 시간이 섞이며, 여러 호출이 겹칠 수 있어 전체 응답시간과 단순 합산하지 않는다.

### 메모리·CPU 확인

- 세 시험 컨테이너 모두 실행 후 `nr_throttled=0`, `throttled_usec=0`, `oom=0`, `oom_kill=0`이었다.
- 종료 직전 컨테이너 메모리는 약 214~226MiB였다. 8GiB 제한에 의한 메모리 부족은 관측되지 않았다.
- 관측한 네 엔진 모두 선점·재개 카운터 증가가 0이었다.
- GPU VRAM 할당량은 GPU 0 138,838MiB, GPU 1 119,682MiB로 측정 구간에서 일정했다. 할당량이 큰 사실만으로 부족이나 대역폭 병목을 입증하지 못한다.
- GPU 사용률은 공유 장치 전체 지표다. 이번 측정만으로 GPU 연산과 메모리 대역폭 중 어느 쪽이 제한인지 확정하지 못했다.

### 모든 LLM 경로가 하네스 안에 있는 것은 아니다

공통 LLM 함수에서 관측한 호출은 기존 469개, 전달 대기 제거 466개, 하네스 469개였다. 하네스 조건에서는 이 관측 호출 469개를 모두 관리했다. 그러나 운영 이미지에는 검색어 준비 단계의 직접 SDK 호출과 안전성 검사의 직접 HTTP 호출도 있었다. 이 우회 경로는 이번 개별 호출 제어 범위 밖이다. 따라서 469개를 전체 LLM 호출 수라고 쓰면 안 된다.

세 조건 모두 내부 비교 모델 호출에서 입력 길이 초과 오류 4건이 있었다. 원래 앱이 이후 대체 경로로 응답을 반환했으므로 HTTP 정상 응답 수와 내부 단계 성공 수는 다르다. 입력 길이나 모델 설정을 바꾸어 이 오류를 숨기지 않았다.

## 실제 로그에서 고른 예

개선 폭이 큰 질문을 골라내지 않았다. 기준 방식의 완료시간 순서에서 가운데에 위치한 질문 `l1-009-us`를 사용했다. 아래는 원시 로그의 필드만 발췌·초 단위로 반올림한 것이며, CoT 본문이 아니다.

```text
동일 case_id: l1-009-us-r1-c16

기존     client=101.017s  entrance_wait=80.380s
         longest_observed_llm_api=7.714s   completion_tokens=222
전달     client=84.254s   entrance_wait=61.517s
         longest_observed_llm_api=9.989s   completion_tokens=222
하네스   client=80.252s   entrance_wait=53.813s
         longest_observed_llm_api=16.324s  completion_tokens=222
```

이 질문에서는 반환 법령 ID와 순서가 같았다. 전체 완료시간이 줄었지만 가장 긴 관측 LLM 호출은 오히려 길어졌다. 따라서 응답시간 단축과 추론시간 단축은 구분해야 한다. 기준 방식에서 가장 느렸던 질문도 분석 JSON에 함께 남겼다. 개별 예를 전체 효과로 일반화하지 않는다.

## 다음 개선의 초점

현재 하네스를 운영에 그대로 반영하는 것은 권하지 않는다. 우선 직접 SDK·HTTP 경로까지 관측·제어 경계를 완성해야 한다. 그 후 질문 전체가 슬롯을 오래 점유하는 방식과, 필요한 LLM 단계에서만 자원별 허가를 받는 방식을 비교하는 것이 다음 검증 대상이다. 같은 질문의 내부 순서와 동일 세션 직렬화는 유지해야 한다.

입구 한도를 단순히 높이는 것은 GPU 부하를 늘릴 수 있다. 단계별 제어와 입구 한도 변경을 분리해 평가하고, 모델·프롬프트·엔진 설정은 유지해야 한다. 이는 다음 실험 제안이지 이번에 측정한 성과가 아니다.

이번 본 실험은 동시 사용자 16명만 측정했다. 사용자 1·2·4·8·32명 곡선, 실행 순서 교차·기준 재측정, 법령·조항 전문가 검증, 다른 도메인 실험은 완료되지 않았다. 과거 메일의 13.45초 등과 동일한 조건임을 확인하지 않았으므로 직접 비교하지 않는다. 논문용 인과 효과·비열등성·범용성 판정은 `inconclusive`다.
