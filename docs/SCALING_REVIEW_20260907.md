## 현재 코드에서 직접 확인한 제한

통합 애플리케이션의 `src/main_server.py`는 입구 미들웨어의 동시 요청을 4개로
고정한다. `src/api/concurrency.py`에도 전역 생성 슬롯 기본값 4가 있다.
따라서 사용자 8·16·32명 실험에서 GPU에 도달하기 전 로컬에서 기다릴 수 있다.
특히 입구 미들웨어의 대기는 기존 요청 trace가 생성되기 **이전**에 발생한다.
이 시간을 GPU 대기나 메모리 병목으로 잘못 해석하지 않도록 별도로 계측한다.

## 새 실험 구성

모델·프롬프트·vLLM 옵션·스트리밍 설정·검색 코드는 그대로 유지한다.
기존 평가 스크립트와 데이터도 수정하지 않는다. 로컬 실행 프로세스에만 별도
어댑터를 삽입한다.

1. 기존 방식: 입구/생성 동시 4개를 그대로 두고 입구 대기만 추가 기록.
2. 요청 창 확대: 입구/생성 한도를 32개로 하여 거친 전역 제한 효과를 분리.
3. 단계별 슬롯: 요청 창 32개 + 실제 추론 자원별 슬롯과 질문별 처리 순서 적용.
   같은 추론 엔진을 가리키는 worker/retrieval 별칭은 용량을 함께 계산.
4. 필요 시 단계별 FIFO 대조군으로 슬롯 분리 효과와 질문별 순서 효과를 분리.

현재 발견된 모델 구성에는 동일 모델의 독립 복제본이 확인되지 않았다.
따라서 이 실험은 **단계별 대기 관리** 실험이며 복제본 분산 효과를 측정했다고
표현하면 안 된다. 새 복제본 배포나 기존 엔진 재설정은 하지 않는다.

본 측정 목표는 동일 질문 400개를 모든 방법에 넣고 사용자 수 1·2·4·8·16·32에서
전체 응답 시간, p95, 처리량, 실패율, 기존 답변 대비 검색 충실도를 비교하는 것이다.
소규모 실행은 연결/계측 점검으로만 표시하며 400개 최종 결과와 합치지 않는다.

## 메모리 원인을 구분하는 기준

- 애플리케이션 대기: 입구 대기 및 생성 슬롯 대기.
- 모델 대기: vLLM의 waiting/running과 queue 시간 누적 카운터 차이.
- KV 캐시 용량 압박: KV 캐시 사용률, preemption 증가, 대기 변화의 동시 관찰.
- 물리 GPU 메모리: 별도 GPU 계측 권한 필요. SSH 공개키 인증이 현재 실패해
  VRAM·SM·메모리 대역폭 병목은 아직 판단할 수 없음.
- VRAM 할당량이 높다는 이유만으로 메모리 부족이라고 결론내리지 않음.
- vLLM 지표는 장치 전체 집계이므로 다른 운영 요청이 있으면 섞일 수 있음.

검증 판정은 원시 응답 대조 전까지 `inconclusive`. 전문가 정답도 아직 제공되지 않았다.
