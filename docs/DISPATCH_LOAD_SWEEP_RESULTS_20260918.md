## 요약

- 검색 재작성 호출(원본 경로의 비핸들러 시간)은 부하와 함께 브랜치당 **1.2초(C=8) → 4.5 → 6.4 → 19.1 → 22.4초(C=100)**로
  커진다(p95 16–32초). 서명 직접 디스패치는 모든 수준에서 1.2–1.6 ms.
- 도구/답변 엔진 요청은 배치당 41–46% 줄고, 요청당 큐 시간은 **29–72% 감소**(C=8 1.19→0.63초, C=100 39.0→10.8초), 최대 대기 수
  17–143 → 9–21.
- 그러나 종단 절감은 수준별 문항 평균 **+0.44초(1.4%, C=8), +1.54(2.9%, 16), −3.35(−3.6%, 32), +3.54(2.6%, 64), +3.73(2.3%, 100)**.
  문항별 부호 검정은 32를 제외한 모든 수준에서 어댑터를 지지(최대 149/51, C=100)하지만 평균의 부트스트랩 구간은 100에서만 0을 제외.
- 원인: 동시성 32부터 오케스트레이터 엔진이 KV 100%·선점 상태로 포화되어 요청당 큐가 0.1–0.5초 → 28 → 85–87 → 122–138초로
  커진다. 검색 브랜치에서 덜어낸 시간이 오케스트레이터 대기로 옮겨간다. C=100에서는 어댑터 arm의 오케스트레이터 큐가 오히려
  더 크다(138 대 122초/요청).
- 처리량·60초 내 완료율은 arm 간 동일(93–94% → 61–66% → 15–18% → 8–11%). 검색 핸들러 자체도 0.6초 → 2.8–3.3초(64) → 5.0–6.0초(100)로
  느려진다(공유 검색 서비스).
- 포화 상태에서는 두 arm 모두 출력 안정성이 떨어진다: 라운드 간 정확 집합 자기 일치가 92–94%(≤32)에서 83/82%(64), 81/73%(100)로,
  자기 재현율이 97–99%에서 84/80%(100)로 하락.

## 실행 기록과 한계

- 20셀 4,000요청 모두 전송 실패 없이 완료. 00:10–05:07 KST.
- part1(8·16·32 라운드 1) 뒤 오케스트레이터 엔진에 완료되지 않는 요청 1건이 남아 엄격 유휴 게이트(실행 0)가 180초 안에 통과하지
  못해 러너가 정지했다. 남은 10셀은 "대기 0, 실행 ≤1" 게이트로 재개했으며 양쪽 arm에 같은 조건이다.
- 라운드 2회로는 포화 경계(C=32)의 순서 효과(±8초)를 해소하지 못했다. 프로덕션이 엔진을 공유했다. 품질은 기준 일치도이며
  전문가 정확도가 아니다.
- 해석: 호출 제거는 문항 단위로 일관되게 작은 이득을 주지만, 이 배포에서는 오케스트레이터 용량이 종단 이득을 몇 % 수준으로
  제한한다. 오케스트레이터 prefill/KV 용량을 늘리는 개입(09-06 추측 디코딩 등)과 결합해야 이득이 커진다.
