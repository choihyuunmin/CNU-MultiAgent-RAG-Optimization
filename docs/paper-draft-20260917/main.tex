\title[Direct Dispatch in Multi-Agent RAG]
{Removing a Redundant Tool-Call Rewrite in Multi-Agent RAG: A Checked Direct-Dispatch Adapter Evaluated from the Call Boundary to Concurrency 100}
\authorlist{}

\begin{summary}
In a multi-agent retrieval-augmented generation (RAG) system for legal search, a preparation agent already forms the complete arguments of a search tool, but a second language-model call rewrites them into a tool call before the tool runs. This paper removes that rewrite with a checked direct-dispatch adapter that validates the prepared arguments and calls the same handler, optionally inside a signed execution envelope. Branch traces show that the rewrite never changed the prepared arguments in 648 of 648 invocations, so removing it is safe. Before the change, the rewrite cost 0.54 s per search branch at concurrency 4 and grew to 22 s per branch at concurrency 100 because it waited in the tool engine's queue; it accounted for 41\% of that engine's requests. After the change, the boundary costs 0.5--0.9 ms, the tool engine's queue time per request falls by 29--72\%, and the time from request start to search completion falls by 0.46--0.64 s in every round. The end-to-end response-time gain is smaller than the removed work: 0.5\% at concurrency 4, 1.4--2.9\% at 8--16, and 2.3--2.6\% at 64--100, with per-question sign tests favoring the adapter at every load except 32, because the orchestrator engine saturates from concurrency 32 and absorbs the released time. Source-set agreement with the original path is within the retrieval path's own instance-to-instance variation, so no quality loss is attributable to the adapter.
\end{summary}

\section{Introduction}
Retrieval-augmented generation (RAG) combines document retrieval with language generation\cite{rag}. A multi-agent RAG system divides one request among agents for question analysis, search preparation, search, evidence selection, and answer writing. Each hand-off between agents can cost a language-model call, and not every call makes a decision. Some only reformat data that the program already holds.

This paper studies one such call in a production multi-country legal search system. A preparation agent produces the country, search terms, and keywords of a search. The original implementation then hands these values to a tool-calling model, which emits the same values as a structured tool call, and only then does the search handler run. The second call chooses no tool and adds no term. It is a text-to-JSON relay between two parts of one program.

The relay is not free. At concurrency 4 it costs 0.54 s per search branch. Under load it waits in the queue of the tool-serving engine like every other request, so its cost grows to 4.5 s per branch at concurrency 16 and 22 s at concurrency 100, and it makes up 41\% of all requests served by that engine.

We remove the relay with a direct-dispatch adapter. Trusted application code registers the search operation with an argument validator, copies the prepared arguments through canonical JSON, validates them, and calls the existing handler; the result enters the existing parser unchanged. An optional signed envelope adds scope, expiry, and one-time-use checks for deployments with an untrusted hop. We verify the feature before measuring it: prepared and executed arguments are hashed on every branch, and the rewrite is shown to preserve them in all 648 recorded invocations.

The evaluation asks what the removal buys at three scopes and across load. At the boundary, the rewrite time disappears at every concurrency. At the search-completion endpoint, requests reach the end of their search 0.46--0.64 s earlier. At the user-visible response, the gain is 0.5\% at concurrency 4 and 1.4--2.9\% below saturation, with per-question sign tests favoring the adapter at every level except 32. The reason the whole-request gain is small is measured, not assumed: the orchestrator engine saturates from concurrency 32 and its queue absorbs the time released from the search branch. Quality is checked against the original path with instance-level controls, and no source-set loss is attributable to dispatch.

\section{Related Work}
RAG supports generation with retrieved documents\cite{rag}. ReAct interleaves reasoning and actions\cite{react}; Toolformer learns when to call an API\cite{toolformer}; ToolLLM studies tool use over a large API collection\cite{toolllm}. These works decide which tool to call. Our change applies after that decision, when application code already holds the operation and its arguments.

AutoGen structures agent conversations\cite{autogen}. LLMCompiler separates planning from execution so that a program dispatches ready function calls\cite{llmcompiler}; its executor is the closest analogue to our adapter, which executes one prepared call without a planner. Parrot and Agentix improve serving by exposing application structure to the engine\cite{parrot,agentix}; SGLang reuses KV state and speeds structured decoding\cite{sglang}; RAGCache caches knowledge states\cite{ragcache}. Those approaches change the serving layer. We leave the engines unchanged and remove one request from the application.

HMAC authenticates a message with a shared secret\cite{hmac}; Macaroons extend it with contextual caveats\cite{macaroons}. Our optional envelope uses HMAC-SHA256 with a scope and a nonce as a deployment safeguard. It is not a new authorization design and, as shown below, not the source of any speedup.

\subsection{The rewrite step}
The search-dispatch function receives the country, merged keywords, search terms, and a request ID. The first three form the argument object of the registered \texttt{search} tool. In the original route the function sends this object to the tool/answer model together with the tool schema, receives the model's tool call, and runs the handler with the returned arguments. Source inspection shows that the loop allows one model round, keeps the raw handler result, and passes it to the parser; the model can only reproduce or alter the arguments.

\subsection{What the step costs}
Table~\ref{tab:before} quantifies the step in the original route, measured with the branch traces of Section~5. At concurrency 4 the rewrite adds 543 ms to a search branch whose handler takes 575 ms. Under load the rewrite is queued behind other requests of the tool/answer engine. Its mean cost per branch rises to 1.2 s at concurrency 8, 4.5 s at 16, 6.4 s at 32, 19.1 s at 64, and 22.4 s at 100, with 95th percentiles of 16--32 s from concurrency 16 upward. Because every search branch issues one rewrite, the engine serves 500--521 requests per 200-question batch of which 216 are rewrites, and its queue depth grows to 143 waiting requests at concurrency 100.

\subsection{Why the step is redundant}
A fixed operation does not by itself make the rewrite unnecessary; the model might correct an argument. We therefore hash the prepared object and the object the handler actually receives on every search branch. Across the three-round study of Section~5, all 648 rewrites in the original route produced arguments identical to the prepared ones; no changed field was recorded. The rewrite is a relay with no observed effect on what is executed.

\section{The Direct-Dispatch Adapter}
\subsection{Execution boundary}
The adapter registers a read-only operation, an argument validator, and an asynchronous handler. For legal search the validator requires exactly three fields: a nonempty string of search terms, a country string or null, and a list of string keywords. Dispatch copies the prepared object through JSON serialization with fixed key order and separators, validates the copy, and calls the registered handler. The handler's result enters the existing parser and the existing return structure, so later agents receive the same fields as before.

Eligibility is decided before dispatch. If the object fails the validator, the integration takes the original route. After dispatch, a failure raises an error; it is never silently retried through a model. The adapter contains no learned routing and no scheduling; its only effect on a request is one omitted model call per eligible search branch.

\subsection{Optional signed envelope}
For deployments where the plan crosses an untrusted hop, dispatch can wrap the object in an envelope carrying a version, receiver, request scope, operation, issue time, expiry, and a 128-bit nonce, authenticated by
\begin{equation}
M=\operatorname{HMAC\mbox{-}SHA256}(K,P),
\end{equation}
where $P$ is the canonical payload and $K$ a per-invocation 32-byte key. The executor checks the code, version, receiver, scope, time range, registered operation, argument schema, and nonce, and marks the nonce spent before calling the handler. In the tested prototype issuer and executor share one process, so the envelope is a safeguard and the unsigned direct call is sufficient; both are evaluated. A 200-case contract test (40 valid plans and 40 each of altered, wrong-scope, expired, and replayed plans) produced the expected decision in every case.

\subsection{Feature verification}
Before any latency measurement, the adapter was checked on the same traces. In each of 600 attempted questions per condition, all 216 search branches (132 single-search questions, 42 two-search comparison questions, 26 questions that bypass search) reached the handler once; no schema fallback and no boundary error occurred. Prepared and executed argument hashes were identical on all 648 branches of both adapter arms. Table~\ref{tab:boundary} gives the boundary timing at concurrency 4: the non-handler time falls from 543.140 ms to 0.521 ms for unsigned dispatch and 0.880 ms for signed dispatch, while handler time is unchanged within 12 ms. Signing costs 0.36 ms per branch.

\section{Experimental Method}
\subsection{Conditions and runs}
Three conditions share one frozen application image, the same models, prompts, tool handlers, search data, and vLLM options: the original route, unsigned direct dispatch, and signed direct dispatch. Each condition runs in its own isolated application instance (2 CPU cores, 8 GiB) on the GPU host; a separate client instance (2 cores, 2 GiB) generates load. Production traffic shares the engines.

Three runs are reported. (1) Concurrency 4: 200 country-specific legal questions per condition in three rounds whose serial order rotates (a $3\times3$ Latin square), 1,800 requests, request timeout 180 s. (2) Load sweep: original versus signed dispatch at concurrency 8, 16, 32, 64, and 100, two rounds per level with the order reversed, 4,000 requests, timeout 600 s, and the instance's admission limit raised from 4 to 100 so that client concurrency reaches the engines. (3) Instance control: two instances of the original route and two of signed dispatch, one batch each at concurrency 4, with handler-output hashes recorded. The question set has 20 countries and four types of 50 questions (finding a law, explaining content, comparing countries, analyzing a case), with a fixed seeded order. All 6,600 requests completed; six read timeouts occurred, all in the concurrency-4 runs.

Before each batch the runner waited for idle engines. In the load sweep, after ten cells, one request that never completed remained running in the orchestrator engine; the remaining ten cells and the instance control used a gate that tolerates one running request per engine with zero waiting, applied equally to all arms.

\subsection{Measurements}
Every request stores its client start and end time, status, and returned law IDs. Application traces record every wrapped model call with token counts and API time, and every search branch with prepared and executed argument hashes, handler time, and boundary time. vLLM counters of each engine are sampled every second; batch differences give requests, queue time, prefill and decode time, and preemptions, and gauges give waiting depth and KV usage. A traffic check compares engine request counts with wrapped calls: in every batch the orchestrator engine's count equals the wrapped orchestrator calls within one request and the safety engine serves exactly 200, so no outside traffic reached the engines during measurement.

For a completed pair of the same question in two conditions, $d_i$ is the original minus the candidate response time; positive values favor the adapter. We report the mean with a 10,000-sample question-bootstrap interval, the median, and an exact two-sided sign test. For the sweep, each question's two round differences are averaged before pooling. The same statistics are applied to original-versus-original pairs across rounds as a null control. Two intermediate endpoints use the traces: $E_i$, from client start to the last search-branch completion, and $S_i$, from the first prepared-search event to that completion. Source agreement compares deduplicated law-ID sets: nonempty-reference recall, exact-set agreement, and within-arm agreement across rounds or instances.

\subsection{The saving reaches the search-completion endpoint}
At concurrency 4, signed dispatch shortens the interval from the first prepared search to the last search completion by 0.543, 0.504, and 0.561 s in the three rounds, with question-bootstrap intervals of $[0.511,0.577]$, $[0.483,0.526]$, and $[0.522,0.606]$, and the interval from client start to the last search completion by 0.529, 0.639, and 0.464 s, all with intervals above zero. Unsigned dispatch gives 0.523, 0.497, and 0.550 s on the search interval. The same endpoints between two original rounds change by at most 0.06 s (search interval) and 0.12 s (request start), so the reduction is an order of magnitude above ordinary variation. The removed call therefore reaches the request's path: requests finish searching about half a second earlier at concurrency 4, and by the amounts of Table~\ref{tab:sweep-boundary} under load.

\paragraph{Why the whole-request gain is smaller than the removed work.}
The removed rewrite is worth 0.59 s per question at concurrency 4 and tens of seconds per branch under load, yet the response-time saving is 0.1--3.7 s. Table~\ref{tab:sweep-boundary} shows where the time goes. From concurrency 32 the orchestrator engine reaches 100\% KV usage with preemptions, and its queue time per request rises from 0.1--0.5 s to 28, 85--87, and 122--138 s. A request that leaves the search branch earlier waits for the orchestrator instead; at concurrency 100 the adapter's requests even carry more orchestrator queueing than the original's (138 versus 122 s per request). Throughput and the share of requests completed within 60 s are equal between arms at every level (93--94\% at 8, 61--66\% at 16, 15--18\% at 32, 8--11\% at 64 and 100): the closed loop fixes throughput, and the orchestrator, not the search branch, sets the tail. The adapter therefore removes a real and growing cost on the search branch, and the response-time benefit is bounded by the next bottleneck.

\subsection{Quality}
\paragraph{Agreement with the original route.}
Source agreement uses the same-round original response as reference. At concurrency 4, signed dispatch reproduces 98.53\%, 98.25\%, and 98.50\% of the reference's law IDs over 173, 174, and 172 nonempty references, and its exact law-set agreement is 182/199, 184/200, and 183/198. Repeated original rounds agree at 98.87\%, 98.62\%, and 99.13\% recall and 190/199, 187/198, and 192/199 exact sets. The same 26 questions return no law in every batch of every condition; they are the questions that never call the search boundary. Under load, agreement with the original falls for both arms as the system saturates: nonempty recall 96\% at 8, 95--96\% at 16, 94--95\% at 32, 88--93\% at 64, and 83--87\% at 100, while each arm's own round-to-round exact-set agreement falls from 92--94\% to 81--83\% (original) and 73--82\% (signed).

\paragraph{Is the residual gap caused by dispatch?}
Between-arm agreement is a few points below within-arm agreement even at concurrency 4 (89--92\% versus 95\%), but the two adapter arms, which share one mechanism, also agree with each other at only 91\%, and each condition ran in its own application instance. The instance control resolves this. Table~\ref{tab:instance-followup} shows that two instances of the same route agree on exact law sets in 86.4\% (original) and 83.5\% (signed) of questions, no more than instances of different routes (83.0--87.0\%). For questions whose prepared arguments were identical in both instances, the search handler returned an identical law-ID list in only 65--79\% of cases and a byte-identical result in 5--17\%. The retrieval path itself varies between instances by more than the between-arm gap. No source-set loss is attributable to the adapter; the adapter's own contribution to variation, the arguments it dispatches, is identical to the original's on every branch.

\subsection{Signing}
Unsigned and signed dispatch differ by 0.36 ms per branch at the boundary and by 0.729, $-0.049$, and $-0.043$ s in round means at concurrency 4, differences of the same size as the null control. The envelope is therefore neutral for speed; it adds the scope, expiry, and replay checks that the contract test exercises and that a distributed deployment would need.

\section{Discussion}
\paragraph{What the adapter solves.}
The redundant call is gone from every eligible search branch: 648 of 648 rewrites per condition are replaced by a 0.5--0.9 ms check, the tool/answer engine handles 41--46\% fewer requests, its queue time per request falls by 29--72\% under load, and requests complete their search 0.5 s earlier at concurrency 4 and by seconds under load. These effects are repeatable across rounds and hold at every concurrency tested.

\paragraph{What it does not solve.}
The user-visible response time improves by a few percent, not by the removed work, because this deployment's orchestrator engine saturates from concurrency 32 and absorbs the released time; at concurrency 4 the improvement (0.5\%) is below the round-to-round variation of the original route itself. Removing the rewrite is worthwhile as a service-load and search-latency improvement, and its response-time value grows only when the orchestrator has spare capacity. The adapter does not change the number of orchestrator calls, their decoding, or their KV footprint, which the measurements identify as the binding constraint.

\paragraph{Limits.}
Two rounds per sweep level leave position effects of up to 9 s at concurrency 32; ten sweep cells and the instance control ran while one stuck request occupied an orchestrator slot; production shared the engines; the question set is single-turn; and source agreement is measured against the original route, not against expert-labeled answers. The instance control shows that quality comparisons of any dispatch change in this system need several instances per arm or a deterministic retrieval configuration.

\section{Conclusion}
A multi-agent legal search system re-serialized prepared search arguments through a model call before every search. Branch traces showed the call to be a pure relay, identical in its output to its input in 648 of 648 cases, and increasingly expensive under load, from 0.54 s per branch at concurrency 4 to 22 s at concurrency 100. A checked direct-dispatch adapter replaced it with a 0.5--0.9 ms validation and dispatch to the same handler, optionally inside a signed envelope that costs 0.36 ms and changes no result. The tool/answer engine's request count fell by 41--46\% and its queue time per request by 29--72\%; requests reached the end of their search 0.46--0.64 s earlier at concurrency 4. The end-to-end response time improved by 0.5\% at concurrency 4, 1.4--2.9\% at 8--16, and 2.3--2.6\% at 64--100, with per-question sign tests favoring the adapter at every load except 32, because the orchestrator engine saturates and bounds the gain. Source-set agreement with the original route lies within the retrieval path's own instance-to-instance variation. The adapter is a safe, measurable removal of redundant work whose response-time value depends on the capacity of the remaining orchestration stages.
