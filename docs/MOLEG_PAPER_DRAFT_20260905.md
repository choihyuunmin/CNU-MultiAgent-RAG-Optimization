# 다중 에이전트의 관측 가능한 추론 흐름과 병목 기반 실행 어댑터: 정확도 우선 지연 최적화

작성 기준: 2026-09-05 완료 실험, 2026-09-07 사용자 규모·병목 분석, 2026-09-08 통합 어댑터 구현·실제 GPU 중단 실험.
아래는 실측 결과에 기반한 논문 본문 초안이다. 전문가 평가가 완료된 법률 정확도 연구가 아니라,
출처 기반 검색 평가와 백엔드 API 지연을 결합한 시스템 실증 연구로 범위를 한정한다.
추가 부하 실험은 기존 9월 5일 조건과 환경이 다르므로 별도 실험으로 보고한다.

## 초록

본 연구의 목표는 다중 에이전트의 관측 가능한 추론·도구 호출 흐름을 계측하여 병목을
찾고, 실행 어댑터를 통해 답변 정확도를 유지하면서 지연을 줄이는 것이다. 모델 API가
제공하는 reasoning 통계와 앱의 구조화 호출 시간을 구분하며, 정확도 보존은 설계 의도와
별도로 출처·답변·안전 회귀로 검증해야 하는 가설로 둔다. 기존 구성요소 실험을 관측,
모델별 실행 예산, 검증된 선실행, 품질 배포 게이트에 연결하였다. 새 호출/토큰 예산의
실제 GPU 비교는 192회 중 timeout 1건으로 중단됐으며, KV 압력 감소에도 추가 가속을
보이지 못했다. 새 선실행 결합 효과와 전문가 답변 비열등성은 아직 입증하지 않았다.

다중 에이전트 검색 시스템의 최적화에서는 모델 호출 지연뿐 아니라 질의 변환, 후보 검색, 재정렬, 답변 생성 사이의 상호작용을 함께 평가해야 한다. 본 연구는 법령 검색 시스템에서 동일 모델의 실행 경로 최적화, 인증이 복구된 재정렬, 답변 생성의 추론량 조정, 원 질문 보존 검색을 비교하였다. 400개 고유 질문을 구성하고 스트리밍 API 2,400회와 일반 JSON API 800회를 측정하였다. 검색 평가는 기존 시스템 출력과의 일치도 외에, 서로 다른 법령 240개에서 구성한 출처 라벨과 참조 문자열 검증을 통과한 조문 질문 131개를 사용하였다.

복합 최적화 조건은 스트리밍 API 평균 지연을 13.772초에서 10.619초로 22.89% 단축하였고, 평균 첫 답변 지연을 21.43% 단축하였다. 동일 후보 집합의 재정렬은 출처 조문 Hit@1을 0.8168에서 0.9008로 개선하였다. 별도의 준비·검색·재정렬 실험에서 원 질문을 유지하고 생성형 추출을 생략한 조건은 평균 8.03배 빨랐다. 특히 동일한 131문항에서 원 질문 조건은 작은 모델 추출보다 기존 문서 일치도가 낮았지만 출처 조문 Hit@1은 높았다. 이는 기존 출력에 대한 회귀 지표와 출처 기반 검색 지표가 최적화 후보를 상반되게 평가할 수 있음을 보여준다. 다만 최종 답변 품질의 개선이나 동등성은 입증하지 못했으며, 출처 라벨은 전문가 정답을 대체하지 않는다.

추가로 64개 고정 질문을 외부 사용자 1·2·4·8·16·32명에서 측정한 결과, 평균 관측
지연은 13.855초에서 108.077초로 증가했다. 384회 중 1회가 기한을 초과해 후속 반복을
중단했다. 사용자 1→16명의 지연 증가 중 약 94%는 첫 진행 이벤트 이전 구간에서
발생했으며, 보관된 앱의 전역 생성 상한 4와 현재 응답 시작 순서가 일치했다.
모델 대기·KV 선점만으로는 이 증가를 설명할 수 없었다. 따라서 사용자 수와 내부
실행 동시성을 구분해야 한다. 이후 현재 pod의 HTTP·생성 이중 상한을 확인한 별도
320회 대조에서 U16 평균은 두 상한 4의 58.177초에서 두 상한 16·즉시 전송의
36.050초로 감소했다. 선택된 설정을 고정한 별도 512회 순서 교차 검증에서는 U16 평균
60.360→34.045초(43.60% 단축), U32 104.162→52.611초(49.49% 단축)를 관측했다.
모든 요청이 정상 완료했으며 출처 포함은 같았지만 전문가 답변 품질은 미평가다.
가용 host RAM 부족이나 장치 DRAM 인터페이스의 지속 포화는 관측하지 못했지만,
상한 16의 논리적 KV 최대는 99.73%였다. 앱 대기와 모델 경합의 상충 관계가 중요하다.

## 1. 연구 목적과 연구 질문

중심 연구 대상은 개별 모델의 CoT를 임의로 줄이는 기법이 아니라, 에이전트 단계·모델
호출·수용 대기·답변 전송을 연결해 병목에 맞는 실행 방법을 선택하는 어댑터다.
구조화된 분류·준비 호출 시간은 관측 가능한 워크플로 비용이며 모델의 비공개 내부
사고 과정과 동일시하지 않는다. 과거의 품질 변경 실험은 안전한 기본 가속과 분리한다.

기존 실험에서는 오케스트레이터의 디코드 지연과 질의 추출 변화에 따른 검색 문서 불일치가 주요 문제로 관찰되었다. 그러나 분석·검색 단계의 지연만으로 최종 사용자 응답 시간을 설명할 수 없고, 기존 시스템이 반환한 문서를 정답으로 간주하면 기존 오류를 반복하는 최적화가 유리하게 평가될 수 있다. 따라서 본 연구는 속도, 출처 검색, 최종 답변 평가를 분리하여 다음을 검증하였다.

1. 모델을 교체하지 않고 호출 경로와 실행 순서를 바꾸면 백엔드 API 전체 지연을 줄일 수 있는가?
2. 재정렬 복구는 새로운 관련 법령의 발견과 이미 검색된 조문의 순위 중 어느 부분을 개선하는가?
3. 값싼 모델로 추출기를 대체하는 대신 원 질문을 검색에 사용하면 어떤 지연·출처 적중 특성이 나타나는가?
4. 기존 출력 일치도와 출처 기반 지표는 최적화 후보에 같은 우선순위를 부여하는가?
5. 네트워크, 생성 추론량, 국가 후처리, 안전 분류 등의 실패 요인을 단계별로 구분할 수 있는가?
6. 사용자 규모 증가에 따라 단계별 가속의 종단 효과가 어떻게 달라지며,
   서버 대기·입력 처리·출력 생성·KV 용량 중 어떤 관측이 지연 증가를 설명하는가?

주 종단 조건은 본 실행 전에 결정하였다. 국가 보정, 원 질문 검색 등의 추가 분석은 탐색적 분석으로 구분하며, 전체 연구가 외부에 사전 등록되었다고 주장하지 않는다.

## 2. 실험 방법

### 2.1 시스템과 실행 환경

시스템은 의도 분류, 검색 준비, 하이브리드 검색, 재정렬, 문서 선별 및 답변 생성으로 구성된다. 오케스트레이터는 gemma-4-31B-it, 주요 worker는 gpt-oss-20b, 임베딩은 BGE-M3, 리랭커는 bge-reranker-v2-m3-ko를 사용하였다. 최종 답변의 자동 심사에는 생성 worker와 다른 phi-4를 사용하였다.

GPU 추론은 gpu-host(.53)의 기존 H200 NVL 2개에서 수행하였다. app-host(.52)에는 GPU가 없음을 확인하여 서버 간 네트워크 측정에만 사용하였다. 운영 모델을 재시작하지 않고 고정한 앱 소스 복사본과 별도 loopback 앱 프로세스에서 실험하였다. 검색 대상은 번역 문서 453,965건과 원문 문서 3,197,052건, 합계 3,651,017건의 실제 공유 색인이었다.

종단 지연의 측정 범위는 .53의 클라이언트가 백엔드 API 요청을 시작한 시점부터 응답을 모두 받은 시점까지다. .52의 운영 Nginx, 실제 배포 앱의 CPU 배치, 브라우저 렌더링까지 포함한 서비스 SLA 시험은 아니다. GPU는 기존 서비스와 공유하였고 prefix cache를 초기화하지 않은 warm 조건이었다.

### 2.2 질문 집합과 출처 라벨

400개 질문을 중복 없이 구성하였다. 출처형 질문은 서로 다른 법령 240개 및 57개 국가·지역·기구에 걸쳐 표집하였다.

| 질문 유형 | 문항 수 |
|---|---:|
| 법령명 검색 | 80 |
| 출처 조문 주제 질문 | 63 |
| 출처 의미 재서술 질문 | 68 |
| 참조 문자열 검증 실패 후 법령·조문명 검색으로 대체 | 29 |
| 상황형 법령 검색 | 100 |
| 국가 비교 | 20 |
| 자기완결적 번역 | 20 |
| 대화·서비스 안내·범위 밖 | 20 |
| 합계 | 400 |

법령 수준 평가는 출처형 240문항에 적용하였다. 정확한 조문 수준 평가는 참조 답변이 출처 원문에 실제로 존재하는 연속 문자열인지 검증한 131문항에만 적용하였다. 법령명만 묻는 질문에 특정 조문을 임의의 유일 정답으로 지정하지 않았으며, 나머지 질문에도 정답 문서를 임의로 부여하지 않았다.

이 라벨은 출처가 알려진 문서를 다시 찾는 평가용 silver known-item 라벨이다. 모든 관련 문서를 열거한 relevance gold가 아니며, 다른 문서도 질문에 유효한 답을 제공할 수 있다. 질문의 법률적 타당성과 답변의 사실성에 대한 전문가 검토는 아직 수행하지 않았다. 별도의 예비 24문항은 본 실험과 출처 법령 ID가 겹치지 않으며 본 결과에 합산하지 않았다.

### 2.3 종단 비교 조건

| 조건 | 변경 사항 |
|---|---|
| baseline | 고정한 현재 앱의 순차 실행과 LiteLLM 프록시 경로. 리랭커 인증 실패 시 기존 fallback 유지 |
| speed | 동일 모델 직접 연결, typed dispatch, 입력 일치 확인을 거친 준비 단계 중첩, 진행 중 동일 임베딩 요청 합치기, 반복 검색 설정 호출 감소, 인위적 스트리밍 대기 제거 |
| balanced | speed에 본문 리랭커 인증 복구와 gpt-oss 스트리밍 답변의 낮은 추론량 설정 추가 |

모델·임베딩·가드레일 인증은 실행 가능한 공통 전제 조건으로 모든 조건에서 복구하였다. 따라서 이번 baseline은 이전 날짜의 실험 baseline과 동일하지 않다.

준비 단계 중첩은 적격한 신규 단일 법령 질의에 한해 분류 결과가 나오기 전에 준비를 시작하는 방식이다. 분류가 해당 검색 경로를 허용하고 실제 사용될 전체 대화 입력과 준비 입력이 정확히 일치할 때만 결과를 사용한다. 그렇지 않으면 정상 준비 경로를 실행하고 사용하지 않은 작업은 취소·회수한다. 임베딩 요청 합치기는 동시에 진행 중인 동일 입력에만 적용하며 완료된 답변을 캐시하는 방식이 아니다.

낮은 추론량 설정은 SSE 답변 생성에만 적용하였다. JSON 경로에는 적용하지 않았다. 또한 정상 재정렬은 Top-20을 반환하지만 기존 401 fallback은 후보 전체를 반환할 수 있으므로 balanced의 종단 효과에는 생성 문맥 구성 차이도 포함된다. 이를 인증만 또는 추론량만 바꾼 독립 대조 실험으로 해석하지 않는다.

### 2.4 반복, 측정 지표 및 통계

SSE는 400문항 × 3조건 × 2회로 2,400회, JSON은 400문항 × 2조건 × 1회로 800회 측정하였다. SSE 동시성은 4였으며 8문항 블록별로 조건 순서를 회전·반전하였다. 조건 간 요청은 겹치지 않게 하고 매 요청에 새 세션을 사용하였다. 조건별 2개의 warmup 요청은 제외하였다.

전체 지연은 요청 시작부터 응답 종료까지로, TTFT는 progress 이벤트가 아니라 처음 표시 가능한 답변이 도착할 때까지로 정의하였다. 평균과 p50·p95·p99·최댓값을 산출하고 타임아웃과 긴 꼬리를 제거하지 않았다.

검색 평가는 재정렬 직후의 출처 조문 Hit@1/5/20과 MRR@20을 사용하였다. 최종 API는 반환 법령을 item_id로 다시 정렬하므로 반환 목록의 첫 항목을 검색 Top-1으로 평가하지 않았다. 종단에서는 반환 근거에 출처 법령·조문이 포함되는지를 측정하였다. 기존 문서 일치도는 baseline 문서 집합을 기준으로 한 문서 ID Recall로 별도 보고하고, 빈 참조 집합은 해당 지표에서 제외하였다.

반복값은 질문별로 평균을 낸 후 질문 단위의 짝지은 bootstrap 4,000회로 95% 신뢰구간을 구하였다. 배속은 평균 지연의 비율로 계산하였다. Hit@1의 McNemar 정확 검정은 첫 반복의 질문별 쌍을 사용하고 세 재정렬 후보 비교에는 Holm 보정을 적용하였다. 반복을 독립 질문으로 계산하지 않았다. 사전 비열등성 한계를 설정하지 않았으므로 유의한 차이가 없다는 사실을 품질 동등성으로 해석하지 않았다.

### 2.5 사용자 규모별 추가 실험의 별도 조건

9월 7일에는 로컬 부하 발생기에서 현재 원격 SSE API를 호출했다. 앞선 loopback
앱 실험과 배포·측정 경로가 다르며, 현재 오케스트레이터·워커의 vLLM 버전은 0.19.0으로
HTTP 확인했다. 이 초기 스윕 시점에는 GPU 기종·배치를 직접 확인하지 못했으며,
후속 접속 복구 후의 하드웨어 검증은 2.6절에서 구분한다.
400문항에서 유형 비율에 따라 고정 선택한 64문항을 각 U에 재사용하고, 완료된 사용자가
즉시 다음 질문을 보내도록 했다. 시작·종료 구간이 있는 유한 워크로드이므로 실제
시간가중 미완료 요청 수도 함께 보고했다. 외부 사용자 U와 내부 생성 슬롯 수는 별개다.

첫 진행 이벤트, 첫 답변 TTFT, 최종 SSE 완료를 구분하고 요청 발생부터 180초의 전체
기한을 적용했다. 오류가 발생한 trial은 보존하고 후속 부하·반복을 중단했다.
별도의 서버 histogram delta와 2초 표집 KV·대기·선점을 수집했다. 해당 메트릭은
공유 모델 인스턴스 전체 값으로, 개별 API 요청의 독점적 자원 소비가 아니다.
원래 두 반복 중 첫 스윕만 수행한 결과와 U=16의 외부 수용 제어 탐색적 대조를
9월 5일의 3,200회 종단 실험에 합산하거나 같은 baseline으로 비교하지 않았다.

### 2.6 현재 pod 기준의 이중 상한 대조와 반복 검증

접속 복구 후 현재 pod의 소스 해시 6개와 환경 설정, H200 NVL 2개·호스트 RAM 약
504GiB를 직접 확인했다. 운영 모델 프로세스와 K8s 배포는 바꾸지 않고 loopback 앱에서
두 수용 상한과 전송 방식을 비교했다. 첫 설정 확인에서 발견한 예전 리랭커 인증
fallback은 예비 결과에서 제외하고 모든 조건에 현재 pod 설정을 공통 적용했다.

현재 경로는 HTTP 요청 전체 수명의 ASGI 상한 4와 `execute_generate` 수명의 생성
상한 4가 중첩된다. A=4/기존 전송, B=4/즉시 전송, C=8/기존 전송, D=8/즉시 전송,
E=16/즉시 전송으로 두 상한을 함께 조정했다. 같은 64문항을 U16에서 각 1회 실행한
320회를 후보 선택용으로 구분한다. HTTP 상한만·생성 상한만의 독립 기여까지 분리한
완전 요인 설계는 아니다. 첫 기준 실행 중 내부 상한 외에 ASGI 상한을 발견했으며,
아직 요청하지 않은 C/D/E만 재기동한 보정 시점과 실제 active를 기록했다.

사전에 정한 완료·출처 조건을 만족하면서 평균이 최소인 E를 고정한 후 U16·32에서
각 64문항×2회씩 A/E를 비교한다. 별도 검증의 양쪽 전체 기한은 240초이고, goodput
기준은 30초다. 초기 검증 runner의 순서 회전 오류를 발견해 해당 실행을 별도 보존하고,
U16 A/E → U32 E/A → U32 A/E → U16 E/A 순서의 새 캠페인으로 교정했다.
선택용 실행과 순서 교정 전 실행을 검증의 효과 추정에 합산하지 않는다.

1초 간격 호스트 RAM·swap·PSI·NVML, 앱 active/queued와 2초 간격 모델 메트릭에
Nsight GPU Metrics 100Hz를 추가했다. DRAM 지표는 장치 전체 인터페이스 활동
백분율이며 실제 GB/s나 특정 모델에 귀속된 트래픽이 아니다. 기준 선택 trial의
첫 약 1.6초는 Nsight 범위 밖이므로 표본 범위도 보고한다.
[조건·보정 기록](MOLEG_SCALING_ISOLATED_PROTOCOL_20260907.md),
[자원 실측](MOLEG_SCALING_ISOLATED_RESULTS_20260907.md).

### 2.7 기존 실험을 결합한 관측·제어·검증 어댑터

9월 8일 `WorkflowAdapter`를 구현해 관측 전용/모델별 토큰 예산 모드를 기존 격리 앱
launcher에 연결했다. 외부 ASGI 수명과 agent/model 호출 수명을 구분하고 단계 이름,
모델, 대기, 입력/출력/reasoning 통계를 기록한다. 모르는 단계·reasoning은 추정하지 않는다.
병렬 호출은 구간 합집합과 작업 시간 합계를 구분해 종단 지연을 중복 계산하지 않는다.

예약 예산은 캐시를 포함한 입력 전체+예상 출력의 논리 KV 토큰과 캐시에 없는 prefill
입력으로 구분한다. 출력의 `max_tokens`나 문맥을 줄이지 않는다. 긴 요청·추정 미제공
요청은 FIFO 단독 실행하며 취소·예외 때 예약을 반환한다. 물리 VRAM 용량의 보장은 아니다.
완전 입력 일치 기반 선실행 API는 read-only 호출, 신선한 KV/대기/선점 관측과 여유
예산을 요구한다. MOLEG 오케스트레이터에는 실제 서빙 tokenizer/압력 관측을 연결했다.
새 선실행 hook은 활성화하지 않으며 기존 자원 관측 없는 준비 선실행도 통합 모드에서는 끈다.

품질 게이트는 실행 성공·출처·블라인드 답변 정확성/근거성·안전 회귀를 분리한다.
사전 비열등성 한계·독립 질문 평가·전문가 근거가 없으면 운영 release를 허용하지 않는다.
기존 추측 디코딩 제안기는 모델 내부 가속 계층으로 유지하며 통합판에서 새로 측정한
가속으로 서술하지 않는다. CPU 합성 계약 검사와 이전 GPU 실험은 서로 다른 증거다.
[구현·기존 실험 대응·후속 A/B/C/D/E 설계](WORKFLOW_ADAPTER_20260908.md).

### 2.8 실제 예산 비교와 사전 중단 규칙

별도 개발 32문항에서 고정한 호출 상한 8, prefill 46,232, KV 예약 50,328토큰을
U16/32의 A=기존 4/4, B=16/16·즉시 전송, C=B+예산으로 비교하도록 계획했다.

검증 64문항은 개발 및 9월 7일 선택 질문과 분리했다. 768회 중 U16 첫 반복 192회에서

실패를 제외하지 않았다. [사전 계획](WORKFLOW_GPU_PROTOCOL_20260908.md).

### 3.3 동일 후보 집합의 재정렬

첫 대형 모델 추출을 고정하고 400문항을 세 번 새로 검색하였다. 각 검색의 동일 후보를 네 재정렬 방식으로 비교하였다. 조문 지표는 131문항에 해당하며 검색 시간은 400문항 기준으로 추출 시간을 제외한다.

| 재정렬 조건 | Hit@1 | Hit@5 | MRR@20 | 검색+재정렬 평균 |
|---|---:|---:|---:|---:|
| 재정렬 없는 raw | 0.8168 | 0.9695 | 0.8817 | 0.337초 |
| 인증 정상·본문 입력 | 0.9008 | 0.9618 | 0.9245 | 0.438초 |
| 국가·제목·조문 메타데이터 입력 | 0.9084 | 0.9695 | 0.9307 | 0.443초 |
| 질의 관련 본문 구간 입력 | 0.9084 | 0.9695 | 0.9307 | 0.441초 |

본문 리랭커는 출처 조문 Hit@1을 107/131에서 118/131로 8.40%p 개선하였다. 질문별 개선은 15개, 악화는 4개였으며 McNemar p=0.01921, Holm 보정 p=0.03545였다. MRR 증가량 0.04283의 CI는 0.00614–0.08079였다. 검색·재정렬 평균 비용은 약 0.101초 증가하였다.

오류 분해에서는 raw의 Top-1이 출처 조문 107개, 같은 법령의 다른 조문 19개, 다른 법령 5개였고, 본문 리랭커 적용 후 각각 118개, 8개, 5개였다. 개선과 악화는 모두 같은 법령 내부의 조문 순서 변화였다. 따라서 결과는 법령 자체의 추가 발견보다 조문 선택 정밀도의 개선을 뒷받침한다. Hit@20은 모든 조건에서 0.9695였고 본문 조건의 Hit@5는 한 문항 낮았으므로 모든 순위 절단점의 개선은 아니다.

메타데이터와 관련 구간 입력은 본문 입력보다 Top-1이 한 문항 높았으나 추가 효과의 유의성을 입증하지 못하였다. 별도 400문항 잘림 처리 대조군에서는 원 helper와 실험 본문 입력의 출처 지표가 같았지만 전체 Top-20 순서의 완전 일치는 80%였다. 이를 순위 전체의 동일성 증거로 사용하지 않는다.

### 3.4 원 질문 보존과 작은 추출기 비교

400문항을 네 조건에서 한 번씩 실행한 검색 전용 실험 1,600회가 모두 완료되었다. 모든 조건에서 인증이 정상인 본문 리랭커를 사용하였다. 시간은 준비·검색·재정렬을 포함하되 의도 분류, 가드레일, 문서 선별, 대화 처리, 답변 생성은 포함하지 않는다.

| 같은 전체 준비 프롬프트의 작은 모델 추출 | 2.631초 | 110/131 (0.8397) | 127/131 | 0.8842 | 231/240 |

원 질문 조건은 8.034배 빨랐고 평균 지연은 87.55% 감소하였다(CI 86.66–88.34%). 기존 준비 조건 대비 Top-1은 개선 7문항, 악화 5문항으로 McNemar p=0.7744였으며 MRR 변화 +0.02091의 CI는 −0.01798–+0.06272였다. 따라서 관측된 검색 단계 가속은 확인했지만 품질의 유의한 개선이나 동등성을 입증하지는 않았다.

작은 모델 추출은 1.302배 빨랐으나 Top-1이 6.11%p 낮았다. MRR 변화는 −0.04027(CI −0.07281–−0.01136)이었다. Top-1의 원 p값은 0.02148이지만 Holm 보정 후 0.06445이므로 보정된 Top-1 검정의 유의성을 주장하지 않는다. 관측된 출처 손실 때문에 정확도 우선 대안으로 선정하지 않았다.

후보 합집합은 원 질문과 기존 준비 검색을 병렬 실행하고 중복을 제거한 뒤 전체 합집합을 재정렬하였다. 지정된 법령 240개가 모두 후보에, 지정된 조문 131개가 모두 Top-20에 포함되었다. 다만 평균 시간은 기존 준비보다 44.57ms 증가하였다(CI 37.35–51.52ms). 이 결과는 서로 다른 검색 표현의 후보 보완성을 보여주지만 모든 관련 문서의 Recall 100% 또는 법률적 정확도 100%를 의미하지 않는다. 전체 합집합을 다시 재정렬하므로 효과를 RRF 순위 공식만의 독립 효과로 돌리지 않는다.

### 3.5 기존 출력 일치도와 출처 지표의 후보 순위 역전

평가 모집단 차이로 인한 착시를 피하기 위해 동일한 출처 조문 질문 131개에서 두 지표를 비교하였다.

| 후보 | 기존 준비 결과 대비 문서 ID Recall | 출처 조문 Hit@1 |
|---|---:|---:|
| 원 질문 검색 | 0.5116 | 0.9160 |
| 작은 모델 추출 | 0.6934 | 0.8397 |

기존 문서와의 일치도만 보면 작은 모델 추출이 우세하지만, 알려진 출처 조문을 첫 순위에 반환하는 비율은 원 질문 조건이 높다. 이는 같은 평가 집합에서도 지표 선택에 따라 후보 우선순위가 뒤집힐 수 있음을 보여주는 실측 반례다. 따라서 기존 출력 일치도는 회귀 감시 지표로 사용할 수 있으나 관련 출처 검색이나 답변 정확도의 대리 정답으로 단독 사용해서는 안 된다.

이는 이번 데이터의 관측 결과이지, 과거 다른 질문 집합에서 나타난 작은 모델의 실패를 소급하여 무효화하는 증거가 아니다. 또한 원 질문 조건의 전문가 정확도 우월성이나 기존 조건 대비 품질 동등성을 의미하지 않는다.

### 3.6 생성·네트워크·후처리 분리 실험

고정 생성 입력 60문항을 세 조건에서 두 번씩 실행한 360회 대조군에서는 다음을 관측하였다.

| 생성 호출 조건 | 평균 시간 | 평균 모델 TTFT |
|---|---:|---:|
| 프록시·기본 추론 | 2.804초 | 1.936초 |
| 직접 연결·기본 추론 | 1.996초 | 1.298초 |
| 직접 연결·낮은 추론 | 1.161초 | 0.247초 |

직접 연결 기본 대비 낮은 추론은 평균 41.84% 빨랐다(CI 23.95–53.17%). 표시 답변 평균 길이는 감소하지 않았고 추론 문자 수가 줄었다. 그러나 출력은 동일하지 않았고 이 대조군의 전문가 답변 평가는 없으므로 무손실 생성 가속이 아니다. 프록시와 직접 연결 사이에서도 추론·답변 길이가 달라져 0.808초 차이를 순수 네트워크 비용으로 해석할 수 없다.

서버 간 health 요청은 새 연결 1.699ms, 연결 재사용 1.042ms였다. LLM 추론을 제외한 연결 재사용 효과는 밀리초 수준이므로 전체 수초 단축의 주원인으로 설명할 수 없다. 실제 스트리밍 delta를 재생한 CPU 실험 340문항에서는 인위적 전송 대기 제거로 평균 95.44ms가 줄었고 문자와 순서는 340/340문항에서 같았다. 이 동일성은 해당 전송 helper 재생에만 적용되며 전체 생성 결과나 브라우저 표시의 무손실성을 뜻하지 않는다.

국가 후처리 감사에서는 동일 서빙의 국가 반복 일치율이 100%인데도 출처 국가가 다른 질문 7개를 발견하였다. 긴 관할명 뒤에 붙은 한글 조사 때문에 짧은 상위 국가가 선택되는 최소 차이 사례를 재현하였다. 국가만 보정한 새 검색 대조군에서는 출처 법령 후보 포함이 232/240에서 238/240으로, 조문 Hit@1이 118/131에서 120/131로 증가하였다. 후자의 McNemar p=0.5이므로 일반적 개선으로 확대하지 않는다. 원 종단 경로에서는 복수 하위 검색을 통해 국가 불일치 7문항 모두 이미 출처 법령을 반환했으므로 이 개선량을 종단 효과로 대입하지 않는다.

또한 자동 답변 평가의 공통 저득점 5문항은 검색 순위와 무관한 개인정보 경고 경로에 진입하였다. 사후 동일 입력 재생에서 5개 모두 `<UNSAFE-S4>`가 반환되고 앱에서 `pii`로 매핑됨을 확인하였다. 이는 검색 전 단계의 코드·안내 범주를 함께 감사해야 함을 보여주는 오류 진단이며, 전체 안전 분류 정확도 평가나 차단 완화의 근거가 아니다. 원 실험의 원시 분류 토큰은 저장하지 않았으므로 최초 요청을 소급 복원한 결과로 기술하지 않는다.

### 3.8 외부 수용 제어의 음성 대조

내부 상한을 유지한 U=16에서 같은 64문항을 기준·고정 상한 8·적응형 상한으로 각 1회
측정해 192회 모두 정상 완료했다. 총 지연 평균은 각각 59.819·58.694·59.416초였다.
고정 상한의 HTTP 구간은 30.828초로 짧아졌지만 외부 대기 27.866초가 추가됐다.
기준 대비 총 단축률은 고정 1.88%(질문 bootstrap CI −6.37~+10.07%), 적응형
0.67%(−7.09~+8.18%)로 유의한 개선을 확인하지 못했다. 단일 실행의 질문 간 스케줄링
의존성과 시간대 변동은 이 CI로 통제되지 않는다.

적응형은 낮은 모델 압력을 관측해 상한 8→16으로 증가했지만 내부 앱 상한을 바꾸지
못했다. 모델 서버의 대기·KV만을 제어 입력으로 쓰면 앱 앞단 병목을 놓칠 수 있다.
두 정책은 기본 개선안으로 채택하지 않고, 대기 위치 이동의 음성 대조로 보고한다.
세 조건의 출처 법령·조문 포함은 같았지만 반환 목록이 완전히 같지는 않았으므로,
전문가 품질 동등성이나 답변 무손실성의 증거는 아니다.

### 3.9 이중 수용 상한과 전송 방식의 선택용 대조

U16에서 다섯 조건은 각각 64/64 완료했으며, 출처 법령·조문 포함은 모두
37/39·16/21이었다. 평균 지연은 A 58.177, B 58.274, C 43.432, D 42.084,
E 36.050초였다. p95는 각각 78.962, 81.224, 59.967, 60.251, 59.317초였다.
전송 대기만 제거한 B의 전체 평균은 개선되지 않았다. C와 E의 평균 단축은
각각 25.34%, 38.03%였으며 E를 후속 검증 후보로 고정했다. 한 번의 후보 선택에서
가장 좋은 값을 고른 것이므로 이 수치를 독립 검증 결과로 주장하지 않는다.

A→C→E에서 첫 진행 이벤트 이전 평균은 42.044→20.301→0.032초로 감소했지만
이후 평균은 16.133→23.131→36.018초로 증가했다. 공유 오케스트레이터의 호출당
평균 decode는 3.026→5.038→9.097초였으며 입력 약 3,970토큰·출력 약 83토큰은
유사했다. 즉 앞단 대기의 감소와 모델 호출 경합 증가가 동시에 발생했다.

오케스트레이터 KV 최대는 A 60.17%, C 71.10%, E 99.73%였으며 모든 조건에서
선점 증가는 0이었다. host 가용 RAM 최소는 모두 460GiB 이상, swap·OOM 증가는
0이었다. GPU 0의 DRAM read 평균/p95는 A 39.45/66%, C 28.52/62%, E 21.98/44%로,
장치 메모리 인터페이스의 지속 포화는 관측하지 못했다. 이것으로 개별 kernel의 메모리
지연 병목을 배제할 수는 없다. KV 용량 압력, HBM 활동, host RAM 부족을 구분해야 한다.

## 4. 비교 분석과 논의

### 4.1 사용자 증가에서의 병목 이동과 메모리 가설

9월 6일의 추측 디코딩 실험은 분류·준비 호출을 2.68배 가속했지만, 동시성 4의
종단 단축률은 2.9%(95% CI −4.4~+9.3%)였다. 이 수치는 동시성 16의 종단 결과가
아니며, 유의한 종단 개선을 입증하지 않는다. 동시성 16의 구조화 호출 재생에서는
51.3% 단축이 관측되었으나 측정 범위가 달라 두 수치를 같은 부하곡선에 넣을 수 없다.

후속 E1의 단일 워커 조건에서는 동시성 4→8→16에서 전체 지연이
9.392→12.543→19.743초로 늘었다. 오케스트레이터 호출 합계는 요청당
4.433→7.413→12.469초였고, 초기 세 번째 호출(통상 선별)의 평균은
2.566→4.654→8.425초였다. 해당 위치의 입력 토큰 평균은 4,794→4,781→4,769,
출력은 약 103토큰으로 유지되었다. 따라서 관측된 증가를 생성 길이 증가만으로
설명할 수 없다. 다만 호출 순번은 모든 분기에서 같은 의미의 단계라는 보장이 없으며,
호출 시간은 queue·prefill·decode를 모두 포함한다.

원시 요청 시간과 10초 간격 서버 로그를 재분석한 결과, 각 비교군이 활성화된 구간의
평균 동시 요청 수는 상한 4·8·16에 대해 약 2.90·4.31·6.18이었다. 작은 묶음마다
완료를 기다린 기존 설계는 지속 사용자 U명의 정상상태를 재현하지 않는다.
같은 부하 구간에서 두 비교군을 합친 KV 사용률의 관측 최대는 38.9·58.1·81.3%,
대기열 최대는 1·2·9건이었다. 이는 메모리·스케줄링 가설을 검증할 근거이지만,
GPU HBM 대역폭 포화나 물리 메모리 부족의 확증은 아니다. 10초 표집은 순간적인
포화를 놓칠 수 있고, GPU 메모리 할당량과 메모리 대역폭은 다른 지표다.

이를 보완한 9월 7일 실험에서는 완료 즉시 다음 요청을 투입하는 폐쇄 루프의
U=1,2,4,8,16,32 곡선과 서버 queue·prefill·decode histogram delta를 함께 측정했다.
외부 수용 대기를 사용자 지연에 포함하고, 고정 상한과 서버 압력 기반 적응형 상한을
같은 질문에서 비교하도록 했다. 구현·조건·실행별 결과는
[부하 실험 프로토콜](MOLEG_SCALING_PROTOCOL_20260907.md)과
[추가 결과 보고서](MOLEG_SCALING_RESULTS_20260907.md)에 분리한다.

새 운영 API 측정에서는 중요한 수용 제약이 확인되었다. 보관된 배포 코드·실행 설정의
생성 슬롯 상한은 4였고, 현재 8개 초기 요청의 진행 시작 순서도 이 제약과 일치했다.
첫 반복 U=8의 평균 29.60초 중 14.12초, U=16의 평균 59.78초 중 43.18초가 첫 진행
이벤트 이전이었다. U=1→16 지연 증가의 약 94%가 이 구간에 해당한다.
따라서 이 운영 API 곡선은 외부 사용자 증가의 체감 성능을 보여주지만, GPU 파이프라인
동시성을 16까지 증가시킨 결과가 아니다. 내부 슬롯을 독립적으로 제어하는 별도 앱
대조가 필요하며, 전역 상한과 전송 대기가 고정된 채로 GPU 최적화만 평가하면
실제 개선 효과와 병목 위치를 잘못 해석할 수 있다. 후속 3.9절은 현재 pod에서 이중
상한을 직접 확인하고 조정한 대조다. 내부 생성 큐 바깥의 fallback 전송도 ASGI 슬롯을
계속 보유하므로, 생성 큐의 대기 수가 0인 상태를 앱 전체의 무대기로 해석하면 안 된다.

### 4.2 단계별 자원 예산과 추측 디코딩의 결합

개선 방향은 구조화 출력의 decode 가속과 장문 입력의 처리 경합을 함께 다루는 것이다.
분류·준비에는 기존 단계별 이력 제안기를 사용하고, 선별처럼 검색 문서를 읽는 단계는
입력 토큰 예산·KV 블록 수요·대기열을 기준으로 실행을 조절한다. 혼잡 시 투기적
병렬 작업을 줄이고, 여유가 생기면 독립 단계를 겹치는 부하 적응 전략을 제안한다.
평가 목표는 평균 지연뿐 아니라 30초 이내 정상 완료 처리량과 반환 근거 보존이다.

이 방법의 핵심 가설은 단일 단계의 가속이 다음 단계의 동시 자원 수요를 늘릴 수
있다는 것이다. 전체 파이프라인의 서버 압력 기반 수용 제어는 이를 검증하는 저비용
대조군이며, 단계별 엔진 조절과 동일하지 않다. 효과가 없으면 음성 결과로 보고하고,
사용자 규모가 크다는 이유만으로 전역 상한 축소를 기본 정책으로 채택하지 않는다.

관련 연구에서 [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal)는
분할 prefill과 decode의 배치를, [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)는
두 단계의 자원 분리를 다룬다. 본 연구는 이 기법 자체의 신규성을 주장하지 않으며,
멀티에이전트 DAG의 단계별 추측 정책·자원 소비·종단 품질을 연결하는 실증을 기여로 삼는다.
또한 [REST](https://aclanthology.org/2024.naacl-long.88/)는 저장소 검색을 이용한 초안
생성을 이미 제시하므로, 과거 출력 활용 자체를 신규 알고리즘으로 주장하지 않는다.
단계 구분·누수 없는 이력 구성·부하 적응의 효과는 각각의 대조군으로 검증해야 한다.

추가로, 모델 RPC의 완료와 HTTP 스트림의 완료를 구분해야 한다. 9월 7일 비교 질문의
16,749자 응답은 첫 답변 이후 68.04초가 걸렸으며, 보관된 emitter의 5자/20ms 대기
모형(66.98초)과 가까웠다. 같은 길이의 합성 완성 텍스트를 보관된 helper로 재생하면
동시 작업 1·8·32에서 각각 67.67·68.05·69.39초가 걸렸고, 인위적 대기를 제거하면
약 1ms 이내에 같은 문자를 반환했다. 이는 CPU 전송 경로의 재현이며 현재 배포 API의
GPU 가속 결과가 아니다. 화면 표시를 위한 대기가 긴 요청을 GPU 부하로 오인하지 않도록
단계별 수용 슬롯의 수명을 정의해야 한다.

후속 직접 대조에서는 이미 준비된 전송을 빠르게 하는 것만으로 평균 개선이 나오지
않았고, 두 상한을 조정할 때 개선이 나타났다. 이에 따라 실측된 실행 설정 조정과
미검증 자원 스케줄러 제안을 구분한다. 후속 정책은 모델별 입력 토큰·예상 KV 블록을
예산으로 삼고 긴 문서 선별에 대한 수용을 조절하되 aging으로 긴 요청의 기아를 방지한다.
KV 포화·선점 증가 시에는 새 투기 작업을 줄이고, 이미 수행한 권위 경로와 입력이
정확히 일치하는 경우에만 준비 선실행 결과를 소비한다. 출력 전송에는 별도의 유한
버퍼와 백프레셔를 두며 그 대기도 종단 지연에 포함한다.

[Parrot](https://www.usenix.org/conference/osdi24/presentation/lin-chaofan)은
여러 LLM 호출의 앱 수준 의존성을 드러내는 추상화를 제시했다. 본 연구의 차별점은
일반적인 앱 수준 스케줄링 자체가 아니라, 실제 법령 다중 에이전트의 이중 수용 제한,
전송 수명, 출처 지표와 장치 압력을 연결한 진단·대조다. 토큰 예산·단계별 추측 실행의
추가 효과는 단순 고정 상한과 별도로 검증해야 하며 이번 설정 조정의 개선율로 대신하지 않는다.

### 4.3 기존 검색·품질 결과의 해석

첫째, 단계별 배속과 종단 배속을 구분해야 한다. 원 질문 검색의 8.03배는 생성형 준비를 생략한 검색 전용 결과이고, 사용자가 답변을 모두 받을 때까지의 스트리밍 API 배속은 1.297배였다. 과거 n-gram 분석 단계의 1.89배 역시 이번 전체 API 결과와 직접 비교하거나 곱할 수 없다. 이번 연구에서 n-gram은 CPU 호환성·제안기 참조 검사를 수행했을 뿐 GPU 종단 가속을 재측정하지 않았다.

둘째, 정확도 변화는 후보 발견, 후보 순위, 최종 근거 포함, 답변 품질로 나누어야 한다. 재정렬의 +8.40%p는 동일 법령 내부의 출처 조문 순위 개선이었다. 반면 국가 필터 오류는 출처가 후보에 들어오는지에 영향을 주었다. 최종 근거 포함과 자동 답변 점수는 별도의 단계이며 검색 Top-1 개선만으로 최종 답변 정확도 개선을 결론 내릴 수 없다.

셋째, 값싼 추출기와 추출 생략은 다른 설계 선택이다. 작은 모델로 전체 준비 프롬프트를 실행하면 질의 표현 변화에 따른 출처 손실과 생성 비용이 함께 남을 수 있다. 이번 명시적 국가·법령 질문 집합에서는 원 질문 검색이 더 빠르고 높은 출처 적중 점 추정치를 보였다. 그러나 원 질문 조건은 국가 선택과 키워드 생략도 함께 바꾸었고, 국가-only 대조군 역시 Top-1이 120/131이었다. 원 질문 보존만의 독립적인 정확도 효과를 주장할 수는 없다.

넷째, 출력 안정성과 정확성은 다르다. 같은 baseline의 반복 문서 ID Recall도 0.9882였고 준비 필드 완전 일치율은 397/400이었다. 반대로 국가 후처리 오류는 매번 동일하게 반복되었다. 반복 대조군은 자연 변동을 측정하지만 정확성을 보장하지 않으며, 출처 라벨은 기존 시스템의 일관된 오류를 발견하는 보완 수단이다.

### 4.4 어댑터 통합의 검증 상태

U1/2/4/8/16/32, observe/budget의 CPU 합성 요청 768회에서 입력 payload·출력 문자와
순서 보존, 슬롯 반환을 확인했다. 이는 실행 계약 검사이며 모델 정확도나 GPU 속도
실험이 아니다. 후속 GPU 비교의 실행된 U16 첫 반복에서 A/B/C 평균 관측시간은
70.49/37.60/42.13초, SSE 완료는 64/64·64/64·63/64였다. C의 평균에는 240초 실패가
포함되며 모든 응답이 완료될 때의 평균이 아니다. A에서도 내부 오류 후 반환 사례가
관측됐다. C는 B보다 관측 평균이 12.06% 길어 추가 가속을 보이지 못했다.

오케스트레이터 KV 최대는 B 83.62%에서 C 56.78%로 줄었지만 C에는 요청당 단계
대기 합계 16.41초가 발생했다. 실패 질문에서는 워커 스트림 196.62초 동안 reasoning
126,142문자·답변 본문 0문자가 관측됐다. 이는 숨겨진 CoT 내용 분석이 아니라
API 노출 통계이며, 예산이 이 현상을 유발했다는 인과 증명은 아니다.
Host RAM 최저 460.91GiB, swap/OOM 증가는 0이었으며 이번 HBM 대역폭은 직접 계측하지 않았다.

21문항×3조건의 자동 답변 평가에서 근거 충실성 평균은 A/B 1.952, C 1.857/2였다.
빈 답변도 포함했고 전문가 답변·안전 비열등성은 입증하지 못했다. U32·둘째 반복과
압력 기반 선실행·서버 추측 디코딩의 추가 효과는 미실행이다.
[상세 결과·제약·실패 감사](WORKFLOW_GPU_RESULTS_20260908.md).
현재 답변 품질 게이트는 근거 부족으로 release를 거절한다. 43.60%·49.49%를 새
스케줄러의 성능으로 재명명하거나 과거 62.7% 단계 단축과 합산하지 않는다.

## 5. 연구의 기여

### 기여 1: 회귀 일치도와 출처 검색 성능의 불일치를 실측으로 제시

동일한 131문항에서 문서 ID Recall은 작은 추출기를, 출처 조문 Hit@1은 원 질문 검색을 우선하는 후보 순위 역전을 확인하였다. 새로운 정확도 지표를 발명했다기보다, 기존 출력만을 정답으로 사용하는 최적화 평가의 한계를 실제 법령 검색 시스템에서 구체적으로 드러낸 경험적 기여다.

### 기여 2: 입력 일치 검증을 포함한 실행 최적화와 백엔드 종단 검증

준비 단계 선실행 결과의 사용 조건을 의도 경로와 전체 입력 일치로 제한하고, typed dispatch·동시 임베딩 요청 합치기·전송 대기 제거 등을 통합하였다. 동일 모델 실행 경로 조건에서 SSE 평균 지연 11.32%, 복합 조건에서 22.89% 단축을 측정하였다. 개별 기법 각각의 독립 기여나 출력 동일성을 입증한 연구로 표현하지 않는다.

### 기여 3: 원 질문 보존과 후보 보완의 비교 근거 제공

대형 추출기, 작은 추출기, 원 질문, 두 경로 후보 합집합을 같은 질문 집합과 정상 리랭커에서 비교하였다. 원 질문 조건의 검색 단계 8.03배 가속과 후보 합집합의 알려진 출처 보완성을 관찰하였다. RRF나 질의 결합 자체의 알고리즘 신규성 대신, 해당 시스템에서의 비교 결과와 적용 조건을 기여로 제시한다.

### 기여 4: 오류 전파와 긴 꼬리의 단계별 분해

리랭커 인증 fallback, 동일 법령 내 조문 순위, 국가 후처리의 후보 누락, 검색 전 안전 분류 경로, 첫 답변 전 추론과 첫 답변 후 장문 생성 지연을 구분하였다. 이를 통해 단순히 LLM 호출 전체를 병목으로 묶는 분석보다 구체적인 개선·검증 대상을 제시하였다. 인증 수정 자체를 새로운 검색 알고리즘으로 주장하지 않는다.

### 기여 5: 다층 측정과 재현 가능한 실험 산출물

400개 고유 질문, 3,200회의 API 요청, 동일 서빙 반복, 동일 후보 재정렬, 고정 생성 입력 및 조건명을 숨긴 자동 심사를 연결하였다. 주·추가 워크로드 8,353행의 질문·조건·반복 조합과 해시를 감사하여 중복·누락이 없음을 확인하였다. 이 행 수는 GPU 추론 호출 수가 아니며, 산출물 완결성은 답변 정확성을 보증하지 않는다.

### 기여 6: 사용자 수와 실제 실행 동시성의 분리

새 384회 API 요청에서 사용자 규모별 지연·처리량·첫 진행 이벤트와 모델 내부 지표를
연결했다. 외부 사용자 증가가 곧 GPU 파이프라인 동시성 증가라는 가정을 배제하고,
앱 상한과 장문 전송 대기를 별도의 검증 대상으로 도출했다. 기존 E1 1,200회의 재분석과
새 API 측정, CPU 전송 helper 재현은 서로 다른 증거로 명시한다. 이 결과는 병목 진단의
기여이며, 아직 수행하지 않은 단계별 적응형 GPU 스케줄러의 성능 개선 주장은 아니다.
후속 현재 pod 기반 선택용 320회와 순서 교차 검증 512회에서는 이중 상한과 전송 방식
조정의 종단 효과를 확인했다. U16·32의 43.60%·49.49% 단축은 이 설정 대조의 실증이며,
새 토큰 예산 스케줄러나 추측 실행 결합의 성능 주장으로 확대하지 않는다.

## 6. 한계와 후속 검증

가장 큰 한계는 전문가 gold의 부재다. 출처 문자열 검사와 단일 LLM 심사는 법률적 사실성, 유용성, 질문의 타당성을 검증하지 못한다. 후속 연구에서는 서로 독립적인 전문가가 질문의 답변 가능성과 관련 법령을 판정하고, 조건명을 숨긴 최종 답변을 검토해야 한다. 이미 준비한 검토 패킷의 전문가 라벨은 현재 모두 미작성 상태다.

질문은 합성이고 국가·법령이 명시된 경우가 많다. 실제 로그의 빈도, 생략된 관할, 별칭, 다중 턴 문맥에 대한 대표성을 확보하지 못하였다. 일부 출처 질문 생성에는 답변 worker와 같은 모델 계열을 사용했으므로 표현 편향도 남아 있다.

공유 GPU 부하와 warm cache는 완전히 통제하지 않았으며 반복 수는 SSE 2회, JSON과 원 질문 비교 1회로 제한적이다. 질문 단위 신뢰구간이 모든 시간대의 경합 변동을 포괄하지 않는다. 장치 전력은 후속 표집에 포함했으나 요청에 귀속한 에너지·GPU-second 비용이나 포화 최대 처리량을 측정한 것은 아니다. 준비 선실행은 지연을 줄이는 대신 소비되지 않는 작업을 만들 수 있다.

balanced는 여러 변경을 묶은 조건이다. 독립 효과를 밝히려면 리랭커 정상화와 후보 수를 모든 비교군에서 맞추고, 직접 연결·준비 중첩·낮은 추론량을 요인별로 나눈 후속 대조가 필요하다. 품질 보존 주장을 위해서는 사전 비열등성 한계와 충분한 표본 수를 정해야 한다.

운영 소스와 모델은 고정했지만 색인은 immutable snapshot이 아니라 공유 색인이었다. 관측한 조기·최종 색인 상태는 같았으나 조기 점검이 주 측정 시작 이후였으므로 전 기간 불변성을 보증하지 않는다. 운영 배포, UI 회귀, 실제 .52 경로의 SLA도 검증하지 않았다. TP·MTP·EAGLE 및 n-gram의 GPU 파라미터 탐색은 이번 실측 결과에 포함하지 않는다.

9월 7일 초기 규모 스윕은 64문항씩 한 번의 유한 실행이며 32명 타임아웃으로 후속
반복을 중단했다. 이후 현재 pod 기반 별도 앱에서 두 상한·전송 방식 대조와 DRAM
활동·host RAM·swap 계측을 추가했다. 이 서로 다른 실행을 같은 baseline으로
합산하지 않는다. 장치 지표는 개별 모델·kernel 병목의 인과 증명이 아니며, 상한 16은
KV 용량에 가까웠다. 두 상한 각각의 독립 효과, 단계별 토큰 예산과 추측 실행 결합은
아직 검증하지 않았다. 관측한 결과를 100·1000명이나 다른 하드웨어로 외삽하지 않는다.

## 2026-09-10 보완: 조건별300문항 어댑터 검증

재부팅으로 중단된400문항 캠페인은 별도로 보존하고, 사용자 요청에 따라 조건별300문항
× 3조건 × 6개 부하 × 남은2반복의10,800요청을 완료했다. 응답 스트림 비정상14건과
자동 평가1,764건 중 판정 오류2건도 보존했다. 복구 전후 색인·실행 환경이 달라졌으므로
이전 자료와 단순 합산하지 않는다.

고정16조건(B)과 추가 호출/토큰 예산(C)의 평균 관측시간은 U16에서28.92/29.96초,
U32에서53.19/60.19초였다. U32의 C는B보다13.16% 느렸으며, 단축률95% 구간은
−15.70~−10.77%다. 오케스트레이터 KV 최대는92.62%→63.12%로 감소했지만
종단 가속으로 연결되지 않았다. Host RAM 최저463.33GiB와 OOM/swap 증가0은
host RAM 고갈을 지지하지 않는다. 공유 인스턴스 관측만으로 HBM 병목은 확정하지 않는다.

따라서 정적 예산의 추가 가속이나 전문가 답변 비열등성을 주장하지 않는다.
관측·진단·실행 제어를 결합한 어댑터의 장점과 특정 정적 제어 정책의 성능은 분리한다.
전체 부하별 수치, 실패와 품질 한계는 [300문항 결과](WORKFLOW300_RESULTS_20260910.md)에
기록한다. 아래 결론의 역사적 실험 수치는 이 새 비교와 합산하지 않는다.

## 7. 결론

통합 관점에서의 연구 산출물은 **관측 가능한 추론 흐름 기반의 병목 진단과 정확도 우선
실행 어댑터**다. 기존 구성요소의 실증 결과를 모델별 예산과 검증된 선실행의 설계 근거로
연결했으며, 새로운 통합 정책의 속도·정확도 주장은 후속 대조를 통과할 때까지 유보한다.

본 연구는 다중 에이전트 법령 검색에서 동일 모델의 실행 경로 최적화와 단계별 평가를 통해 백엔드 응답 지연을 줄일 수 있음을 확인하였다. 복합 조건은 SSE 평균 지연을 22.89% 단축했고, 동일 후보의 재정렬은 출처 조문 Hit@1을 8.40%p 개선하였다. 별도의 원 질문 검색은 준비·검색·재정렬 구간에서 8.03배 빨랐다.

핵심적인 방법론적 결과는 기존 출력과의 일치도가 출처 기반 검색 성능과 다른 후보 순위를 만들 수 있다는 점이다. 따라서 속도 최적화는 기존 출력 회귀, 출처 검색, 최종 답변 품질을 분리하여 평가해야 한다. 현재 결과는 지연 감소와 일부 출처 순위 개선을 뒷받침하지만, 전문가 수준의 답변 정확도 개선이나 무손실성을 입증하지는 않는다.

사용자 증가에서의 별도 관측은 개선 우선순위를 바꾼다. 현재 경로에서는 모델 내부
대기보다 앱 실행 전 대기가 크게 증가했고, 장문 비교 응답에는 의도적인 전송 지연과
일치하는 패턴이 있었다. 후속 앱 대조에서는 이중 상한 조정으로 앞단 대기가 줄고
모델 호출 경합이 커지는 상충 관계를 확인했다. 같은 설정의 추가 검증 512회에서
평균 지연은 U16 43.60%, U32 49.49% 단축되었으나, 단계별 추측 디코딩·자원 예산의
추가 효과는 같은 GPU 자원에서 별도로 비교해야 한다. 논문의 종단
성능 주장은 이러한 실행 범위와 실패·품질 지표를 함께 명시해야 한다.
