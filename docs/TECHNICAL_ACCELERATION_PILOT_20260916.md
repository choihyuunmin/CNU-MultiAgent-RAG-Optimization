# 호출 수를 유지하는 기술적 가속: 후보 선별과 예비 검증

## 상태

2026-09-16 연결 복구 후, 고정-k 검색 도구 호출 예비 비교 **96건**을 완료했다.
동시 1/4에서 평균 35.0%/37.6% 단축, 도구 출력 48쌍 일치였다. 아직 전체 검색 개선이나
새 적응형 정책의 효과로 해석하지 않는다. 독립 질문 종단 비교와 채택 여부는
[실측 결과](WORKER_DRAFT_RESULTS_20260916.md)에 기록한다. 운영 배포는 변경하지 않았다.

새 비교에서는 사용자 요청 수, 애플리케이션 모델 호출 수, 검색 후보 수, 모델·프롬프트,
추론량·출력 한도를 동일하게 유지한다. 이전 인증 오류는 모든 조건에서 수정한다.
동시 호출 제한·호출 생략·답변 캐시는 후보에서 제외한다.

## 실제 소스에서 확인한 출발점

- `infra/llm/client.py`는 이미 싱글턴 클라이언트로 연결을 재사용한다.
  연결 풀을 새 기술적 개선이라고 제안할 근거가 없다.
- `infra/llm/tool_loop.py`는 완결형 응답을 받은 다음 도구를 순서대로 실행한다.
  따라서 생성 중 도구 실행과 독립 도구 병렬 실행은 서로 분리해 비교할 수 있다.
- `agent/law_search_agent.py`는 `search_laws` 하나를 등록하고 한 라운드를 실행한다.
  여러 도구 생성의 겹침이 이 경로에 큰 효과를 낼 것이라고 가정하면 안 된다.
- 현재 Chat Completions 델타에서 JSON 괄호가 닫혔다고 인자가 확정됐다고 간주하지 않는다.
  프로바이더가 호출별 인자 완성을 보장하는 이벤트를 제공하거나 파서가 이를 보장해야 한다.
  그 기능을 확인하지 못하면 조기 실행을 연결하지 않는다.
- [이전 전달 경로 실험](MOLEG_INFRA_RESULTS_20260906.md)에서 압축은 오히려 느렸고,
  경로 변경의 이득도 모델 호출당 약 0.19초였다. 당시 결과를 현재 성능으로 대입하지 않는다.

## 후보 A: 생성–도구 실행 스트리밍 파이프라인

예: 모델이 조회 A의 인자를 확정하면 A를 시작하고, 모델은 조회 B의 인자를 생성한다.
모든 도구 결과는 원래 호출 순서로 모아 다음 모델 호출에 전달한다.

[공통 구현](../src/cnu_rag_optimization/stream_tools.py)은 `CallReady`와 `RoundEnd`
이벤트만 사용한다. 프레임워크·법령·모델 이름을 가정하지 않는다.

- 조기 실행은 독립적이며 고정된 데이터 버전을 읽는다고 명시한 도구만 허용한다.
- 승인이나 가드레일보다 앞서 실행하면 안 된다. 데이터 버전·권한의 동일성은 앱이 보장한다.
- 쓰기 등 순서를 유지해야 하는 도구를 만나면 이후의 조기 실행을 중지한다.
- 중복 ID, 잘못된 JSON, 미등록 도구, 완료 신호 누락은 명시적 실패다.
- 취소·오류 시 남은 도구 작업을 취소하고 종료를 기다린다. 숨은 재시도는 없다.
- 정상 스트림에서는 각 도구를 정확히 한 번 실행한다. 스트림이 나중에 실패하면 이미 시작한
  읽기는 비용을 사용했을 수 있으므로, 실패 요청의 도구 호출 수도 실험 비용에 포함한다.

### 예비 동작 검증과 탈락 판단

`scripts/measure_stream_tool_overlap.py`로 3조건 × 3상황 × 3회, **27라운드**를 실행했다.
모델·네트워크 호출은 없으며 `asyncio.sleep`으로 생성/도구 지연을 넣은 합성 시험이다.
이는 실제 효과가 있다는 근거로 사용하지 않는다.

| 합성 상황 | 생성 완료 후 순차 | 생성 완료 후 병렬 | 생성 중 실행 |
|---|---:|---:|---:|
| 도구 4개, 순차적으로 인자 확정 | 263.26ms | 142.67ms | 143.91ms |
| 도구 1개, 음성 대조 | 65.87ms | 65.86ms | 65.91ms |
| 서버가 전체를 버퍼링, 음성 대조 | 261.82ms | 141.67ms | 141.53ms |

세 방식의 호출 수와 반환 결과 해시는 상황별로 모두 같았다. 독립 도구 병렬화보다
스트리밍 방식의 추가 이득은 관찰되지 않았다. 마지막 도구의 실행 시간이 전체 완료를
결정하는 조건이기 때문이다. **본 실험 승격: 아니오.** 유리한 합성 지연을 다시 골라
실제 성능 개선처럼 보고하지 않는다. 실제 장시간 선행 도구와 후속 생성의 겹침이
관측되는 별도 경로가 있을 때만 이 후보를 다시 평가한다.

14개 추가 테스트(전체 294개 통과)는 실행 시점·결과 순서·호출 수·취소·잘못된 입력을
검증한다. 프레임워크별 플러그인이나 프로바이더 완료 이벤트의 실제 지원을 검증한 것은 아니다.

## 다음 후보 B: 검증 비용에 따라 제안 길이를 조절하는 추측 디코딩

**후속 구현:** 비용 선택 모듈, 동기화 측정 훅, 고정-k GPU 단계 실행기를 구현했다.
고정-k GPU 실측은 완료했다. 설치 버전의 동적 k 필드는 미지원이며 원격 동적 정책 연결은 미완료다.
[구현 범위와 실행 방법](DRAFT_BUDGET_IMPLEMENTATION_20260916.md)을 참조한다.

기존 실험은 n-gram/과거 출력 제안기를 사용해 정해진 개수의 다음 토큰을 제안했다.
새 비교에서는 외부 모델 호출을 모두 유지하고, GPU 내부에서 한 번에 검증할 제안 토큰 수
`k ∈ {0, 2, 4, 8, 16}`를 단계·현재 배치 상태에 따라 선택한다. `k=0`은 일반 디코딩이다.
정답 모델이 수락한 토큰만 사용하며 답변 길이나 reasoning 설정을 줄이지 않는다.

하네스는 모델/프롬프트/스키마 버전을 나타내는 호출 유형을 전달하고, 추론 엔진 플러그인은
각 검증 단계에서 수락 토큰 수, 제안·검증 GPU 시간, 현재 배치 크기와 KV 사용량을 기록한다.
선택 기준은 수락률 자체가 아니라 **확정한 토큰 수 / 제안·검증에 든 시간**이다.
GPU 시간을 클라이언트 응답시간으로 대신 추정하지 않는다.

1. 현재 버전·모델에서 제안 길이를 요청별/단계별로 변경할 수 있는지 먼저 검사한다.
   미지원이면 격리된 고정-k 서빙 실험까지만 수행하고, 적응형 구현이라고 부르지 않는다.
2. 고정-k 후보를 작은 단계 재생으로 비교하고 현재 무추측·기존 고정-k를 대조군으로 둔다.
3. 예비 자료로 비용 표를 만든 뒤 동결하고, 별도 질문에서 선택 정책을 검증한다.
4. 비용 표의 조건을 벗어나면 무추측 경로를 사용한다. 임의의 최대 출력 길이를 도입하지 않는다.
5. 엔진 설정·KV 메모리·GPU 배치 차이를 기록한다. 검증 토큰 공간 때문에 줄어든 KV 용량까지
   포함한 종단 결과로 채택 여부를 결정한다.

추측 디코딩 자체는 새로운 발명이 아니다. 제안 기여는 **호출 유형과 현재 배치 상태를
함께 이용한 검증 비용 기반 선택**이며, 기존 적응형 추측 디코딩 연구와 비교해야 한다.
같은 모델을 쓰더라도 부동소수점·배치 변화로 출력이 달라질 수 있어 실제 품질 검증이 필요하다.

## 대체 후보 C: 다음 단계에서 사용할 KV를 유지·미리 읽는 하네스

**입력 재계산/캐시 교체 비용이 크다고 실측될 때 진행한다. 구현·실측 전이다.**

모델 호출의 시작·완료 이벤트로 다음에 사용할 입력 prefix를 예상해, 곧 다시 쓸 KV 블록의
퇴출 우선순위를 낮추거나 CPU→GPU 전송을 현재 계산과 겹친다. 추가 모델 호출로 캐시를
데우는 방법은 사용하지 않는다. GPU 메모리 예산도 대조군과 동일하게 둔다.

- 키에는 모델·LoRA·토크나이저·템플릿 버전, 권한 범위와 실제 prefix 토큰을 포함한다.
  중간에 내용이나 위치가 다른 KV를 임의로 다른 에이전트에 넘기지 않는다.
- 정적 DAG가 있으면 다음 단계 정보를 사용하고, 동적/반복 구조는 과거 전이 기록으로
  예상한다. 예측이 불확실하면 기존 캐시 정책을 사용한다.
- 재계산 절감 시간에서 사전 전송 시간과 다른 KV의 퇴출 비용을 뺀 이득을 평가한다.
- 캐시 적중률만 높고 p95/유효 처리량이 나빠지면 탈락시킨다.
- 별도 서버 간 KV 이동은 실제 링크 대역폭을 확인한 뒤 결정한다. 과거 측정의 1Gbps 경로에
  대용량 KV 전송을 추가하는 것은 우선 후보가 아니다.

KVFlow는 SGLang 계열의 비교를 보고한 연구다. 현재 vLLM에 그대로 설치되는 플러그인이라고
가정하지 않는다. 엔진 연결이 필요하며, 임의의 외부 모델 API에도 적용된다고 주장하지 않는다.

## 실제 예비 실험 → 본 실험 진입 규칙

아래 32문항 예비 비교 전에, 고정-k 12문항 단계 재생(96건)과 겹치지 않는 8문항의
동시 1/4 종단 확인(64건 계획)을 추가했다. 이는 추가 사전 점검이며 승격 기준을 대체하지 않는다.

서버 접속 복구 후 이전 캠페인의 실행 상태·자원 사용부터 확인한다. 진행 중인 실험과
새 GPU 실험을 겹쳐 실행하지 않는다. 새 기준 소스·모델·설정 해시를 저장하고 시작한다.

1. **진단:** 고정 12문항, 동시성 1/8. queue/prefill/decode/tool/전송 시간을 가능한 원천 계측으로
   나눈다. 엔진 계측이 없으면 해당 구간은 미관측으로 남기며 원인을 확정하지 않는다.
2. **예비:** 고정 32문항, 동시성 4/16/32, 대조군/후보 각각 3회. 순서를 교차하고 실패·재시도도
   전체 시간과 비용에 포함한다. 후보 A는 병렬 대조군을 추가해야 한다.
3. **승격:** 최소 두 부하에서 평균 종단 시간이 5% 이상 줄고 paired 95% 구간 하한 >0,
   p95 악화 ≤2%, 오류 없는 완료율 저하 없음, 유효 처리량 저하 없음일 때만 후보로 남긴다.
   같은 모델 호출/입력/검색 후보를 유지했는지 확인하고, 알려진 법령 포함률과 근거 ID 변화가
   기존 반복 변동을 넘는지 점검한다. 이 작은 표본으로 전문가 정확도 동등성을 선언하지 않는다.
4. **본 실험:** 예비에 쓰지 않은 고정 200문항, 동시성 1/4/8/16/32/64/100/150/200,
   대조군/통과 후보 각 3회. 총 10,800요청 계획이며 시작 전 계획을 동결한다.
   이것은 1~200의 대표 9개 지점이지 모든 정수 지점을 측정하는 실험은 아니다.
5. **중단:** 초기 부하에서 완료율이 하락하거나 p95가 반복해서 악화하면 높은 부하로 확대하지 않는다.
   통과 조건이 없으면 본 실험 0건으로 보고하고 다음 후보를 시험한다.

진입 기준은 탐색용 공학 기준이다. 여러 후보 중 선택한 결과를 독립적인 확증으로 취급하지 않는다.
본 실험의 질문 단위 반복 비교, 품질 평가, 실패 포함 지연·유효 처리량을 별도 보고한다.
문항 수는 GPU 실험 시작 전에 24→32로 보정했다. 24문항만 동시에 보내고 동시성 32라고
기록하지 않기 위한 변경이다. 실행기는 문항 수보다 큰 동시성 지정을 거부한다.
