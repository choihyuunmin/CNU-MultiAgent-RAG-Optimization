# 프로그램 의존성 하네스 실험

## 핵심 아이디어

멀티에이전트 RAG를 독립적인 LLM 요청 묶음이 아니라 의존성을 가진 하나의 프로그램으로 본다.
기존 검색 그래프는 온톨로지 로드, 하이브리드 검색, 시나리오 분해, 규제 후보 검색을 시작한 뒤
모든 작업이 끝나는 장벽에서 기다린다. 온톨로지 실제 검색은 온톨로지 로더만 필요하지만
관련 없는 검색 작업까지 기다린 뒤 시작한다.

제안 하네스는 요청별 작업 그래프를 만들고, 필요한 선행 작업이 끝난 후속 작업을 즉시 실행한다.
원래 합류 지점에서는 같은 결과를 기다리고 기존 병합 코드를 그대로 실행한다.
모델·프롬프트·검색 인자·반환값·vLLM 설정·기존 timeout을 변경하지 않는다.
동시 호출 제한, 답변 캐시, LLM 호출 생략, 질문 재구조화도 없다.

이 구조는 법령 전용 규칙이 아니다. 로더→검색, 계획→도구 호출, 문서 준비→재정렬처럼
명시된 작업 의존성을 가진 멀티에이전트 RAG에 적용할 수 있다. 다만 독립성이 확인된 노드만 옮겨야 한다.

## 최신 연구와 차이

[Agentix, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/luo)는 에이전트를
일반 프로그램으로 보고 프로그램 진행도에 따라 LLM 호출을 스케줄링한다.
[Kairos, 2025](https://arxiv.org/abs/2508.06948)는 워크플로 우선순위와 메모리 인지 배치를 결합한다.
[Parrot, OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/lin-chaofan)는
LLM 워크플로의 의미적 변수를 노출해 데이터 흐름을 최적화한다.

이들 시스템의 보고 성능은 본 실험 결과가 아니다. 엔진 선점·모델 배치·서버 스케줄러 변경이 필요한
기능은 현재 제약 때문에 적용하지 않았다. 이번 하네스는 외부 검색 애플리케이션의 준비된 후속 작업만
앞당긴다. 최신 연구 전체를 재현했다고 주장하지 않는다.

## 선행 후보를 제외한 근거

- 마감시간 우선 전송: 실제 400요청에서 평균 7.3% 악화, 법령 누락 25건. 폐기.
- 검색 도구 single-flight: 기존 방식 200호출 중 동일 입력은 18회였으나 동시에 겹친 중복은 1회뿐이었다.
  제거 가능한 측정 시간 상한은 200문항 전체 약 0.91초여서 확대하지 않았다.
- 하네스 스트림 버퍼·네트워크 압축: 전송 지연이 약 1~2ms인 환경에서 주 병목인 수십 초 엔진 대기를 줄이지 못한다.

## 구현과 검증

- `ProgramHarness`: 요청별 ContextVar 작업 그래프, 이름 있는 후속 노드, 구조화된 취소·오류 전파.
- 후속 노드 실행시간, 원래 장벽 전 중첩시간, 합류 대기시간 기록. 질문·프롬프트·답변은 기록하지 않는다.
- 원격 검색 함수 SHA-256이 다르면 연결을 거부한다.
- 원본 앱 파일과 운영 Pod를 수정하지 않는다. 격리 앱 두 개와 전용 부하 발생기만 사용한다.
- 로컬 테스트: `.venv/bin/python -m pytest -q` → 200 passed.
- smoke: 원본 11.161초, 후보 9.623초. 양쪽 법령 ID `12288` 일치.
  온톨로지 검색 126.6ms가 장벽 전에 실행됐고 합류 대기는 0.004ms였다.
  한 문항이므로 개선 증거로 사용하지 않는다.

## 본 실험 설계

국가명이 포함된 고정 질문 200개를 원본과 후보에 각각 한 번 실행한다.
동시 요청 수는 100, 총 요청은 400개다. 각 조건 전 엔진 유휴 상태를 확인하며 순서는 원본→후보다.
HTTP 성공과 검색 성공을 구분한다.

평가 지표는 평균·중앙·p95 응답시간, 200건 배치 실행시간, 처리량, 법령 포함 응답 수,
기존 응답 기준 법령 재현율, 기존 법령 누락 질문, 시간 초과 질문이다.
추가로 하네스가 실제로 앞당긴 작업 시간과 합류 대기를 보고한다.

독립 전문가 정답은 없다. 기존 응답 일치율은 법적 정확도가 아니다.
단일 반복이며 공유 엔진의 시간 변동이 있어 결과 판정은 `inconclusive`로 둔다.
채택 조건은 최소한 평균·p95·처리량 개선과 법령 재현율 유지다.

## 결과

400요청 모두 HTTP 전송과 유효 JSON 응답에 성공했다. 그러나 HTTP 성공은 법령 검색 정확도를 뜻하지 않는다.

| 지표 | 기존 방식 | 프로그램 하네스 | 변화 |
|---|---:|---:|---:|
| 평균 응답시간 | 153.42초 | 145.46초 | 5.2% 단축 |
| 중앙 응답시간 | 150.97초 | 141.78초 | 6.1% 단축 |
| p95 응답시간 | 249.53초 | 246.42초 | 1.2% 단축 |
| 200건 배치 실행시간 | 406.03초 | 401.27초 | 1.2% 단축 |
| 처리량 | 0.493건/초 | 0.498건/초 | 1.2% 증가 |
| 법령 포함 응답 | 127/200 | 127/200 | 동일 |
| 기존 응답 기준 법령 재현율 | 기준 100% | 84.36% | 유지 미입증 |
| 기존 법령 포함 127문항 재현율 | 기준 100% | 84.81% | 유지 미입증 |
| 법령 집합 완전 일치 | 기준 200/200 | 160/200 | 40건 다름 |
| 기존 법령 누락 질문 | — | 26/200 | 누락 확인 |
| 하위 작업 timeout 질문 | 52/200 | 48/200 | 4건 감소 |
| LLM timeout 이벤트 | 39회 | 36회 | 3회 감소 |

하네스는 201개 검색 워크플로의 온톨로지 노드를 모두 성공시켰다.
해당 노드의 평균 실행시간 3.032초가 원래 장벽 전에 겹쳤고, 합류 후 평균 대기는 0.004ms였다.
취소된 하네스 노드는 없다. 실행 지점과 메커니즘이 실제 동작했음은 확인됐다.

공유 검색·답변 엔진의 평균 대기는 20.80초에서 13.45초로 줄었다.
반면 조정 모델 엔진 대기는 27.28초에서 28.30초로 늘었다.
작업 중첩이 전체 평균 감소에 기여했을 가능성은 있지만, 단회 공유 엔진 실험으로 7.96초 차이 전부를
하네스의 인과 효과로 돌릴 수 없다.

## 정확도와 재현성 판단

바로 앞선 동일 원본 검색기의 별도 200문항 실행을 현재 원본과 비교했다.
원본끼리도 전체 법령 재현율 88.11%, 법령 포함 질문 재현율 89.15%, 완전 일치 170/200이었다.
이는 모델 출력과 고부하 timeout 때문에 원본 자체가 반복 실행마다 달라짐을 보여준다.

하네스 결과는 현재 원본 대비 전체 84.36%, 법령 포함 질문 84.81%, 완전 일치 160/200으로
원본 반복 비교보다 낮다. 독립 정답지와 사전 비열등성 기준도 없다.
따라서 **속도 개선 신호는 있으나 정확도 유지가 과학적으로 입증됐다고 판단하지 않는다.**
이번 결과를 최종 성능 개선 수치나 운영 채택 근거로 사용하지 않는다.

속도 수치가 좋은 다른 반복을 찾아 선택하는 방식도 사용하지 않는다.
다음 확증 실험에는 전문가 정답 또는 고정된 법령 ID 정답, 원본 A/A 반복, 실행 순서 무작위화,
최소 3회 반복, 사전 비열등성 기준이 필요하다.

## 판정 및 산출물

판정: `inconclusive`. 실행 메커니즘과 응답시간 감소는 확인됐지만 정확도 유지 조건을 충족하지 못했다.

- 구현: `src/cnu_rag_optimization/program_harness.py`
- 연결: `scripts/program_harness_attachment.py`, `scripts/build_program_harness_trial.py`
- 분석: `scripts/analyze_program_harness.py`
- 계산 결과: `experiment-results/program-harness-20260914/analysis/summary.json`
- 원시 응답·로그: `experiment-results/program-harness-20260914/`
- 기존 평가 함수는 수정하지 않았다.

이번 작업에서 커밋·푸시·운영 배포는 하지 않았다. 비공개 번들과 원시 로그는 Git 제외 상태다.
응답·로그 아카이브의 로컬/원격 SHA-256 일치를 확인한 뒤 격리 Pod 3개와 ConfigMap만 제거했다.
격리 자원은 비공개 실험 번들로 재생성할 수 있으며 측정 결과는 로컬과 원격 아카이브에 보존됐다.
운영 Pod는 기존과 같은 1/1 Running, 재시작 1 상태였다.
