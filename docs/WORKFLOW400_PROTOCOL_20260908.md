# 400문항 조건별 규모 실험 — 실행 전 고정 계획

2026-09-08. 기존 64문항 중단 실험을 덮어쓰지 않는 별도의 회귀·규모 평가다.
현재 보유한 고유 질문 400개를 모든 조건에서 사용한다. 이미 정책 개발/이전 실험에
사용된 질문이 포함되므로 독립 holdout 또는 전문가 정확도 검증이라고 부르지 않는다.

## 조건과 규모

- A `baseline`: 앱 HTTP/생성 상한 4/4, 원래 전송, 관측 어댑터.
- B `fixed16`: 두 상한 16/16, 즉시 전송, 관측 어댑터.
- C `budget`: B + 기존에 고정한 오케스트레이터 호출/토큰 예산.
- C는 호출 상한 8, prefill 46,232토큰, KV 논리 예약 50,328토큰, 출력 예약 512토큰.
  이번 400문항 결과를 보고 값을 바꾸지 않는다. 생성 max_tokens 제한을 줄이지 않는다.
- 모든 조건은 동일한 tokenizer/pressure 계측, 모델, 프롬프트, 검색 설정, 출력 제한을 사용한다.
  새 선실행·기존 speed 복합 경로·서빙 추측 디코딩 변경은 하지 않는다.
- 사용자 수 1/2/4/8/16/32 × 3조건 × 각 400문항 × 3반복 = **21,600회 계획**.

첫 반복의 부하 순서는 16/32/8/4/2/1로 두어 이전 고부하 쟁점을 먼저 관측한다.
둘째 반복은 부하 순서를 반전, 셋째는 원순서다. 부하별 조건 시작 순서를 반복마다
회전해 세 조건이 각 위치에 한 번씩 등장한다. 질문 순서는 seed 20260909+반복 번호로
고정하고 같은 반복/부하의 세 조건에 동일하게 사용한다. 공유 warm cache는 초기화하지
않으며 시간·cache·다른 트래픽 영향이 완전히 제거된 설계라고 주장하지 않는다.

## 실패와 중단을 분리

각 요청은 240초의 전체 기한을 적용한다. 개별 timeout·알려진 장애 응답은 실패 행으로
보존하고 남은 질문과 조건을 계속 평가한다. 이 변경은 이전 실패를 지우기 위한 재시도가
아니며 새 400문항 캠페인에만 적용한다. 오류율을 낮추기 위한 질문 교체·재시도는 없다.

각 trial 종료 후 앱과 모델 gate가 비었는지 확인하고, 400개 요청의 비공개 pipeline trace를
대조한다. 내부 오류 후 fallback으로 반환된 응답은 SSE 완료와 별도로 집계한다.
trace 누락/중복 또는 취소 후 60초 내 앱이 비워지지 않으면 측정 무결성 문제로 중단한다.
미실행/취소 요청을 성공이나 임의의 완료시간으로 채우지 않는다.

인프라 안전 중단 기준은 다음과 같다.

- Host OOM kill 카운터 증가, 가용 RAM 8GiB 미만, 실행 디스크 여유 10GiB 미만.
- GPU 온도 90°C 이상 또는 GPU 관측 실패.
- 기존 모델 PID/시작 시각/명령 해시 변경 또는 health 실패가 10초 주기 3회 연속 발생.
- 검색 cluster health 또는 PostgreSQL read-only `SELECT 1` 실패가 3회 연속 발생.
- 운영자의 실행 디렉터리 `STOP` 파일 생성, 서비스 종료, 최대 실행시간 72시간 도달.

새 실험 전용 systemd 서비스의 cgroup 안에서만 실행한다. 운영 모델/배포 서비스는
수정·재시작하지 않는다. 종료 시 실험 앱/자식 프로세스와 임시 인증 복사본을 정리하며,
부분 결과와 stop 사유를 남긴다. 자동 재시작·실패 trial 재실행은 하지 않는다.
장기 실행의 실제 완료 시점은 요청 지연/실패에 따라 달라지며 수십 시간이 예상된다.

## 관측과 품질

400문항 전체에서 완료/실패, 첫 보이는 답변, p95/p99, 평균 관측시간, 30초 goodput,
출처 포함, 내부 fallback을 기록한다. 실패 기한 포함 평균을 모든 응답의 완료시간
평균이라고 부르지 않는다. 추론 원문 대신 stage/model 시간, reasoning 문자 수,
보이는 답변 문자 수와 첫 보이는 토큰까지의 시간을 계측한다.

서버 Prometheus는 2초, 앱 상태는 1초, host/NVML/모델 health는 약 10초 주기로 수집한다.
NVML 활동률은 HBM 대역폭 GB/s가 아니며, 모델 RPC 수명은 내부 CoT 시간이나
순수 GPU 실행 시간이 아니다. 실제 서빙 입력은 계측하지만 요청 ID가 포함된 기존
호출 해시만으로 실행 간 의미 입력 동일성을 입증하지 않는다.

출처 라벨은 240문항, 비어 있지 않은 참조 답변을 갖는 QA는 131문항이다.
지연 측정이 모두 끝난 뒤 각 부하 첫 반복의 QA 131×3조건을 별도 phi-4로 조건명을
숨겨 평가한다(6부하 총 2,358개 평가 레코드 계획). 빈/실패 답변도 제외하지 않는다.
나머지 질문을 자동으로 정확한 답변으로 간주하지 않으며 전체 응답은 비공개로 보존한다.
전문가 답변/안전 라벨과 사전 비열등성 한계가 없으므로 **운영 release는 허용하지 않는다.**

주 비교는 C 대 B의 추가 효과다. A 대 B/C도 함께 보고하되 과거 개선율과 합산하지 않는다.
질문별 반복을 묶어 통계를 계산하며 3회 반복을 고유 질문 1,200개라고 세지 않는다.
정적 call cap과 token budget의 독립 효과는 이번에도 분리되지 않는다.

## 초기 구성 오류와 새 실행의 구분

첫 시작 디렉터리 `.6ZsEfv`에서는 pod의 exec 환경만 복사하고 앱이 시작 시 로드하는
`/app/.env`를 반영하지 못했다. 검색 근거가 없는 응답을 초반 점검에서 발견해 운영자
중단 신호로 종료했다(완료 행 151개; 정상 검색 성능 자료 아님). 해당 원자료·실행 코드는
보존하고 새 비교에 합산하지 않는다. 이는 정적 예산의 성능에 따른 정책 재조정이 아니다.

새 실행은 앱과 같은 dotenv 로드 순서로 유효 설정을 추출하고, 모델뿐 아니라 검색
인덱스 문서 수·인증 연결·PostgreSQL 읽기 연결을 확인한 후 시작한다. 모델/SSE health만으로
의존 서비스 정상성을 보증할 수 없다는 이번 시작 점검의 한계를 명시한다.
