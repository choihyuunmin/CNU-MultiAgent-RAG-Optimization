# 네트워크 기법을 결합한 멀티에이전트 실행 하네스

실제 100문항 비교 결과와 채택 보류 사유는
[2026-09-07 실험 결과](NETWORK_HARNESS_RESULTS_20260907.md)에 정리했다.

## 하네스가 하는 일

이 하네스는 모델 밖에서 작업 순서, 추론 자원 점유, 스트림 전달, 취소 정리와
측정을 관리하는 실행 코드다. 새로운 LLM 에이전트나 프롬프트 스킬을 추가하지 않는다.
에이전트가 어떤 검색·판단을 할지는 기존 시스템이 그대로 정한다.

실행 경로는 다음과 같다.

`기존 에이전트 → 질문별 순환 대기줄 → 추론 자원별 실행 자리 → 기존 LLM API → 제한된 응답 버퍼 → 기존 후처리`

## 결합한 세 가지 기술

| 네트워크 개념 | 하네스에서의 적용 | 그대로 유지하는 것 |
|---|---|---|
| 흐름별 큐·라운드로빈 | 질문 ID별 대기줄을 분리하고 한 질문씩 순환. 같은 질문 안에서는 도착순 | 질문·하위 작업·판단 내용 |
| 수신 측 크레딧 | 같은 추론 주소를 사용하는 별칭은 실행 한도를 공유. 빈 자리가 생겼을 때 원래 요청 전송 | 모델·API 주소·요청 인자·추론 옵션 |
| 제한된 버퍼·역압 제어 | 별도 수신 태스크가 원래 스트림을 읽고 최대 64개 조각을 보관. 가득 차면 기다림 | 응답 조각의 객체·내용·순서·오류 |

첫 기법은 한 질문이 하위 작업을 많이 만들어 다른 질문을 뒤로 미는 현상을 줄이려는
것이다. **실행 기회를 순환 배분**하며 GPU 사용 시간이나 토큰 수의 완전한 공정성을
보장하지 않는다. 이미 실행 중인 LLM을 중단하지 않아 긴 호출 하나를 짧게 만드는
기법도 아니다. 새로 활성화된 질문이 지속 유입되는 상황의 지연 상한을 보장하지 않는다.

세 번째 기법에서는 추론 자리를 스트림 생산자가 소유한다. 원래 LLM 스트림 읽기가
끝나면 자리를 반환하므로, 남은 조각의 후처리 때문에 그 자리를 계속 잡지 않는다.
버퍼가 가득 차면 생산자도 기다려야 한다. **무한한 선행 수신이나 무한 메모리 사용은
허용하지 않는다.** 64개는 조각 수 상한이며 바이트 상한은 아니다. 큐 밖에서 생산자와
소비자가 각각 한 조각씩 더 보유할 수 있다.

흐름 분리와 순환 처리 아이디어는 네트워크 큐 관리와 관련 있다. 이 구현은 Linux
FQ-CoDel이나 DRR 전체를 구현한 것이 아니며, CoDel의 패킷 드롭도 하지 않는다.
[RFC 8290](https://www.rfc-editor.org/info/rfc8290/).
제한된 `asyncio.Queue`가 가득 찼을 때 생산자가 기다리는 동작을 사용한다.
[Python 공식 문서](https://docs.python.org/3/library/asyncio-queue.html).

## 적용 지점 및 범용성

- `completion.py`: 기존 실행 제어기에 `ordering="fair"` 추가. 기존 FIFO·coflow는 유지.
- `network_harness.py`: 제공된 원래 스트림을 감싸는 제한된 전달 계층.
- `serve_scaling_adapter.py`: 원래 앱의 LLM 입장 제어 지점과 스트림 함수에 연결.
- 입력은 질문 ID, 단계 ID, 자원 ID다. 국가명·법령명·질문 문장을 해석하지 않는다.
- 고정된 자원·모델 별칭으로만 보낸다. 다른 모델로 우회하거나 복제본을 배포하지 않는다.
- 검색 결과를 캐시하지 않고 LLM 호출을 합치거나 생략하지 않는다. 별도 재시도도 없다.
- 취소·오류 시 생산자를 정리하고 자원을 반환한다. 정상 호출의 결과를 버리지 않는다.

따라서 다른 검색 도메인에도 연결 가능한 실행 구조다. **다른 도메인에서도 속도가
개선된다는 실험적 증거는 아직 없다.** 같은 기법을 결합했다는 사실만으로 새로운
알고리즘이나 학위논문 기여를 입증한 것은 아니다.

## 실험 계획

먼저 실제 4문항으로 연결·로그·응답 저장을 점검한다. 본 비교는 기존 400문항에서
난이도별 25개씩 추출한 **동일 100문항**, 동시 사용자 16명을 중심으로 진행한다.
질문을 새로 만들어 대체하지 않는다. 전문가 정답은 현재 없다.

| 방법 | 목적 |
|---|---|
| 화면 대기를 제거한 기준 검색기 (`delivery`) | UI 인위적 지연을 제거한 기준 |
| 자원별 도착순 (`delivery_fifo`) | 자원 한도·질문 진입 한도 조정만의 효과 |
| 네트워크 하네스 (`network_harness`) | 질문별 순환과 제한된 스트림 전달을 결합한 추가 효과 |
| 같은 기준 재측정 (`delivery_repeat`) | 기준 검색기 자체의 시간·출력 변동 확인 |

같은 부하에서 같은 질문 순서를 사용한다. 모든 방법은 모델·프롬프트·LLM 스트리밍
인자와 원래 검색기를 유지한다. 모든 방법의 화면 대기는 동일하게 제거한다.
화면 대기 제거로 얻은 시간을 하네스 개선율에 포함하지 않는다.

평가: 전체 응답 평균·p95·처리량·실패율, 앱/엔진 대기, KV 캐시·preemption,
실제 LLM 호출 수와 토큰 수, 기존 답변의 법령 재현율·첫 법령 일치율, 버퍼 크기와
대기 시간. 모델 비결정성과 실행 변동을 확인하기 위해 동일 기준의 반복 실행도
가능한 측정 범위에서 수행한다. 결과가 좋지 않아도 제외하거나 유리한 문항만 고르지 않는다.

법령 일치도는 법적 정확도가 아니다. 기존의 8월 평가 설정은 다른 배포·기준 답변을
가리키므로 이번 결과에 그대로 `pass`를 부여하지 않는다. 비교 가능한 실측 지표를
보고하되 전문가 정답·검증된 비열등성 기준이 없으면 정확도 유지는 `inconclusive`다.

```sh
PYTHONPATH=src /path/to/application/.venv/bin/python scripts/run_scaling_experiment.py \
  --application-root /path/to/application \
  --questions /path/to/application/scripts/experiment/questions_400_country_law_balanced.jsonl \
  --count 100 --concurrency 16 \
  --modes delivery,delivery_fifo,network_harness,delivery_repeat \
  --run-id network-harness-100-unique-id
```

원격 엔진에 실행·대기 요청이 남아 있으면 먼저 유휴 상태를 기다린다. 타임아웃이면
새 추론 없이 중단한다. 과부하 중단 규칙과 원시 자료 보존 규칙은
[실험 실행 설명](SCALING_EXPERIMENT.md)을 따른다.

위 구성은 **100개의 같은 질문을 4번 실행하는 총 400요청**이다. 서로 다른 400문항
검증이나 사용자 수별 전체 곡선과 혼동하지 않는다. 단위 테스트는 실제 모델 검증과
별도다. 재측정은 1회이므로 모든 자연 변동이나 통계적 유의성을 확정할 수는 없다.
