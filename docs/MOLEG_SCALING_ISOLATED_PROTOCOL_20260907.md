# 내부 슬롯·전송 방식 독립 대조와 GPU 메모리 계측

2026-09-07 SSH 접근 복구 후 작성. 운영 중단은 허용받았지만 먼저 서빙을 유지한 채
별도 loopback 앱에서 비교한다. 기존 운영 API 스윕과 다른 실행 경로의 실험이다.
앱의 전송·상한 관련 소스 해시와 운영 상한 4는 현재 K8s pod에서 다시 검증했다.

## 단계 1: 요인 분리

동일한 64개 층화 질문, 외부 사용자 U=16, 비교군별 1회(총 320요청).
기존 `evaluate_moleg_scaling.py`의 SSE 요청·전체 기한·메트릭 수집 함수를 재사용한다.
`policy` 필드는 이 실험에서 앱 비교군 이름이며, 추가 외부 gate를 적용하지 않는다.

| 비교군 | 내부 슬롯 | 전송 방식 |
|---|---:|---|
| baseline (A) | 4 | 기존 |
| emit (B) | 4 | 즉시 전송 |
| slots8 (C) | 8 | 기존 |
| emit8 (D) | 8 | 즉시 전송 |
| emit16 (E) | 16 | 즉시 전송 |

모든 조건은 같은 pod 소스 복사본, 앱 Python 환경, 설정 파일, baseline 계측 어댑터를
사용한다. 어댑터의 인증 복구는 공통 전제 조건이며 운영 배포와 완전히 같은 실행 환경을
주장하지 않는다. 프롬프트·모델·검색 후보 수·생성 길이 제한은 조건별로 변경하지 않는다.
모델 서버는 공유되며 prefix cache를 초기화하지 않는다. 질문 집합은 앞선 64문항과 같다.

모든 조건을 한 번씩 비교한 뒤 성공률·출처 포함·타임아웃·KV 선점을 확인한다.
속도가 빨라도 오류 증가·출처 회귀가 나타나는 후보는 채택하지 않는다. 이 1회 대조로
최종 성능 우월성을 확정하지 않으며, 선택된 후보는 별도 반복 부하 검증이 필요하다.
한 trial에서 실패가 있으면 해당 trial을 보존하고 캠페인을 중단한다. 기한은 180초다.

## 계측과 하드웨어 검증

- 종단 지연·p95·첫 답변 TTFT·30초 이내 정상 완료 처리량·반환 근거 해시.
- 모델별 2초 간격 KV·running·waiting·선점과 queue/prefill/decode histogram delta.
- 별도 앱의 1초 간격 실제 active·queued·상한, CPU 누적시간·최대 RSS.
- GPU 호스트의 1초 간격 메모리 할당·GPU/메모리 활동·전력과 RAM·PSI·swap 카운터.
- Nsight Systems GPU Metrics로 장치 전체 SM 활동·DRAM read/write throughput을 수집한다.
  API/CUDA trace는 끄고, 이 공유 장치 지표를 특정 모델의 독점적 소비로 귀속시키지 않는다.
  주 측정에 profiler를 포함하면 그 계측 조건을 모든 비교군에 공통 적용한다.
  본 요인 대조는 GH100 일반 지표를 100Hz로 표집한다. 1kHz·5초 연결 검사는 별도다.

Nsight의 GPU Metrics는 장치 전체 관측이며 프로세스 귀속은 제공하지 않는다.
활동 시간 비율인 NVML memory utilization과 DRAM throughput을 구분한다.
[NVIDIA 공식 GPU Metrics 문서](https://docs.nvidia.com/nsight-systems/UserGuide/index.html#gpu-metrics).

현재 GPU는 H200 NVL 2개이며, 추론 호스트 RAM은 약 504GiB, swap은 구성되지 않았다.
이 초기 상태만으로 부하 중 병목을 판단하지 않는다. K8s의 다른 NotReady 노드는
이번 실험 범위 밖으로 두고 수정하거나 추가 자원으로 간주하지 않는다.

## 안전과 복구

실험 앱은 loopback에만 바인딩하고 등록된 PID·실행 인자를 확인해 자기 프로세스만 종료한다.
기존 vLLM 재시작이 필요해지면 먼저 현재 프로세스의 정확한 설정과 복구 정보를 보호된
서버 내 경로에 확보한 뒤 변경한다. 기존 실험의 오래된 PID나 복구 파일을 재사용하지 않는다.
계정 비밀번호는 SSH 인증 입력에만 사용하며 코드·산출물·명령 인자에 저장하지 않는다.
비공개 앱 trace와 계측 원본은 공개 통계와 분리한다. 종료 후 앱/모델 health와 원 설정을 확인한다.

## 본 측정 전 환경 보정 기록

첫 연결 smoke 4회에서 예전 호스트 `.env`를 사용한 앱의 리랭커 401 fallback을 발견했다.
현재 K8s pod는 리랭커 키가 설정돼 있었으므로, 이 4회는 성능 비교에서 제외한다.
pod의 현재 `.env`를 보호된 임시 운영 설정 파일로 전달하고 모든 실험 앱을 다시 기동했다.
K8s deployment의 별도 `env`/`envFrom` 항목이 없음을 확인했다. 운영 pod 자체는 수정하지 않았다.
임시 설정 복사본은 공개 산출물에 포함하지 않고 실험 종료 시 제거한다.

소스를 더 확인한 결과 `/api/generate/stream`의 최종 fallback fake-stream은
`generate_queue.limit` 밖에서 실행된다. 반면 그래프 내부의 실제 delta 전송 helper는
모델 실행 중에도 사용된다. 따라서 모든 전송 대기가 생성 슬롯을 점유한다고 가정하지
않고, 앱 상태와 `execute_generate` 완료·SSE 완료를 구분한다. 기존 보고서의 슬롯 수명
분리 제안은 이미 분리된 fallback 경로에는 추가 개선 효과가 없을 수 있다.

## 첫 기준 trial 중 발견한 두 번째 앱 제한

`main_server.py`는 별도로 `GlobalWaitQueueMiddleware(max_concurrency=4)`를 등록한다.
이는 일반 응답 헤더까지만 제한하는 middleware가 아니라 `await self.app(...)` 전체를
감싸는 ASGI semaphore로, SSE 전송 종료까지 점유한다. 따라서 첫 기준 실행에서는
내부 `generate_queue.queued=0`이면서 앞단에 대기가 생겼다. fallback 전송이 내부
생성 슬롯을 반환하더라도 바깥 HTTP 슬롯을 계속 잡는 구조다.

아직 C/D/E 요청을 실행하기 전에 idle 상태인 세 앱만 다시 기동해 HTTP 상한도 각각
8/8/16으로 맞춘다. A/B는 원래 의도한 4/4 제한으로 실행하므로 바꾸지 않는다.
`--max-pipelines`만 바꾸고 HTTP 상한을 4로 남긴 결과를 GPU 동시성 확장으로 보고하지 않는다.
새 launcher는 두 상한을 독립적으로 지정할 수 있으며, 이 첫 대조는 두 상한을 같은 값으로
맞춘다. 시점별 앱 상태에 `max_http`를 기록하고 이 변경을 기존 manifest의 초기 앱 상태와
함께 보관한다. 운영 앱·vLLM은 수정하지 않는다.

## 단계 2: 높은 사용자 부하의 독립 반복 검증

첫 대조에서 64/64 완료하고 출처 법령·조문 포함이 기준보다 낮지 않은 후보 중 평균
종단 지연이 가장 짧은 조건을 선택한다. 첫 대조의 선택용 결과와 새 검증 결과를 합쳐
후보를 재선택하지 않는다. 기준과 선택된 후보를 U=16·32, 같은 64문항, 각 2회씩 비교한다
(계획 512요청). 반복마다 부하·비교군 순서를 회전/반전한다.

이 검증의 전체 클라이언트 기한은 양쪽 모두 240초로 정한다. 기존 운영 API의 U=32에서
앞단 대기+장문 전송으로 180초 기한을 넘었던 점을 반영한 측정 설계이며, 모델의 내부
생성 제한이나 답변 길이는 바꾸지 않는다. 30초 goodput 기준은 유지한다. 앞선 180초
캠페인과 실패율을 직접 합산하지 않고, 새 검증의 같은 240초 조건끼리 비교한다.
새 검증에서도 실패한 trial을 보존하고 후속 실행을 중단한다.

선택되지 않은 후보의 추가 튜닝이나 운영 적용은 이 검증에 포함하지 않는다.
검증 중 모델·검색·서빙 설정을 바꾸지 않으며 GPU 메모리와 장치 지표를 계속 수집한다.

### 반복 순서 보정 (후보 고정 후, 첫 검증 캠페인 도중)

최초 검증 runner는 역순 부하의 위치를 기준으로 비교군을 회전하여, 같은 U에서 두
반복의 비교군 순서가 같아지는 문제가 있었다. 해당 캠페인을 `validation`에 진단용으로
보존하고 중단했다. 선택용 320회와 E 후보 선택은 그대로 유지한다. 수정 후 새 경로
`validation-counterbalanced`에서 512회를 실행한다. Nsight·모델·앱 설정은 그대로다.
수정된 계획 순서는 U16 A/E → U32 E/A → U32 A/E → U16 E/A이며,
문항 순서는 두 번째 반복에서 seed+1로 바뀌되 그 반복의 양쪽 조건에 동일하다.
실행 전에 전체 순서를 manifest에 저장하고 같은 U에서 A/E와 E/A가 모두 나타나는지
단위 테스트한다. 중단한 캠페인은 새 효과 추정에 합산하지 않는다.
