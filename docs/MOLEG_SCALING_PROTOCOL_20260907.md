# 다중 사용자 부하와 메모리 병목: 실험 프로토콜

작성일: 2026-09-07. 본 문서는 추가 부하 실험 시작 전에 정한 비교 기준이다.
외부 사전등록은 아니며, pilot·본 측정·사후 가설을 구분한다.

SSH 복구 후 내부/HTTP 상한·전송 대조와 GPU 계측은
[별도 후속 프로토콜](MOLEG_SCALING_ISOLATED_PROTOCOL_20260907.md) 및
[결과](MOLEG_SCALING_ISOLATED_RESULTS_20260907.md)에서 관리한다.
아래의 코드 준비·미실행 상태는 후속 실행 전의 기록이다.

## 1. 검증할 질문과 기존 결과의 정정

1. 동시 사용자 U=1, 2, 4, 8, 16, 32에서 전체 응답 지연, 첫 답변 지연,
   처리량, 30초 이내 성공 처리량이 어떻게 달라지는가?
2. 지연 증가가 모델 요청 대기, 입력 처리(prefill), 출력 생성(decode),
   KV 캐시 용량 중 어느 관측량과 함께 발생하는가?
3. 서버 압력에 따른 수용 제어가 사용자 대기시간까지 포함한 지연·처리량을 개선하는가?

2026-09-06 결과의 **2.9%는 U=4의 종단 단축률**이다. U=16의 분류·준비
호출 재생은 51.3% 단축이었으며, 다른 날짜·경로·측정 범위다. 2.9%의 95% CI는
−4.4~+9.3%로, 유의한 종단 개선을 확인한 결과가 아니다.

이전 E1은 작은 블록마다 모든 요청이 끝난 뒤 다음 블록을 실행했다.
최대 요청 수 U와 지속 접속 사용자 U는 같지 않다. 또한 `completion_tokens / 호출시간`은
대기·prefill을 포함하므로 GPU의 순수 decode tok/s가 아니다. 이 값만으로
prefill 병목 또는 HBM 대역폭 포화를 확정하지 않는다.

## 2. 기술적 개선안

### 2.1 이번 실측 대상: 서버 압력 기반 FIFO 수용 제어

외부 게이트웨이에서 요청 본문은 그대로 전달하고 진행 중인 전체 파이프라인 수만 조절한다.
기준은 제한 없음(해당 실험의 U까지), 대조는 고정 상한 8,
후보는 시작 상한 8의 적응형 상한이다. 감소 시 이미 시작한 요청을 취소하지 않는다.
이번 실험 구현은 부하 발생기 안의 게이트로 같은 수용 정책을 실행한다. 별도 HTTP
게이트웨이 홉은 추가하지 않았으므로 운영 프록시의 처리 비용까지 검증한 것은 아니다.

- 2초마다 모델별 대기 요청 수, KV 사용 비율, 선점 카운터 증가를 읽는다.
- 대기 ≥2, KV ≥0.85 또는 선점 증가가 있으면 상한을 절반으로 낮춘다(최소 1).
- 대기 0, KV <0.65, 외부 대기 요청이 있는 상태가 3회 이어지면 상한을 1 올린다.
- 메트릭이 빠지거나 잘못된 값이면 여유로 해석하지 않고 마지막 상한을 유지한다.
- FIFO로 기아를 방지하고, 취소된 대기 요청과 완료된 요청의 슬롯을 반환한다.

이는 탐색용 AIMD 대조군이다. 알고리즘 신규성이나 효과를 미리 주장하지 않는다.
상한이 배치 효율을 낮추거나 대기 위치만 바꾸면 실패로 기록한다.

### 2.2 논문에서 발전시킬 방법: 단계별 자원 예산을 이용한 실행 조절

사용자 수만 세는 대신 요청 DAG의 각 단계에 대해 대기·prefill·decode 시간과
입력 토큰, 공유 prefix, 잔여 출력 길이를 기록한다. 엔진의 실제 KV 블록 회계에 맞춘
예측 필요량이 가용 예산을 넘을 때 새로운 장문 단계를 늦춘다. 단순 dense attention
공식을 sliding-window/hybrid attention 모델의 실제 용량으로 대입하지 않는다.

분류·준비처럼 구조화 출력이 많은 단계는 기존 이력 기반 추측 디코딩을 사용하고,
긴 검색 결과를 읽는 선별 단계는 prefill 토큰 예산과 간섭을 우선 조절한다.
평가 항목은 단계별 추측 길이 k={0,4,8,16}, 배치 토큰 예산 {2048,4096,8192},
동일 정밀도의 KV 예산이다. 요청별 k 변경 지원 여부는 사용 엔진에서 먼저 확인한다.
제안 토큰을 덜 만드는 것만으로 정적으로 할당된 CUDA graph/KV 메모리가 반환된다고
가정하지 않는다. 이 변경은 별도 서빙 인스턴스에서 측정해야 한다.

독립 에이전트의 무조건 동시 실행도 부하가 커지면 추가 prefill·KV 소비가 된다.
여유가 있을 때만 겹쳐 실행하고, 혼잡할 때는 예상 잔여 임계경로가 짧은 요청을
aging과 함께 우선 처리하는 대조를 추가한다. 답변 길이·검색 후보 수 축소는 별도
품질 변경이므로 이 실험의 수용 제어에 섞지 않는다.

두 GPU를 쓸 때는 워커 복제뿐 아니라 오케스트레이터 복제와 TP를 같은 총 GPU 수로
비교한다. 같은 GPU 안의 프로세스 복제는 GPU 자원 추가가 아니다. TP의 통신 비용과
복제의 prefix 재사용 손실까지 포함해 유효 처리량/GPU로 비교해야 한다.

### 2.3 왜 사용자 수가 늘면 단계 배속이 사라지는가

외부 도착률을 λ, 사용자 요청 하나가 모델 j를 호출하는 평균 횟수를 a_j라 하면
모델의 평균 호출 유입은 대략 λ_j = λ·a_j다. 호출 횟수뿐 아니라 각 호출의 입력 길이와
출력 길이가 서비스 수요를 결정한다. 따라서 사용자 수가 같아도 분기·fan-out과
긴 검색 문서의 비중에 따라 병목이 달라진다. a_j는 실제 trace에서 측정해야 하며,
공유 서버의 누적 호출 카운터를 무조건 해당 앱의 호출 증폭률로 사용하지 않는다.

단일 단계가 전체 지연의 비율 f를 차지하고 그 단계만 s배 빨라질 때, 다른 시간이
변하지 않는 이상적 종단 배속은 `1 / ((1-f) + f/s)`다. 실제 부하에서는 새로 생긴
대기·경합의 정규화된 증가량 δ를 더한 `1 / ((1-f) + f/s + δ)`로 해석할 수 있다.
이는 원인을 설명하는 모형이지 관측하지 않은 대기시간을 역산하여 확정하는 방법이 아니다.
병렬 DAG에서는 모든 LLM 호출 시간을 더한 값을 f의 분자로 쓰지 않고 임계경로를
복원해야 한다. 이번 외부 SSE 진행 구간은 단계 위치를 파악하는 보조 관측이며,
내부 GPU 연산 시간이나 정확한 분산 trace와 같지 않다.

9월 6일 U=4에서는 오케스트레이터 합계가 요청당 2.46초 줄었지만 종단은 약 0.39초
줄었다. 두 감소량의 차이가 다른 구간·경합을 살펴볼 동기이며, 그 차이를 측정 없이
모두 워커 큐 또는 메모리 병목으로 귀속시키지 않는다.

## 3. 측정 설계

`scripts/evaluate_moleg_scaling.py`는 실제 `/api/generate/stream`을 호출한다.
폐쇄 루프는 U개의 가상 사용자가 완료 즉시 다음 질문을 가져간다(think time 0).
큰 장벽 블록을 두지 않는다. 유한 작업량의 시작·종료 구간은 남으므로 최대·평균
실제 미완료 요청 수를 함께 기록한다. U=32에서 질문 32개만 쓰면 한 번의 burst가
되므로 본 실험에서는 U보다 많은 질문을 사용한다.

기존 400개 고유 질문에서 유형 비율대로 고정 표집한다. 모든 부하와 비교군에 같은
문항을 쓰고 질문 해시·유형·난수 seed를 저장한다. 반복 순서는 정방향/역방향으로
회전하고, 같은 부하에서 비교군 순서도 회전한다. pilot은 본 측정에 합산하지 않는다.
공유 prefix cache를 초기화하지 않으며, 앞선 부하가 cache에 미치는 영향을
반복 순서와 cache hit delta로 관찰한다. 완전히 동일한 cache 상태를 주장하지 않는다.

별도 개방 루프는 도착률 λ에 따른 정규 또는 Poisson 간격으로 시작 시각을 먼저
정한다. CPU 스케줄 지연·외부 수용 대기·네트워크·서버 대기·응답 수신을 모두
예정 도착 시각부터 측정한다. 밀렸다고 다음 도착을 늦추지 않아 coordinated omission을
피한다. 사용자 수 U와 λ는 서로 다른 실험 축이다.

표본 수와 모든 trial 목록은 각 실행의 `manifest.json`이 최종 기준이다.
64~96문항 규모의 반복은 병목 진단용이며, 400문항×3회와 장시간 정상상태 검증을
대체하지 않는다. 100·1000명은 32명까지의 곡선과 서버 상태를 확인한 뒤 확대한다.

## 4. 지표와 해석

- 전체 지연 L: 가상 사용자의 요청 발생부터 스트림 종료까지. 오류·타임아웃 포함.
- TTFT: progress 이벤트가 아닌 첫 답변 delta까지. 답변 delta가 없으면 결측.
- 처리량 X: 정상 SSE 완료 수 / 전체 trial 시간. 모델 호출 req/s와 구분한다.
- Goodput: 30초 이내 정상 SSE 완료 수 / trial 시간. 30초는 실험 기준이지 운영 SLA가 아니다.
- API 정상 완료, 답변 길이, 반환 근거, 출처 법령·조문 포함을 따로 보고한다.
  정상 SSE가 정확한 답변 또는 내부 fallback 부재를 뜻하지 않는다.
- 질문별 반복 평균을 단위로 baseline과 짝지은 bootstrap CI를 산출한다.
  반복값을 독립 질문으로 부풀리지 않는다. 꼬리 백분위수의 표본 크기도 명시한다.
- 외부 대기 + HTTP 구간을 분해하고, 서버 histogram의 delta로 queue/prefill/decode
  평균을 산출한다. 서버 카운터는 공유 인스턴스 전체 값이므로 해당 API 트래픽만의
  독점적 원인 분해가 아니다. 누락·재시작은 0으로 채우지 않는다.

| 병목 가설 | 필요한 관측 | 주의할 해석 |
|---|---|---|
| KV 용량 부족 | KV 사용, 선점·재계산, 장문 요청 수, KV 예산 대조 | GPU 할당 메모리 95%만으로 부족을 판정하지 않음 |
| 입력 계산 포화 | prefill 시간·실제 계산 토큰, SM/Tensor 활동, 토큰 예산 대조 | TTFT 증가에는 queue도 포함됨 |
| HBM 대역폭 포화 | DRAM active/실측 bytes/s, decode ITL, GPU 단독 프로파일 | 메모리 사용량과 메모리 대역폭은 다름 |
| 앱/서빙 상한 | active·waiting, 설정 상한, GPU 여유 | 사용자 수와 모델 동시 요청 수는 다름 |
| 호스트 메모리 | 추론 호스트 RSS·MemAvailable·PSI·swap-in/out·major fault | 부하 발생기 RAM/swap을 원격 GPU 원인으로 쓰지 않음 |

GPU 호스트 SSH와 exporter에 접근할 수 없는 동안 하드웨어 대역폭·호스트 RAM은
미측정으로 남긴다. API와 vLLM 메트릭으로 확인 가능한 가설 검증은 계속한다.
실패 응답이 나오면 해당 trial을 보존하고 후속 부하 증가는 중지한다.

## 5. 관련 연구와 기여의 경계

[Leviathan et al. (ICML 2023)](https://proceedings.mlr.press/v202/leviathan23a.html)은
목표 모델의 검증을 거치는 추측 디코딩을 제시한다.
[REST (NAACL 2024)](https://aclanthology.org/2024.naacl-long.88/)는 별도의 초안 모델 없이
기존 텍스트 저장소에서 초안 토큰을 검색한다. 따라서 "응답 이력에서 초안을 가져온다"는
생각만으로 신규성을 주장할 수 없다. 본 방법은 단계별 이력 구분·질문 교차분할·제안
정책 선택과 멀티에이전트 부하에서의 실효성을 구체적인 비교 대상으로 삼아야 한다.

[Sarathi-Serve (OSDI 2024)](https://www.usenix.org/conference/osdi24/presentation/agrawal)는
긴 prefill을 나누고 decode와 함께 배치해 처리량·지연 간 상충을 완화한다.
[DistServe (OSDI 2024)](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)는
prefill과 decode의 자원을 분리하고 지연 제약을 만족하는 처리량을 목표로 한다.
따라서 chunked prefill, 역할 분리, goodput 자체를 본 연구의 발명으로 제시하지 않는다.

[vLLM 0.19.0 최적화 문서](https://docs.vllm.ai/en/v0.19.0/configuration/optimization/)는
KV 부족의 선점·재계산과 배치 토큰 예산에 따른 ITL·TTFT 상충을 설명한다.
이는 실험 변수 선정 근거이며, 문서 권고만으로 현재 시스템의 병목을 확정하지 않는다.

본 연구의 구체적 기여 후보는 **멀티에이전트 DAG의 단계별 특성에 따라 추측 디코딩과
자원 예산 조절을 결합하고, 사용자 증가에서 생기는 병목 이동을 종단·서버 계측·품질
평가로 연결하는 것**이다. 이번에 실측되지 않은 단계별 엔진 조절은 제안으로만 기술한다.

## 6. 재현 명령과 제출 전 확장

인증이 필요한 경우 환경변수 이름을 `--api-key-env`에 전달한다. 아래 URL 변수는
실행 환경에서 주입하고 Git에 값을 저장하지 않는다.

```bash
.venv/bin/python scripts/evaluate_moleg_scaling.py \
  --base "$SCALING_APP_BASE" \
  --cases experiments/private/moleg-paper-20260905/cases.json \
  --output experiments/results/scaling-new-run \
  --metrics "orchestrator=$SCALING_ORCH_METRICS" \
  --metrics "worker=$SCALING_WORKER_METRICS" \
  --users 1 2 4 8 16 32 --limit 64 --repeats 2

.venv/bin/python scripts/evaluate_moleg_scaling.py \
  --base "$SCALING_APP_BASE" \
  --cases experiments/private/moleg-paper-20260905/cases.json \
  --output experiments/results/scaling-ablation-new-run \
  --metrics "orchestrator=$SCALING_ORCH_METRICS" \
  --metrics "worker=$SCALING_WORKER_METRICS" \
  --users 16 32 --policies baseline fixed adaptive --limit 64 --repeats 2

.venv/bin/python scripts/summarize_moleg_scaling.py \
  --directory experiments/results/scaling-new-run
uv run scripts/plot_moleg_scaling.py --directory experiments/results/scaling-new-run
```

개방 루프에서는 `--users` 대신 `--rates 0.25 0.5 1 2 --arrivals poisson`을 지정한다.
이 값들은 실행 방법의 예시이며, 실제 측정 도착률은 해당 manifest를 확인한다.
비교군은 한 번에 하나씩 실행해 서로의 실험 트래픽이 겹치지 않게 한다.

학술 제출 전에는 400문항×3회 이상의 독립 반복과 충분히 긴 정상상태 구간,
실제 유입의 도착 간격·입출력 길이 분포, 100명 이상 및 동일 GPU 예산의 확장 실험을
추가한다. 32명 결과를 100·1000명 성능으로 외삽하지 않는다. 목표 학회 양식과
전문가 평가가 확정되기 전에는 제출 준비용 본문으로 표시한다.

## 7. 실측 중 발견한 앱 상한에 따른 프로토콜 보완

첫 반복 U=8 이후, 보관된 실제 배포 소스의 `api/concurrency.py`와 검증된 실행
설정에서 `MAX_CONCURRENT_GENERATE_REQUESTS=4`를 확인했다. 현재 U=8의 초기
요청 4개는 즉시 첫 이벤트를 받고, 다음 4개의 시작은 앞선 요청 완료와 최대 약
12ms 차이로 일치했다. 이는 현재 경로에서도 같은 4개 제한이 작동한다는 강한 근거다.
현재 서버에 SSH로 접속해 설정을 새로 읽은 결과와는 구분한다.

따라서 이번 운영 API의 U=16·32 곡선은 **외부 사용자 증가 + 내부 앱 동시 실행 상한 4**의
결과다. GPU에 16·32개의 전체 파이프라인을 동시에 투입한 실험으로 표현하지 않는다.
모델 자체는 한 파이프라인의 fan-out 때문에 4보다 많은 요청을 처리할 수 있으므로
API 슬롯 수와 모델 요청 수도 구분한다.

외부 gate 실험의 의미도 바뀐다. 이미 내부 상한이 4인 상태에서 바깥 상한 8을
추가하는 것은 GPU 용량을 늘리지 못한다. 이를 수용 제어의 주 개선안이 아닌
**대기 위치 이동을 검증하는 음성 대조군**으로 보고, U=32·64문항·각 조건 1회의
탐색적 대조로 축소한다. 이 변경은 외부 gate 비교를 실행하기 전에 정했으며,
미래의 충분한 표본·반복 검증 명령과 실제 측정 manifest를 구분한다.

이후 첫 U=32에서 q343이 180초 전체 기한을 초과했다. 서버가 idle로 복귀한 것을
확인하고, 외부 gate 대조의 부하는 앞서 64/64 완료한 **U=16으로 낮췄다**.
최종 대조 계획은 U=16·64문항·baseline/fixed/adaptive 각 1회다.
원래 스윕의 두 번째 반복은 사전 중단 규칙에 따라 실행하지 않았다.
384개 행과 첫 여섯 부하 조건은 유지하며, 계획한 768개 행을 완료했다고 표시하지 않는다.

주 개선 대조는 다음처럼 재정의한다. 설정 변경은 별도 loopback 앱에서만 수행한다.

| 비교군 | 앱 내부 슬롯 | 전송 | 독립적으로 검증할 요인 |
|---|---:|---|---|
| A | 4 | 기존 | 기준 |
| B | 4 | 즉시 emit | 이미 준비된 텍스트의 의도적 전송 대기 |
| C | 8 | 기존 | 내부 수용 상한과 실제 GPU 부하 증가 |
| D | 8 | 즉시 emit | 두 요인의 결합 |
| E | 16 | 즉시 emit | KV·대기·선점을 확인한 뒤의 확장 |

`scripts/launch_moleg_scaling_app.py`는 A~E를 실행할 수 있게 앱 환경을 별도로 읽고,
설정된 실제 상한을 검사하며, 원본/즉시 emitter만 독립적으로 바꾼다.
이 launcher는 준비 및 CLI 검사까지 완료한 상태이며, 앱/서빙 설정 파일 접근이 없어
A~E의 새 종단 실측은 아직 실행하지 않았다. 이미 실행한 CPU emitter 재현으로
이 종단 실험을 대체하지 않는다.

```bash
"$SCALING_APP_PYTHON" scripts/launch_moleg_scaling_app.py \
  --app-root "$SCALING_APP_SNAPSHOT" --app-env "$SCALING_APP_ENV" \
  --serving-env "$SCALING_SERVING_ENV" --proxy-config "$SCALING_PROXY_CONFIG" \
  --trace experiments/private/scaling-B.trace.jsonl \
  --port 28220 --max-pipelines 4 --emission immediate
```

인위적 전송 대기가 compute 슬롯까지 잡고 있으면, 긴 응답이 GPU를 쓰지 않는 동안에도
후속 사용자를 막을 수 있다. 장기 설계는 모델 실행 슬롯과 HTTP 전송 수명을 분리하는
것이다. 다만 첫 토큰이 왔다는 이유만으로 실제 decode가 끝났다고 가정해서는 안 된다.
모델 RPC의 완료 또는 완성 본문 경로의 확실한 완료 신호로 슬롯 수명을 관리해야 한다.

추가 설계 조건은 제어 입력에 앱 단계별 queue·실행 슬롯 점유·모델 RPC 완료를 포함하는
것이다. GPU 대기 0·낮은 KV만으로는 내부 앱 상한이나 인위적 전송 대기를 감지할 수 없다.
이 조건은 이번 관측에서 도출한 후속 제안이며, 실행 중인 AIMD 대조의 입력·임계값을
사후 변경하지 않았다.
