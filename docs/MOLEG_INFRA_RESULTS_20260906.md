# 검색기를 바꾸지 않는 RAG 가속: 외부 중계와 GPU 통신 실험

실험일: 2026-09-06. 본 실험과 보조 실험 완료·검증.

## 1. 이번 작업이 해결하려는 문제

검색어를 바꾸거나 작은 모델로 대체하면 검색 결과가 달라질 수 있다. 이번에는
검색기와 모델의 판단 내용은 유지하고, **요청을 보내는 통로와 GPU에 일을 맡기는
방식만 바꿔 시간을 줄일 수 있는가**를 연구 문제로 삼았다.

운영 검색 화면과 RAG 백엔드의 코드·배포·설정을 수정하지 않았다. 기존 GPU 모델도
재시작하지 않았다. 별도 CPU 중계 프로그램과 실험 클라이언트를 실행했다.
운영 트래픽을 새 중계기로 돌린 실험이 아니라, 실제 앱의 분석 요청을 별도 실행한
실험이다. 따라서 아래 결과는 전체 검색 시간이나 최종 답변 정확도의 개선 수치가 아니다.

## 2. 확인한 장비와 경로

| 위치 | 실제 역할 | 이번 사용 |
|---|---|---|
| .52 서버 | Kubernetes 검색 화면, GPU 없음 | 실험용 CPU 중계기 |
| .53 서버 | Kubernetes RAG 백엔드, H200 NVL GPU 2개 | 기존 Gemma 모델 호출, 마지막에 작은 GPU 복사 시험 |
| 두 서버 사이 | 현재 사용 경로의 링크 속도 1Gbps | 실제 요청 본문 전송 비교 |
| .53의 두 GPU 사이 | 연결 구조 표시가 `SYS` | 데이터 이동 비용 확인 |

실제 경로는 `.52 검색 화면 → .53 RAG 백엔드 → .53 모델 서비스`였다.
운영 백엔드의 동시 생성 요청 제한은 4, 모델 호출 재시도 기본값은 2로 확인했다.
실험 클라이언트에는 자동 재시도를 넣지 않았다.

`SYS`는 GPU 사이에 PCIe와 CPU 소켓 간 연결을 거친다는 뜻이다. 이 장비의 현재
연결을 NVLink 연결로 가정하지 않았다. 이는 NVIDIA의
[연결 구조 설명](https://docs.nvidia.com/deploy/nvidia-smi/index.html)에 따른 해석이다.
추가 GPU 노드는 사용 범위가 확인되지 않아 접속하지 않았다.

## 3. 400개 질문과 실험 방법

이전 캠페인에서 구성한 고유 질문 400개를 고정하여 재사용했다. 이전 요약의
국가×주제 조합 질문만으로 된 초기 세트와는 구분한다. 질문 구성은 다음과 같다.

| 질문 구성 | 개수 |
|---|---:|
| 상황 설명형 | 100 |
| 법령명 지정형 | 80 |
| 원문을 바꿔 표현한 질문 | 68 |
| 조문 주제형 | 63 |
| 조문 주제 생성의 대체 형식 | 29 |
| 비교 | 20 |
| 번역 보조 | 20 |
| 대화형 | 20 |
| 합계 | 400 |

실제 사용자 로그 표본이나 전문가 정답 세트는 아니다. 비교·번역·대화도 포함하지만,
실제 앱이 선택하는 분기까지 실행하지 않는다. 따라서 운영 대표성의 한계가 남는다.

운영 Pod에서 Python 소스만 읽어 분류와 검색 준비 요청을 만들었다. 소스 해시를
대조했고, 질문별로 분류 200개·검색 준비 200개를 고정 배정했다. 모든 조건에서
같은 질문, 같은 단계, 같은 지시문, 같은 `google/gemma-4-31B-it` 모델과 생성 설정을
사용했다. 답변 길이를 줄이거나 답변을 캐시하지 않았다.

| 조건 | 쉬운 설명 |
|---|---|
| 기존 통로 (`proxy`) | 운영에서 쓰는 모델 중계 서비스를 거친다. |
| 가벼운 외부 중계 (`pass`) | .52의 별도 프로그램이 요청 본문을 그대로 같은 GPU 모델에 보낸다. |
| 8개 제한 (`fifo8`) | 같은 외부 중계에서 8개까지만 보내고 나머지는 도착 순서대로 기다린다. |
| 짧은 요청 우선 (`fair8`) | 같은 8개 제한에서 분류를 먼저 보내되, 준비 요청도 계속 기회를 준다. |

`pass`도 구현상 안전 한도는 128개지만, 본 실험 최대 16개에서는 제한이 걸리지 않는다.
`fair8`은 분류를 연속 3개 선택한 뒤 기다리는 준비 요청에 기회를 주고, 대기 6초를
넘긴 요청을 우선한다. 실행 중인 GPU 작업을 중단하거나 옮기지는 않는다.

400문항 × 4조건 × 2반복 = 3,200회 모델 요청이다. 16개를 동시에 보내고 전부
끝나면 다음 조건을 실행했다. 묶음 구성은 조건 간 같고, 실행 순서를 회전·반전했다.
실패나 느린 요청을 임의로 빼지 않는다. 초기 준비 요청은 본 수치에서 제외한다.

시간은 요청 시작부터 응답 전체 수신까지이며 중계기의 대기도 포함한다. p95는
요청 95%가 끝나는 시간이다. 평균 차이의 95% 신뢰구간은 같은 16개 요청 묶음을
짝지어 4,000번 다시 뽑는 방식으로 구했다. 이는 반복 결과의 불확실성을 나타내며,
다른 날·다른 장비에서도 같은 범위라는 보장은 아니다.

기존 통로와 외부 중계는 프로그램과 네트워크 경로가 모두 다르다. 시간 차이를
순수 네트워크 비용이나 특정 라이브러리 하나의 비용으로 단정하지 않는다.

## 4. 측정 결과

### 4.1 본 실험: 400문항, 동시 요청 16개

| 조건 | 측정 수 | 평균 | p95 | p99 |
|---|---:|---:|---:|---:|
| 기존 통로 | 800 | 2.537초 | 4.814초 | 5.298초 |
| 가벼운 외부 중계 | 800 | 2.351초 | 4.584초 | 5.065초 |
| 8개 제한 | 800 | 2.737초 | 5.426초 | 6.279초 |
| 짧은 요청 우선 + 8개 제한 | 800 | 2.688초 | 5.480초 | 6.653초 |

외부 중계는 기존 통로보다 평균 **0.186초, 7.34% 단축(1.079배)**했다. 단축률의
95% 신뢰구간은 **6.22–8.85%**였다. p95도 4.814초에서 4.584초로 줄었다.
이는 모델 요청 구간의 비교이며 전체 검색이 7.34% 빨라졌다는 뜻은 아니다.

분류는 1.203 → 1.015초(15.70% 단축), 검색 준비는 3.870 → 3.687초(4.74% 단축)였다.
두 단계 모두 절대 차이는 약 0.18–0.19초였다. 짧은 단계에서 전달 통로 비용의
비중이 더 컸다는 해석과 맞지만, 내부 원인을 각각 분해해 증명한 결과는 아니다.

외부 중계에 8개 제한을 추가하면 16.42% 느려졌고(95% 구간 14.33–18.48%),
짧은 요청 우선을 함께 넣어도 14.34% 느렸다(12.69–16.07%). 이 조건에서는
GPU 앞에 대기를 추가하는 방법을 채택할 근거가 없었다.
중계기에서 발생한 대기만 평균 0.748초와 0.697초였다. GPU 서버에 보낸 뒤의
시간만 재면 이 대기가 빠지므로, 반드시 요청 시작부터 전체 시간을 비교해야 한다.

우선 처리는 도착 순서의 8개 제한과 비교하면 분류를 10.22% 줄였지만 준비는
1.46% 늘렸다. 전체 평균 차이는 1.79%로 작았으며, 질문 단위로 다시 계산한
신뢰구간은 -0.61–4.14%로 0을 포함했다. 제한 없는 중계보다도 느렸으므로 이를
전체 시스템 개선으로 포장하지 않는다.

16개 묶음 전체 완료 시간은 기존 4.738초, 외부 중계 4.556초로 3.83% 줄었다.
묶음 처리율은 각각 초당 3.377개, 3.512개였다. 이는 계속 요청이 들어오는 상황의
최대 처리량이 아니다. 요청 평균 단축률 7.34%와 처리율 증가를 혼동하지 않는다.

상태 조회가 남은 199개 묶음 모두 모델 서버의 성공 횟수 증가가 실험 요청 수와
일치했고, GPU 계산 강제 중단 카운터 증가는 0이었다. 입력 캐시의 토큰 재사용률은
조건별 약 99.21–99.25%였다. 따라서 공통 입력 캐시가 많이 재사용된 환경의
결과이며, 처음 보는 긴 입력이 많은 환경으로 그대로 일반화하지 않는다.

### 4.2 출력·전달 검증: 정확도와 구분

- 3,200/3,200회 HTTP 성공, 유효 JSON. 모두 정상 종료, 숨은 추론 문자는 0이었다.
- 외부 중계를 거친 2,400/2,400회 요청 본문과 응답 본문의 바이트 해시가 일치했다.
- 기존 통로와 외부 중계의 정규화된 JSON 출력 일치는 779/800회, **97.375%**였다.
  분류는 400/400회 일치, 검색 준비는 379/400회(94.75%) 일치했다.
- 기존 통로 자체를 두 번 실행해도 392/400회(98.0%)만 같았다. 외부 중계 자체의
  두 반복은 390/400회(97.5%) 같았다.
- 평균 출력 토큰은 기존 81.443, 외부 중계 81.446으로, 답변을 짧게 잘라 얻은 가속이 아니다.

전달 과정에서 내용이 손상되지 않았다는 점은 확인했다. 그러나 출력 차이를 전부
자연 변동이라고 확정하거나, 검색 정확도가 완전히 보존됐다고 판정할 수는 없다.
특히 검색 준비의 작은 출력 차이가 검색 문서에 주는 영향은 별도 평가가 필요하다.
법률 전문가 정답률이나 최종 답변 정확도는 이번에 측정하지 않았다.

### 4.3 동시 요청 4개 보조 실험

본 실험과 같은 단계 배정에서 분류 24개·준비 24개를 고정 시드로 선택했다.
48문항 × 2조건 × 2반복 = 192회이며, 처음부터 계획한 400문항 본 실험과 별개인
탐색적 확인이다.

평균은 기존 **1.828초 → 외부 중계 1.790초**, 약 **0.038초·2.06% 단축**이었다.
95% 신뢰구간은 1.48–2.71%다. p95는 3.638 → 3.614초였고, 192회 모두 성공했다.
조건 간 96쌍의 정규화 JSON 출력도 모두 같았다.

낮은 부하에서도 작은 이득은 관찰됐지만, 본 실험의 7.34%보다 훨씬 작았다.
48개 표본과 측정 시점도 다르므로 차이를 전부 동시 요청 수 하나의 인과 효과로
단정하지 않는다. 운영에서 7.34%가 그대로 재현된다고 예상하면 안 된다는 근거다.

### 4.4 실제 요청 본문 압축 전송

400개 요청 본문 × 원문/gzip × 3반복 = 2,400회 전송했다. 압축 시간, 전송,
압축 해제와 해시 확인을 포함했으며 GPU 모델은 호출하지 않았다.

| 전송 방식 | 평균 본문 크기 | 평균 시간 | p95 |
|---|---:|---:|---:|
| 원문 | 15,053.6바이트 | 1.770밀리초 | 1.923밀리초 |
| gzip level 1 | 6,052.2바이트 | 2.240밀리초 | 2.401밀리초 |

본문은 **59.80% 줄었지만 시간은 0.470밀리초 늘었다**. 증가량의 95% 구간은
0.454–0.483밀리초였다. 2,400회 모두 압축 전후 본문 해시와 길이가 같았다.
압축은 평균 0.174밀리초, 수신 측 해제·해시 확인은 0.384밀리초가 들었다.

즉, 이 정도 크기의 요청과 현재 연결에서는 압축을 속도 개선책으로 채택하지 않는다.
전송량 감소는 HTTP 본문 기준이며 통신 헤더까지 포함한 전체 트래픽 감소율이 아니다.
모델 요청은 초 단위, 이 전송 시험은 밀리초 단위였다는 차이도 중요하다. 다만 별도
전송 시험이므로 이 값을 운영 모델 경로의 정확한 네트워크 비용으로 대입하지 않는다.

### 4.5 GPU 사이 작은 데이터 복사

1KiB–64MiB의 다섯 크기, 네 방향, 크기·방향당 30회로 **600회 복사**를 측정했다.
GPU당 데이터 버퍼는 128MiB였고 CUDA 실행 환경의 추가 메모리는 별도다.
모든 크기·방향의 복사 결과 내용 검사에 통과했다.

64MiB(67,108,864바이트) 결과는 다음과 같다.

| 방향 | 평균 복사 시간 | 초당 이동량 |
|---|---:|---:|
| GPU 0 내부 | 0.0478밀리초 | 1,402.7GB/s |
| GPU 0 → GPU 1 | 1.7235밀리초 | 38.94GB/s |
| GPU 1 → GPU 0 | 1.7332밀리초 | 38.72GB/s |
| GPU 1 내부 | 0.0450밀리초 | 1,492.4GB/s |

두 GPU의 직접 접근 기능은 사용 가능했다. `SYS` 표시만 보고 GPU 간 통신이
불가능하다거나 분산 추론이 반드시 느리다고 결론 내리지 않는다. 실제 측정에서는
같은 서버의 GPU 간 복사가 약 39GB/s였다. 이것은 모델 분산 실행의 배속이 아니다.

반면 서버 간 1Gbps 연결에서 같은 64MiB를 보내는 데는 계산상 최소 약 537밀리초가
필요하다(헤더·경합을 빼고 링크를 모두 쓴다는 이론값, 실측 아님). **같은 서버의
GPU 두 개를 활용하는 것과 1Gbps로 연결된 다른 컴퓨터에 계산을 나누는 것은 전혀
다른 조건**이다. 중간 자료를 자주 옮길 계획이라면 먼저 이 차이를 고려해야 한다.

### 4.6 운영 보존과 시간 기록 확인

실험 전후 검색 화면·RAG의 배포 템플릿, Pod 식별자·재시작 수, 서비스 설정이
같았다. 기존 모델 API 프로세스 8개의 PID·실행 인자·GPU 배치도 같았고, GPU 메모리
사용량은 처음 수준으로 돌아왔다. 실험용 중계와 압축 수신 프로세스는 종료했다.
실험 중 사용자 요청과 자원 경합이 전혀 없었다는 보장까지 의미하지는 않는다.

마지막에 거의 동시에 읽은 서버 시계에는 약 **42초 차이**가 있었다. 설정을 바꾸지는
않았다. 이번 지연은 각 프로세스 안의 경과 시간(`perf_counter`)으로 쟀으므로
서로 다른 서버의 시각을 빼서 지연을 계산하지 않았다. 로그 시각으로 여러 서버의
구간을 이어 분석할 때는 먼저 시계 동기화를 확인해야 한다. 원본 UTC 시각은
서버별 기록이며, 서버 간 정확한 선후관계를 나타내는 값으로 쓰지 않는다.
경과 시간 측정의 기준은 Python의
[`perf_counter` 설명](https://docs.python.org/3/library/time.html#time.perf_counter)을 참고한다.

## 5. 논문으로 발전시킬 기술적 질문

### A. 검색기 밖에서 요청 전달 비용을 줄이는 방법

CPU 서버에 가벼운 중계기를 두고 같은 GPU 모델로 전달한다. 질문과 지시문은
바꾸지 않는다. 이번에 실제 구현·비교한 범위다. 운영 적용에는 인증·권한·사용량
기록·장애 복구·스트리밍 등 기존 중계의 필요한 기능도 보존해야 한다. 단순 실험
중계기를 운영 중계 서비스의 완성된 대체품으로 볼 수 없다.

### B. 요청 종류와 혼잡도에 맞춰 GPU에 보내는 양을 결정하기

항상 적게 보내면 GPU가 여러 요청을 함께 처리하는 이점을 잃을 수 있다. 반대로
너무 많이 보내면 기다림이 길어질 수 있다. 논문 질문은 “분류와 긴 준비 작업이
섞였을 때, 언제 즉시 보내고 언제 기다리게 해야 하는가?”다.

이번에는 고정 8개 제한과 간단한 우선 처리만 시험했다. GPU 상태에 따라 한도를
자동 조절하는 완성 알고리즘을 구현하거나 검증한 것은 아니다. 이러한 처리량과
응답 시간의 절충은 [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal)
등이 다룬 기존 문제다. 단순 우선순위 자체를 새로운 발명으로 주장하지 않는다.

### C. 추가 GPU 컴퓨터가 생기면, 계산을 쪼개기 전에 요청을 나눠 보내기

동일 모델을 추가 GPU 서버에도 올리고, 새 요청 전체를 덜 바쁜 쪽에 보내는 방식이다.
한 요청의 계산 중간 자료를 매번 서버 사이로 보내는 방식과 구분된다. 이 방식은
여러 사용자의 대기를 줄일 후보이지, 한 사람의 생성 속도가 반드시 빨라지는 방법은
아니다. 기존 [Llumnix](https://www.usenix.org/conference/osdi24/presentation/sun-biao)는
여러 모델 인스턴스 사이의 실행 중 요청 이동까지 다룬다. 이번 중계는 그 이동을 구현하지 않았다.

입력을 읽는 계산과 답을 만드는 계산을 다른 GPU에 맡기는
[DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin) 방식도 후보지만,
중간 자료를 옮기는 연결 속도가 중요하다. 이번 장비의 1Gbps 서버 연결과 GPU 복사
측정만으로 해당 방식의 가속을 주장할 수 없다. 별도 모델 인스턴스를 올릴 여유 GPU가
확보되지 않아 이번에는 모델 복제·분산 추론을 실행하지 않았다.

### D. 더 큰 개선의 후보: 복사형 분석 요청만 여러 단어를 한 번에 검증하기

입력의 단어를 많이 복사하는 단계에서는 다음 몇 단어를 미리 제안하고 큰 모델이
검증하게 할 수 있다. 사용자가 제공한 기존 n-gram 실험은 이 방향의 근거다.
다만 이번 실행의 새 결과는 아니며 기존 1.89배와 이번 수치를 곱하지 않는다.
현재 설치 버전의 [후보 검증 설정](https://docs.vllm.ai/en/v0.19.0/api/vllm/config/speculative/)을
기준으로, 별도 모델 서버에서 후보 개수와 부하를 바꿔 비교해야 한다.

권장 후속 연구 문제는 **“입력을 복사하는 분석과 자유롭게 문장을 만드는 요청을
구분하여, 이득이 있는 요청에만 가속 방식을 적용할 수 있는가?”**다. 성공 조건은
기존 통로보다 빠르고, 같은 조건 반복의 자연 차이와 비교해 출력·검색·답변 품질이
나빠지지 않는 것이다. 현재 운영 모델을 임의로 재시작해 이 시험을 하지는 않았다.

공통 입력을 재사용하는 prefix cache는 이미 켜져 있다. 이 캐시는 입력 계산을
줄이는 기능이며 출력 단어 생성 자체를 직접 단축하지 않는다는
[vLLM 공식 설명](https://docs.vllm.ai/en/v0.19.0/features/automatic_prefix_caching/)을 따른다.

## 6. 기여와 한계

기여로 제시할 수 있는 것은 외부 중계의 실제 구현, 같은 입력을 이용한 짝 비교,
불리한 대안까지 포함한 측정, 그리고 전달 무결성과 모델 출력 변동을 분리하는
검증 절차다. 이것만으로 새로운 최적 스케줄링 알고리즘이나 논문 채택 가능성이
입증된 것은 아니다. 후속 정책이 기존 기법보다 언제 좋은지 추가로 보여야 한다.

논문에 담을 핵심 관찰은 다음 네 가지다.

1. 같은 모델·지시문을 유지해도 전달 통로 차이가 존재하며, 본 부하에서 평균
   7.34%, 작은 보조 부하에서는 2.06% 차이가 관찰됐다.
2. 외부에서 요청 수를 줄이고 짧은 일을 먼저 보내는 단순 정책은 제한 없는 기준을
   이기지 못했다. GPU 앞의 대기를 빠뜨리면 잘못된 개선 주장이 될 수 있다.
3. 실제 요청 압축은 바이트를 59.80% 줄여도 시간을 줄이지 못했다. 전송량과
   응답 시간은 별도 지표로 평가해야 한다.
4. 같은 서버의 GPU 간 복사와 다른 서버까지의 전송 조건은 크게 달랐다.
   추가 컴퓨터를 활용하는 연구에서는 계산 이득과 자료 이동 비용을 함께 봐야 한다.

이번에 증명하지 않은 것은 전문가 기준 법률 정확도 개선, 검색 Recall 개선,
최종 답변 품질 개선, 전체 `/api/generate` 가속, 모델 분산 실행의 가속이다.
분석 모델 요청의 성공률과 JSON 형식 준수율을 이런 정확도 지표로 바꾸어 쓰지 않는다.

같은 GPU의 기존 캐시는 비우지 않았고 다른 운영 부하를 독점 통제하지 않았다.
두 번 반복은 단발보다 낫지만 시간대별 변동과 지속 유입 상황을 충분히 대표하지 못한다.
16개 묶음 실험과 운영 앱의 4개 제한은 다르며, 별도의 낮은 부하 보조 실험도 전체
사용자 세션을 재현하지 않는다.

## 8. 논문 제목과 요약문 초안

제목 후보: **RAG 분석 요청의 외부 가속: 중계 비용, 동시 처리, GPU 통신의 실증 비교**

요약문 초안:

기존 RAG 검색 시스템의 지시문과 모델을 변경하지 않고 분석 요청의 지연을 줄이는
방법을 평가하였다. 고유 질문 400개에 분류와 검색 준비 단계를 균등하게 배정하고,
기존 모델 중계, 가벼운 외부 중계, 동시 요청 제한, 짧은 요청 우선 처리의 네 조건을
두 번 반복하여 3,200회 측정하였다. 외부 중계는 동시 요청 16개에서 평균 지연을
2.537초에서 2.351초로 7.34% 줄였으나, 48문항의 동시 요청 4개 보조 실험에서는
단축률이 2.06%였다. 동시 요청을 8개로 제한하는 정책은 제한 없는 중계보다 느렸고,
우선 처리도 이를 해소하지 못했다. 별도의 2,400회 전송 시험에서는 요청 본문을
59.80% 압축했지만 처리 시간이 0.470밀리초 증가하였다. GPU 복사 시험으로 동일
서버 내 GPU 연결과 서버 간 연결 조건을 구분하였다. 모든 본 실험 요청은 성공했고
외부 중계의 입출력 바이트는 보존되었으나, 조건 간 모델 출력 일치는 97.375%여서
법률 정답 정확도나 최종 검색 품질의 무손실을 주장하지 않는다. 결과는 기존 검색기를
유지하는 외부 가속 연구에서 요청 부하, 전달 비용, GPU 자료 이동, 출력 변동을
함께 평가해야 함을 보여 준다.
