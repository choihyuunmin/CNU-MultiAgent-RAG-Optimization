# 후속 단계 우선 실행과 단계 실패 검증

## 찾아서 보완한 세 가지 문제

1. **재정렬 인증 실패:** 실제 검색기는 재정렬 서버에서 HTTP 401을 받고 기존 검색 순서로 계속 진행했다. 격리 앱에서 올바른 서빙 인증을 연결하고 시작할 때 두 문서의 재정렬 점수가 반환되는지 확인한다. 키는 환경 파일에서 메모리로만 읽고, 지정된 서버 origin만 허용하며 HTTP 리다이렉트를 차단한다.
2. **대기가 모델 실행 제한 시간을 소모:** 모델 서버 앞에서 기다리다가 개별 모델 호출의 120초 제한에 걸리면, 준비·선택 단계가 실패할 수 있다. 모델 앞에 별도 대기열을 두고 입장 후 모델 호출 제한 시간을 시작한다. 사용자의 전체 240초 기한에는 대기시간도 포함한다.
3. **오류 안내문을 성공으로 집계:** 응답 문구에 의존하지 않고 준비 실패 이벤트와 모델 호출 실패 기록을 연결한다. 응답 수신 완료, 단계 오류 없는 완료, 외부 기능 오류 없는 완료를 따로 보고한다.

인증 수정은 결함 보정이다. 새 실행 제어와 효과를 섞지 않도록 인증만 바꾼 비교를 먼저 수행한다.

## 후속 단계 우선 실행은 무엇을 하는가

모델별로 현재 실행 중인 호출 수와 대기 중인 호출을 관리한다. 각 사용자 요청에는 해당
모델 호출을 성공적으로 마친 횟수를 기록한다. 자리가 나면 다음 규칙으로 하나를 실행한다.

- 오래 기다린 호출이 있으면 그중 먼저 들어온 호출을 선택한다.
- 그렇지 않으면 이미 더 많은 호출을 끝낸 요청의 후속 호출을 먼저 실행한다. 우선순위 계산에는 최대 3회까지만 반영한다.
- 진행 횟수가 같으면 선착순이다. 새 요청도 계속 들어오고 기존 요청이 반복하더라도 오래 기다린 호출은 우선권을 받는다.
- 실패한 호출은 진행 횟수에 더하지 않는다. 취소되거나 스트림이 끝나면 실행 자리를 반환한다.

예를 들어 새 질문 B의 준비 호출과, 준비를 끝낸 질문 A의 법령 선택 호출이 함께 기다리면
A를 먼저 실행할 수 있다. 모델 입력·검색 후보·출력 토큰 한도를 줄이지 않고 호출 순서를 조정한다.
앱 밖의 공유 모델 서버에 이미 제출된 작업을 선점하거나 서버 대기열을 완전히 통제하는 기능은 아니다.

예비 실험은 조정 모델 동시 호출 16개, 오래 기다린 호출 기준 30초를 사용한다.
같은 16개 제한의 **선착순 조건**도 비교해, 단순 대기열 제한과 후속 호출 우선순위의 효과를 구분한다.

## 다른 멀티에이전트 코드에 붙이는 방법

공통 모듈은 법령·검색·특정 에이전트 이름을 모른다. 모델 같은 공유 자원마다 창을 하나 만들고,
사용자 요청 범위에서 `flow()`, 실제 호출 경계에서 `slot()`을 사용한다.

```python
import asyncio
from cnu_rag_optimization.continuation import ContinuationWindow

window = ContinuationWindow(16, ordering="continuation", aging_s=30)

async def invoke_model(messages):
    async with window.slot():                 # 대기는 사용자 전체 기한에 포함
        return await asyncio.wait_for(
            model_call(messages), timeout=120 # 입장 후 개별 호출 제한 시작
        )

async def answer(question):
    async with asyncio.timeout(240):
        with window.flow():
            # 순차·병렬 분기·반복 모두 같은 flow의 진행 횟수를 공유한다.
            prepared = await invoke_model(prepare_messages(question))
            return await invoke_model(answer_messages(prepared))
```

순차, `asyncio.gather` 병렬 분기, 반복 구조에서 같은 경계를 사용한다. 하위 비동기 작업이
부모의 실행 자리를 잘못 빌려 쓰지 않도록 작업 단위로 소유권을 검사한다. 같은 작업에서
전송 래퍼가 중첩된 경우에는 중복 입장을 막는다. 실제 검색기 연결 코드는
`wait_for`가 생성하는 하위 전송 작업에 대해서만 이미 확보한 자리를 전달한다.

**적용 범위:** 하나의 프로세스·이벤트 루프에서 해당 자원 호출을 모두 감싼 경우의 제한이다.
여러 앱 프로세스에 각각 16을 설정하면 서버 전체 16개 제한이 되지 않는다. 분산 에이전트에는
공통 호출 게이트웨이 또는 분산 실행 자리 관리가 추가로 필요하며, 이 구현에서 제공하지 않는다.
모든 구조에서 성능이 좋아진다는 보장이나 정확도 유지 증명도 아니다.

## 관측과 검증

- `dispatch` 기록: 입장 전 대기시간, 입장 후 호출시간, 대기 수·실행 수, 성공 여부.
- `dependency_failure`: 준비 실패와 재정렬 HTTP 오류.
- 요청별 추적 ID로 모델 호출 실패를 연결하며, 완료 응답에 추적이 없으면 감사 실패.
- 취소 경합, 중첩 호출, 병렬 하위 작업, 대기와 실행 제한 분리, 오류 기록을 단위·연결 테스트한다.
- 실제 성능은 인증 보정 → 3조건 예비 비교 → 효과가 있는 설정의 높은 부하 검증 순서로 판단한다.

## 관련 연구와 연구 기여의 범위

[Parrot (OSDI 2024)](https://www.usenix.org/conference/osdi24/presentation/lin-chaofan)은
LLM 앱의 의존 정보를 이용한 서비스 최적화를 다룬다.
[Astraea](https://arxiv.org/abs/2512.14142)는 에이전트 작업 상태를 고려하는 스케줄링을,
[KVFlow](https://arxiv.org/abs/2507.07400)는 에이전트 실행 그래프를 이용한 KV 관리를 다룬다.
우선순위·노화·동시 호출 제한 자체를 새로운 발명으로 주장하지 않는다.

여기서 검증하는 설계는 **실제 완료 호출 수에 따른 후속 호출 우선권, 입장 대기와 모델 실행
제한의 분리, 실패 단계에 근거한 완료 판정**을 모델 서버 수정 없이 연결하는 방법이다.
관련 연구 대비 학술적 신규성이나 일반적 우월성은 추가 비교가 필요하다.

## 실제 검색기 실행 설정

격리 앱 실행기에 `--continuation-harness CONFIG.json`을 추가한다. 설정 파일에는 인증 값을
넣지 않는다. 공개 실험 계획의 `configurations`에 실제 사용한 설정과 소스 해시가 있다.

| 설정 | 의미 |
|---|---|
| `fingerprints` | `tools.search_tool.engine`, `agent.validation_agent`, `infra.llm.client`, `api.controller.generate_controller` 네 모듈의 SHA-256 |
| `rerank_serving_auth` | 서빙 환경 파일의 인증을 재정렬 서버에 연결하고 시작 전 점수 응답 검사 |
| `rerank_origin` | 인증을 보낼 수 있는 재정렬 서버의 프로토콜·호스트·포트 |
| `model_slots` | 모델별 동시 실행 수. `{}`이면 호출 순서·동시 실행을 제한하지 않음 |
| `ordering` | `fifo` 또는 `continuation` |
| `aging_s` | 이 시간 이상 대기한 호출은 먼저 들어온 순서로 우선 처리 |

현재 적용 예는 `model_slots={"orchestrator":32}`, `ordering="continuation"`, `aging_s=30`이다.
이는 실험 후보 설정이며, 모든 서버의 권장값이 아니다. 앱이 변경되면 소스를 검토하고 연결
테스트를 거쳐 해시를 갱신한다. 해시만 다시 계산하는 것은 호환성 검증을 대신하지 않는다.
