# 단계 실패 보정과 후속 호출 실행 제어: 측정 방법

## 비교를 분리하는 이유

이전 실험에는 재정렬 인증 오류와 내부 실패 집계 누락이 있었다. 새 실행 제어의 효과를
이 결함 보정과 섞지 않기 위해 다음 순서로 시험한다.

| 실험 | 동시 요청 | 조건 | 반복·문항 | 목적 |
|---|---|---|---|---|
| 인증 보정 | 4, 32 | 인증 오류 상태 / 인증 정상 | 조건별 32문항, 2회 | 기존 재정렬 복구 효과 |
| 실행 창 16 | 4, 64 | 제한 없음 / 선착순 16 / 후속 우선 16 | 부하별 4·64문항, 2회 | 연결 확인과 우선순위 효과 분리 |
| 실행 창 32 | 100 | 제한 없음 / 후속 우선 32 | 조건별 100문항, 2회 | 16개 제한의 과도한 대기 완화 |
| 200개 검증 | 200 | 제한 없음 / 선착순 32 / 후속 우선 32 | 조건별 200문항, 2회 | 실패 감소와 우선순위의 추가 효과 |

모든 조건은 같은 worker의 낮은 reasoning과 16후보 이상 참조 ID 축약을 사용한다.
실행 창 비교는 모두 재정렬 인증을 정상화한다. 프롬프트, 모델 선택, 검색 조건과 서빙
설정은 같은 실험 안에서 유지한다. 모델에는 같은 호출 옵션을 전달한다.

실행 창 16의 C4는 4문항 연결 확인이다. 처음 실행한 조건의 준비 비용·캐시 상태 영향을
분리하지 못하며, 여기서 나온 개선율이나 좁은 질문 단위 구간을 기능 효과로 해석하지 않는다.
C64에서 후속 우선 16은 대조군보다 평균 3.03% 느려 기본 설정으로 선택하지 않았다.

## 실행과 시간 측정

- 실제 배포 소스 124개 Python 파일의 해시를 재확인했다. 격리 앱과 일치한다.
- 각 부하 안에서 동일 질문·제출 순서를 사용하고, 반복에서 조건 실행 순서를 뒤집는다.
- 다음 조건 전에 조정·worker 모델의 실행/대기 수가 0인 상태를 두 번 확인한다.
- 사용자 요청 기한은 240초다. 어댑터 대기, 모델 대기, 실행, 출력 시간을 모두 포함한다.
- 실패를 삭제하거나 재시도하지 않는다. 시간 초과는 240초 부근의 중도 관측 종료이며 실제 완료시간이 아니다.
- C≥32는 질문 수와 동시 요청 수가 같은 유한 묶음이다. 지속적인 동시 사용자 용량 시험이 아니다.
- 부하별 질문 집합은 고정하지만 부하 사이에는 다를 수 있다. 다른 실험의 평균을 직접 빼서 개선율을 만들지 않는다.
- 모델 서버는 공유한다. 다른 트래픽과 서버 캐시 변동을 전부 제거하지 못했다.

질문별 반복 평균을 단위로 paired bootstrap 4,000회를 계산한다. 이는 문항 차이에 대한
불확실성이고, 두 번의 실행으로 서버 상태의 실행 간 변동까지 충분히 추정한 것은 아니다.

## 실패와 품질

응답 수신 완료와 내부 오류 없는 완료를 분리한다. 자세한 정의와 이전 결과 정정은
[단계 판정 문서](STAGE_OUTCOME_CORRECTION_20260916.md)에 있다. 원천 법령 포함률은
known-item 지표이며 전문가 답변 정확도가 아니다.

100·200개 부하의 자동 답변 평가 표본은 결과를 보기 전에 지정한 기준으로 선정한다.
참조 근거가 있는 질문 중 seed 202609163으로 최대 16개를 고르고, 같은 질문의 두 조건·두
반복을 평가한다. 이 표본 선택은 회귀셋 안의 선택이며 새로운 비공개 평가셋이 아니다.

성능 측정 종료 후 별도 모델 `microsoft/phi-4`로 관련성과 근거 지지를 각각 0~2점으로
평가한다. 조건명은 모델 입력에서 제외한다. 평가 모델의 오류와 근거 잘림을 기록하며,
전문가 정확도·비열등성 증명으로 제시하지 않는다.

인증 보정은 C32 예비셋에서 참조 근거가 있는 10문항 전부를 두 조건·두 반복으로
사후 평가하도록 구성했다(40건). C100·C200의 사전 지정 160건과 분리한다.
실행·회수 완료 여부는 [공개 자료 상태](../experiments/results/continuation-20260916/README.md)를 따른다.

## 버전과 재현

인증·16개 창 예비 실행은 첫 번째 코드 스냅샷을 보존했다. 이후 32개 창 실행에는 다음을
추가한 별도 스냅샷을 사용한다: 재정렬 통신 오류·비정상 점수 감지, 연결 모듈 4개의 해시
확인, 위치 인자로 전달한 모델 역할 처리, 0에서 시작하는 계측 시계의 대기시간 수정.
정상 응답의 호출 순서·모델 입력 정책은 같은 알고리즘이며 각 실험의 두 조건에 같은 버전을 쓴다.

실행 도중 소스를 덮어쓰지 않는다. 계획의 코드·설정·질문 해시, 실행 순서, 최대 동시 요청,
모델 프로세스 전후 일치를 종료 후 검사한다. 원래 인증 예비 계획에는 설정 파일 해시가
빠져 있었으므로 보존 설정과 실행 상태를 별도로 공개하고 이 한계를 감사 파일에 남긴다.

```bash
python scripts/run_moleg_continuation_study.py \
  --directory PRIVATE_STUDY_ROOT --name STUDY_NAME \
  --arms arms.window32.json --levels 100 --min-requests 100 \
  --app-env APP_ENV --serving-env SERVING_ENV --proxy-config PROXY_CONFIG

python scripts/export_moleg_continuation.py \
  --directory PRIVATE_STUDY_ROOT --name STUDY_NAME --output PUBLIC_OUTPUT
```

인증 값과 질문·답변 원문은 비공개 서버에만 둔다. 공개 자료에는 수치, 사례 ID, 해시,
인증 값을 제외한 설정과 감사 결과를 넣는다. 운영 앱 배포와 모델 서버 재시작은 하지 않는다.
