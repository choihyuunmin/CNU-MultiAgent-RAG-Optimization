# 무손실 추측 디코딩으로 오케스트레이터 CoT 시간 줄이기: 실험 프로토콜

실험일: 2026-09-06. 본 측정 전에 작성한 내부 프로토콜이며 외부 사전등록은 아니다.
결과·해석은 [결과 보고서](MOLEG_SPECDEC_RESULTS_20260906.md)에 따로 기록한다.

## 1. 문제와 기존 결과의 한계

2026-09-04~06 실험에서 검색 시스템(.52) 요청 지연의 대부분은 .53의 오케스트레이터
모델(gemma-4-31B-it)이 요청마다 순차로 수행하는 세 번의 구조화 출력 호출
(의도 분류 → 검색 준비 → 문서 선별)에서 발생함을 확인했다. 이 모델은 초당 약 50
토큰으로 디코드하고, 호출당 출력은 25~140 토큰이다. 앱 수준 기법(호출 병합,
작은 모델 대체, 압축 스키마)은 출력이 바뀌어 검색 Recall이 0.33~0.92로 무너졌고,
외부 중계·압축·동시 요청 제한 같은 전달 경로 기법은 7% 이하였다.

따라서 남은 큰 지렛대는 **같은 모델·같은 프롬프트·같은 탐욕 디코딩(temperature 0)
결과를 유지하면서 토큰 생성 자체를 빠르게 하는 것**이다. 검증 기반 추측 디코딩은
이론적으로 출력 분포를 보존하지만, 이 시스템에서 실제로 얼마나 빨라지는지, 검색
결과와 최종 답변이 유지되는지는 10문항 예비 측정(2026-09-04, 분류·준비 단계 26%
처리량 향상)밖에 없었다.

## 2. 이번 연구의 기술적 아이디어

### 아이디어 A. 로그 기반 오라클 시뮬레이션으로 제안기(proposer) 정책을 GPU 없이 고른다

탐욕 디코딩은 결정적이므로, 실제 프롬프트와 실제 출력 토큰열이 있으면 어떤 제안
정책(n-gram 길이 범위, 제안 토큰 수 k, 같은 n-gram이 여러 번 나올 때 어느 위치를
쓸지, 프롬프트 밖의 자료를 참조할지)이 몇 번의 검증 단계로 출력을 완성하는지를
CPU에서 정확히 계산할 수 있다. 이 값(출력 토큰 수 ÷ 검증 단계 수)은 검증 단계당
비용이 일정하다고 가정했을 때의 **이상 배속 상한**이다. 우리는 운영 프롬프트
400건과 운영 모델의 실제 출력(2026-09-06 재생 실험에서 저장)으로 이 시뮬레이션을
먼저 돌리고, 그 결과로 GPU 실측 조건을 고른다. 실측 배속과 이상 배속의 비율은
검증 단계의 추가 비용(초안 토큰 검증, 문법 제약 확장, 비동기 스케줄링 해제)을
분리해 보여 준다.

### 아이디어 B. 단계별 출력 구조에 따른 제안 자료의 선택

- 검색 준비 단계 출력은 사용자 질문의 단어(키워드, 국가명, 법령명)와 시스템
  프롬프트의 응답 형식 예시를 대량으로 복사한다. 프롬프트 안 n-gram 조회만으로
  높은 수락률이 기대된다.
- 의도 분류 단계 출력은 짧고 정형적이지만(`{"task": "law_search", ...}`) 그 골격
  문자열이 프롬프트에 그대로 있지는 않다. 다른 질문의 과거 출력(응답 이력)을
  제안 자료로 추가하면 골격을 한 번에 제안할 수 있다. 이는 프롬프트 조회와
  응답 이력 조회를 단계별로 결합하는 것이며, 평가 질문 자신의 과거 출력은
  절대 참조하지 않도록(누수 방지) 질문 집합을 둘로 나눠 교차 구성한다.
- 어느 쪽이든 모델의 검증을 거치므로 출력은 탐욕 디코딩 결과와 같아야 한다.
  같음은 가정하지 않고 실측한다(같은 조건 반복의 자연 변동과 비교).

### 아이디어 C. 서비스 수준 검증: 검색기와 앱은 그대로 두고 오케스트레이터만 바꾼다

이 저장소의 고정 앱 복사본(2026-09-05 캠페인과 동일)에서 오케스트레이터 역할의
요청만 실험 인스턴스로 보내는 라우팅 어댑터를 사용한다. 운영 배포·모델 서버
설정·검색 색인은 변경하지 않는다.

## 3. 장비와 GPU 배치 (원상복구 대상)

.53의 H200 NVL 2장은 상주 모델로 가득 차 있어, 사용자 승인에 따라 실험 동안
다음을 변경하고 종료 시 저장한 원래 명령·환경변수로 복구한다.

| 변경 | 이유 |
|---|---|
| phi-4(:8002, GPU1) 중지 | 앱 경로에서 사용하지 않음(자동 심사 전용). 41GB 확보 |
| mineru-vl(:8010, GPU0) 중지 | OCR 전용, 마지막 사용 당일 02:03. kanana 임시 자리 확보 |
| kanana(:8020) GPU1→GPU0 임시 이동 | 가드레일을 앱 경로에 유지하면서 GPU1 확보 |
| 실험 gemma-4-31B-it 인스턴스(:8100, GPU1, util 0.59) | 운영과 같은 모델·dtype·최대 길이. KV 캐시는 운영(26,464 토큰)보다 작은 20,352 토큰 |

운영 오케스트레이터(:8000, GPU0)와 gpt-oss(:8006), 임베딩, 리랭커, 비교 SFT 모델은
건드리지 않는다. 실험 인스턴스는 조건마다 재시작한다(무추측 → 추측 설정들).

## 4. 실험 단계

1. **오라클 시뮬레이션**: 400문항 × (분류 200, 준비 200) 실제 출력으로 제안 정책
   격자(n-gram 1~12, k 3~24, 최초/최근 위치, 응답 이력 유무)를 시뮬레이션한다.
2. **단계 재생(stage replay)**: 400문항 × 2단계 = 800개 고정 요청을 운영 인스턴스와
   실험 인스턴스에 동시성 4로 재생한다. 16개 요청 묶음마다 조건 순서를 회전·반전하고
   2회 반복한다. 실험 인스턴스는 (a) 무추측, (b) vLLM 기본 n-gram 설정,
   (c) 시뮬레이션이 고른 설정, (d) 응답 이력 결합 설정 순으로 바꿔 측정하며,
   운영 인스턴스는 모든 국면에서 함께 측정해 시간대 변동의 대조군으로 쓴다.
   요청 시작부터 전체 응답 수신까지의 시간, 출력 토큰 수, 정규화 JSON 일치,
   서버 카운터(초안 토큰·수락 토큰·선점·prefix cache)를 기록한다.
3. **검색 정확도**: 각 조건의 준비 단계 출력을 앱의 후처리·하이브리드 검색·
   인증 리랭커에 그대로 통과시켜 출처 라벨(법령 240, 조문 131)로 Hit@1/5/20·MRR@20을
   계산한다. 정규화 출력이 같으면 검색을 공유하므로 추출 차이만 검색 차이를 만든다.
4. **종단(E2E)**: 고정 앱 복사본 3개 프로세스(원래 프록시 경로 / 운영 인스턴스 직접 /
   실험 인스턴스 직접)에 400문항 스트리밍 요청을 동시성 4로 보내 전체 지연·첫 답변
   지연·반환 근거의 출처 포함률·baseline 문서 ID Recall을 비교한다.
5. **원상복구와 감사**: 실험 프로세스 종료, 중지한 모델을 저장된 명령·환경으로
   원래 GPU에 재기동, 전 포트 응답 확인, GPU 메모리 비교.

## 5. 지표와 통계

지연은 평균·p50·p95·p99, 질문 단위 짝지은 bootstrap 4,000회의 95% 신뢰구간(평균의
비율). 출력 일치는 정규화 JSON의 해시 일치율이며, 같은 조건 두 반복의 일치율을 자연
변동 기준으로 함께 보고한다. 검색은 출처 라벨 Hit@k·MRR, McNemar 정확 검정.
수락률은 서버 카운터의 (수락 토큰 ÷ 초안 토큰)이며 시뮬레이션 수락률과 대조한다.
전문가 정답률은 측정하지 않는다.

## 6. 하지 않는 것

fp8·TP·draft 모델 추측 디코딩(gemma-4 multimodal 제약으로 불가)은 범위 밖이다.
