# 호출 제한 없는 CoT 비교 실험

2026-09-11 사용자 요청에 따른 실행 계획. 앞선 코드 변경의 실제 GPU 성능과 답변 품질을
측정한다. 두 조건 모두 전역 HTTP·생성·모델 예산·클라이언트 admission queue가 없다.
부하 생성기의 사용자 수는 실험 조건이며 앱의 호출 상한으로 전달하지 않는다.

| 조건 | 모델 호출·전송 | reasoning 설정 |
|---|---|---|
| baseline | 동일 프록시, 생성 옵션 전달 수정, SDK 종료 처리, 즉시 전송 | 기존 모델 기본값, 관측만 |
| reasoning | baseline과 동일 | worker agent low, 첫 유효 출력 60초, 답변 전 reasoning 32,768자 |

모델·검색·프롬프트·최대 출력 토큰은 두 조건에서 동일하다. 낮은 추론량 및 장기화 종료의
복합 효과를 비교하며 두 요소 각각의 독립 기여를 주장하지 않는다. 종료 실패가 빨라진 것을
정상 답변의 가속으로 계산하지 않는다. 상위 앱의 fallback과 미완료 모델 스트림도 별도 집계한다.

## 실행 순서

1. 현재 앱 소스·유효 설정, GPU 모델 health·프로세스, 검색·DB 연결을 확인한다.
   기존 배포는 유지하고 별도 loopback 앱만 실행한다. 현재 소스가 가정한 hook·queue
   인터페이스와 다르면 수정·검증 후 새 동결본을 만들고 이전 준비 기록은 보존한다.
2. 9월 9일 재개 실험의 300문항을 ID와 질문 해시로 동일하게 고정한다.
   남은 질문에서 seed 20260911로 8문항을 선정해 두 조건을 U1로 점검한다(16요청).
   질문·답변 원문은 0600의 비공개 파일에만 저장한다.
3. 점검 통과 후 300문항 × 2조건 × U1/2/4/8/16/32 × 2반복 = **7,200요청**을 실행한다.
   같은 문항 순서를 사용하고 조건 순서를 부하·반복별로 회전하며 둘째 반복은 부하 순서를
   반대로 한다. smoke와 본 실험은 파일·통계에서 분리한다.
4. 모든 요청의 완료 또는 240초 기한까지의 관측시간을 보존한다. 실패를 삭제·재시도하여
   성공 자료로 바꾸지 않는다. 모델 health 연속 실패·OOM·앱이 취소 후에도 남는 경우에는
   해당 실험 프로세스만 중단한다. 운영 모델·배포의 자동 재시작은 수행하지 않는다.
5. 첫 반복의 참조 답변 문항을 기존 별도 모델 판정기로 조건명을 숨겨 평가한다.
   빈 답변과 판정기 오류를 구분하며 전문가 정확도 동등성으로 표현하지 않는다.

## 분석

평균·p95·첫 답변 시간·성공률·30초 내 성공률, 완료/실패를 나눈 지연, 출처 적중,
답변 관련성·근거 충실성을 보고한다. 같은 질문의 반복을 묶은 paired bootstrap을 사용한다.
reasoning 문자 수, 첫 reasoning과 첫 답변 간 관측시간, 장기화 중단 수, 정상 종료·잘림을
모델별로 집계한다. 서버 queue/prefill/decode·KV·선점은 공유 인스턴스 통계로 표시한다.

응답 성공률이나 답변 품질이 낮아지면 단순 지연 감소를 개선으로 채택하지 않는다.
과거 300문항의 측정값과 이번 결과를 합산하지 않는다. 기존 회귀 질문이며 독립 holdout은 아니다.

## 환경 확인과 사전 점검

사용자가 제공한 인증으로 GPU 서버 접속을 확보했다. 이전 300문항 실험의 앱 소스
124개 파일과 동일한 복사본을 사용한다. 운영 pod의 새 snapshot은 아니다. GPU 호스트의
기존 앱 설정으로 검색·DB 연결을 검증했으며 검색 문서 수는 454,351/3,194,294/19,583이다.
H200 NVL 두 장과 기존 모델 프로세스 8개를 확인했고 모델 health는 정상이다.

첫 사전 점검은 SSE 16요청 모두 완료했고 두 앱 모두 실행·대기 0으로 정리됐다.
그러나 내부 오류 대조에서 개선 조건 8건 모두 `BadRequestError` 및 fallback이 발견됐다.
LiteLLM이 gpt-oss의 `reasoning_effort`를 지원 옵션으로 인식하지 못한 것이 원인이다.
이때의 평균 10.72→7.38초 차이는 성능 개선으로 채택하지 않는다.

프록시 요청에 `allowed_openai_params=["reasoning_effort"]`를 명시하는 호환성 수정을
추가했다. 운영 프록시 설정이나 추론량·시간·문자 기준은 변경하지 않았다. 단독 API
검증에서 HTTP 200과 정상 종료를 확인한 뒤 같은 8문항을 두 조건에서 다시 점검한다.
첫 점검 자료는 `smoke-validation`, 호환성 수정 후 점검은 `smoke-verified`로 분리한다.
본 실험은 두 번째 점검의 SSE 완료·내부 오류·잔여 작업 검사를 모두 통과해야 시작한다.

첫 앱 시작 시 상대 경로를 전달한 두 프로세스는 추론 요청 전에 종료됐으며 기록은
보존했다. 절대 경로로 시작한 앱에서 점검을 수행했다. 실험 인증정보는 공개 코드나
결과에 포함하지 않는다. 동결된 추론 정책과 질문은 점검 결과로 재조정하지 않는다.
