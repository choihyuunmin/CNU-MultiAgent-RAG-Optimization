# 관측 가능한 CoT·워크플로 기반 정확도 우선 어댑터

2026-09-08. 목표는 **다중 에이전트의 실제 실행 흐름에서 병목을 찾고, 모델이 수행할
작업의 의미를 보존하면서 실행 방식으로 응답 지연을 줄이는 것**이다. 개별 기법의
실험 나열을 넘어 관측·제어·검증을 하나의 어댑터 인터페이스로 연결한다.

## 1. CoT의 정의와 관측 범위

이 연구에서 워크플로는 분류 → 준비 → 검색 → 재정렬 → 선별 → 답변의 호출 관계다.
모델이 API로 제공하는 reasoning 토큰·문자 수는 별도로 관측한다. 구조화된 모델
호출 시간 전체를 모델 내부 CoT 시간으로 부르지 않는다. reasoning 필드가 없으면
`미관측`이지 `reasoning 0`이라는 증거가 아니다. 어댑터는 숨겨진 사고 과정을 추정하지
않고, reasoning 원문·질문·답변 본문을 새 계측 로그에 저장하지 않는다.

```text
사용자 요청 ─ HTTP 수용/전송 수명 계측 ─ 기존 에이전트 워크플로
                                          │
                         단계 이름·모델 호출·usage 관측
                                          │
                         모델별 동시 호출·토큰 예산 제어
                                          │
                             기존 모델/검색 요청 그대로 실행
                                          │
                    출처 + 답변 정확성/근거성 + 안전성 회귀 평가
                                          │
                           기준 충족 전 운영 적용 보류
```

모델 RPC 구간은 클라이언트에서 본 수명이며 서버 queue/prefill/decode의 인과 분해가
아니다. 병렬 구간은 구간 합집합으로 집계하고 단계별 호출 시간 합계는 `work`로 별도
보고한다. 이를 종단 지연이나 정확한 critical path와 혼동하지 않는다. 앞단 대기는
외부 ASGI 관측과 기존 클라이언트 SSE 이벤트·앱 active/queued를 함께 분석해야 한다.

## 2. 기존 실험을 어댑터 설계에 연결

| 기존 근거 | 병목/주의점 | 통합 어댑터 반영 |
|---|---|---|
| 분류·준비 추측 디코딩 62.7% 단축, U4 종단 2.9% | 단계 가속이 종단 가속을 보장하지 않음 | 단계·모델별 계측과 종단 지표를 분리; 기존 vLLM 제안기는 별도 서빙 계층으로 유지 |
| 작은 모델·호출 융합에서 검색 충실도 저하 | 입력·모델을 바꾸면 의미 변화 가능 | 기본 경로에서 모델 교체·프롬프트 축약·추론량 감소 금지 |
| 이전 typed dispatch·중복 임베딩 병합·연결 재사용 | 일부 불필요 호출/전송 비용 | 기존 `speed` 프로파일을 명시적 복합 대조로 연결; 품질 검증 없이 기본 채택하지 않음 |
| 외부 gate 단축 1.88%/0.67%, CI에 0 포함 | 대기 위치 이동만으로 처리 능력이 늘지 않음 | HTTP 수명과 생성 수명 분리, 외부 대기를 지연에서 빼지 않음 |
| 두 상한 조정, U16 43.60%·U32 49.49% 단축 | HTTP/생성 상한 4의 이중 대기 | 기존 launcher의 두 상한 제어를 동일 진입점에서 사용 |
| 개선 설정 KV 최대 약 99%, RAM 여유 >460GiB | RAM 부족과 KV 압력은 다름 | 모델별 토큰 예약과 신선한 KV/대기/선점 관측에 의한 선실행 허용 조건 |

날짜·경로·워크로드가 다른 개선율을 더하거나 곱하지 않는다. 특히 43.60%·49.49%는
**기존 고정 상한 실험**의 결과이며 새 토큰 예산 정책의 측정 결과가 아니다.

## 3. 구현한 기능과 보존 계약

- `WorkflowAdapter(mode="observe")`: 모델 요청을 변경하지 않는 단계 계측.
- `mode="budget"`: 명시적으로 설정한 모델에만 FIFO 동시 호출·토큰 예산 적용.
  설정하지 않은 모델은 관측만 하므로 모델 별칭과 실제 서빙 배치를 확인해야 한다.
- `TokenReservation`: 입력 전체 + 예상 출력은 논리 KV 예약, 캐시에 없는 입력은
  prefill 예약으로 분리한다. `max_tokens`를 변경하는 출력 제한 기능이 아니다.
  모델별 보수적 추정치이며 물리 KV block/VRAM byte 계산기나 GPU OOM 방지 보장은 아니다.
- 캐시 입력도 KV를 점유하므로 KV 예산에서 빼지 않는다. 긴 요청을 짧은 요청이
  계속 앞지르지 않도록 FIFO를 사용한다. aging/짧은 작업 우선은 아직 구현하지 않았다.
- 예산 초과·토큰 추정 미제공 요청은 예산 전체를 점유해 단독 실행한다. 요청·문맥을
  자르거나 무기한 대기시키지 않는다. 실제 서버 context 한도를 초과하면 기존 오류가 전달된다.
- 비스트리밍 호출은 RPC 반환 시 슬롯 반환. 스트리밍은 원본 iterator 종료/close까지
  보유한다. 소비자 backpressure도 이 수명에 포함하며 무제한 선읽기를 하지 않는다.
- `verified_overlap`: 명시적 read-only 호출만 선실행. 모델/버전·전체 messages/history·
  옵션·tools·근거 내용·tenant 권한 범위를 포함한 전체 입력의 정확한 일치를 확인한다.
  문서 ID만 같은 경우는 재사용 조건이 아니다. 불일치·초안 오류 시 권위 경로 실행,
  취소·예외 때 시작한 작업을 회수한다. 상태 변경 도구 호출에는 사용하지 않는다.
- 선실행은 새 KV/queue/preemption-delta 관측이 건강하고 예약 공간이 있으며 앞선
  정상 대기 요청이 없을 때만 허용한다. 누락·오래된 표본·고압력은 선실행 금지다.
  실행 중인 정상 요청의 추론을 자르거나 취소하는 정책은 아니다.

현재 MOLEG bridge는 명시적 `serving_meter` 설정으로 오케스트레이터의 실제 서빙
tokenizer와 KV/queue/선점 계측에 연결된다. 모델 입력/옵션은 그대로 전달하며 계측
실패 시 보수적인 단독 실행으로 전환한다. 다른 모델까지 예산을 자동 추정하지는 않는다.
generic API의 압력 기반 선실행은 별개 기능이며 MOLEG launcher에서 자동 활성화하지 않는다.
기존 `speed`의 자원 관측 없는 준비 선실행도 통합 모드에서는 꺼서 우회 실행을 막는다.
새 API를 앱에 연결할 때 `invoke`는 같은 gate를 중첩하지 않는 원래 모델 RPC여야 한다.

모든 gate는 앱 프로세스 내부 제어다. 여러 K8s replica 사이의 GPU 전체 예산을 보장하지
않는다. 그런 배포에는 중앙 제어 또는 공유 예산이 별도로 필요하다.

## 4. 정확도 유지 판단

`quality_gate.py`는 실행 성공, 출처 적중, 답변 정확성, 근거 충실성, 가드레일 회귀를
분리한다. 같은 질문별 쌍의 후보−기준 차이 신뢰구간 하한을 사전 비열등성 한계와 비교한다.
독립 holdout·블라인드 전문가 답변 평가·사전 기준이 없으면 release를 거절한다.
기본 한계 0 및 최소 100개 고유 질문은 보수적 템플릿이지 표본수 검정력 계산이 아니다.
실험 전에 도메인별 허용 한계와 필요한 표본수를 정해야 한다.

이 게이트는 평가 결과를 소비할 뿐 전문가를 대신 평가하지 않는다. 출처 포함이 같거나
모델 입력이 같다는 이유만으로 정확도가 유지됐다고 판단하지 않는다. 저장된 64문항
반복 검증을 넣은 현재 판정은 **release_allowed=false**다. 이는 기존 측정이 실패했다는
뜻이 아니라 새 통합판의 정확도 보존을 주장할 근거가 아직 충분하지 않다는 뜻이다.

## 5. 실행 진입점

라이브러리만 사용하는 예제(외부 호출 없음):

```bash
.venv/bin/python examples/workflow_adapter.py
```

기존 격리 앱 launcher에 아래 옵션을 추가하면 현재 payload를 유지한 관측 모드다.
기존 필수 `--app-root`, `--app-env`, `--serving-env`, `--proxy-config`, `--trace`는
운영자가 보관한 파일 경로로 제공한다. 새 프로세스에서 한 번만 설치한다.

```text
--adapter-config integrations/2025-moleg-search/workflow-observe.json
--adapter-trace /operator-owned-private-run/workflow.jsonl
--max-pipelines 4 --max-http 4 --emission original
```

이후 대조에서 `--max-pipelines 16 --max-http 16 --emission immediate`로 고정 설정을
재현한다. 16을 무조건 안전한 운영 기본값으로 선택한 것은 아니다. 별도 프로파일
`--base-profile speed`는 과거 앱 최적화를 결합하는 탐색적 조건이며 baseline과
동일한 모델 요청·검색 결과를 보증하지 않는다. 이전 날짜의 `speed`와도 준비 선실행
활성 여부가 다르므로 같은 조건명만 보고 데이터를 합치지 않는다.

예산 모드는 별도 설정 JSON에 `mode=budget`, 모델별 `budgets`와 선택적 `reservations`를
명시한다. 추정치를 제공하지 않으면 해당 모델 요청은 단독 실행하므로 성능이 저하될 수 있다.
고정 예약 추정은 실제 입력의 정확한 토큰화가 아니다. 실험 전 별도 개발 세트에서
보수적으로 보정하고 실제 usage를 함께 검증한다. 단계 hook은 확인된 async 함수만
명시하며 모르는 단계는 `unclassified`로 남긴다. 호출 순번/프롬프트 내용으로 추측하지 않는다.

새 trace는 보호된 0600 파일이다. 기존 `--trace`의 paper trace는 답변 원문을 포함할 수
있어 계속 비공개로 취급한다. 운영 K8s/vLLM을 수정하거나 재시작하는 명령은 포함하지 않는다.

## 6. CPU 계약 검증과 GPU 비교를 구분

최초 통합 구현에서 단위/통합 계약 검사와 **CPU 합성 요청 768회**를 수행했다.
64 fixture × 사용자 상한 1/2/4/8/16/32 × observe/budget이며 payload·출력 문자·순서
보존 및 슬롯 반환을 검사했다. reasoning 단축이나 GPU 속도/정확도 실험이 아니다.
[검증 산출물](../experiments/results/workflow-adapter-20260908/offline-contracts.json).

후속 GPU 실험은 같은 현재 모델·프롬프트·검색·인증·답변 제한을 모든 조건에서 고정한다.

| 조건 | 변경 | 검증할 질문 |
|---|---|---|
| A | 기존 4/4 + 관측 어댑터 | 계측 오버헤드와 현재 기준 |
| B | 16/16 + 즉시 전송 + 관측 어댑터 | 과거 고정 설정 개선 재현 |
| C | B + 모델별 토큰 예산 | KV 압력/긴 꼬리 완화의 추가 효과 |
| D | C + 완전 입력 일치·압력 기반 선실행 | 추가 작업 비용 대비 종단 이득 |
| E, 별도 대조 | D + 기존 서버 추측 디코딩 제안기 | 단계 가속과 전체 처리량의 결합 효과 |

C/D 예산·임계값은 개발 질문에서 고정한 뒤 새 holdout의 U1/2/4/8/16/32를 반복·역순
교차한다. 64문항의 같은 질문 반복만으로 외적 타당성을 주장하지 않는다. 사용자를
100명 이상으로 늘리기 전에 U32의 30초 목표 미달과 KV 여유를 먼저 재검증한다.
최종 후보는 평균/p95/TTFT/30초 goodput뿐 아니라 실패·취소된 선실행·출력 길이·출처·
전문가 답변·안전 회귀를 모두 평가한다.

9월 8일 후속 실행은 위 전체 확장안의 첫 단계로 A/B/C의 U16/32에 한정한다.
개발 32문항에서 예산을 고정하고 별도 64문항으로 768회 비교하며, D/E는 실행하지 않는다.
진행 조건은 [실제 GPU 사전 계획](WORKFLOW_GPU_PROTOCOL_20260908.md)에 명시했다.

실제 실행은 U16 첫 반복 192회에서 C의 timeout 1건으로 중단됐다. KV 압력은 줄었으나
B 대비 추가 가속·신뢰성 기준을 통과하지 못했고 워커의 답변 전 reasoning 장기화를
관측했다. U32·둘째 반복은 미실행이며 C를 기본 정책으로 승격하지 않는다.
[실제 GPU 결과와 어댑터 후속 판단](WORKFLOW_GPU_RESULTS_20260908.md)을 참조한다.
