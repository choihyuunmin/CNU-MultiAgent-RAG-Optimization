같았다(McNemar 불일치 0/0). 단일 사용자 종단 40문항의 반환 문서는 완전히 같았다.

방법의 새로운 점은 세 가지다. (1) 실제 프롬프트·출력 로그로 제안 정책의 검증 단계 수를
GPU 없이 정확히 계산하는 오라클 시뮬레이션으로 정책을 고른다(vLLM 기본 설정 대비 이상
배속 2.0/2.3배 → 4.7/4.9배). (2) 단계별 응답 이력(다른 질문의 과거 출력)을 프롬프트 조회와
결합해 더 긴 일치를 택하는 제안기를 vLLM 플러그인으로 구현했다(엔진·모델 수정 없음,
2겹 교차로 누수 차단). (3) 서비스 수준에서 KV 용량·대기열 선두 차단·병목 이동이라는
배치 함정을 실측으로 분리했다: 추측 디코딩은 같은 GPU 예산에서 KV를 21% 줄이며, 초장문
프롬프트가 있으면 동시 사용자 전체가 2분 멈출 수 있고, 오케스트레이터가 빨라지면 동시
부하에서 워커(gpt-oss, 동시 4 상한)가 새 병목이 된다.

네트워크 기술: 전달 경로(ingress·오버레이·NodePort) 오버헤드는 1~2 ms이고 스트리밍
버퍼링도 없어 전달 계층은 병목이 아니다. 복제본 부하분산은 이질 복제본에서 지연 인지
라우팅이 최소 미처리 정책보다 6.7% 나았지만, 빠른 복제본이 포화되기 전에는 서빙 가속
단독보다 못했다.

## 2. 오라클 시뮬레이션: 제안 정책별 이상 배속 (GPU 미사용)

400문항 × 2단계(분류 200, 준비 200)의 실제 프롬프트(챗 템플릿 적용 후 토큰화, 평균
4,097 / 3,577 토큰)와 운영 모델의 실제 탐욕 출력(평균 25.4 / 137.5 토큰)을 사용했다.
재토큰화한 출력 길이는 서버가 보고한 completion_tokens와 400건 모두 정확히 같았다.
표의 값은 (출력 토큰 수 ÷ 검증 단계 수)의 합산 비율이며, 검증 단계당 비용이 일정하다는
가정하의 상한이다.

| 제안 정책 | 분류 | 준비 | 수락률(분류/준비) |
|---|---:|---:|---|
| 프롬프트 조회, n-gram 2–4, k=5, 최초 위치 (vLLM 기본형) | 2.02 | 2.29 | 0.42 / 0.41 |
| 프롬프트 조회, 1–3, k=12 | 2.47 | 3.32 | 0.18 / 0.21 |
| 프롬프트 조회, 2–8, k=12 | 2.18 | 2.97 | 0.23 / 0.31 |
| 프롬프트 조회, 2–8, k=16 | 2.18 | 3.05 | 0.18 / 0.25 |
| 프롬프트 조회 실패 시 응답 이력 조회, 2–8, k=12 | 3.94 | 4.34 | 0.49 / 0.36 |
| 프롬프트 조회 실패 시 응답 이력 조회, 2–8, k=16 | 3.97 | 4.73 | 0.41 / 0.31 |
| 더 긴 일치 우선(프롬프트·이력 중 긴 n-gram), 2–8, k=16 | **4.74** | **4.91** | 0.56 / 0.34 |

관찰:
- 같은 n-gram이 여러 번 나올 때 최초 위치를 쓰는 vLLM 기본 방식이 최근 위치보다
  대체로 나았다(분류에서 특히). 최근 위치 방식은 채택하지 않았다.
- k를 5에서 12~16으로 올리면 준비 단계의 상한이 크게 오른다. 준비 출력이 질문의
  긴 구절을 그대로 복사하기 때문이다. 분류 단계는 k≥8에서 포화한다.
- 응답 이력(다른 질문의 출력, 자기 출력 제외)을 결합하면 분류 단계 상한이 약 2배가
  된다. 분류 출력의 골격(`{"task": "law_search", "confidence": "HIGH", ...`)은
  프롬프트에 그대로 없지만 이력에는 늘 있기 때문이다.
- 실측에는 검증 비용이 더해지므로 이 상한이 그대로 나오지 않는다(아래 절 참조).

## 5. 종단(E2E) 400문항

### 5.1 첫 종단 실행(홀수 겹 200문항)에서 드러난 배치 함정: 초안 버퍼가 줄인 KV 용량과 대기열 선두 차단

첫 종단 실행은 국면 4a의 실험 인스턴스(util 0.59, KV 16,016 토큰)로 수행했다.
세 조건(원래 프록시 경로 `orig`, 운영 인스턴스 직접 `direct`, 실험 인스턴스 `spec`)
모두 200/200 HTTP 성공이었지만, `spec` 조건의 평균 지연은 19.11초로 `orig` 14.02초보다
느렸다. 반면 p50은 11.52초 vs 12.00초, 60초 미만 요청만의 평균은 13.15초 vs 13.76초로
`spec`이 약간 빨랐다. 차이는 100초 이상 걸린 요청이 `spec`에 10건, `direct` 1건, `orig`
0건 있었다는 데서 나왔다.

원인 추적 결과는 다음과 같다.
- 지연 100초 이상 요청은 4개 묶음(동시 8요청 단위)에 몰려 있었고, 각 묶음에는
  선별(select) 단계 프롬프트가 16,016 토큰을 넘는 질문이 정확히 하나씩 있었다
  (q347 19,318 / q141 18,584 / q223 17,730 / q169 19,795 토큰; 원래 경로 기준).
- 실험 인스턴스 로그는 해당 시각에 "Running: 0, Waiting: 3, KV 0%" 상태로 약 110초간
  정지했다. vLLM V1 스케줄러는 KV 캐시 전체보다 긴 프롬프트를 배치할 수 없으면
  대기열 선두에서 멈추고 그 뒤의 정상 요청(4,100토큰짜리 분류 호출 포함)까지 함께
  기다리게 한다(head-of-line blocking). 클라이언트 타임아웃(120초)으로 선두 요청이
  취소된 뒤에야 나머지가 처리되었다. 같은 묶음의 다른 질문들이 116~119초 만에
  "성공"한 것이 그 흔적이다.
- 앱은 타임아웃 후 후보를 줄여 재시도했고, 그 결과 4문항에서 출처 조문이 반환
  근거에서 빠졌다(0.906 → 0.844). 즉 정확도 하락도 이 배치 함정의 결과이지 추측
  디코딩의 출력 변화가 아니다.
- 운영 인스턴스는 KV가 26,464 토큰이라 같은 프롬프트를 처리했다. 실험 인스턴스는
  같은 util 0.59에서도 추측 디코딩의 초안 검증 버퍼 때문에 무추측 인스턴스(20,352
  토큰)보다 KV가 21% 작았다.

교훈: 추측 디코딩은 같은 GPU 예산에서 KV 용량을 줄이며, 이 시스템처럼 검색 결과를
프롬프트에 넣는 단계가 있으면 드물게 나타나는 초장문 프롬프트가 모든 동시 사용자를
2분간 멈추게 할 수 있다. 첫 실행 자료는 `e2e_odd.jsonl`로 보존하되 본 종단 결과로
쓰지 않고, gpt-oss의 KV 예산을 일시 축소(0.33→0.24)해 실험 인스턴스에 운영과 같은
KV 용량(util 0.65, `--max-num-seqs 64`)을 준 뒤 두 겹 모두 다시 측정했다.

### 5.2 종단 재실행 (실험 인스턴스 KV 32,352 토큰, 400문항, 동시성 4, 1회)

gpt-oss의 KV 예산을 0.33→0.24로 일시 축소해 확보한 메모리로 실험 인스턴스를

## 6. 네트워크 기술 접목: 경로 오버헤드, 복제본 부하분산, 스트리밍 전달

### 6.1 전달 경로 오버헤드 (무추론, .52 → .53 백엔드 pod)

.52(UI 호스트)에서 백엔드의 `/docs`를 네 경로로 각 200회 호출했다(연결 재사용/신규
연결 교대). 경로는 ingress-nginx(.52:80) → Calico VXLAN → pod, NodePort(.53:31800,
kube-proxy), ClusterIP(<cluster-ip>:28000), pod IP 직결(<pod-ip>:28000)이다.

| 경로 | 재사용 연결 p50 | 신규 연결 p50 |
|---|---:|---:|
| ingress-nginx | 1.05 ms | 1.25 ms |
| NodePort | 0.98 ms | 1.70 ms |
| ClusterIP | 1.05 ms | 1.60 ms |
| pod IP(VXLAN) | 1.05 ms | 1.70 ms |

어느 경로든 왕복 1~2 ms로, 수 초 단위 응답에서 전달 경로 자체는 병목이 아니다.
앞선 실험의 gzip 압축(−0.47 ms)·프록시 우회(7%)·앞단 동시 요청 제한(역효과)과 함께,
이 시스템에서 네트워크 기술의 이득은 "바이트·홉 줄이기"가 아니라 아래의 복제·라우팅·
스트리밍 전달에서 찾아야 함을 뜻한다.

### 6.2 복제본 L7 부하분산 (동시성 16, 홀수 겹 400요청)

운영 인스턴스(:8000)와 이력 결합 추측 인스턴스(:8100) 앞에 최소 미처리 요청
(least-outstanding) 게이트웨이를 두고, 단일 인스턴스 조건과 비교했다.

| 조건 | 분류 평균 | 준비 평균 | 전체 평균 | 전체 p95 | 묶음 처리율 |
|---|---:|---:|---:|---:|---:|
| 운영 인스턴스 단독 | 0.973초 | 3.970초 | 2.472초 | 5.022초 | 4.56 req/s |

| 부하분산(운영+추측) | 0.523초 | 2.101초 | 1.312초 | 3.611초 | 7.00 req/s |

- 동시성 16에서도 추측 인스턴스 단독은 운영 대비 2.05배(51.3% 단축, CI 49.4–53.0)로,
  동시성 4의 2.68배보다 작지만 처리율은 2배가 됐다. 검증 단계의 추가 계산이 부하가
  클수록 무료가 아니기 때문이다(디코드가 대역폭 한계에서 계산 한계로 이동).
- 부하분산은 두 복제본의 개별 서비스 시간을 모두 줄였다(게이트웨이 기록: 운영 2.47→1.97초,
  추측 1.20→0.83초; 요청은 160:242로 빠른 쪽에 더 많이 배정). 그러나 묶음 완료 시간은
  느린 복제본에 배정된 요청이 결정하므로, 전체 평균·p95·묶음 처리율은 추측 인스턴스
  단독보다 나빴다. 이질적 복제본에서는 미처리 수만 보는 정책이 꼬리에 불리하다는 뜻이며,
  복제본별 서비스 시간(EWMA)을 고려한 비용 기반 라우팅을 추가 비교한다(6.3).
- 출력 일치: 분류 200/200, 준비 184/200(부하분산)·185/200(추측 단독)으로 동시성 4와 같다.

| 추측 인스턴스 단독 | 1.081초 | 2.555초 | 9.86 req/s | — | — | — |
| 최소 미처리 요청 LB | 1.287초 | 3.737초 | 6.68 req/s | 157:244 | 1.997초 | 0.792초 |
| EWMA 비용 LB | 1.201초 | 3.400초 | 7.37 req/s | 115:287 | 1.863초 | 0.900초 |

지연 인지 정책은 느린 복제본 배정을 39%에서 28%로 줄여 최소 미처리 요청 정책보다 평균
6.7%·p95 9% 개선했지만, 여전히 빠른 복제본 단독보다 11% 느렸다(CI −16.2~−6.1%).
해석: 디코드가 대역폭 한계인 큰 모델은 배치가 동시성 16을 흡수하므로 빠른 복제본 하나가
포화되지 않았고, 이 상태에서 2배 느린 복제본을 풀에 넣으면 그쪽에 배정된 요청이 꼬리를
만든다. 복제본 추가는 빠른 복제본이 포화되는 부하(더 큰 동시성·지속 유입)에서만 이득이며,
그 전까지는 서빙 가속(추측 디코딩)이 네트워크 계층의 복제·부하분산보다 우선한다.
이질 복제본 환경에서는 지연 인지 라우팅이 필수이고, 동질 복제본·개방 루프 유입에 대한
측정은 후속 과제다.

### 6.4 스트리밍 전달 경로: ingress-nginx vs NodePort vs pod 직결 (실제 요청 12문항 × 3경로)

.52에서 같은 12개 질문을 세 경로로 회전 순서로 보내 SSE 스트림의 첫 바이트·첫 이벤트·
첫 답변 토큰·청크 간격을 기록했다(운영 백엔드 pod 사용, 36요청 모두 200).

| 경로 | 첫 바이트 p50 | 첫 이벤트 p50 | 청크 간격 p50 | 수신 청크 수 / 이벤트 수 |
|---|---:|---:|---:|---:|
| ingress-nginx(.52) → VXLAN → pod | 7 ms | 7 ms | 3.8 ms | 219 / 256 |
| NodePort(.53:31800) | 6 ms | 6 ms | 3.8 ms | 215 / 213 |
| pod IP 직결 | 6 ms | 6 ms | 3.8 ms | 267 / 266 |

ingress 경로에서도 첫 이벤트가 7 ms에 도착하고 청크가 이벤트 단위로 흘러(버퍼링·병합
없음), 같은 질문의 경로 간 TTFT·전체 시간 차이의 중앙값은 0.2초 이내로 모델 추론의
자연 변동 안이었다. 즉 이 배포의 ingress·오버레이는 스트리밍 체감 지연에 영향을 주지
않으며, 네트워크 전달 계층은 "문제 없음"으로 확정할 수 있다. 이는 네트워크 기술의
기여가 전달이 아니라 복제·라우팅·큐잉(6.2~6.3, 5.1)에 있어야 한다는 결론을 뒷받침한다.

## 7. 다른 모델 계열로의 전이 (gpt-oss-20b): 적용 경계의 실측

같은 800개 구조화 요청(메시지·응답 형식·temperature 0 동일, `reasoning_effort=low`)을
전혀 다른 계열의 워커 모델 gpt-oss-20b(MoE, o200k 토크나이저, 초당 약 240토큰)에 보내
같은 절차로 측정했다. 비교 기준은 운영 gpt-oss 인스턴스(:8006, 실험 동안 KV 예산 축소
상태)이고, 실험 인스턴스(:8101)는 같은 인자에 추측 설정만 추가했다.

**T1. 튜닝 프롬프트 조회(2–8, k=16), 800요청 × 2조건**

| 조건 | 분류 평균 | 준비 평균 | 전체 평균 | 출력 토큰(분류/준비) | 추론 문자(분류/준비) |
|---|---:|---:|---:|---:|---:|
| gpt-oss 운영 | 0.468초 | 2.043초 | 1.255초 | 82.7 / 412.6 | 193 / 770 |
| gpt-oss + 추측 | 0.665초 | 1.901초 | 1.283초 | 86.3 / 414.2 | 206 / 768 |

분류는 **42% 느려졌고**(CI −46.6~−37.9%), 준비는 6.9% 빨라졌으며(CI 3.7–10.5), 전체는
−2.2%(CI −5.3~+1.1)로 이득이 없었다. 수락률 0.19(gemma 0.36), 초안당 수락 2.8토큰.
원인은 두 가지가 겹친다. (1) 출력의 대부분이 JSON이 아니라 자유 서술 추론 토큰이다
(완료 토큰 83/413개 중 JSON은 gemma와 같은 26/139개 수준). 추론 토큰은 프롬프트에도
이력에도 없어 제안이 거의 맞지 않고, 검증 단계의 추가 계산과 비동기 스케줄링 해제 비용만
남는다. (2) 이 모델은 이미 초당 240토큰으로 디코드하므로 단계당 절약 폭이 작다.
같은 조건 반복 출력 일치는 분류 390/400, 준비 133/400으로, 추론을 동반한 출력은
temperature 0에서도 매우 불안정했다. 이 결과는 방법의 적용 경계를 정한다:
**구조화·복사 위주 출력을 내는 디코드 한계형 대형 모델의 단계**에 적용해야 하며, 추론
토큰이 긴 단계나 이미 빠른 소형 모델에는 적용하지 않는 것이 맞다(단계별 선택 적용).

**T2. 응답 이력 결합(gpt-oss 자기 출력의 짝수 겹 이력, 홀수 겹 400요청)**

분류 −21.2%(CI −25.6~−16.7), 준비 +2.3%(CI −1.3~+5.8), 전체 −2.0%(CI −5.2~+1.0).
이력 초안은 15,400회 제안 중 4,096회(그중 프롬프트보다 긴 일치 1,405회)에 그쳤고
제안 없음이 32,796회였다. 추론 토큰이 이력에 없기 때문이다. gemma 오케스트레이터에서
2.66배를 낸 같은 플러그인·정책이 이 모델에서는 이득이 없으므로, 방법은 모델 무관하게
동작하지만 **이득은 단계 출력의 구조와 모델의 디코드 속도에 달려 있다**. 논문에서는
이 경계를 조건으로 명시하고 단계별 선택 적용(프롬프트 해시 기반 라우팅)을 권고한다.

## 8. 기여, 한계, 재현

### 기여로 제시할 수 있는 것
1. **로그 기반 오라클 시뮬레이션에 의한 제안 정책 선택**: 탐욕 디코딩의 결정성을 이용해
   실제 프롬프트·출력 400건으로 검증 단계 수를 GPU 없이 정확히 계산하고, 그 순위가 실측
   순위와 일치함을 보였다(기본형 1.56배 < 튜닝 1.94배 < 이력 결합 2.68배). 실측/상한 비율
   (56~70%)은 검증 단계의 추가 비용을 정량화한다.
2. **단계별 응답 이력 결합 제안기**: 프롬프트에 없는 JSON 골격을 다른 질문의 과거 출력에서
   가져와, 프롬프트 조회와 이력 조회 중 더 긴 n-gram 일치를 택한다. vLLM 일반 플러그인으로
   엔진·모델 수정 없이 동작하며, 2겹 교차로 자기 출력 참조를 배제한 상태에서 분류 단계
   배속을 1.45배에서 2.66배로 끌어올렸다.
3. **정확도 보존의 다층 검증**: 출력 해시 일치율을 같은 서버 반복 호출의 자연 변동과
   비교하고, 출력이 달라진 질문의 문서 집합 변화를 자연 변동과 비교하며, 출처 라벨 검색
   지표와 종단 반환 근거까지 확인했다.
4. **배치 함정의 실측 분리**: 추측 디코딩의 KV 용량 감소 → 초장문 프롬프트의 대기열 선두
   차단 → 동시 사용자 전체 정지(2분), 그리고 오케스트레이터 가속 → 워커 병목 이동 →
   동시 부하 종단 이득 축소. 둘 다 단계별 실행 로그와 서버 카운터로 원인을 확정했다.
5. **네트워크 계층의 위치 확정**: 전달 경로·스트리밍 버퍼링은 병목이 아니며(1~2 ms,
   버퍼링 없음), 복제·부하분산은 빠른 복제본이 포화되기 전에는 서빙 가속을 이기지 못하고
   이질 복제본에서는 지연 인지 라우팅이 필요함을 실측했다.

### 한계
- 라벨은 출처 기반 silver known-item이며 전문가 정답률·전체 관련 문서 Recall이 아니다.
- 동시성 4 종단은 1회 반복이고 앱 자체의 긴 꼬리(워커 생성 40초 이상)가 평균을 흔든다.
- 응답 이력은 200문항 출력으로 만들었고 운영에서는 이력 누적·갱신 정책이 필요하다.
  샘플링 온도 사용, 자유 서술 출력, 작은 모델에서는 이득이 줄어든다.
- 실험 인스턴스는 운영과 GPU·KV 용량이 달랐고(전용 무추측 인스턴스가 운영보다 2% 느림),
  이를 보수적으로 포함한 채 배속을 보고했다. gpt-oss는 전이 실험 동안 KV 예산이 축소됐다.
- 부하분산 시험은 이질 복제본·닫힌 루프 묶음 방식이며 개방 루프 유입·동질 복제본 결과가 아니다.
