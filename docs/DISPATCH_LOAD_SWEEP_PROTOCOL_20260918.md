# 직접 디스패치 부하 스윕 프로토콜 (2026-09-18)

## 목적

준비된 검색 인자를 모델이 다시 쓰는 호출(검색 재작성)을 없애는 직접 디스패치가 **부하가 높아질 때**
사용자 응답시간을 줄이는지 확인한다. 동시성 4의 3라운드 실험(`cnu-review-20260916`)에서는 브랜치당
약 0.54초의 국소 절감과 워커 엔진 요청 41% 감소가 확인됐지만 종단 응답시간 차이는 잡음 안에 있었다.
09-13/14 단일 패스 스윕(C=1·2·5·10·20·50·100)은 C=20에서 5.4% 단축을 보였으나 C≥50에서는 먼저 실행된
arm이 빨라지는 순서 교란이 있었다. 이 실험은 같은 수준을 **회전 순서**로 반복해 순서 교란을 제거한다.

## 설계

| 항목 | 값 |
|---|---|
| arm | `original`(모델 재작성), `capability`(HMAC 서명 직접 디스패치). `direct` 파드는 준비만 함 |
| 동시성 수준 | 8, 16, 32, 64, 100 |
| 라운드 | 수준당 2회, 순서 회전 (원본→어댑터, 어댑터→원본) |
| 셀 | 동결 질문 200개, 닫힌 루프, 시드 20260912 |
| 요청 타임아웃 | 600초 (09-13/14 스윕과 동일) |
| 앱 인스턴스 | 동결 이미지 `localhost/moleg-rag@sha256:3fb707…`, CPU 2·메모리 8 GiB, 대기열 상한 100 (`serve_sweep.py`, `MAX_CONCURRENT_GENERATE_REQUESTS=100`) |
| 부하 클라이언트 | 별도 파드(CPU 2·2 GiB), `run_rag_experiment.py` |
| 계측 | 클라이언트 요청 기록, 앱 브랜치 추적(준비/실행 인자 해시, 핸들러·비핸들러 시간, 출력 해시), vLLM 엔진 카운터 1초 샘플 |
| 안전 정지 | 엔진 텔레메트리 손실 또는 대기 >256 30초, 최근 20건 중 4건 실패, 무진행 300초, 셀 3,600초 |
| 총 요청 | 2 arm × 5 수준 × 2 라운드 × 200 = 4,000 |

모델·엔진·프롬프트·검색 데이터는 바꾸지 않았다. 파드는 GPU 노드(moleg-gpu)에 배치되며 프로덕션과 엔진을 공유한다.

## 실행

`docs/paper-draft-20260917/sweep/`의 스크립트로 매니페스트를 만들고(`make_sweep_manifest.py`), moleg-app에서
`sudo kubectl apply -f sweep.private.json` 후 `sudo python3 launch_sweep_remote.py --folder ~/cnu-sweep-20260917`을
실행한다. 감독 스크립트는 스모크(질문 1개 × arm) → 본 실행 → 앱 로그 보존 → 결과 복사 → `analyze_sweep.py` 순으로
진행한다. 원시 질문·응답은 서버에만 남기고 저장소에는 집계와 엔진 카운터만 둔다.

## 분석 규칙

- 수준·라운드별로 양쪽 모두 완료한 문항을 짝지어 원본 − 어댑터 응답시간의 평균(문항 부트스트랩 4,000회 구간),
  중앙값, 부호 검정을 계산한다. 수준 요약은 라운드 동일 가중 평균이다.
- 처리량은 유효 응답 수 / 배치 벽시계 시간, SLO 달성률은 60초 이내 완료 비율이다.
- 엔진 카운터는 배치의 첫·끝 샘플 차로 요청 수·큐 시간·토큰을 구하고 200으로 나눠 요청당 값을 낸다.
  최대 대기 수·KV 점유·선점은 배치 내 최댓값이다.
- 브랜치 추적의 비핸들러 시간은 수준별로 arm 사이의 재작성 호출 비용(부하에 따라 커짐)을 보인다.
- 법령 집합 일치·재현율은 기준 일치도이며 전문가 정확도가 아니다. arm당 인스턴스가 하나이므로 arm 간 품질
  차이는 인스턴스 효과와 분리되지 않는다(`cnu-review-20260916` 분석 참조).
