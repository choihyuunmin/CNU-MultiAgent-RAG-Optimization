# 오케스트레이터 입력 감사 (2026-09-18): 문맥 관리 어댑터의 채택 여부 판단

목적: "에이전트 간 문맥 관리(중복 도구 결과·과거 실행 기록 제거)"가 오케스트레이터 병목을 줄일 수 있는지,
구현 전에 같은 200문항에서 (1) 단계별 입력·출력 토큰과 시간, (2) 입력에서 중복 도구 결과·과거 기록의 비율,
(3) 긴 입력이 대기·선점·응답시간을 실제로 늘리는지 측정한다. 줄일 입력이 거의 없으면 채택하지 않는다.

데이터: 원본 경로(모델 재작성) arm의 앱 추적 로그(호출별 prompt/completion 토큰, API 시간, 대기)와 vLLM 엔진
카운터. 동시성 4는 `cnu-review-20260916` 3라운드(598요청), 8·16·32·64·100은 `cnu-sweep-20260917`(수준당 2배치).
프롬프트 구성은 09-06 캡처 페이로드(classify·prepare 각 400건)와 앱 소스(로컬 이미지)로 확인했다.
집계: `experiments/results/orchestrator-input-audit-20260918/`, 스크립트 `docs/paper-draft-20260917/analysis/orch_input_load.py`.

## 1. 단계별 입력·출력 토큰과 시간 (원본 arm)

요청당 오케스트레이터 호출 3.7회, 입력 합계 약 14,900토큰, 출력 합계 약 360토큰. 호출 순서(pos)는 그래프 순서와 같다.

| pos | 단계 | n(C=4) | 입력 토큰 평균(p50 / p95) | 출력 | API 시간 C=4 | C=8 | C=16 | C=32 | C=64 | C=100 |
|--:|---|--:|---|--:|--:|--:|--:|--:|--:|--:|
| 1 | classify(의도 분류·분해) | 598 | 4,096 (4,097 / 4,110) | 40 | 1.6초 | 3.0 | 5.0 | 14.0 | 27.5 | 35.0 |
| 2 | prepare(검색어·키워드) | 532 | 2,697 (3,572 / 3,590) | 133 | 4.2 | 6.1 | 12.2 | 20.4 | 12.5 | 16.5 |
| 3 | select(후보 법령 선택) | 532 | 4,685 (3,571 / 9,303) | 126 | 4.6 | 6.8 | 13.5 | 29.4 | 36.1 | 37.6 |
| 4 | 선택 법령 요약·비교 준비 | 276 | 5,524 (5,208 / 11,519) | 111 | 5.3 | 8.3 | 15.1 | 29.1 | 38.4 | 32.8 |
| 5 | 후속 요약 | 276 | 3,304 (1,128 / 9,026) | 57 | 3.1 | 5.3 | 9.4 | 33.4 | 36.6 | 32.3 |

입력 구성: classify는 7,790자 고정 지시문(역할 목록·58개국 목록 포함) + 질문 약 50자, prepare는 6,707자 고정 지시문 + 질문.
두 단계의 고정 지시문이 요청당 약 6,500토큰(44%)이다. select는 응답 시스템 프롬프트 + 검색 도구 결과 JSON(후보 법령 본문),
pos4·5는 선택된 법령 본문(항목당 600자, 최대 15,000자) 요약이다. 출력은 모든 단계에서 40–135토큰으로 작다.

## 2. 입력에서 중복 도구 결과·과거 기록의 비율

- **대화 이력·과거 실행 기록: 0.** 200문항 벤치마크는 단일 턴이며, 캡처된 classify·prepare 페이로드의 사용자 메시지는
  질문 1개(평균 53자)뿐이다. 이전 단계 출력(변환 질의, 선택 ID)은 수십 토큰 수준으로 다음 단계에 전달된다.
- **도구 결과의 중복 전달:** 검색 후보 전체(JSON)는 select 한 번만 전달된다. pos4·5는 *선택된* 법령의 본문을 다시 받지만
  이는 다른 작업(요약)의 필수 입력이며 후보 전체를 다시 보내는 것이 아니다. 같은 판단을 위해 같은 내용을 두 번 보내는
  중복은 확인되지 않았다. 다단계 흐름(요청의 46%)에서 pos4 입력 5.5k토큰은 select에 포함됐던 본문의 부분집합이다.
- **고정 지시문 44%**가 가장 큰 덩어리지만, prefix cache가 이미 공유한다(아래).

## 3. 긴 입력이 대기·선점·응답시간을 늘리는가

오케스트레이터 엔진 카운터(배치 합계 / 요청 수):

| C | prefill/호출 | decode/호출 | queue/호출 | 시간 비중 prefill / decode / queue | prefix cache 적중 | 선점 |
|--:|--:|--:|--:|---|--:|--:|
| 4 | 0.46–0.49초 | 2.9초 | 0.00초 | 14% / 86% / 0% | 58–59% | 0 |
| 8 | 0.72–0.79 | 4.3–4.6 | 0.02–0.05 | 14% / 85% / 1% | 56–57% | 0 |
| 16 | 1.08–1.17 | 8.2–9.5 | 0.08–0.16 | 11% / 88% / 1% | 41–45% | 0 |
| 32 | 1.64–1.75 | 13.3–14.2 | 6.0–9.2 | 7% / 55–65% / 28–38% | 12–14% | 0–6 |
| 64 | 1.36–1.41 | 11.3–11.7 | 22.4–23.9 | 4% / 32% / 64% | 16% | 4–10 |
| 100 | 1.17–1.28 | 11.1 | 32.2–32.9 | 3% / 25% / 72% | 17–18% | 2–23 |

- 입력 처리(prefill)는 저부하에서 엔진 시간의 14%, 포화에서 3%다. 병목은 디코드(호출당 95–105토큰에 2.9–14초)와 큐 대기다.
- 요청 단위 입력 합계와 응답시간의 순위 상관은 C=4에서 0.71이지만 C=100에서 0.24로 떨어진다. 이 상관은 호출 수(다단계
  흐름은 호출·토큰·시간이 함께 큼) 때문이며, 호출 단위 입력–시간 상관은 0.25–0.48에 그친다. 포화에서는 큐 대기가 요청 자체의
  입력 길이와 무관하게 지배한다. 입력 상위 사분위 요청이 하위 사분위보다 느린 것(C=4: 42.8 대 12.7초)은 단계 수 차이다.
- prefix cache 적중률은 C≥32에서 12–18%로 붕괴한다(캐시 조회가 프롬프트 토큰의 6배 → 재계산). 고정 지시문 공유가 포화에서
  깨지므로 시퀀스당 KV 점유가 커지지만, 그 상태에서도 prefill 시간 비중은 3–7%다.

## 판단

**채택하지 않는다.** 이 워크로드에서 문맥 관리 어댑터가 제거할 수 있는 입력(중복 도구 결과·과거 기록)은 사실상 0이고,
줄일 수 있는 가장 큰 입력(고정 지시문 44%)은 이미 prefix cache가 공유하며, 입력 처리 자체가 오케스트레이터 시간의
3–14%에 불과하다. 종단 지연을 지배하는 것은 순차 호출 수(3.7회)와 호출당 디코드, 포화 시 큐 대기다. 이 결론은 이전 조사
(동일 요청 내 완전 중복 병합 0건, 외부 우선순위 조정의 근거 부족)와 일치한다.

남는 입력 관련 지렛대는 하나뿐이다. 포화(C≥32)에서 prefix cache 공유가 깨지면 classify·prepare의 고정 지시문(각 4.1k·2.7k토큰)이
시퀀스마다 KV를 차지하므로, 지시문을 압축하면 동시 시퀀스 용량이 늘어 큐 대기가 줄 수 있다. 이는 프롬프트 압축이지
문맥 관리 어댑터가 아니고, 분류·검색어 정확도를 다시 검증해야 하며, 저부하 이득은 없다. 시험하려면 200문항에서
지시문 길이를 절반으로 줄인 변형과 C=32·64에서의 큐 대기·KV·정확도를 비교하면 된다.

논문 방향으로는, 이미 확립된 병목 순서(오케스트레이터 순차 호출 수 → 디코드 → 포화 시 KV/큐)를 겨냥하는 개입이
문맥 관리보다 근거가 있다: 호출 병합(09-04, 단계 −28%), 추측 디코딩(09-06, 오케스트레이터 2.68배), 그리고 이번 스윕이
보인 "워커 호출 제거는 오케스트레이터 포화에 막힌다"는 결과의 결합이다.
