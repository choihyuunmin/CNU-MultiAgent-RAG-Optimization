# 실제 검색 애플리케이션에 연결하는 어댑터

## 연결 위치

독립적인 가짜 RAG 서버를 만드는 방식이 아니다. 기존 검색 애플리케이션의 같은 컨테이너 이미지 안에서 어댑터를 먼저 로드하고, 원래 `main_server`를 실행한다. 모델·검색 DB·프롬프트·LLM 요청 인자는 기존 애플리케이션이 결정한다.

```text
동일 평가 질문
  → 기존 검색 API / 기존 질문 대기열
  → 기존 에이전트 실행
  → 어댑터: LLM 호출 관측 / 수신 모델별 슬롯 / 질문별 순환 순서
  → 원래 SDK 함수 → 원래 모델 게이트웨이 → 원래 추론 엔진
  → 원래 응답 청크 → 제한된 중계 버퍼 → 기존 검색 API 응답
```

LLM 함수의 인자와 반환 객체를 보존한다. 스트림은 원래 청크의 순서와 내용을 보존하며, 오류와 취소를 전달한다. 답변 캐시, 질문 재작성, 모델 교체, 토큰 제한 축소, 추론 중단을 사용하지 않는다.

## 비교 조건

| 조건 | 실제 변경 | 바꾸지 않는 항목 |
|---|---|---|
| 기존 방식 | 계측만 추가 | 기존 화면 전달 지연, 질문 동시 실행 한도, 모든 추론 설정 |
| 화면 전달 대기 제거 | 글자를 천천히 표시하려고 넣었던 기본 대기만 0으로 조정 | 청크 내용·순서·크기, 명시적인 호출별 설정, LLM 요청 |
| 네트워크 하네스 추가 | 위 조건 + 질문별 순환 순서 + 같은 추론 자원을 공유하는 별칭의 슬롯 통합 + 64개 청크 한도의 중계 버퍼 | 모델 선택, 프롬프트, SDK 재시도·시간 제한, 원래 질문 실행 한도 |

같은 모델 별칭을 공유하는 요청은 물리 수신 자원별로 묶는다. 질문 하나가 여러 호출을 만들더라도 다른 질문의 대기 요청이 계속 밀리지 않도록 순환한다. 스트림을 읽는 작업과 앱에 넘기는 작업은 분리하되, 버퍼가 차면 읽기를 기다린다. 슬롯은 upstream 종료·오류·취소 때 반환한다.

이번 구성은 모델 별칭을 고정한다. 복제본 중 빠른 GPU를 선택하거나 모델을 다른 GPU로 옮긴 실험이 아니다. 슬롯과 순환 대기열도 프로세스 내부 상태이므로, 여러 검색 서버에 설치했을 때 전역 동시 호출 한도를 보장하는 분산 조정 기능은 아직 없다.

이 구성은 기존 네트워크 흐름 제어 원리를 응용한 시험 구현이다. 독창성, 일반적인 속도 향상, 법적 정확도 유지가 증명됐다는 뜻은 아니다.

## 파일

- `src/cnu_rag_optimization/application_adapter.py`: 기존 async LLM 함수에 연결하는 관측·제어 래퍼.
- `src/cnu_rag_optimization/network_harness.py`: 한도가 있는 스트림 중계, 취소·오류·슬롯 수명 관리.
- `scripts/serve_embedded_adapter.py`: 애플리케이션 파일 해시 확인 후 원래 서버에 연결.
- `scripts/build_embedded_adapter_bundle.py`: 원본 앱 소스나 비밀정보를 복사하지 않고 어댑터 코드만 시험용 ConfigMap에 구성.
- `scripts/run_attached_experiment.py`: 원래 평가기로 동일 질문을 각 API에 전송; 엔진 상태 관측과 안전 중단 포함.
- `scripts/collect_ssh_gpu.py`: 읽기 전용 GPU 관측. 암호는 대화형 입력만 사용.
- `scripts/analyze_attached_experiment.py`: 원래 평가 함수로 답변 일치도 계산; 실패·누락·내부 호출 오류도 보고.

## 안전한 시험 연결 절차

1. 운영 이미지의 불변 digest, CPU·메모리 한도, 원래 함수 위치와 파일 해시를 먼저 확인한다. 토폴로지에는 별칭·수신 자원·용량·관측 URL·해시만 넣는다. 암호·API 키는 넣지 않는다.
2. `build_embedded_adapter_bundle.py`로 별도 이름의 시험 Pod 세 개를 생성한다. 생성물을 확인하고 Kubernetes 서버 측 dry-run을 먼저 수행한다.
3. 시험 Pod의 label은 운영 Service selector와 겹치지 않게 유지한다. Service·Ingress·NodePort·hostPort를 만들지 않는다. 운영 이미지에 있는 기존 설정을 사용한다.
4. 세 조건 모두 원본 파일 해시 확인에 성공했는지 시작 로그로 검증한다. API는 SSH의 로컬 전용 포트로 접근한다.
5. 적은 수의 연결 점검 후 같은 질문 ID와 순서를 사용해 본 실험을 진행한다. 각 조건 시작 전 관측 가능한 엔진이 두 번 연속 유휴 상태인지 확인한다.
6. 결과·Pod 로그·GPU 로그를 저장한다. 시험 Pod와 ConfigMap, 본인이 만든 터널·관측 프로세스만 정리한다. 검증 없이 운영 트래픽을 전환하지 않는다.

빌더는 현재 `/app/.venv/bin/python`, `/app/src`, 특정 앱 진입 함수를 전제로 한다. 다른 검색 시스템에는 `ApplicationAdapter`를 재사용하되, 연결 함수·파일 해시·이미지 실행 경로를 해당 시스템에 맞춰야 한다. 모든 RAG에 무설정으로 붙는 도구는 아니다.

## 이번 운영 이미지에서 확인한 적용 범위

공통 `acompletion_via_proxy`, `acompletion_stream_via_proxy` 경로에 연결했다. 다음 경로는 우회 호출이므로 이번 하네스의 슬롯 제어·개별 호출 계측 범위에 포함하지 않는다.

- `core/query_loop/runner.py`의 직접 `client.chat.completions.create` 호출.
- `agent/guardrail.py`의 직접 HTTP 호출.

따라서 로그의 `managed_calls`가 관측 호출 수와 같아도, **전체 검색 시스템의 모든 LLM 호출을 제어했다는 의미는 아니다.** 공유 엔진의 완료 카운터와 공통 함수 호출 수가 다른 이유도 함께 확인해야 한다. 이 차이를 바로 외부 트래픽이라고 단정하지 않는다.

향후 질문 동시 실행 한도를 늘리려면 이 우회 경로를 먼저 제어 범위에 포함하고 별도 비교 실험을 해야 한다. 현재 한도를 유지한 결과를 한도 확대 결과처럼 설명하지 않는다.

## 로그 해석과 평가 한계

- `CNU_INGRESS_V1`: 질문 입구의 대기시간.
- `CNU_APP_ADAPTER_V1`: 질문 ID별 관측 LLM 호출, 슬롯 대기, API 소요시간, 오류, 사용량이 제공된 경우의 토큰 수.
- `CNU_HARNESS_V1`: 중계 버퍼 최대 점유, 버퍼 대기, upstream 종료와 중계 완료 여부.
- `api_ms`에는 SDK·네트워크·엔진 대기 및 스트림 소비 시간이 포함될 수 있다. 순수 GPU 추론시간이 아니다.
- 동시에 실행되는 LLM 호출들의 시간을 더해 전체 응답시간이라고 계산하지 않는다. 스트림 청크 수도 토큰 수로 바꾸어 부르지 않는다.
- GPU 지표는 공유 장치 전체 값이다. VRAM 할당량, KV 캐시 사용률, 메모리 대역폭은 같은 지표가 아니다.
- HTTP 정상 응답과 내부 모든 단계의 성공은 다르다. 폴백으로 정상 응답이 만들어질 수 있다.
- 기존 답변은 비교 기준이지 전문가가 검증한 법령 정답지가 아니다. 기준 법령 재현율과 첫 법령 일치율을 법적 정확도로 표현하지 않는다.
- 현재 case ID에는 run ID가 없다. 같은 Pod에서 같은 동시 사용자 수로 재실험하면 ID가 겹친다. 새 시험 Pod를 사용하거나 실행별 로그 경계를 명확히 분리해야 한다. 분석기는 중복을 표시한다.

진단에는 `investigate-first`, 연결 범위 축소에는 `lean-build`, 정답·일치도 구분에는 `ml-model-validator` 작업 지침을 적용했다. 이 작업 지침을 검색 모델의 프롬프트에 넣은 것은 아니다.
